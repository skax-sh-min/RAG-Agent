# 자연어 지식 수정 사전 평가 — AGENT_MCP_DESIGN §10.12 6c (2026-11-20)

6c(`KnowledgeEditWorkflow` — 해석 · 후보 · 판정 · 편집)는 사전 평가 없이 구현했고 유형 넷이 모두 열려 있다. 이 평가는 설계서의 판단표([AGENT_MCP_DESIGN.md](AGENT_MCP_DESIGN.md) §10.12)로 **어느 유형을 열어 둘지** 정하려고 쟀다. 세 모델(Gemma 4 12B · E4B · E2B)을 같은 조건으로 비교했다.

> **아직 빠진 것: 사람 수용률.** 판단표의 넷째 기준(가드를 통과한 수정안을 고치지 않고 승인할 만한 비율 ≥70%)은 사람이 `review.md` 를 읽고 표시해야 나온다. 아래 결정은 그 숫자 없이 낸 **잠정** 결정이고, 수용률이 나오면 §4 표와 §1 을 고친다.

## 1. 한눈에

- **잠정 결정: `deprecate`·`add_note` 만 연다**(판단표 둘째 줄). `remove`·`revise` 는 외부 에이전트(6b)나 관리자 고치기로 돌린다. 근거: 12B·E4B 모두 해석은 통과하지만 **precision 이 0.65** 로 기준(0.8)에 못 미치고, `remove`·`revise` 의 가드 통과율이 0.4~0.64 다. `deprecate`·`add_note` 는 세 모델 모두 가드 통과 1.00 이다.
- **운영 모델은 E4B 가 현실적이다.** 해석 96.6%, recall 0.83, 가드 통과 0.78(세 모델 중 최고), 판정 호출 2.9초 — 12B(16.5초)의 약 6배 빠르다. 12B 는 recall 0.91 로 판정이 가장 낫지만 느리다.
- **E2B 로는 6c 를 열 수 없다**(판단표 셋째 줄 — 폼만). 해석 75.9%, recall 0.50, `remove`·`revise` 의 편집 응답 형식을 26건 모두 지키지 못했다.
- **precision 이 낮은 원인은 모델이 아니라 판정 기준 쪽에 가깝다.** 세 모델 모두 대상을 *쓰는* 예제 프로그램(BEDU…, "예제 - Reader")을 "설명함"으로 고른다(§5.1).

**지표.** 해석 = 유형이 맞은 비율 / 유형과 대상(subject)이 둘 다 맞은 비율. recall·precision = 판정 "설명함" 대 정답 D (A 라벨은 셈에서 뺀다). 가드 통과율 = 편집 대상 중 가드(G3·G4·G10·`AnchoredEdit`)를 넘어 수정안이 된 비율. 자동 점검 = 수정안이 유형의 모양을 갖췄는지(안내 블록이 있는가, 대상 구간이 사라졌는가 등)를 하네스가 본 것. 수용률 = 사람이 `review.md` 의 `수용` 칸에 O 를 적은 비율.

**재현.**

```
mvn -q test -Dtest=KnowledgeEditEvaluationTest -Dsurefire.failIfNoSpecifiedTests=false -Dsqlite-vec.skip=true \
  -Dedit-eval.enabled=true -Dedit-eval.db=<memory.db 사본> \
  -Dedit-eval.base-url=http://127.0.0.1:1234/v1 -Dedit-eval.rerank-url=http://127.0.0.1:28095 \
  -Dedit-eval.label=<라벨> -Dsurefire.timeout=0
```

결과는 `target/edit-eval/<라벨>/`(`summary.md` · `review.md` · `proposals.json`)에 쓰인다. 이번 세 런의 `summary.md`·`review.md` 는 `scripts/knowledge_edit_eval/results/<라벨>/` 에 옮겨 두었다(`target/` 은 `mvn clean` 으로 지워진다). **DB 사본과 로그를 OS 임시 폴더에 두지 말 것** — 12B 의 첫 재실행이 70분째에 임시 폴더 정리로 `-wal` 이 지워져 `SQLITE_CANTOPEN` 으로 죽었다. 하네스는 결과를 끝에서 한 번에 쓰므로 중간에 죽으면 처음부터 다시 돈다.

## 5. 관찰

### 5.1 precision 을 깎는 판정 오류

- **예제가 "설명함"이 된다.** 대상을 호출하는 예제 프로그램·샘플 코드 청크(`BEDU5001 — 병렬 SharedQueue Reader`, `7.11.3.2 단일큐 예제 - Reader`, `3.9.8 비동기 응답 예제`)를 세 모델 모두 "설명함"으로 고른다. 12B 에서 판정이 정답과 다른 37건 중 31건이 정답 D 가 아닌 청크를 "설명함"으로 올린 것이고 대부분 이 모양이다. 그 청크에 사용 중단 안내를 넣는 것이 틀렸다고 단정하기도 어려워(예제는 따라 쓰는 코드다) 수용률에서 갈릴 부분이다.
- **API 레퍼런스가 "언급만"이 된다.** 시그니처·패키지만 있는 레퍼런스 청크(`PaddableDataOutputStream`, `getJobExecutionId`, `BaseRuntimeException`, `sendErrorResponseOnFail`)를 12B 가 "언급만"으로 놓친다 — 12B recall 손실의 대부분.
- **클래스 사용 중단 = 메서드 청크 전부.** E4B 는 `OldFileDailyCleaner` 의 수정안 7개 중 6개가 그 클래스의 메서드 섹션(골든셋 A)이다. 클래스가 쓰이지 않으면 메서드도 쓰이지 않으니 틀린 것은 아니지만 같은 안내가 일곱 번 들어간다.

### 5.2 가드가 버린 것

| 사유 | 12B (28건) | E4B (19건) | E2B (26건) |
|---|---|---|---|
| G3 — 인용에도 섹션 제목에도 대상이 없다 | **19** (`revise` `callAsyncServiceNow` 의 정답 D 3건 포함) | 6 | — |
| 인용을 원문에서 못 찾음 · 여러 곳에 있음 | 4 | 12 | — |
| 다른 작업과 구간이 겹침 | 4 | — | — |
| G4 — 지시문에 없는 숫자 | 1 | — | — |
| 변경 없음 | — | 1 | — |
| 편집 응답을 읽지 못함(형식) | — | — | **26 (전부)** |

- 12B 의 G3 버림은 모델이 **대상 이름이 없는 문장을 인용**해서다(대상 섹션 안이지만 제목도 아닌 줄). 가드가 설계대로 엄격한 것이고 버그가 아니다. 섹션 판정을 `wholeChunkBelongsTo` 처럼 "대상 제목 아래인가"로 넓히면 살아나지만, 같은 완화가 무관한 섹션 삭제도 통과시킬 수 있어 이번에는 바꾸지 않았다.
- E2B 는 해석·판정과 별개로 **편집 JSON 을 만들지 못한다** — 내용 이전에 형식이다.

### 5.3 글자 바꾸기 해석 실패의 모양

E2B 3건, E4B 1건이 같은 실수다: `replace` 를 맞게 골랐는데 새 말을 `to` 가 아니라 `replacement`(대안) 칸에 넣어 "바꿀 말과 새 말이 필요합니다"로 거절됐다. `replace` 이고 `from`·`to` 가 비었고 `subject`·`replacement` 가 지시문의 부분 문자열이면 옮겨 읽는 관용 처리로 살릴 수 있다 — 작은 모델을 쓸 이유가 생기면 고칠 일.

## 6. 남은 일

1. **사람 수용률.** `scripts/knowledge_edit_eval/results/gemma-4-e4b/review.md`(69건)와 `gemma-4-12b-r2/review.md`(60건)의 `수용` 칸 — 운영할 모델 하나만 본다면 E4B. 나오면 §3.1 · §4 · §1 을 고친다. 수용 70% 이상이고 `remove`·`revise` 의 수용도 높으면 첫째 줄(넷 모두)을 다시 검토한다.
2. **결정 반영.** 판단표가 둘째 줄로 확정되면 `remove`·`revise` 를 자연어 경로(채팅 되묻기·`/admin` 자연어 입력·MCP 지시문)에서 닫고 유형 선택 폼과 6b 로만 받는다 — 지금은 넷 모두 열려 있다(설계서 §10 「구현: 6c」 ①).
3. 다른 서버·모델(원격 31B 등)이 들어오면 같은 하네스로 다시 재고 이 문서에 열을 더한다.
