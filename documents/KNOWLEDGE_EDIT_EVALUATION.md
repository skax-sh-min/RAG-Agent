# 자연어 지식 수정 사전 평가 — AGENT_MCP_DESIGN §10.12 6c (2026-11-20)

6c(`KnowledgeEditWorkflow` — 해석 · 후보 · 판정 · 편집)는 사전 평가 없이 구현했고 유형 넷이 모두 열려 있다. 이 평가는 설계서의 판단표([AGENT_MCP_DESIGN.md](AGENT_MCP_DESIGN.md) §10.12)로 **어느 유형을 열어 둘지** 정하려고 쟀다. 세 모델(Gemma 4 12B · E4B · E2B)을 같은 조건으로 비교했다.

> **사람 수용률은 2026-11-20 에 E4B(68/69건)·12B(59/60건)를 표시했다**(각 1건 미표시), 배치 규칙을 고친 뒤의 `deprecate` 재실행(`gemma-4-e4b-dep2`, 31건)도 같은 날 표시했다. E2B 는 판단표 셋째 줄이 이미 정해져 표시하지 않았다. 표시는 `scripts/knowledge_edit_eval/results/<라벨>/review.md` 의 `수용` 칸.

## 1. 한눈에

- **결정: `deprecate`·`add_note` 만 연다**(판단표 둘째 줄). `remove`·`revise` 는 외부 에이전트(6b)나 관리자 고치기로 돌린다. 근거: 12B·E4B 모두 해석은 통과하지만 **precision 이 0.65** 로 기준(0.8)에 못 미치고, 사람 수용률이 전체 **E4B 55.9% · 12B 47.5%** 로 70% 아래다. 유형별로는 E4B 의 `deprecate`+`add_note` 가 **76.9%**(30/39)로 기준을 넘고 `remove` 21% · `revise` 44% 는 한참 못 미친다.
- **`deprecate` 의 배치를 고쳐 E4B 수용률이 72.7% → 93.5%(29/31)가 됐다**(§3.3). 처음 런에서 거절된 사용 중단 수정안(E4B 9 · 12B 13)은 전부 **대상 이름이 없는 상위 섹션 제목 바로 아래**에 안내를 넣었다(`### 3.4 어플리케이션 호출`, `## 6. 클래스: …ProcessUnit` — 메서드 하나의 중단이 섹션 전체의 중단처럼 읽힌다). 안내를 대상 이름이 든 제목 아래, 없으면 대상이 나오는 블록 앞에 넣도록 고친 뒤 그 9개 중 7개를 받았다. 남은 거절 2건은 둘 다 **여러 API 를 나열한 표 바로 앞**에 들어간 안내다. 이로써 E4B 의 `deprecate`+`add_note` 는 **94.6%**(35/37).
- **`remove` 는 설명과 코드를 가르지 못한다**(검토자 의견). 대상을 *쓰는* 예제 코드에서 그 줄을 지우면 예제가 동작하지 않는다 — 지울 것이 아니라 "사용 중단된 API 를 쓰는 예제"라는 주석이 필요하다.
- **운영 모델은 E4B 가 현실적이다.** 해석 96.6%, recall 0.83, 가드 통과 0.78(세 모델 중 최고), 판정 호출 2.9초 — 12B(16.5초)의 약 6배 빠르다. 12B 는 recall 0.91 로 판정이 가장 낫지만 느리다.
- **E2B 로는 6c 를 열 수 없다**(판단표 셋째 줄 — 폼만). 해석 75.9%, recall 0.50, `remove`·`revise` 의 편집 응답 형식을 26건 모두 지키지 못했다.
- **precision 이 낮은 원인은 모델이 아니라 판정 기준 쪽에 가깝다.** 세 모델 모두 대상을 *쓰는* 예제 프로그램(BEDU…, "예제 - Reader")을 "설명함"으로 고른다(§5.1).

- 판정이 틀린 청크(M)의 수정안은 거의 거절된다 — precision 이 곧 수용률의 상한이다. 정답 D 청크에서도 절반가량이 거절된 것은 편집 쪽 문제다(아래 두 항목).
- **`deprecate` 의 사례별 차이가 크다.** 클래스·컴포넌트 단위(`OldFileDailyCleaner` 7/7 · `CaseIgnoreHashMap` 6/6 · `PaddableDataOutputStream` 7/7 · `FUAttcFileMng` 3/4, E4B)는 거의 다 받고, 가이드 문서 안의 메서드 단위(`callBatchNow` 1/5 · `reserveCallTimerService` 0/4)는 거의 다 거절했다. 거절된 수정안은 예외 없이 안내가 **청크의 첫 제목 = 대상 이름이 없는 위치 표시용 상위 제목** 아래에 들어갔다. "섹션마다 첫 청크의 첫 제목 아래"라는 배치 규칙이 클래스 문서에서는 맞고 가이드 문서에서는 틀린다. 12B 의 `deprecate` 수용률이 E4B 보다 낮은 것도 이 메서드 단위 사례에 수정안을 더 많이 냈기 때문이다(12 대 9). E4B 의 72.7% 는 클래스 사례가 수정안을 여러 개씩 내서 부풀려진 숫자이기도 하다 — 사례 단위로는 여섯 중 넷이 좋다.
- **`remove` 는 예제 코드에서 대상 줄을 지운다.** 검토자 의견: 삭제 요청에서 설명과 코드를 가르지 못하고 있고, 대상이 코드에서 쓰이는 경우 그 줄을 지우면 예제가 동작하지 않으므로 사용 중단된 API 를 쓰는 예제라는 주석이 필요하다. E4B `remove` 의 정답 D 청크도 4/11 만 받았다.

### 3.4 가드 수정 전후 (12B)

같은 12B 로 수정 전 코드(2026-11-19)와 비교했다. 판정은 거의 같고(recall 0.89 → 0.91), 가드 통과율이 0.61 → 0.68 로 올랐다. `remove` 만 보면 0.49 → 0.64 — `readLines` 수정안 0 → 4, `closeQuietly` 2 → 5. 청크가 위치 표시용 상위 제목(`## 26. 클래스: …FileUtils`)으로 시작해 "첫 제목" 검사가 맞는 판정을 버리던 것이다(PITFALLS 6c).

## 5. 관찰

### 5.1 precision 을 깎는 판정 오류

- **예제가 "설명함"이 된다.** 대상을 호출하는 예제 프로그램·샘플 코드 청크(`BEDU5001 — 병렬 SharedQueue Reader`, `7.11.3.2 단일큐 예제 - Reader`, `3.9.8 비동기 응답 예제`)를 세 모델 모두 "설명함"으로 고른다. 12B 에서 판정이 정답과 다른 37건 중 31건이 정답 D 가 아닌 청크를 "설명함"으로 올린 것이고 대부분 이 모양이다. 그 청크에 사용 중단 안내를 넣는 것이 틀렸다고 단정하기도 어려워(예제는 따라 쓰는 코드다) 수용률에서 갈릴 부분이다.
- **API 레퍼런스가 "언급만"이 된다.** 시그니처·패키지만 있는 레퍼런스 청크(`PaddableDataOutputStream`, `getJobExecutionId`, `BaseRuntimeException`, `sendErrorResponseOnFail`)를 12B 가 "언급만"으로 놓친다 — 12B recall 손실의 대부분.
- **클래스 사용 중단 = 메서드 청크 전부.** E4B 는 `OldFileDailyCleaner` 의 수정안 7개 중 6개가 그 클래스의 메서드 섹션(골든셋 A)이다. 클래스가 쓰이지 않으면 메서드도 쓰이지 않으니 틀린 것은 아니지만 같은 안내가 일곱 번 들어간다.

### 5.3 글자 바꾸기 해석 실패의 모양

E2B 3건, E4B 1건이 같은 실수다: `replace` 를 맞게 골랐는데 새 말을 `to` 가 아니라 `replacement`(대안) 칸에 넣어 "바꿀 말과 새 말이 필요합니다"로 거절됐다. `replace` 이고 `from`·`to` 가 비었고 `subject`·`replacement` 가 지시문의 부분 문자열이면 옮겨 읽는 관용 처리로 살릴 수 있다 — 작은 모델을 쓸 이유가 생기면 고칠 일.

## 6. 남은 일

1. **`deprecate` 배치 규칙 — 고침·재측정 완료(2026-11-20, 수용 93.5%).** `KnowledgeEditWorkflow.deprecationPosition` 이 이제 **대상 이름이 든 첫 제목** 아래, 없으면 대상이 처음 나오는 블록 앞(코드 펜스 안이면 펜스 앞), 청크에 대상이 없을 때만 첫 제목 아래에 넣는다. 이번 E4B 사용 중단 33건의 실제 청크에 새 규칙을 대 보면(LLM 없이 위치만): 수용된 24건은 위치가 그대로이고, 거절된 9건 중 `reserveCallTimerService` 레퍼런스 청크(P6)는 `### 6.11 메서드: reserveCallTimerService(…)` 아래로, 가이드 청크 6건(P3·P4·P5·P7·P8·P9)은 대상이 나오는 표·예제 코드·문단 바로 앞으로, P33 은 대상을 소개하는 문단 앞으로 간다. P2 는 판정 오류(정답 M)라 위치로는 못 고친다. 같은 날 E4B 로 `deprecate` 사례 6개만 다시 돌렸다(`scripts/knowledge_edit_eval/results/gemma-4-e4b-dep2/`, 라벨 `gemma-4-e4b-dep2`): 수정안 31개(전 런 33개 — `PaddableDataOutputStream` 판정이 2개 덜 골랐다), 가드 버림 0. 위치는 위의 대입과 같다 — 클래스 청크 22개는 그대로, 거절됐던 가이드·레퍼런스 청크 8개는 대상 이름이 든 제목(P6) · 대상이 나오는 표(P3·P4·P7) · 예제 코드(P5·P8) · 문단(P9·P31) 바로 앞. 표시 결과 29/31 수용(§3.3). 이 런은 서버가 지난 런보다 훨씬 느렸다(판정 평균 25.4초, 전 런 2.9초) — 결과에는 영향이 없다.
2. **`remove` 의 코드 구간.** 지울 구간이 코드 펜스 안이면 지우지 않고 사용 중단 주석을 붙이는 쪽으로 — `remove` 를 자연어 경로에서 닫으면 6b·관리자 고치기에서 같은 판단이 필요하다.
3. **결정 반영.** 판단표가 둘째 줄로 확정되면 `remove`·`revise` 를 자연어 경로(채팅 되묻기·`/admin` 자연어 입력·MCP 지시문)에서 닫고 유형 선택 폼과 6b 로만 받는다 — 지금은 넷 모두 열려 있다(설계서 §10 「구현: 6c」 ①).
4. 다른 서버·모델(원격 31B 등)이 들어오면 같은 하네스로 다시 재고 이 문서에 열을 더한다.
