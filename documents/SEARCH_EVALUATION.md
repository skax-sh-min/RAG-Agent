## 1. 한눈에

- **검색은 7월 기준선에서 물러서지 않았다.** 골든셋 recall@10 은 `.env` 구성 0.962(nDCG 0.803~0.808), 지금 운영 설정 + 질의 확장 1.000 — 2026-07-16 기준선(0.962, nDCG 0.810)과 같은 수준이다. 그 사이 문서가 3종에서 23종(청크 2,388개)으로 늘었다.
- **다만 고치기 전의 골든셋으로는 0.923 으로 보였다.** 정답 문자열 26개 중 6개가 낡아 있었다 — 5개는 문서를 "RAG-수정"판으로 바꾸며 표현·서식이 달라졌고, 1개(arch-09)는 그 뒤 들어온 개발가이드에 더 직접적인 답이 생겼다(§3.1). 숫자가 떨어진 것이 검색 탓인지 골든셋 탓인지를 가르려고 하네스가 이제 매번 **코퍼스 점검**(정답 문자열이 코퍼스 어딘가에 있는가 = recall 상한)을 찍는다.
- **키워드(BM25) 검색어에 조사·어미를 뗀 어간을 더하자 골든셋이 두 구성 모두 1.000 이 됐다**(nDCG env 0.803 → 0.844 · 운영 0.811 → 0.902, 2026-10-13). 질문 토큰을 조사가 붙은 그대로 구문 검색해 3글자 이상 토큰의 26% 가 코퍼스에서 0건이었다 — 늘 놓치던 arch-11(`노드매니저는`)이 그 경우다(§3.5).
- **질의 확장(MultiQuery)은 거의 아무것도 바꾸지 않는다.** `.env` 구성에서는 확장을 켜든 끄든 26건 전부 같은 결과(3회 · 2회), 운영 구성(top-K 15)에서만 1건(arch-11)을 되찾았다(4/4). 대가는 검색마다 LLM 호출 1회와 약 1.1~1.3초(중앙값 0.2초 → 1.3초)다(§3.3).
- **후속 질문 독립화(§10.12)는 값을 한다.** 맥락에 기댄 짧은 질문 14개와 주제를 바꾼 짧은 질문 7개에서 지금의 파이프라인이 recall@10 0.714~0.762 로 원문 그대로(0.667)보다 1~2건 낫고, 주제 전환에서 손해가 없다. LLM 없이 앞 질문을 이어 붙이는 대안은 같은 주제에서는 더 낫지만(0.786) 주제 전환 7건 중 2건을 놓쳐 전체로는 원문과 같고, 원문과 이어 붙인 질문을 함께 검색하는 대안은 독립화와 비겼다(§3.4). **10-12 에 적은 "독립화는 거의 이득이 없고 이어 붙이기가 낫다"는 하네스 결함(재실행마다 앞 질문이 이력에 쌓였다) 위의 결론이라 철회한다**(§3.4.4).
- **유사도 임계값 폴백(통과 < top-k 의 70% 면 0.05 한 번 낮춤)은 이 코퍼스의 출하·운영 설정에서 한 번도 발동하지 않았다** — 골든셋 26 · 후속 질문 21 문항, env(0.30) · ops(0.35) 모두 0회, 숫자는 그대로다. 임계값을 0.6 으로 올리면 26문항 중 12번 발동한다(§3.6).

## 2. 환경과 방법

### 2.1 환경

[THINKING_EVALUATION.md §2.1](THINKING_EVALUATION.md) 과 같은 노트북(Core 7 150U · 32 GiB · MX570 A), 같은 서버 두 대(생성 `:1234` b11433 · 창 32,768, 임베딩 `:8091` bge-m3 · 창 8,192), 같은 개발 DB 의 스크래치 복사본이다. 벡터 백엔드는 sqlite-vec(`memory.db` 한 파일), 하이브리드(BM25) 켬, 리랭커 끔.

**코퍼스**: 문서 23종 · 청크 2,388개(`version=latest`) + 큐레이션 1건 — 개발교육 PPTX(143) · 개발가이드 DOCX(393) · API 레퍼런스 MD 13종(`fwk-util` 646 · `fwk-data` 501 · `fwk-online` 101 · `fwk-kube-*` …) · 샘플 분석 MD 5종 · 가이드 PPTX 3종. 7월 기준선 때는 앞의 셋 정도였다.

### 2.3 판정

정답은 케이스마다 **정답 문자열**(`mustContainAny`, 하나라도 맞으면 정답)이고, 검색 결과 상위 10개 안에서 처음 맞는 순위로 recall@10(0/1)·nDCG@10(1/log2(rank+1))을 낸다(§10.7.5 와 같다). 이번에 바꾼 것 하나: **비교 전에 양쪽에서 공백과 마크다운 장식(`* \` # > _ | ~ -`)을 걷는다**(`SearchQualityMetrics.containsAnyMarker`). 문서를 다시 교정하면 같은 문장에 `**굵게**` 가 붙거나 줄이 바뀌어, 내용은 그대로인데 "정답 없음"이 됐다. 표현 자체가 바뀐 경우(애플리케이션 → 어플리케이션)는 이 규칙으로 잡지 않고 골든셋에 지금 표현을 더했다.

### 3.3 질의 확장의 값

- **env 구성: 0건.** 정비 전 3회·2회, 정비 후 1회·1회 모두 확장 켬과 끔의 recall 이 같다. 순위가 달라진 케이스(batch-01 · arch-06 · sample-06 등)는 오르내림이 섞여 nDCG 는 끔이 조금 높다(0.770 vs 0.761~0.764, 정비 후 0.808 vs 0.803).
- **ops 구성: 1건.** arch-11 을 확장이 되찾는다(4/4) — top-K 15·임계 0.35 의 넓은 후보 풀에서 확장 질의 하나가 그 표 청크를 끌어올린다.
- **대가**: 검색 한 번에 LLM 호출 1회, 중앙값 0.2초 → 1.3초. 2026-10-07 의 13건 측정(확장 없음·끔·낮게 모두 recall@10 0.692)과 같은 방향이다.

### 3.4 후속 질문 — §10.12 독립화 (2026-10-13 재측정)

> **10-12 의 첫 측정은 하네스 결함 위에서 돌았다.** 후속 질문 절이 대화 스레드 id 를 실행마다 같게 써서, 같은 스크래치 DB 로 다시 돌릴 때마다 앞 질문이 그 스레드의 이력에 한 번씩 더 쌓였다. 독립화의 재료가 "같은 질문 ×2~4"가 되자 재작성이 앞 질문의 내용을 끌어오는 일이 늘었고, 그 위에서 "독립화는 거의 이득이 없고 LLM 없는 이어 붙이기가 낫다"고 적었다. 스레드를 실행마다 새로 만들도록 고치고, 이어 붙이기가 지는 쪽인 **주제 전환 질문 7개**를 더해 다시 쟀다. 아래가 그 결과이고, 10-12 의 숫자와 무엇이 틀렸는지는 §3.4.4 에 남긴다.

#### 3.4.1 세트와 갈래

**세트**(`nexcore-followup.json`, 21문항 — 정답은 `targetId` 골든 케이스의 정답 문자열):

- **같은 주제 14건**(fu-01~14): 골든셋 케이스 하나를 앞 질문으로 이력에 넣고, 이웃 케이스의 답을 묻는 **맥락에 기댄 짧은 질문**을 던진다(“처리일자는 어떻게 꺼내?” — 앞 질문은 “IBatchContext 객체는 무엇을 전달하기 위한 것인가?”). 길이 6~28자.
- **주제 전환 7건**(fu-15~21): 짧지만 앞 질문과 **다른 문서의 주제**를 꺼내는 질문(“메타 로더는?” — 앞 질문은 배치의 IBatchContext). 길이 7~13자로 전부 출하 게이트(15) 아래다. 앞 질문을 검색어에 섞으면 손해를 보는 쪽이다.

**갈래** — 같은 후속 질문을 여섯 가지로 검색한다.

| 갈래 | 검색어 | 확장 |
|---|---|---|
| raw | 후속 질문 원문 | 없음 |
| pipeline | **지금의 동작** — 게이트 아래면 독립화, 위면 원문 + 확장 | 게이트 위에서만 |
| condensed | 길이와 무관하게 독립화한 질문 | 없음 |
| concat | 앞 질문 + 후속 질문을 **이어 붙인 것**(LLM 없음) | 없음 |
| fused | raw 와 concat 의 결과를 RRF(k=60)로 **합친 것**(LLM 없음 — 두 검색어로 함께 검색하는 방식의 근사) | 없음 |
| full | 정답 케이스의 원래 질문(사람이 쓴 자립 질문 = 상한) | 설정대로 |

`fused` 는 하네스가 두 결과 목록(각 상위 10개)을 합친 것이라, 합친 상위 10개에는 각 목록의 대략 상위 5개씩만 남는다. 제품에서 축 단위로 합쳐도 두 질의가 같은 top-K 자리를 나눠 쓰는 것은 같다.

#### 3.4.3 읽은 것

- **독립화는 값을 한다 — 원문보다 1~2건 낫고, 주제 전환에서 손해가 없다.** 이력이 깨끗하면 재작성이 앞 질문의 핵심어를 제대로 가져오고(“처리일자는 어떻게 꺼내?” → “IBatchContext에서 처리일자를 어떻게 꺼내나요?”) 주제를 바꾼 질문은 자립 문장으로 다듬기만 한다(“메타 로더는?” → “메타 로더는 무엇인가요?” — 7건 모두 앞 주제를 끌어오지 않았다). 출하 게이트(15)에서 두 구성 모두 0.762 로 대안 중 가장 높거나 같다.
- **이어 붙이기는 주제 전환에서 무너진다.** 같은 주제에서는 가장 좋은 갈래 중 하나(0.786)지만, 주제 전환 7건 중 둘(fu-15 “메타 로더는?” · fu-21 “UIO 편집돼?”)을 원문이면 맞히다가 놓쳤다(0.714 → 0.429) — 앞 질문이 검색어의 대부분을 차지해 앞 주제의 문서를 가져온다. 전체로는 원문과 같다(0.667).
- **함께 검색(fused)은 독립화와 비긴다.** 같은 주제에서는 env 0.857 로 가장 좋지만, 주제 전환에서 원문보다 1건 진다 — fu-19 는 원문·이어 붙이기 모두 7~8위로 맞힌 청크가 합친 뒤 10위 밖으로 밀려났다(두 목록이 열 자리를 나눠 쓰면 각자의 깊은 순위는 살아남지 못한다). 게이트 모의에서 독립화 대비 env L=10 에서 +1, 운영 게이트에서 −1, 출하 게이트에서 env 같음 · ops −1. LLM 호출이 없는 것이 장점이지만 독립화의 비용(약 1초)은 확장과 같은 크기라 답변 생성(12~50초)에 비하면 작다(§4 의 2번과 같은 판단).
- **남은 오류 모드는 "되풀이" 하나다.** fu-07 · fu-14 는 실행마다 **앞 질문을 그대로** 돌려줬다(재작성이 원문과 다르므로 원문 검색으로 떨어지지도 않는다 — 10-12 의 깨끗한 첫 실행에서도 같았다). fu-14 는 정답이 앞 질문과 같은 청크 근처라 맞혔고, fu-07(15자)은 출하 게이트에서 독립화되지 않는다 — 출하 게이트에서 이 결함이 결과를 바꾼 케이스는 없다. 그 밖에 fu-11 은 “FM 간은?” → “DM 간의 호출이 가능한가?”로 FM 을 앞 질문의 DM 으로 바꿨는데, 정답 청크가 가까이 있어 4위로 맞혔다.

#### 3.4.4 10-12 의 측정 — 무엇이 틀렸나

10-12 에는 같은 주제 14건만으로 env 4회 · ops 3회를 돌렸다(그 사이에 골든셋 정비가 있었다 — 정비는 정답 후보를 **더하기만** 하므로 정비 뒤의 숫자가 낮아질 수는 없다). 실행 순서대로 condensed 가 **env 0.714 → 0.643 → 0.643 → 0.571, ops 0.714 → 0.571 → 0.571** 로 내려갔다 — 실행마다 앞 질문이 이력에 한 번씩 더 쌓인 순서 그대로다. 이력이 깨끗했던 각 구성의 첫 실행(0.714)은 10-13 의 결과와 같다. "XA 타입이면?" → "XA 타입이면 NOTX로 실행된 SQL은 …"(앞 질문 흡수)과 fu-01 의 "IBatchContext" 누락은 쌓인 실행에서만 나왔다. 이어 붙이기의 0.786(같은 주제)은 맞는 숫자였지만, 세트에 주제 전환이 없어 그 대가가 보이지 않았다. **그날 적은 "독립화는 이 모델에서 거의 이득이 없다 · 이어 붙이기가 낫다"는 철회한다.**

### 3.5 키워드(BM25) 검색어의 조사·어미 (2026-10-13)

**문제.** 키워드 축은 질문의 토큰을 따옴표로 묶어 **그 글자 그대로의 연속**으로 찾는다(`trigram` 색인의 구문 일치). 한국어 질문의 토큰에는 조사·어미가 붙어 있어, `"노드매니저는"` 은 본문의 `노드매니저` · `노드매니저를` 을 놓친다. 골든셋 질문의 3글자 이상 토큰 138개 중 **36개(26%)가 코퍼스에서 0건**이었고, 그중에는 `노드매니저는` · `NOTX로` · `시그니처는` · `명명규칙은` 같은 핵심어가 있었다(`노드매니저는` 0건 → `노드매니저` 3건). 늘 놓치던 arch-11 이 바로 이 경우다.

**바꾼 것.** 토큰마다 **원래 형태 옆에 조사·어미를 뗀 어간을 더한다**(`KeywordSearchRepository.matchTerms` — 추천 후보 검색의 `QuestionKeywords` 규칙을 그대로 쓴다). 어간은 원래 토큰의 접두사라 더 넓게 맞히고, 원래 형태가 남아 있으니 MATCH 결과는 언제나 예전 결과를 포함한다. 어간이 3글자에 못 미치면(`로그는` → `로그`) trigram 이 없어 더하지 않는다.

**세 가지를 쟀다**(확장을 끈 골든셋 — LLM 이 끼지 않아 실행마다 같다):

| 변형 | env recall · nDCG | ops recall · nDCG | 키워드 축 단독 recall@10 |
|---|---|---|---|
| 예전(원래 형태만) | 0.962 · 0.808 | 0.962 · 0.809 | 0.808 |
| 어간으로 **바꾸고** 의문·기능어는 뺌 | 0.962 · **0.803** | 1.000 · 0.860 | 0.808 |
| **원래 형태 + 어간**, 의문·기능어는 뺌 | 0.962 · 0.835 | 1.000 · 0.876 | **0.885** |
| **원래 형태 + 어간**, 의문·기능어는 그대로(채택) | 0.962 · 0.835 | 1.000 · 0.876 | **0.885** |

- **바꾸기만 하면 흔한 단어에서 잃는다.** `클래스는` → `클래스`(1,826개 청크)처럼 넓어지면, 본문에 그 구문이 그대로 있던 정답 청크가 받던 점수가 사라진다 — 키워드 축이 정답 셋을 얻고(batch-04 · arch-11 · sample-06) 셋을 잃었다(batch-01 · batch-05 · arch-03, 모두 5~9위). 원래 형태를 함께 두면 그런 청크는 두 항이 함께 맞아 점수가 오르고, 잃은 것은 1위 → 2위 한 건(arch-03, env)뿐이었다.
- **의문·기능어(`어떻게` · `하는가` …)를 빼도 결과가 같았다.** 그래서 더 작은 변경 — 원래 형태는 전부 그대로 두고 어간만 더하는 쪽 — 을 택했다.

**실제 조건(확장 켬)의 결과** — 같은 날 같은 DB, 바꾸기 전 / 후:

| 구성 | recall@10 | nDCG@10 | 놓친 것 | 검색 중앙값 |
|---|---|---|---|---|
| env 전 | 0.962 | 0.803 | arch-11 | 1.16초 |
| **env 후** | **1.000** | **0.844** | — | 1.13초 |
| ops 전 | 0.962 | 0.811 | arch-11 | 1.18초 |
| **ops 후** | **1.000** | **0.902** | — | 1.15초 |

케이스별로 오른 것: batch-04(3 → 1) · sample-06(3·4 → 1) · arch-11(놓침 → 1~4) · arch-05(4 → 3). 후속 질문 21문항은 갈래마다 전과 같았다(자립 질문 상한만 env 0.952 → 1.000). 검색 시간은 그대로다.

이것으로 §3.2 의 기준선은 **env 1.000 / ops 1.000**(nDCG 0.844 / 0.902)이 된다 — arch-11 은 질의 확장이 아니라 키워드 축이 되찾는다. 하네스는 이제 골든셋 행마다 키워드 축 단독의 순위(`bm25Rank`)를 남긴다(요약 표의 "BM25 축 단독 recall@10").

### 3.6 유사도 임계값 폴백 (2026-10-13)

**바꾼 것.** 벡터 검색에서 임계값(`app.search-similarity-threshold`)을 통과한 청크가 `ceil(70% × min(요청 개수, top-k))` 보다 적으면, 그 질의에서만 임계값을 **0.05 낮춰 한 번** 다시 거른다(`SimilarityFallback` — 이미 topK×2 로 가져온 행을 다시 거르므로 추가 조회는 없다, 큐레이션 축 제외). 결정 근거는 [PITFALLS § SimilarityFallback](PITFALLS.md#ingestionsimilarityfallbackjava).

**잰 것** — 바꾼 코드로 §3.5 와 같은 스크래치 DB(env · ops)를 다시 돌리고, `LOGGING_LEVEL=DEBUG` 로 발동 횟수(`[SEARCH] 유사도 임계값 … 로 낮춰`)를 셌다:

| 실행 | recall@10 · nDCG@10 | §3.5 의 값 | 발동 |
|---|---|---|---|
| env · nomq | 0.962 · 0.835 | 0.962 · 0.835 | 0 / 26 |
| ops · nomq | 1.000 · 0.876 | 1.000 · 0.876 | 0 / 26 |
| env · mq | 1.000 · 0.844 | 1.000 · 0.844 | — (로그 미수집) |
| ops · mq | 1.000 · 0.883 | 1.000 · 0.902 | — (로그 미수집) |
| 후속 질문 21 × 6갈래 (env · ops) | raw 0.667 · pipeline 0.714 / 0.762 | §3.4 와 같은 범위 | 0 |
| 임계값 **0.6**(env 복사본에 오버라이드) · nomq | 1.000 · 0.890 | — | **12 / 26** |

- 확장을 끈 실행은 LLM 이 끼지 않아 실행마다 같다 — §3.5 와 **케이스별 순위까지** 같다. ops · mq 의 nDCG 차이(0.883 vs 0.902)는 확장 LLM 출력의 흔들림이다(§3.3 — 같은 구성이 0.789~0.847 사이를 오갔다). 발동이 0회이므로 이 실행에서 폴백이 바꾼 것은 없다.
- **왜 발동하지 않는가.** 이 코퍼스(청크 2,388개)와 bge-m3 에서는 짧은 후속 질문("처리일자는 어떻게 꺼내?")도 상위 청크 대부분이 0.3~0.35 를 넘는다. 폴백은 임계값을 올려 둔 배포나 코퍼스가 작은 배포의 안전판이다.
- **경로가 실제로 도는지**는 0.6 실행으로 확인했다 — 26문항 중 12번 발동했고, 낮춘 0.55 로 질의당 0~10개를 되찾았다. 이 실행의 recall 1.000 은 폴백이 없는 0.6 과 비교한 값이 아니므로 "0.6 이 낫다"는 근거가 아니다(그 비교는 하지 않았다).
- 확장을 켠 실행은 로그 수집 전이라 발동 수가 없다 — 확장 질의도 같은 판정을 받지만, 끈 실행이 0회이므로 확장 질의만 따로 많이 발동할 이유는 없다.

## 4. 결론과 제안

측정이 권한 것과 그 근거다. 다섯 다 권고대로 결정했다 — 2(질의 확장 유지)·4(게이트 임계값 유지)는 2026-10-12, 3(독립화 유지 — PLAN §10.12 (e))·5(키워드 검색어 개선)는 2026-10-13.

1. **검색 품질은 회귀하지 않았다** — §10.10 (d) · §10.11 (d)(큐레이션 축 합류 뒤 재측정)를 닫는다. 기준선은 §3.5 이후 두 구성 모두 1.000(nDCG `.env` 0.844 · 운영 0.902)이고, 비교할 때는 코퍼스 점검 줄(상한)을 먼저 본다.
2. **질의 확장은 켠 채로 둔다(출하값 그대로).** 이득은 운영 구성의 1건(arch-11, 4/4)뿐이지만, 대가(검색당 약 1.1초 + LLM 1회)는 답변 생성(12~50초)에 비하면 작고, 끈다고 얻는 것이 없다. 코퍼스가 더 커지면(arch-11 처럼 표 한 행이 대형 문서에 밀리는 일) 확장의 몫이 커질 수 있다. **→ 유지하기로 결정.** (§3.5 이후 운영 구성은 확장 없이도 arch-11 을 1위로 맞히고, `.env` 구성은 확장을 켜야 4위로 맞힌다 — 확장의 몫이 옮겨 갔을 뿐 사라지지 않았다.)
3. **§10.12 독립화는 그대로 둔다**(2026-10-13 재측정, §3.4). 깨끗한 이력에서 원문보다 1~2건 낫고 주제 전환에서 손해가 없다. **이어 붙이기는 뺀다** — 주제 전환에서 무너진다. **원문 + 이어 붙이기 함께 검색도 바꿀 근거가 없다** — 독립화와 비기고(출하 게이트에서 env 같음 · ops −1), LLM 호출 하나(약 1초)를 아끼는 대신 깊은 순위를 잃는다. **되풀이 가드**(재작성이 앞 질문을 그대로 돌려주면 원문으로)는 출하 게이트에서 결과를 바꾼 케이스가 없어 지금은 넣지 않는다 — 생성 모델을 바꾸면 이 절을 다시 잰다. **→ 유지하기로 결정(2026-10-13).**
4. **게이트 임계값(§10.12 (a))은 그대로 둔다.** 모의 결과 L=10~15 사이에서 독립화의 성적이 1건 안에서 같았고 출하값 15 가 가장 좋거나 같았다(전체 21건 0.762, §3.4.2). 별도 키를 만들 근거도 없다. **→ 유지하기로 결정.**
5. **키워드 검색어에 조사·어미를 뗀 어간을 더한다(적용).** 원래 형태는 지우지 않는다 — 바꾸기만 하면 흔한 단어에서 정답 청크가 점수를 잃는다(§3.5). 골든셋 두 구성 1.000, nDCG +0.04 · +0.09, 후속 질문 변화 없음, 검색 시간 그대로. **→ 적용(2026-10-13).**

## 5. 한계

- **골든셋이 작다**(26 + 21). 한 건이 recall 0.038(골든셋)·0.048(후속 전체)·0.071(같은 주제 14)·0.143(주제 전환 7)이다. 차이는 건수로 읽는다.
- **후속 질문 세트는 직접 만든 21문항이다.** 주제 전환 7건은 앞 질문과 다른 문서를 골라 만든 깨끗한 전환이라, 반쯤 기댄 전환(“그럼 배포는?”)은 없다. 같은 주제 14건은 앞 질문을 정답의 이웃 케이스로 골라 이어 붙이기에 유리하다.
- **`fused` 는 근사다** — 하네스가 두 결과 목록을 합친다. 제품에서 축 단위로 합치면 숫자는 조금 다를 수 있다(§3.4.1).
- **확장은 실행마다 조금 흔들린다**(온도 0.2~0.25 의 LLM 출력) — 같은 구성을 2~3번 돌려 흔들림의 폭을 적었다. 독립화는 이력이 깨끗하면 두 번의 결과가 같았다(§3.4.2) — 10-12 에 보인 흔들림은 대부분 이력 누적 때문이었다(§3.4.4).
- **코퍼스 하나·모델 하나**(gemma-4-E2B · bge-m3). 더 큰 생성 모델은 독립화를 더 잘할 수 있다.
- 7월 기준선의 구성(top-K 등)은 기록이 없어 정확히 같은 조건의 비교는 아니다.

## 6. 재현 방법

하네스는 `src/test/java/com/example/ragagent/evaluation/SearchQualityEvaluationTest.java`(기본 skip), 요약은 `scripts/search_eval_summary.py` 다. 앱 컨텍스트가 뜨면서 Flyway·백필이 DB 에 쓰고 후속 질문 절은 이력·설정까지 쓰므로 **스크래치 복사본**에서 돌린다.

```bash
# 스크래치 DB — 살아 있는 앱이 WAL 을 쥐고 있을 수 있으니 파일 복사가 아니라 SQLite backup 으로
python -c "import sqlite3,os; os.makedirs('target/search-eval-data/ops',exist_ok=True); sqlite3.connect('file:data/memory.db?mode=ro',uri=True).backup(sqlite3.connect('target/search-eval-data/ops/memory.db'))"
# env 구성은 같은 복사본에서 settings_override 를 비운 것

mvn -o test -Dtest=SearchQualityEvaluationTest -Dsearch-eval.enabled=true \
    -Dsearch-eval.data-dir=target/search-eval-data/ops -Dsearch-eval.label=ops-mq \
    [-Dsearch-eval.multiquery=false] [-Dsearch-eval.followup=true]

python scripts/search_eval_summary.py target/search-eval
```

- 출력은 `<out>/<label>/gold.jsonl`·`followup.jsonl`(케이스마다 한 줄, 상위 10개 문서 이름 포함). 사람이 읽는 표는 Surefire 출력 파일에 찍힌다(Maven 로그가 아니다).
- 발동 횟수를 세려면 `LOGGING_LEVEL=DEBUG` 를 **환경변수로** 준다 — `-Dlogging.level…` 은 Surefire 가 띄운 테스트 JVM 의 로그 설정을 바꾸지 못했다(10-13). 줄은 Surefire XML(`TEST-…SearchQualityEvaluationTest.xml`)에 남는다.
- 실행 하나가 약 2분이다(앱 기동 + 골든셋 26문항 + 후속 질문 21문항 × 6갈래, 확장 켬). **LLM 서버 하나를 쓰므로 실행은 직렬로**, 생각 수준 하네스와 겹치지 않게 돌린다.
- 후속 질문 절은 대화 스레드 id 에 실행마다 새 값을 넣는다 — 같은 스크래치 DB 로 거듭 돌려도 앞 질문이 이력에 겹치지 않는다(10-12 의 결함, §3.4.4). 이력에 기대는 다른 측정을 만들 때도 같은 규칙을 지킬 것.
- `target/` 은 `mvn clean` 이 통째로 지운다 — 스크래치 DB 와 원자료(JSONL)가 함께 사라진다(10-13 에 한 번 겪었다). 숫자는 이 문서로 옮겨 두고, 다시 잴 때는 스크래치부터 다시 만든다.
- 결과가 크게 떨어지면 먼저 `corpus:` 줄(정답이 코퍼스에 있는 케이스 수)을 본다 — 문서를 바꾼 뒤라면 골든셋이 낡은 것일 수 있다.
