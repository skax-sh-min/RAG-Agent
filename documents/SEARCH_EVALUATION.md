## 1. 한눈에

- **검색은 7월 기준선에서 물러서지 않았다.** 골든셋 recall@10 은 `.env` 구성 0.962(nDCG 0.803~0.808), 지금 운영 설정 + 질의 확장 1.000 — 2026-07-16 기준선(0.962, nDCG 0.810)과 같은 수준이다. 그 사이 문서가 3종에서 23종(청크 2,388개)으로 늘었다.
- **다만 고치기 전의 골든셋으로는 0.923 으로 보였다.** 정답 문자열 26개 중 6개가 낡아 있었다 — 5개는 문서를 "RAG-수정"판으로 바꾸며 표현·서식이 달라졌고, 1개(arch-09)는 그 뒤 들어온 개발가이드에 더 직접적인 답이 생겼다(§3.1). 숫자가 떨어진 것이 검색 탓인지 골든셋 탓인지를 가르려고 하네스가 이제 매번 **코퍼스 점검**(정답 문자열이 코퍼스 어딘가에 있는가 = recall 상한)을 찍는다.
- **질의 확장(MultiQuery)은 거의 아무것도 바꾸지 않는다.** `.env` 구성에서는 확장을 켜든 끄든 26건 전부 같은 결과(3회 · 2회), 운영 구성(top-K 15)에서만 1건(arch-11)을 되찾았다(4/4). 대가는 검색마다 LLM 호출 1회와 약 1.1~1.3초(중앙값 0.2초 → 1.3초)다(§3.3).
- **후속 질문(§10.12 독립화)은 거의 이득이 없었다.** 맥락에 기댄 짧은 질문 14개에서 지금의 파이프라인은 recall@10 0.643~0.714 로 **아무것도 안 한 원문(0.643)과 같거나 1건 낫다.** 소형 모델(gemma-4-E2B)의 재작성은 앞 질문의 내용을 섞거나(“XA 타입이면?” → “XA 타입이면 NOTX로 실행된 SQL은…”) 앞 질문을 그대로 되풀이했다. 반면 **LLM 없이 앞 질문을 이어 붙이기만 한 검색어가 0.786** 으로 모든 실행에서 가장 높았다(자립적으로 다시 쓴 질문의 상한 0.929~1.000). 다만 이 세트는 앞뒤 질문이 같은 주제라 이어 붙이기에 유리하다(§3.4).

## 2. 환경과 방법

### 2.1 환경

[THINKING_EVALUATION.md §2.1](THINKING_EVALUATION.md) 과 같은 노트북(Core 7 150U · 32 GiB · MX570 A), 같은 서버 두 대(생성 `:1234` b11433 · 창 32,768, 임베딩 `:8091` bge-m3 · 창 8,192), 같은 개발 DB 의 스크래치 복사본이다. 벡터 백엔드는 sqlite-vec(`memory.db` 한 파일), 하이브리드(BM25) 켬, 리랭커 끔.

**코퍼스**: 문서 23종 · 청크 2,388개(`version=latest`) + 큐레이션 1건 — 개발교육 PPTX(143) · 개발가이드 DOCX(393) · API 레퍼런스 MD 13종(`fwk-util` 646 · `fwk-data` 501 · `fwk-online` 101 · `fwk-kube-*` …) · 샘플 분석 MD 5종 · 가이드 PPTX 3종. 7월 기준선 때는 앞의 셋 정도였다.

### 2.2 두 구성

| 구성 | 만든 법 | top-K | 유사도 임계 | 확장 게이트(min-length) | 그 밖 |

각 구성을 질의 확장 켬(`mq`)·끔(`nomq`)으로 돌렸다. 확장과 독립화는 LLM 출력이 섞여(온도 0.2~0.25) 실행마다 조금 다르므로 같은 구성을 2~3번 돌려 흔들림을 봤다.

### 2.3 판정

정답은 케이스마다 **정답 문자열**(`mustContainAny`, 하나라도 맞으면 정답)이고, 검색 결과 상위 10개 안에서 처음 맞는 순위로 recall@10(0/1)·nDCG@10(1/log2(rank+1))을 낸다(§10.7.5 와 같다). 이번에 바꾼 것 하나: **비교 전에 양쪽에서 공백과 마크다운 장식(`* \` # > _ | ~ -`)을 걷는다**(`SearchQualityMetrics.containsAnyMarker`). 문서를 다시 교정하면 같은 문장에 `**굵게**` 가 붙거나 줄이 바뀌어, 내용은 그대로인데 "정답 없음"이 됐다. 표현 자체가 바뀐 경우(애플리케이션 → 어플리케이션)는 이 규칙으로 잡지 않고 골든셋에 지금 표현을 더했다.

### 3.3 질의 확장의 값

- **env 구성: 0건.** 정비 전 3회·2회, 정비 후 1회·1회 모두 확장 켬과 끔의 recall 이 같다. 순위가 달라진 케이스(batch-01 · arch-06 · sample-06 등)는 오르내림이 섞여 nDCG 는 끔이 조금 높다(0.770 vs 0.761~0.764, 정비 후 0.808 vs 0.803).

### 3.4 후속 질문 — §10.12 독립화

**세트**(`nexcore-followup.json`, 14문항): 골든셋 케이스 하나를 앞 질문으로 이력에 넣고, 이웃 케이스의 답을 묻는 **맥락에 기댄 짧은 질문**을 던진다(“처리일자는 어떻게 꺼내?” — 앞 질문은 “IBatchContext 객체는 무엇을 전달하기 위한 것인가?”). 정답은 이웃 케이스의 정답 문자열이다. 길이 6~28자, 출하 게이트(15) 아래가 8건 · 이 `.env` 의 게이트(10) 아래가 3건이다.

**갈래** — 같은 후속 질문을 다섯 가지 검색어로 검색한다.

| 갈래 | 검색어 | 확장 |
|---|---|---|
| raw | 후속 질문 원문 | 없음 |
| pipeline | **지금의 동작** — 게이트 아래면 독립화, 위면 원문 + 확장 | 게이트 위에서만 |
| condensed | 길이와 무관하게 독립화한 질문 | 없음 |
| concat | 앞 질문 + 후속 질문을 **이어 붙인 것**(LLM 없음 — 독립화의 값싼 대안) | 없음 |
| full | 정답 케이스의 원래 질문(사람이 쓴 자립 질문 = 상한) | 설정대로 |

**결과**(골든셋 정비 후, 두 구성):

| 갈래 | env(게이트 10) | ops(게이트 12) |
|---|---|---|
| raw | 0.643 | 0.643 |
| pipeline(지금) | 0.643 | 0.714 |
| condensed | 0.571 | 0.571 |
| **concat** | **0.786** | **0.786** |
| full(상한) | 0.929 | 1.000 |

- **독립화가 실제로 구한 것은 fu-11 하나다**(“FM 간은?” → “FM 간의 호출은 가능한가요?”, 원문은 놓친다). 대신 원문이면 1위인 fu-05 를 놓쳤고, 길이와 무관하게 독립화하면(condensed) 원문이 2위로 맞히는 fu-07 도 놓친다. 둘 다 재작성이 **앞 질문의 내용을 끌어왔다** — “XA 타입이면?” → “XA 타입이면 NOTX로 실행된 SQL은 본 거래 트랜잭션이 롤백되어도 영향을 받는가?”(앞 질문이 NOTX 를 물었다) · “로그는 파일에 어떻게 남아?” → “로컬 환경에서 onlinelog.level의 로그는 파일에 어떻게 남게 되나요?”. fu-14 는 일곱 번 중 다섯 번 **앞 질문을 그대로 되풀이**했다(“EIMS에서 배포받은 UIO는 수동으로 편집할 수 있는가?”) — 정답이 앞 질문과 같은 청크 근처라 우연히 맞혔다. 독립화는 프롬프트가 금지하는 바로 그 일을 소형 모델에서 한다.
- **이어 붙이기는 원문이 놓친 넷을 구했다**(fu-01 · fu-06 · fu-08 · fu-11 — 앞 질문의 명사가 정답 청크를 가리킨다). 놓친 것은 fu-05 · fu-07 · fu-13 이고, 셋 다 앞 질문의 주제가 검색어를 끌고 간 경우다(fu-13 의 앞 질문은 다른 문서의 케이스다).
- **이 세트는 이어 붙이기에 유리하다.** 앞 질문을 정답 케이스의 **이웃**으로 골랐으므로 앞 질문의 단어가 정답 근처를 가리키는 일이 많다. 실제 대화에서 짧은 후속 질문은 대개 같은 주제를 잇지만, **주제를 바꾸는 짧은 질문**(“그럼 배포는?”)은 이어 붙이기가 앞 주제로 끌고 간다 — 이 세트에는 그런 케이스가 없다.
- **게이트 모의**: 게이트 L 보다 짧은 질문만 독립화(또는 이어 붙이기)하고 나머지는 확장하는 파이프라인을 케이스별 결과로 다시 짜 보면 — 독립화는 L=10~15 에서 0.643~0.714 로 L 에 거의 무관하고, 이어 붙이기는 L=10~12 에서 0.714~0.786, **L=15(출하값)에서 두 구성 모두 0.786** 이다. 게이트를 바꾸는 것만으로는 얻는 것이 없고, 바꿀 것은 게이트 아래에서 하는 일이다.

## 4. 결론과 제안

결정은 사용자 몫이다. 측정이 권하는 것과 그 근거만 적는다.

1. **검색 품질은 회귀하지 않았다** — §10.10 (d) · §10.11 (d)(큐레이션 축 합류 뒤 재측정)를 닫는다. 기준선은 계속 `.env` 구성 0.962 / 운영 구성 1.000 이고, 비교할 때는 코퍼스 점검 줄(상한)을 먼저 본다.
2. **질의 확장은 켠 채로 둔다(출하값 그대로).** 이득은 운영 구성의 1건(arch-11, 4/4)뿐이지만, 대가(검색당 약 1.1초 + LLM 1회)는 답변 생성(12~50초)에 비하면 작고, 끈다고 얻는 것이 없다. 코퍼스가 더 커지면(arch-11 처럼 표 한 행이 대형 문서에 밀리는 일) 확장의 몫이 커질 수 있다.
3. **§10.12 독립화는 이 모델에서 값을 못 한다 — 바꾼다면 "이어 붙이기"를 먼저 시험한다.** 지금의 파이프라인은 원문 대비 0~+1건이고 재작성이 앞 질문을 끌어와 맞던 것을 놓친다. 이어 붙이기는 LLM 호출 없이 네 번 모두 지금의 파이프라인보다 1~2건 많았다(원문보다 +2건). 다만 그대로 교체하기 전에 **주제를 바꾸는 짧은 질문**을 세트에 더해(이어 붙이기가 지는 쪽) 다시 재야 한다 — 지금 세트로는 그 손해를 볼 수 없다. 선택지는 셋이다: (a) 그대로 둔다 · (b) 게이트 아래의 독립화를 이어 붙이기로 바꾼다(호출 −1, 분류기·리랭커가 받는 검색어도 바뀐다) · (c) 독립화 결과가 앞 질문을 되풀이하거나 앞 질문의 핵심어를 끌어오면 버리고 원문으로(가드 추가 — 오류 모드 둘 중 하나만 막는다).
4. **게이트 임계값(§10.12 (a))은 그대로 둔다.** 모의 결과 L=10~15 사이에서 독립화의 성적이 거의 같았다 — 문제는 임계값이 아니라 게이트 아래에서 하는 일이다. 별도 키를 만들 근거도 없다.

## 5. 한계

- **골든셋이 작다**(26 + 14). 한 건이 recall 0.038(골든셋)·0.071(후속)이다. 차이는 건수로 읽는다.
- **후속 질문 세트는 같은 주제를 잇는 질문뿐이다**(§3.4). 주제를 바꾸는 짧은 질문이 없어 이어 붙이기의 손해를 재지 못한다.
- **확장·독립화는 실행마다 흔들린다**(온도 0.2~0.25 의 LLM 출력). 같은 구성을 2~3번 돌려 흔들림의 폭을 적었다.
- **코퍼스 하나·모델 하나**(gemma-4-E2B · bge-m3). 더 큰 생성 모델은 독립화를 더 잘할 수 있다.
- 7월 기준선의 구성(top-K 등)은 기록이 없어 정확히 같은 조건의 비교는 아니다.

## 6. 재현 방법

하네스는 `src/test/java/com/example/ragagent/evaluation/SearchQualityEvaluationTest.java`(기본 skip), 요약은 `scripts/search_eval_summary.py` 다. 앱 컨텍스트가 뜨면서 Flyway·백필이 DB 에 쓰고 후속 질문 절은 이력·설정까지 쓰므로 **스크래치 복사본**에서 돌린다.

```bash
# 스크래치 DB — 살아 있는 앱이 WAL 을 쥐고 있을 수 있으니 파일 복사가 아니라 SQLite backup 으로
python -c "import sqlite3,os; os.makedirs('target/search-eval-data/ops',exist_ok=True); sqlite3.connect('file:data/memory.db?mode=ro',uri=True).backup(sqlite3.connect('target/search-eval-data/ops/memory.db'))"
# env 구성은 같은 복사본에서 settings_override 를 비운 것

mvn -o test -Dtest=SearchQualityEvaluationTest -Dsearch-eval.enabled=true \
    -Dsearch-eval.data-dir=target/search-eval-data/ops -Dsearch-eval.label=ops-mq \
    [-Dsearch-eval.multiquery=false] [-Dsearch-eval.followup=true]

python scripts/search_eval_summary.py target/search-eval
```

- 출력은 `<out>/<label>/gold.jsonl`·`followup.jsonl`(케이스마다 한 줄, 상위 10개 문서 이름 포함). 사람이 읽는 표는 Surefire 출력 파일에 찍힌다(Maven 로그가 아니다).
- 실행 하나가 2~3분(확장 켬)·1분(끔), 후속 질문 절이 3~4분 더한다. **LLM 서버 하나를 쓰므로 실행은 직렬로**, 생각 수준 하네스와 겹치지 않게 돌린다.
- 결과가 크게 떨어지면 먼저 `corpus:` 줄(정답이 코퍼스에 있는 케이스 수)을 본다 — 문서를 바꾼 뒤라면 골든셋이 낡은 것일 수 있다.
