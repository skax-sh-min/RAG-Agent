- **고친 뒤의 최종 결과는 이전보다 같거나 낫다.** 16K 긴 질문은 근거 있음 7 → 8 · 재시도 16 → 14 · LLM 호출 58 → 54 이고, 후속 질문 셋은 지표가 전부 같다. 12K 긴 질문은 근거 있음 6 → 7 · 재시도 11 → 9 · LLM 호출 48 → 44 이고, 조기 종료가 다시 6번 걸린다. 예외는 둘이다(§3.4):

  - ③ 은 12K 에서 근거 있음이 한 건 줄었다(f3-03).
- **E 는 넣지 않는다.** 문서를 줄인 채 나온 반려 뒤의 재시도는 약 3분의 1 이 근거 있음으로 끝났다. 문서를 줄이지 않은 반려보다 낮지 않다.

### 2.2 무엇을 비교했나

**같은 하네스(`PromptLadderEvaluationTest`)를 두 코드에서 돌렸다.** 예전 순서(문서를 RRF 하위부터 → 그래도 넘치면 이력을 오래된 턴부터)는 HEAD 에 없으므로 사다리 직전 커밋(9298a00)의 worktree 에 같은 파일을 복사해 돌린다 — 하네스는 두 커밋에 다 있는 API(채팅 진입점 `StreamingAgentService.run` · `MemoryService.addTurn` · `ProviderContextWindows.record`)만 쓴다. 사다리 쪽은 재시도 규칙 A~D 까지 들어간 코드다(E 는 넣지 않았다 — 이 측정이 그것을 정한다).

- **이력이 두 쪽에서 같다.** 앞 턴의 답변은 `prepare` 절이 한 번 만들어(창 선언 없음 · top-K 10) fixture(`priors.json`, RAG 16 · Direct 8)로 두고, 측정은 그것을 새 대화에 `addTurn` 으로 바로 넣는다. 파이프라인으로 앞 턴을 다시 만들면 답변이 실행마다 달라 비교가 흐려진다.
- **좁은 창은 선언으로 흉내 낸다** — 서버는 그대로 32K 이고, 기동 뒤 프로바이더 창을 `CONFIGURED` 로 기록해 앱의 예산만 그 창으로 계산한다(재탐지가 덮지 않는다). 그래서 **서버가 컨텍스트 초과로 거절하는 일은 없다** — 축소 재시도(`[SHRINK]`)는 이 방법으로 재지 못한다(§6).
- **결정성 대조**: 두 코드가 같은 프롬프트를 보낸 사례(축소가 없었거나 같은 축소)는 답변이 **글자 하나까지 같았다**(16K 의 ①②③ 30건 전부). 그래서 두 실행의 차이는 실행 간 흔들림이 아니라 프롬프트 차이에서 온다 — 다만 프롬프트가 조금만 달라도 답이 달라지므로, 사례 하나의 뒤집힘은 그 프롬프트 변화의 "효과"라기보다 섭동이다. 방향은 여러 사례의 합으로 읽는다.

### 2.4 창과 top-K

- **16K** 는 지원하는 가장 작은 창이다(`ProviderContextWindows.MIN_SUPPORTED_TOKENS`, 2026-10-23 부터). 계획서의 8K 는 그 밑이라 재지 않았다 — 입력 예산이 약 2,400토큰이라 긴 질문 하나로 바닥난다.
- **12K** 는 압박 대용이다. 이 코퍼스의 청크가 계획서 예의 3분의 1 크기라, 16K 에서는 긴 질문에서 문서 1~2개가 빠지는 정도이고 후속 질문(①②③)에는 축소가 거의 걸리지 않는다. 12K 의 입력 예산(6,060) 대 문서 15개(약 7,000토큰)의 비는 계획서 예(16K · 문서 10 × 1,500)와 비슷하다 — 칸 4·5 가 실제로 도는 것은 이 창뿐이다.
- **top-K 15** — 출하·`.env` 값(10)으로는 16K 에서 축소가 거의 일어나지 않아(첫 실행에서 확인하고 멈췄다) 운영 DB 의 실제 값으로 올렸다. 바닥은 `ceil(15/2)` = 8.

### 2.5 판정

- **keyHit** — 정답 마커(`mustContainAny`)가 최종 답변에 있는가. 비교 전에 공백·마크다운 장식을 걷는다(`SearchQualityMetrics.containsAnyMarker`).
- **근거 있음(최종)** — 마지막 시도의 `grounded`(배지를 정하는 값). 재시도를 다 쓴 마지막 시도가 `sufficient=false` 여도 `grounded=true` 면 여기에 든다.
- **재시도 · LLM 호출 · 소요** — 턴 하나의 합. 소요는 채팅 진입점 호출 전체의 벽시계다.
- **시도별**(Maven 로그에서) — 시도마다 `[BUDGET]`(문서 a→b · 이력 · 칸) · 검증 미통과 · 교체(`밀어낼 청크`) · 조기 종료. E 의 근거(문서를 줄인 시도에서 나온 반려 뒤 재시도의 결과)는 여기서 센다.

| arch-03 | 6 · 940 ✗ → 6 · 940 ■ **조기 종료**(keyHit ○) | 7 · 221 ✗ → 7 · 221 ✗ → 8 · 0 ■ (keyHit ×) |
| sample-03 | 6 · 716 ✗ → 6 · 716 ■ **조기 종료**(keyHit ○) | 7 · 366 ✗ → 7 · 567 ✗ → 7 · 165 ■ (keyHit ×) |

**무엇이 일어났나.** 근거 없음 반려에서 검증은 쓴 문서(`usedDocs`)를 대개 비워 보낸다 — 긴 질문 절에서 교체(= 쓴 문서가 보고된 반려)는 16K 이전 4번 중 4번, 12K 설계대로 4번 중 3번이 `grounded=true` 반려에서 나왔고, 반려 대부분(12K 설계대로 19건 중 16건)은 근거 없음이었다. 설계의 D 는 그때 "직전에 실렸던 문서 전부가 첫 무리"(먼저 뺀다)이고, 재시도 쪽 "새로 들어온 문서"는 **직전 시도에 실리지 않은 문서**다 — 재시도가 새로 가져온 문서뿐 아니라 지난번에 **예산 때문에 잘린** 하위 문서도 여기에 든다. 15개 중 7개만 들어가는 창에서는:

1. 첫 시도: 1~7위를 싣는다(순위 순으로 뺐다).
2. 둘째 시도: 같은 15개가 다시 온다(교체도 +1 도 없었다 — 보고가 비어 교체가 없고, 검증 발췌 여유가 없어 +1 도 생략). D 가 1순위를 뺀 2~7위를 먼저 빼고 8~15위의 하위부터 뺀다 → **1위 + 8~13위**를 싣는다.
3. 셋째 시도: 이번에는 8~13위가 "직전에 실린 것"이라 먼저 빠진다 → 다시 **1~7위 근처**.

보낸 집합이 매번 달라 조기 종료(B — 보낸 집합으로 비교한다)가 걸리지 않았고, 둘째 시도는 하위 문서로 답했다가 반려됐으며, 셋째 시도의 `[직전 시도 메모]` 는 그 하위 문서로 낸 반려 사유("문서에 X 가 없다")를 싣는다. 이전 코드는 같은 6개를 다시 보내 같은 집합으로 반려되자 멈췄다(§6.27).

**고친 것.** 사용 보고가 없으면 직전에 실린 문서를 "쓴 것"과 같이 **지킨다**(맨 나중에 뺀다). 빈 보고는 "안 썼다"가 아니라 "모른다"다 — 교체(`RetrievalEviction`)의 가드 ①이 이미 그 규약이고, D 의 설계만 반대였다. 새 문서가 없으면 재시도는 같은 문서를 다시 보내고 같은 재료로 또 반려되면 조기 종료가 멈춘다. 쓴 문서가 보고되면 지금과 같다(봤지만 안 쓴 것 → 새 것 → 쓴 것). `PromptLadder.retryRemovalOrder` 한 줄과 테스트 둘(`PromptLadderTest.unknownUseKeepsThePreviouslySentSet` · `AnswerServiceLadderTest.retryWithUnknownUseKeepsThePreviouslySentDocuments`).

고친 코드로 두 창을 다시 쟀다(같은 fixture · 같은 스크래치 DB 모양). 칸마다 `이전 / 설계대로 / 고친 뒤`.

| 창 · 절 | keyHit | 근거 있음(최종) | 판정 없음 | 재시도(합) | LLM 호출 | 조기 종료 |

| 16K long (13) | 5 / 5 / 5 | 7 / 10 / **8** | 0 / 0 / 0 | 16 / 10 / **14** | 58 / 46 / **54** | 0 / 0 / 0 |
| 16K ① ② ③ | 같다 | 같다 | 0 | 같다(0 · 9 · 0) | 같다(28 · 34 · 16) | 0 |

첫 시도는 고친 것의 영향을 받지 않는다. `retryRemovalOrder` 는 직전 시도가 있을 때만 돌기 때문이고, 실제로 첫 시도의 `[BUDGET]`(문서 수 · 이력 길이 · 칸)은 설계대로와 고친 뒤가 43사례 모두 같았다. 그래서 두 실행의 차이는 두 갈래로 나뉜다.

- **첫 시도의 판정이 뒤집힌 사례는 섭동이다.** 16K batch-05·arch-03 과 12K arch-03 은 같은 프롬프트를 보냈는데 판정이 갈렸다. 앞 사례들의 재시도가 달라 서버 캐시의 상태가 달랐던 것으로 본다(§3.2 의 ① 과 같은 현상). 16K 에서 설계대로 → 고친 뒤의 차이(근거 있음 −2 · 재시도 +4)는 대부분 여기서 왔다. 재시도 +4 는 전부 batch-05·arch-03 이고, 근거 있음 −2 중 하나가 batch-05 다.
- **재시도 순서가 바꾼 사례는 판정으로는 비기고, 비용은 고친 쪽이 적다.**
  - 설계대로의 왕복이 하위 문서에서 근거를 찾은 사례가 셋이다 — 16K sample-05(셋째 시도) · 12K arch-05 · f3-03.
  - 같은 문서를 `[직전 시도 메모]` 와 함께 다시 보낸 쪽이 통과한 사례가 둘이다 — 12K batch-01 · sample-01(둘째 시도).
  - 판정이 같은 나머지 6사례(12K 긴 질문 batch-03·batch-05·arch-07·arch-11·sample-03 · ② f2-04)는 고친 뒤에 한 시도씩 덜 썼다. 판정이 바뀐 사례까지 합치면 12K 긴 질문의 LLM 호출이 64 → 44 다.

**12K 긴 질문의 keyHit 6 → 4 는 손실이 아니다.** 이전 코드에서 keyHit 이 맞은 arch-03·sample-03 의 답은 둘 다 "제공된 문서에는 … 정의/규정이 포함되어 있지 않다"로 시작한다. 마커는 그 뒤에 메서드 이름을 나열하다 우연히 들어갔다. 세 코드 모두 같은 결론(문서에 없다)을 냈다. 고친 뒤의 arch-03 은 같은 결론을 첫 시도에서 근거 있음으로 냈다.

**③ 의 한 건(f3-03).**
- 이전 코드: 문서 7개 + 직전 Direct 답변 전문(3,621자)으로 첫 시도에서 통과했다.
- 사다리(설계대로·고친 뒤 공통): 칸 4 의 요약(270자) + 문서 12개인 첫 시도가 "온라인과 배치의 트랜잭션 처리 차이가 문서에 없다"로 반려됐다. 설계대로는 둘째 시도에서 하위 문서로 갈아타 통과했다. 고친 뒤는 같은 12개로 다시 반려돼 조기 종료됐고, CRITIC 게이트의 답변 재생성(재검색 없음)도 반려됐다.
- keyHit 은 세 코드 모두 ×다. 문서가 늘어난 프롬프트가 근거 없는 답을 낸 사례 하나다. 칸 4 의 손해(요약이 직전 답의 세부를 잃는다)를 보여 주는 사례는 아니다 — 이 질문의 답은 직전 답변이 아니라 문서에 있어야 한다.

**조기 종료 뒤에도 재시도가 하나 더 붙는 것은 설계대로다.** 12K f2-01·f2-02·f3-03 은 `조기 종료 1` 인데 `재시도 2` 다. 불충분 게이트의 조기 종료는 CRITIC 게이트로 내려가고, 그 게이트는 다른 실패라 따로 판단한다(`AgentGraph` — §6.27). 그래서 근거 없음 판정이 검증 발췌를 줄이지 않은 채 나왔으면, 재검색 없이 답변만 한 번 더 만든다. 12K 긴 질문의 조기 종료 6건은 발췌가 잘려 근거 없음 판정이 버려지므로(`unreliableNegative()`) 거기서 끝난다.

### 3.5 재시도 규칙별로

- **A(교체는 보낸 집합 안에서)** — 이전 코드의 16K 긴 질문 교체 4번은 전부 답변 프롬프트가 검색 결과 15~16개 중 13개만 실은 시도에서 나왔다. 교체는 뒤에서부터 고르므로 실리지 않은 하위 문서(2~3개)가 맨 먼저 후보가 되고, 검증이 그것을 썼다고 보고하지 않는 한 "안 쓰임"으로 밀려난다 — A 가 고친 바로 그 모양이다(로그에 밀려난 id 는 남지 않아 실제 개수는 확인하지 못했다). 설계대로 16K 긴 질문에서 교체가 0번인 것은 쓴 문서가 보고된 반려가 없어서다(가드 ①) — A 가 막은 것이 아니다.
- **B(조기 종료를 보낸 집합으로)** — 설계대로는 16K·12K 모두 0회였다. 16K 는 이전 코드도 0회다(재시도마다 +1 로 검색 결과가 달라진다). 12K 의 0회는 §3.3 의 왕복 때문이고, 고친 뒤에는 긴 질문 6회(이전과 같다) · ② 2회 · ③ 1회가 걸렸다.
- **C(재시도가 이력을 더 줄이지 않는다)** — 바닥 위에서는 지켜졌다(16K: 첫 시도 이력 147~567자 → 재시도에서 같거나 늘었다, 문서가 16 → 12~13개로 흡수). 바닥 아래(12K 긴 질문)에서는 설계대로 이력 칸을 더 썼다(0자까지).
- **D(새 문서를 나중에 뺀다)** — §3.3.
- **E(문서를 줄인 채 나온 불충분 판정 — 재시도를 할 것인가)** — 아래 표. "결국 근거 있음" = 그 사례의 마지막 시도가 `grounded=true`.

| 실행 | 문서를 줄인 시도에서 반려된 사례 → 결국 근거 있음 | 줄이지 않은 시도에서만 반려된 사례 → 결국 근거 있음 |
|---|---|---|
| 16K 이전 | 9 → 3 | 5 → 1 |
| 16K 설계대로 | 5 → 2 | 5 → 1 |
| 12K 이전 | 13 → 4 | 1 → 0 |
| 12K 설계대로 | 15 → 5 | 0 → 0 |
| 16K 고친 뒤 | 7 → 2 | 5 → 1 |
| 12K 고친 뒤 | 13 → 4 | 1 → 1 |

문서를 줄인 시도에서 반려된 사례의 약 3분의 1 이 재시도로 근거 있음이 됐다 — 줄이지 않은 시도의 반려(5건 중 1건)보다 낮지 않다. E 를 넣으면 이 3분의 1 을 잃는다.

## 4. 결정

1. **§6.30 은 완료로 판정한다.** 완료 기준(PLAN §6.30)마다 고친 뒤의 결과를 본다.
   - *긴 질문에서 근거가 는다* — 그렇다. 첫 시도의 문서가 16K +1.0개 · 12K +1.2개 늘었고, 최종 근거 있음도 두 창 모두 +1 이다.
   - *① 이 같거나 낫다* — 두 창 모두 지표가 같다.
   - *②·③ 이 나빠지지 않는다* — 16K 는 같다. 12K 의 ② 는 keyHit 5 → 5 · 근거 있음 5 → 6 이다. ③ 은 keyHit 4 → 4 · 근거 있음 8 → 7 로, 한 건(f3-03)이 줄었다. 그 한 건은 칸 4 가 직전 답의 세부를 잃은 사례가 아니다(§3.4). 절당 8사례에서 한 건은 ① 의 기준선(같은 축소인데 답 14건 중 9건이 달라도 지표는 그대로)이 보여 주는 섭동의 폭으로 읽는다. 그래서 칸 4 의 위치와 요약 방식은 그대로 둔다.
   - *재시도 성공률이 나빠지지 않는다* — 같은 수준이다. 문서를 줄인 시도의 반려 뒤 근거 있음은 16K 3/9 → 2/7(작은 수에서 한 건 차이) · 12K 4/13 → 4/13 이다. 재시도와 LLM 호출의 합은 두 창 모두 줄었다.
2. **E 를 넣지 않는다.** 문서를 줄인 채 나온 반려 뒤의 재시도는 약 3분의 1 이 근거 있음으로 끝났다. 문서를 줄이지 않은 반려(16K 5건 중 1건)보다 낮지 않다(§3.5). E 를 넣으면 그 3분의 1 을 잃고, 아끼는 것은 LLM 호출 몇 번이다. 이 측정에서 비용을 실제로 키운 것은 E 가 다루는 경우가 아니라 D 의 왕복이었다.
3. **D 의 "모름" 기본값을 PLAN 문구와 반대로 바꿨다.** 검증이 쓴 문서를 보고하지 않으면 직전에 실린 문서 전부를 "쓴 것"과 같이 지킨다(§3.3). 교체 가드 ①("빈 보고는 모름")과 같은 규약이다. 쓴 문서가 보고된 재시도의 순서는 PLAN 그대로다.
4. **50% 와 500자는 상수로 둔다.** 이 측정은 값을 바꿀 근거를 내지 않았다.
   - 바닥(15 → 8)은 12K 긴 질문에서 늘 들어가지 못했고, 16K 에서는 늘 넉넉히 넘었다. 어느 쪽도 바닥 값 자체를 시험하지 않는다.
   - 칸 1 이 자른 과거 질문은 없었다. 앞 턴의 질문이 전부 짧은 골든·후속 질문이었다.

## 5. 알아 둘 것

- **같은 프롬프트도 다른 답을 낸다.** 서버의 프롬프트 캐시 상태(앞 요청과 겹치는 접두)에 따라 그렇다. 한 실행 안에서 앞 사례의 재시도가 달라지면 뒤 사례의 첫 시도도 흔들린다(§3.2 의 ① · §3.4 의 batch-05·arch-03). 두 코드를 비교할 때는 먼저 첫 시도의 `[BUDGET]` 이 같은지 본다. 같으면 첫 시도의 판정 차이는 섭동으로 뺀다.
- **keyHit 은 "문서에 없다"는 답에서도 맞는다.** 마커가 나열 속에 우연히 들어간다(§3.4). 사례 단위로 읽을 때는 답을 열어 본다.
- **12K 에서는 판정 없음이 절반 가까이다.** 검증 발췌가 15개 중 9~12개만 실려 `unreliableNegative()` 가 근거 없음 판정을 버린다. 좁은 창에서는 근거 있음 열이 약하고, 재시도·LLM 호출이 더 믿을 만한 비교축이다.
- **② 세트는 이력 칸을 시험하지 못한다.** 직전 RAG 턴의 이력은 `## 요약`(약 200자)뿐이라 칸 1·2·4·5 가 할 일이 없다. ② 의 차이는 문서 칸(3)과 재시도에서만 온다.
- **조기 종료 로그의 청크 수는 측정 당시 검색 결과 수였다.** f3-03 의 "same 16 chunk(s)" 가 그 예로, 실제 비교는 실린 12개로 했다. 지금은 비교한 집합의 크기를 찍는다(`AgentState.seenDocCount()`).

## 6. 한계와 후속

- **서버의 컨텍스트 초과는 재지 않았다.** 창을 선언으로 흉내 냈고 서버는 32K 라 `[SHRINK]` 가 0회다. 축소 재시도가 사다리를 한 걸음씩 내려가는 것은 단위 테스트(`AnswerServiceLadderTest`)로만 확인했다. 실제로 좁게 띄운 서버(`-c 16384`)로 한 번 재 볼 만하다.
- **표본이 작다.** 사례는 43개, 절당 8~14개다. ① 의 기준선이 보여 주듯 한두 건의 뒤집힘은 섭동의 폭 안이고, 방향은 합으로 읽었다.
- **칸 1(과거 질문 500자)과 칸 4 의 세부 손실은 시험하지 못했다.** 앞 턴의 질문이 전부 짧았고, ③ 의 질문은 답이 직전 답변이 아니라 문서에 있다. 시험하려면 사례 둘이 필요하다 — "2턴 전에 붙인 로그를 다시 묻는" 사례와 "직전 Direct 답의 두 번째 방법을 더 자세히" 사례.
- **청크가 계획서 예의 3분의 1 크기다**(평균 470토큰). 1,500토큰 청크의 코퍼스라면 16K 에서도 이 측정의 12K 만큼 압박이 걸린다(§2.4).
- **8K 는 재지 않았다** — 지원하는 최소 창(16K)보다 작다.
- **후보: 바닥 아래에서 같은 집합으로 반려되면 하위 문서로 한 번 갈아탄다.** 설계대로의 왕복이 우연히 한 일이다. 이 측정에서 그 왕복은 3번 이기고 2번 졌고(§3.4), 대신 12K 긴 질문에 LLM 호출이 20번 더 들었다. 판정으로는 비기므로 넣지 않는다. 더 큰 세트에서 이기면 재시도 정책(E 와 같은 자리)에서 다시 본다.
- **64K 를 더한 측정은 §6.31 이 같은 하네스로 한다**(PLAN §6.31 완료 기준).

## 7. 재현 방법

하네스는 `src/test/java/com/example/ragagent/evaluation/PromptLadderEvaluationTest.java`(기본 skip), 요약은 `scripts/ladder_eval_summary.py` 다. **쓰는 하네스**(설정 오버라이드·대화 턴이 DB 에 남는다)라 스크래치 DB 가 필수다(`-Dladder-eval.data-dir` 없이는 시작하지 않는다). 생성 서버 하나를 직렬로 써서 실행 하나(43사례)가 약 1시간이다.

```bash
# 스크래치 DB 셋 — 개발 DB 의 백업에서 설정 오버라이드를 비운다(.env + 출하 기본값)
for d in prep old new; do
  mkdir -p target/ladder-eval-data/$d
  python -c "import sqlite3,sys; s=sqlite3.connect('data/memory.db'); t=sqlite3.connect(sys.argv[1]); s.backup(t); t.execute('DELETE FROM settings_override'); t.commit()" target/ladder-eval-data/$d/memory.db
done

# 사다리 직전 코드 — worktree 에 .env · vec0 확장(추적되지 않는다) · 하네스를 복사한다
git worktree add --detach ../RAG-Agent-ladder-old 9298a00
cp .env ../RAG-Agent-ladder-old/ && cp -r lib ../RAG-Agent-ladder-old/
cp src/test/java/com/example/ragagent/evaluation/PromptLadderEvaluationTest.java \
   ../RAG-Agent-ladder-old/src/test/java/com/example/ragagent/evaluation/

# 1) 앞 턴 fixture — 한 번만(창 선언 없음). 답변이 빈 항목만 다시 만든다
mvn -o test -Dtest=PromptLadderEvaluationTest -Dladder-eval.enabled=true -Dsurefire.failIfNoSpecifiedTests=false \
    -Dladder-eval.data-dir=target/ladder-eval-data/prep -Dladder-eval.sections=prepare

# 2) 측정 — 같은 fixture 로 두 코드에서, 창마다(직렬로). old 는 worktree 에서, new 는 여기서
COMMON="-Dtest=PromptLadderEvaluationTest -Dladder-eval.enabled=true -Dsurefire.failIfNoSpecifiedTests=false \
  -Dladder-eval.top-k=15 -Dladder-eval.out=$PWD/target/ladder-eval -Dladder-eval.priors=$PWD/target/ladder-eval/priors.json"
mkdir -p target/ladder-eval/logs
(cd ../RAG-Agent-ladder-old && mvn -o test $COMMON -Dladder-eval.data-dir=$OLDPWD/target/ladder-eval-data/old \
    -Dladder-eval.label=old-k15-16k -Dladder-eval.window=16384) > target/ladder-eval/logs/old-k15-16k.log 2>&1
mvn -o test $COMMON -Dladder-eval.data-dir=target/ladder-eval-data/new \
    -Dladder-eval.label=new-k15-16k -Dladder-eval.window=16384 > target/ladder-eval/logs/new-k15-16k.log 2>&1
# … 12K 는 -Dladder-eval.window=12288, 라벨 old-k15-12k / new-k15-12k. 고친 코드(§3.4)는 라벨 fix-k15-16k / fix-k15-12k

python scripts/ladder_eval_summary.py target/ladder-eval old-k15-16k new-k15-16k --logs target/ladder-eval/logs
```

- 옵션: `-Dladder-eval.sections=long,fu1,fu2,fu3`(기본) · `-Dladder-eval.stride=2`(long 절의 골든셋 간격) · `-Dladder-eval.window=0`(선언 안 함 = 서버 창) · `-Dladder-eval.out` · `-Dladder-eval.priors`.
- 같은 사례를 다시 돌리면 JSONL 에 줄이 더 붙고 요약은 마지막 것을 쓴다. 새로 잴 때는 `target/ladder-eval/<label>/` 을 지운다.
- **측정 중에는 두 저장소 어디에서도 Maven 을 돌리거나 `src/` 를 고치지 않는다** — 다음 실행이 그 저장소에서 `mvn test` 를 다시 컴파일한다. 로그는 `target/` 안에 둔다.
- 측정이 끝나면 worktree 를 지운다(`git worktree remove --force ../RAG-Agent-ladder-old`).
