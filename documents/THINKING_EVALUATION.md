### 2.2 방법

- **같은 입력을 끔/낮게로 번갈아 부른다**(`ThinkingLevelEvaluationTest`). 사례마다 순서를 돌려 앞선 호출이 남기는 캐시·열 효과가 한쪽으로 쏠리지 않게 했다. 답변·검증·답변 뒤 보강은 같은 검색 결과를 한 번 고정(쿼리 확장 끔)해 두 수준이 같은 문서를 본다.
- **재는 것**: 지연(서비스 호출 전체의 벽시계 — 스트리밍 답변은 `answer` 노드 진입부터) · 출력 토큰(서버가 센 `completion_tokens`, `ThinkingObservations` 표본) · 생각 토큰(낮게의 출력 − 끔의 출력, 스트리밍은 생각 델타 수) · 첫 글자(첫 답 토큰까지) · 잘림(`finish_reason=length`) · 결과의 품질.
- **품질은 절마다 다르게 쟀다** — 검증: 정답을 아는 세 종류의 짝(§3.1) · 답변: 골드 마커 `keyHit` 와 **쌍을 직접 읽기** · 분류: 끔과 낮게의 유형 일치 · 독립화: 재작성 여부 · 검색: recall@10·ndcg@10 · 키워드: 본문에 실린 비율 · MD 교정: 산출물 diff.
- **캐시 때문에 첫 글자의 절대값은 흔들린다.** llama.cpp 슬롯이 앞 요청의 프롬프트 접두를 재사용해, 같은 사례의 두 번째 호출은 prefill(약 8~10초)이 사라질 때가 있다(끔의 첫 글자가 0.2~1초로 찍힌 사례). 그래서 첫 글자는 **쌍의 차이**로 읽는다.
- **사례 수**: 분류 34 · 독립화 10 · 확장 26 · 리랭크 13 · 답변 N 13 · S 10 · C 4 · 검증 13쌍 × 3종 · 답변 뒤 12 · 제목 12 · 큐레이션 제안 12 · Direct 8 · Direct S 6 · 메타 6 · 키워드 청크 10 · MD 1 · TXT 1. 서버 하나를 직렬로 써서 약 5시간이 들었다.
- **샘플링 온도**: 운영자 DB 의 값(Direct 0.85 등)으로 쟀고, Direct 는 출하 온도 0.1 로 다시 쟀다(§3.2.4) — 결론이 같았다. (0.1 은 측정 당시의 출하 온도다. 이후 출하값이 일반/RAG 0.0 → 0.2, Direct 0.1 → 0.5 로 바뀌었다 — 두 온도에서 결론이 같았으므로 그 사이의 값에서 뒤집힐 이유는 보이지 않으나 0.5 로는 재지 않았다.)

## 5. 알아 둘 것

1. **출하값의 근거가 바뀌었다.** 2단계는 "참조 배포(서버 기본이 켬)에서 지금과 같은 전송"을 지켜 아무것도 보내지 않던 자리를 `낮게` 로 뒀다. 측정 서버는 `--reasoning off` 라서 그 값은 이 서버의 거의 모든 호출을 되살아난 생각의 대가를 치르게 하고 있었다. 이제는 이득이 확인된 곳만 켠다.
2. **독립화는 생각이 켜지면 원문을 그대로 돌려주는 일이 는다**(§3.3). 오류는 아니다 — `QuestionCondenser` 가 그 경우 원문으로 검색한다 — 하지만 후속 질문의 검색이 독립화 이득을 못 받는다.
3. **낮게 여유 512 는 기본 예약이 작은 호출에서 빠듯했다**(§4.2).
4. **답변 뒤 보강은 낮게면 칩이 안 뜬다**(§3.4). `/settings` 카드의 "⚠ 타임아웃 넘음" 은 읽기 타임아웃(기본 600초)만 보므로 호출 지점마다 다른 실제 한도(이 경우 화면의 20~25초)를 미리 알려 주지 못한다(PLAN 열린 항목 (h)).
5. **쿼리 확장은 이 코퍼스에서 recall 을 올리지 못한다**(§3.3). 이 절의 범위 밖이라 기능은 그대로 둔다.
6. **블로킹 관측의 자동 판정은 긴 출력에서 생각을 놓친다.** 규칙이 "생각이 답보다 클 때만"(`ThinkingObservations.MIN_EXCESS_TOKENS`)이라 의도된 보수성이다 — MD 교정 낮게는 출력이 28% 늘었는데 `thinkSeen` 이 0이다. **`thinkSeen=0` 이 "생각 안 함"은 아니다.** 긴 출력의 절은 두 수준의 출력 토큰 차이로 읽었다.
7. **요청 단위 생각 토큰 예산을 이 서버가 받는다**(llama.cpp b11433). 같은 프롬프트(사과 17개×23상자 계산)로 확인했다:

   | `reasoning_budget_tokens: 64` | **155** | 294자 | 답 125자 그대로, `finish=stop` |
   | `thinking_budget_tokens: 64` | **155** | 294자 | 별칭 |
   | `reasoning_budget: 64` | 506 | 1,287자 | **무시** |
   | `max_tokens: 150` | 150 | 543자 | 생각 한가운데서 잘려 **답 없음**, `finish=length` |
   | `reasoning_effort: low` / `high` | 522 / 525 | 1,283 / 1,294자 | **무시** — 켬/끔만 받는다 |

   2026-10-02 의 소스 확인은 요청 본문에서 읽는 것이 `reasoning_budget_message` 뿐이라고 했다 — 서버가 b10236 → b11433 으로 올라가며 달라졌거나 그때 확인이 틀렸다. 구현 여부는 사용자 결정이다(PLAN 열린 항목 (a)).
8. **`keyHit`(마커 부분 문자열)은 거짓 부정이 난다**(§3.2.1). 답변 품질은 쌍을 직접 읽어 비교했다.
9. **서버의 생각 동작(관측)**: 생각은 `reasoning_content` 로 오고, 블로킹에서는 Spring AI 1.1.8 이 버린다. 생각이 `max_tokens` 안에서 끝나지 않으면 `content` 가 비고 `finish=length` 다. gemma-4-E2B 는 쉬운 입력에도 영어로 300~500토큰을 먼저 생각한다.

## 6. 한계와 후속

- **모델 하나(gemma-4-E2B)·서버 하나·코퍼스 하나의 결과다.** 더 큰 모델은 생각의 몫이 다를 수 있다 — 모델을 바꾸거나 원격 추론 모델을 붙이면 같은 방식으로 다시 잰다(PLAN 열린 항목 (g)).
- **표본이 작다**(검증 13쌍 · 응용 4건 · 리랭크 13건). 이득의 크기보다 **방향**을 본 것이고, 검증의 6% → 44% 는 18건 중 1건 → 8건이다.
- **측정하지 못한 넷**(`SUMMARY` — 소형 모델 계층 MICRO_TEXT offload 가 없으면 LLM 을 부르지 않는다, 이미지 셋 — 비전 모델이 없다)은 옛 값(낮게)을 그대로 뒀다(PLAN 열린 항목 (f)).
- **답변 품질은 마커와 사례별 읽기로 비교했다.** 합성형(여러 청크를 엮는) 질문에서 낮게가 더 나은지는 표본이 모자라 모른다 — batch-05 한 건에서만 낮게가 더 완전했다.
- **생각 토큰 예산 실험(7단계 후보)**: 예산을 줄여도 검증의 탐지율(44%)이 유지되는지를 `evalacc` 로 예산 256 · 512 · 1,024 에서 먼저 재 본다. 유지되면 검증 비용(45~60초)을 크게 줄이면서 낮게/중간/높게가 이 서버에서 처음으로 서로 다른 값이 된다.

## 7. 재현 방법

하네스는 `src/test/java/com/example/ragagent/evaluation/ThinkingLevelEvaluationTest.java`(기본 skip), 요약은 `scripts/thinking_eval_summary.py` 다. **쓰는 하네스**(설정 오버라이드·대화 턴·제목이 DB 에 남는다)라 `data/` 의 **스크래치 복사본이 필수**다(없으면 시작하지 않는다).

```bash
# 스크래치 DB — memory.db 한 파일이면 된다(설정 오버라이드가 같이 따라온다)
mkdir -p target/thinking-eval-data && cp data/memory.db target/thinking-eval-data/

# 절을 직렬로 돌린다(서버 하나 — 병렬이면 지연이 서로를 밀어 흐려진다)
mvn -o test -Dtest=ThinkingLevelEvaluationTest -Dthinking-eval.enabled=true \
    -Dthinking-eval.data-dir=target/thinking-eval-data \
    -Dthinking-eval.sections=classify,condense,retrieval,title,direct,keyword,md,txt     # ≈ 60분
mvn -o test ... -Dthinking-eval.stride=2 -Dthinking-eval.sections=answer,evalacc,post,curated   # ≈ 70분
mvn -o test ... -Dthinking-eval.sections=answerS,answerC,directS                          # ≈ 40분
mvn -o test ... -Dthinking-eval.rerank=true -Dthinking-eval.sections=rerank               # 리랭커가 켜진 컨텍스트에서만

python scripts/thinking_eval_summary.py target/thinking-eval
```

- 옵션: `-Dthinking-eval.n=26`(사례 수 상한) · `-Dthinking-eval.stride=2`(0·2·4… 번째만 — 사례 하나가 1~3분인 절용) · `-Dthinking-eval.answer-combos=3`(검증만 켠 짝을 더함) · `-Dthinking-eval.out=target/thinking-eval`.
- **출하 온도로 재려면** 스크래치 DB 의 `settings_override` 에서 `llm.temperature`·`llm.direct-temperature`·`llm.creative-temperature` 행을 지운다 — 샘플링 온도가 형식 준수(Direct 의 `## 요약`)를 바꾼다.
- **측정 중에는 Maven 을 돌리거나 `src/` 를 고치지 않는다**(재컴파일이 `target/classes` 를 살아 있는 JVM 아래에서 바꾸고 CPU 가 지연을 흔든다). 로그는 임시 폴더가 아니라 `target/` 안에 둔다 — 임시 폴더는 디스크가 찰 때 비워질 수 있다.
- 새 모델·서버에서는 이 표를 다시 만들고 PLAN §6.29 ② 의 출하값과 §4.2 의 상수를 확인한다. 결과를 바꾸는 값이 나오면 `ThinkingSite`·`application.properties`·`ThinkingBudgetTest`/`ThinkingPreviewServiceTest` 골든을 함께 고친다.
