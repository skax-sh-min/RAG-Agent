## 1. 개요

문서를 업로드하면 내용을 이해하고 질문에 답변하는 RAG(Retrieval-Augmented Generation) 서비스입니다.  
**Web UI**(`http://localhost:8080`)와 **REST API** 두 가지 방식으로 사용할 수 있습니다.

**주요 기능**:

| 기능 | 설명 |
|------|------|
| 질문 유형 분류 | concept / usage / error / version / meta 5종 자동 분류 |
| 멀티 쿼리 검색 | 원본 질문 + LLM 생성 변형 쿼리 2개(총 3개) 병렬 검색 후 중복 제거 |
| ReAct 재검색 | 증거 부족 시 자동 재검색 (최대 2회) |
| Critic 검증 | 답변이 문서에 근거하는지 이중 검증 |
| SSE 실시간 스트리밍 | 처리 단계 배지 + 토큰 실시간 출력. 전송 버튼이 스트리밍 중 **중지** 버튼으로 전환되어 즉시 중단 가능 |
| 업로드 취소 | 문서 업로드·인덱싱 진행 중 언제든 파일별로 취소 가능 |
| 멀티턴 대화 | 스레드 단위 대화 이력 유지 (재시작 후에도 유지) |
| 문서 버전 관리 | 버전별 독립된 검색 컬렉션 |
| 이미지 처리 | PDF·PPTX·DOCX 이미지 추출(PPTX는 SmartArt·차트 미리보기·첨부 파일 미리보기 포함) → 답변에 썸네일 표시; 스캔 PDF OCR 지원 |
| 다크 모드 | 시스템 설정 자동 감지 + 사용자 override |
| 출처 hover 미리보기 | 출처 항목에 마우스를 올리면 관련 문서 청크 500자 미리보기 |
| 메시지 메타데이터 영속화 | 발송·수신 시간, 프로바이더, 토큰 수, LLM 호출 횟수를 DB에 저장 — 페이지 새로고침 후에도 유지 |
| DOCX 자동 포맷 교정 | DOCX → MD 변환 후 LLM이 섹션별 포맷(소제목·잘린 문장·오타)을 자동 교정 → 교정본으로 인덱싱 |
| 소제목 번호 매기기 | 업로드 시 "소제목 숫자 생성" 체크박스로 헤딩에 계층적 번호 부여(예: `1.1`, `1.2`) — **PPTX는 적용되지 않음**. 재인덱싱 시 번호가 어긋나 있으면 자동으로 다시 계산 |
| 출처 챕터 번호 | 답변 출처(Sources)가 문서 구조(H2~H6 헤딩)에 따라 `p.12` 대신 `1.5.3` 같은 챕터 번호로 표시됨 — **위 체크박스와 무관하게 항상 자동 계산**(헤딩에 보이는 번호를 매기지 않아도 출처에는 챕터 번호가 붙음). 헤딩이 없는 구간과 PPTX·PDF는 페이지/슬라이드 번호로 표시 |
| 벡터 스토어 관리 | ChromaDB 컬렉션·청크 조회·편집·삭제 + 저장된 MD 파일 기반 재인덱싱 UI (`/admin`) |
| 좋아요 기반 큐레이션 Q&A | 답변에 좋아요를 누르면 별도로 임베딩되어 이후 비슷한 질문의 검색 결과에 반영됨. 본인은 채팅창에서, 관리자는 `/admin`에서 언제든 수정·취소 가능 |
| 인증 모드 | `app.auth.enabled=true`(기본): Spring Security 폼 로그인; `false`: guest/admin 자동 로그인 (로컬 전용) |

**인증 모드 요약**:

| 모드 | 설정 | 접근 방식 |
|------|------|-----------|
| **인증 활성화** (기본) | `app.auth.enabled=true` | `/login`으로 로그인; `/signup`으로 계정 생성 |
| **인증 비활성화** | `app.auth.enabled=false` | 로그인 불필요; 첫 실행 시 `/setup`에서 관리자 계정 생성 후 자동 로그인 |
| **관리 전용 인증** | `app.auth.enabled=false`<br>`app.auth.management-only=true` | 채팅·문서 조회는 로그인 불필요; 문서 업로드·삭제와 `/admin`만 로그인 필요 |

> 인증 모드 변경은 운영자 권한이 필요합니다. [OPERATOR_MANUAL.md §9.4](OPERATOR_MANUAL.md#94-인증-토글-no-auth-모드)를 참고하세요.

> 시스템 설치·배포·LLM 설정은 [OPERATOR_MANUAL.md](OPERATOR_MANUAL.md)를 참고하세요.

## 2. Web UI 사용법

### 2.0 로그인 및 계정

#### 인증 활성화 모드 (`app.auth.enabled=true`, 기본값)

서비스에 접속하면 `/login` 페이지로 리디렉션됩니다.

| 동작 | 경로 | 설명 |
|------|------|------|
| 로그인 | `/login` | 이메일 + 비밀번호 입력 |
| 계정 생성 | `/signup` | 이메일·표시 이름·비밀번호 입력 |
| 로그아웃 | Navbar **Logout** 버튼 | 세션 종료 |

> 5회 연속 로그인 실패 시 15분간 계정이 잠깁니다.

#### 인증 비활성화 모드 (`app.auth.enabled=false`)

로그인 없이 바로 사용할 수 있습니다. 모든 일반 접속은 **게스트(Guest)** 신원으로 자동 처리됩니다.

**첫 실행 시**: DB에 관리자 계정이 없으면 자동으로 `/setup` 페이지로 이동합니다.  
표시 이름·이메일·비밀번호를 입력하고 **관리자 계정 생성** 버튼을 클릭하면 설정이 완료됩니다.  
이후 `/admin` 경로는 이 관리자 계정으로 자동 로그인됩니다.

#### 관리 전용 인증 모드 (`app.auth.enabled=false`, `app.auth.management-only=true`)

채팅과 문서 조회는 로그인 없이 바로 사용할 수 있습니다. 다만 **문서 업로드·삭제와 벡터 스토어 관리(`/admin`)는 로그인이 필요**하며, 게스트 화면에는 해당 버튼·메뉴 자체가 보이지 않습니다.

**첫 실행 시**: DB에 관리자 계정이 없으면 자동으로 `/setup` 페이지로 이동합니다.  
표시 이름·이메일·비밀번호를 입력하고 **관리자 계정 생성** 버튼을 클릭하면 설정이 완료됩니다.  
**이 모드는 `/setup` 완료 후 자동 로그인되지 않습니다** — Navbar의 **Login** 링크에서 방금 만든 계정으로 로그인하세요.

로그인하면 Navbar에 관리자 메뉴와 문서 업로드/삭제 버튼이 나타나고, 다른 페이지로 이동해도 로그인 상태가 유지됩니다.

> 어떤 인증 모드로 배포됐는지는 운영자에게 문의하세요. 세부 동작은 [OPERATOR_MANUAL.md §9.4.2](OPERATOR_MANUAL.md#942-관리-전용-인증-management-only)를 참고하세요.

### 2.1 언어 전환

Navbar 우측 상단 **KO | EN** 링크를 클릭하면 즉시 언어가 전환됩니다.  
선택한 언어는 브라우저 쿠키(`lang`)에 저장되어 재방문 시에도 유지됩니다.

### 2.2 채팅

1. **`http://localhost:8080`** 접속 (새 스레드 자동 생성)
2. 이전 대화를 이어하려면 사이드바에서 해당 스레드 클릭
3. 좌측 상단 **version** 입력창에 검색할 문서 버전 입력 (기본: `latest`)
4. 하단 입력창에 질문 입력 후 **Enter** (줄바꿈: **Shift+Enter**)

**답변 실시간 표시**:
- 상단 배지에서 현재 처리 단계 확인 (질문 분류 → 문서 검색 → 답변 생성 → 검증)
- 토큰이 생성되는 즉시 화면에 출력
- 답변 아래 출처(Sources) — 마우스를 올리면 관련 문서 청크 미리보기 팝오버 표시(PC 화면에서는 더 넓게 표시되어 읽기 편함)
- 검색된 이미지가 있으면 썸네일 그리드로 표시 (클릭 시 원본 확인)
- 소요 시간·토큰 수·사용 LLM·호출 횟수 메타정보 확인 가능 (재방문 시에도 유지)

**답변 중지**: 스트리밍 중에는 전송 버튼이 빨간 **중지** 버튼으로 바뀝니다. 잘못 보낸 질문이나 답변이 너무 길어질 때 클릭하면 즉시 중단되고, 그때까지 생성된 부분 답변은 그대로 남은 채 "사용자가 중단함" 표시가 붙습니다.

**메시지 메타데이터**:

| 표시 위치 | 정보 |
|----------|------|
| 사용자 버블 하단 | 발송 시각 (HH:MM) |
| 어시스턴트 버블 하단 | 수신 시각 · 🤖 사용 프로바이더 · ⏱ 소요 시간 · 📥📤 입/출력 토큰 · 🔄 LLM 호출 횟수 |

> 모든 메타데이터는 DB에 저장되어 스레드를 다시 열어도 복원됩니다.

**좋아요 & 큐레이션 답변 편집**:

마음에 드는 답변에 👍(좋아요)를 누르면, 그 질문·답변이 별도로 저장·임베딩되어 **이후 비슷한 질문을 검색할 때 근거로 함께 활용**됩니다(반복 질문·FAQ성 질문의 정확도 향상 목적). 좋아요는 몇 초 안에 취소하면 저장이 아예 진행되지 않으니 실수로 누른 경우 바로 다시 누르면 됩니다.

| 동작 | 방법 |
|------|------|
| 좋아요 | 답변 하단 👍 클릭 (다시 누르면 취소) |
| 답변 내용 수정 | 좋아요 상태일 때만 나타나는 연필(✏) 아이콘 클릭 → 오른쪽 패널에서 텍스트 수정 후 저장 |

- 수정하면 검색용 데이터도 자동으로 다시 계산됩니다 — 별도 재저장 절차가 없습니다.
- 좋아요를 취소하면 해당 답변은 검색 반영에서 즉시 제외됩니다.
- 본인이 좋아요한 답변만 이 방법으로 수정할 수 있습니다(다른 사용자의 대화는 애초에 보이지 않습니다). 전체 사용자의 큐레이션 답변을 관리하는 기능은 [§2.5](#25-벡터-스토어-관리) 관리자 화면에 별도로 있습니다.
- 대화(스레드) 자체를 삭제해도 이미 좋아요로 등록된 답변은 검색에 계속 반영됩니다 — 완전히 제외하려면 삭제 전에 좋아요를 먼저 취소하세요.

**스레드 관리**:

| 동작 | 방법 |
|------|------|
| 새 대화 시작 | 사이드바 **New Chat** 버튼 |
| 이전 대화 재개 | 사이드바에서 스레드 클릭 → 이전 메시지 버블 복원 |
| 대화 제목 변경 | 스레드 옆 연필 아이콘 클릭 → 인라인 편집 |
| 대화 삭제 | 스레드 옆 휴지통 아이콘 |

> **라우팅 모드** (채팅 화면 드롭다운): `COST_FIRST` · `QUALITY_FIRST` · `PROGRESSIVE` · `DUAL` · `LOCAL_ONLY`  
> 각 모드의 동작 방식은 [OPERATOR_MANUAL.md §5.3](OPERATOR_MANUAL.md)을 참고하세요.  
> 이 드롭다운이 아예 보이지 않는다면 운영자가 이 서비스를 로컬 LLM 전용으로 구성한 것입니다(어떤 모드를 골라도 결과가 같아 선택지 자체를 제공하지 않음) — 정상 동작입니다.

> **메시지 복원 제한**: 이전 turn의 토큰 수·출처 메타데이터는 DB에 저장되지 않으므로 새 turn에서만 표시됩니다.

### 2.3 문서 관리

`/documents` 접속 후:

| 기능 | 방법 |
|------|------|
| **업로드** | 드래그 앤 드롭 또는 영역 클릭 → 파일 선택 → Version 입력 → **Upload & Index** |
| **업로드 취소** | 진행 중인 파일 행의 **Cancel** 버튼 (업로드/인덱싱 중 언제든) |
| **목록 새로고침** | **Refresh** 버튼 |
| **문서 삭제** | 행 우측 **Delete** 버튼 |

**지원 형식**: PDF, PPTX, DOCX, TXT, MD / 최대 200 MB

> 관리 전용 인증 모드([§1](#1-개요) 참고)에서는 업로드 카드와 삭제 버튼이 관리자로 로그인했을 때만 보입니다. 게스트 화면에는 문서 목록 조회만 표시됩니다.

업로드 시 참고 사항:
- 같은 파일을 다시 올리면 SHA-256 기반 변경 감지로 변경된 경우에만 재인덱싱
- 파일 내용이 확장자와 일치하지 않으면 업로드가 거부됩니다 (예: .txt로 이름 바꾼 실행파일)
- 이미지 포함 문서(PDF·PPTX·DOCX)는 이미지도 함께 추출 (운영자 설정 필요)
- 스캔 PDF는 OCR로 텍스트 추출 (운영자 설정 필요)
- 소제목에 번호를 매기고 싶다면 업로드 시 **소제목 숫자 생성** 체크박스를 켜세요 — PPTX는 슬라이드 제목이 문서 목차 구조가 아니라서 이 옵션이 적용되지 않습니다
- 대용량 파일 업로드를 잘못 시작했다면 **Cancel**로 즉시 중단할 수 있습니다. 취소 시점까지 이미 완료된 파일은 그대로 인덱싱되어 남고, 진행 중이던 파일만 취소됩니다
- 업로드/인덱싱 도중 오류가 나면 실패한 파일 행에 오류가 발생한 단계(문서 로드·구조화·이미지 분석·교정·청크 분할·키워드 추출·벡터 DB 저장)와 메시지가 표시됩니다. **로그 보기**를 클릭하면 해당 파일의 진행 이력을 확인할 수 있습니다 (다른 페이지로 이동하면 사라짐)
- "이미지 설명 추가"를 체크한 경우, 문서에 포함된 이미지를 LLM(Vision)이 분석하는 동안 파일 행에 **"이미지 분석 중 (N/M)"**로 진행 상황이 실시간 표시됩니다 — 이미지가 많은 PPTX·PDF 등에서 이 단계가 오래 걸릴 수 있습니다
- `data/documents/` 폴더를 직접 스캔해 신규·변경·삭제 파일을 일괄 반영하는 폴더 동기화는 REST API로만 제공됩니다 → [§3.3 증분 동기화](#33-증분-동기화)

### 2.4 LLM 사용량 통계

`/llm-usage` 접속 후:

| 영역 | 설명 |
|------|------|
| **프로바이더 카드** | 설정된 LLM 프로바이더별 상태 — 정상(초록) / 차단 중(빨강 + 남은 시간 카운트다운) |
| **임베딩 카드** | 문서 인덱싱·검색 시 사용되는 임베딩 모델의 토큰 사용량을 `EMBEDDING` 배지가 붙은 별도 카드로 표시 — 채팅 프로바이더와 분리 집계되며 항상 "정상" 상태 |
| **Orphan 카드** | 설정에서 완전히 제거된 프로바이더(또는 옛 임베딩 모델)의 과거 사용 기록을 회색 `ORPHAN` 배지 카드로 표시 — 관리자만 카드의 🗑 아이콘으로 삭제할 수 있습니다 |
| **일별 차트** | 누적 막대 차트 — 7일 / 30일 / 90일 기간 선택, 프로바이더별 색상 구분 (임베딩은 별도 막대로 구분 표시) |
| **기간별 테이블** | 오늘 / 이번 주 / 이번 달 탭 — 프로바이더별 입력/출력/합계 토큰 및 호출 수 |

카드 영역은 30초마다 자동 갱신됩니다.

> 키가 설정되지 않았고 한 번도 사용된 적 없는 프로바이더는 카드·차트·테이블 어디에도 표시되지 않습니다. 과거에 사용한 적 있는 프로바이더는 이후 키가 제거되어도 이력 확인을 위해 계속 표시됩니다 — 설정에서 완전히 제거되면 ORPHAN 카드로 전환됩니다.

### 2.5 벡터 스토어 관리

`/admin` 접속 후 벡터 스토어에 저장된 청크를 직접 조회·편집·삭제할 수 있습니다. 상단에는 **Vector Store 상태 카드**(백엔드 종류·정상 여부·문서/청크 수)가 표시됩니다.

> 관리 전용 인증 모드([§1](#1-개요) 참고)에서는 `/admin`이 로그인을 요구하며 Navbar에도 관리자로 로그인했을 때만 메뉴가 나타납니다.

> **벡터 스토어 백엔드**: 청크 브라우징/편집은 **ChromaDB·sqlite-vec 두 백엔드 모두** 지원됩니다. 레이아웃·기능은 동일하고 표시 지표·라벨만 백엔드에 맞게 바뀝니다(chroma=컬렉션 / sqlite-vec=버전, `vec_version`·차원 등). 자세한 차이는 [OPERATOR_MANUAL.md §7.4](OPERATOR_MANUAL.md) 참고.

**왼쪽 패널 — 컬렉션(chroma) / 버전(sqlite-vec) 목록**:
- 백엔드별 컬렉션(또는 버전)과 청크 수 표시
- 클릭 시 오른쪽 패널에 해당 청크 목록 로드

**오른쪽 패널 — 청크 테이블**:

표에는 ID·텍스트 미리보기·크기·파일명·페이지/슬라이드·**챕터**·키워드가 함께 표시됩니다. 챕터 열은 §4.2의 `chapter_no`(H2~H6 헤딩 기반 계층 번호)를 보여주며, 실제 챕터가 없는 청크(프롤로그·PPTX·PDF)는 빈 칸으로 표시됩니다. 청크는 문서별로 묶여 **문서 내 실제 순서 그대로** 표시됩니다(청크 ID 순서가 아닙니다).

| 기능 | 방법 |
|------|------|
| 문서 필터 | 드롭다운에서 특정 문서(docId) 선택 → 해당 문서 청크만 표시 |
| 페이지당 건수 | 드롭다운에서 20 / 50 / 100건 선택 (기본값: 20건) — 변경하면 첫 페이지부터 다시 조회 |
| 페이지 이동 | [이전 / 다음] 버튼으로 선택한 건수만큼 이동 |
| 청크 편집 | 행의 연필 아이콘 → 오른쪽 오프캔버스에서 텍스트·메타데이터(JSON) 수정 후 저장 |
| 청크 재인덱싱 | 편집 패널의 **이 청크만 재인덱싱** 버튼 → 저장된 텍스트 기준으로 그 청크만 재임베딩 + 키워드 검색(FTS) 인덱스 갱신 |
| 청크 삭제 | 행의 휴지통 아이콘 → 즉시 ChromaDB에서 제거 |

**하단 — 문서 레지스트리**:
- 인덱싱된 전체 문서 목록 표시 (파일명·버전·청크 수·인덱싱 일시)
- **청크 보기** 버튼으로 해당 문서의 청크를 바로 필터링
- **↺ 버튼 (MD 재인덱싱)**: DOCX·TXT·PPTX·PDF(스캔이 아닌 경우) 문서는 서버에 저장된 교정 MD 파일(`{docId}_corrected.md`)을 기준으로 청크를 다시 생성하고 인덱싱합니다. MD 파일을 직접 수정한 뒤 이 버튼을 누르면 재업로드 없이 인덱싱을 갱신할 수 있습니다(스캔 PDF는 MD 파일 자체가 없어 미지원).
  - MD 파일이 가리키는 이미지가 실제로는 존재하지 않으면(수동 정리 등으로 파일이 사라진 경우) 해당 이미지 참조는 재인덱싱 시 자동으로 제거되고 MD 파일에도 반영됩니다.
  - 소제목에 이미 번호가 매겨져 있던 문서라면, 편집으로 헤딩이 늘거나 줄어 번호가 어긋난 경우 재인덱싱 시 자동으로 다시 계산되어 MD 파일에도 반영됩니다(PPTX 제외 — 애초에 번호가 붙지 않습니다).
  - 빈 줄 정리·프롬프트 마커 제거 같은 마크다운 서식 정리도 매번 다시 적용되어 MD 파일에 반영됩니다(LLM 미사용, 즉시 처리). 단, 코드 블록의 언어 태그 보정은 재인덱싱에서 다시 실행되지 않습니다 — MD 파일을 직접 편집한 뒤라면 코드 블록 안의 빈 줄이 의도와 다르게 정리될 수 있는 위험을 피하기 위한 설계입니다.

> **주의**: 청크 텍스트/메타데이터 **저장**만으로는 벡터 임베딩과 키워드(FTS) 인덱스가 갱신되지 않습니다 (원본 벡터 유지) — 편집한 내용은 표시·답변 프롬프트에는 바로 반영되지만, "이 텍스트/키워드로 검색되는지"는 그대로입니다.  
> 편집한 내용을 검색에도 반영하려면 편집 패널의 **이 청크만 재인덱싱** 버튼을 누르세요 — 저장된 텍스트를 기준으로 그 청크만 재임베딩하고, 키워드 검색 인덱스도 함께 갱신합니다. **키워드 재생성** 체크박스를 켜면 현재 키워드를 그대로 두는 대신 LLM으로 키워드·맥락을 새로 뽑습니다(LLM 호출 1회, 문서 전체 ↺ 재인덱싱과 동일한 품질). 문서 전체를 다시 인덱싱하려면 MD 파일 수정 후 ↺ 재인덱싱 버튼을 사용하거나, Documents 페이지에서 문서를 삭제 후 재업로드하세요.

**큐레이션 Q&A 관리** (관리자 전용, §2.2 "좋아요 & 큐레이션 답변 편집" 참고):

`/admin` 페이지 하단 **큐레이션 Q&A** 카드는 기본적으로 접혀 있습니다 — 카드를 클릭해 펼치면 그때 사용자들이 좋아요한 답변을 최신순으로 불러와 확인할 수 있습니다. 확인할 필요가 없다면 그대로 접어 두면 됩니다.

| 기능 | 방법 |
|------|------|
| 페이지당 건수 | 드롭다운에서 20 / 50 / 100건 선택 (기본값: 20건) |
| 페이지 이동 | [이전 / 다음] 버튼으로 선택한 건수만큼 이동 |
| 답변 수정 | 행의 연필 아이콘 → 텍스트 수정 후 저장 (**청크 편집과 달리 저장 시 자동으로 재임베딩됨**) |
| 강제 삭제 | 행의 휴지통 아이콘 → 좋아요를 누른 사용자와 무관하게 즉시 검색에서 제외 |

부적절한 내용이 좋아요를 받아 검색에 반영된 경우, 사용자가 취소하지 않아도 관리자가 여기서 직접 제거할 수 있습니다.

### 3.6 질의응답 (채팅)

```bash
curl -X POST http://localhost:8080/api/v1/chat \
  -H "Content-Type: application/json" \
  -d '{
    "question": "Spring Security에서 JWT 인증을 어떻게 설정하나요?",
    "version": "latest",
    "thread_id": "user-session-001"
  }'
```

**요청 필드**:

| 필드 | 필수 | 기본값 | 설명 |
|------|------|--------|------|
| `question` | ✅ | — | 사용자 질문 (최대 2,000자) |
| `version` | — | `latest` | 검색할 문서 버전 |
| `thread_id` | — | `default` | 멀티턴 대화 식별자 |

**응답**:
```json
{
  "answer": "## 요약\n...",
  "question_type": "usage",
  "sources": [
    {
      "label": "spring-security-guide.pdf | p.12",
      "preview": "Spring Security에서 JWT 인증 필터를 구성하려면...",
      "doc_id": "spring-security-guide.pdf_a1b2c3d4",
      "page_or_slide": 12
    }
  ],
  "total_input_tokens": 1248,
  "total_output_tokens": 512,
  "llm_call_count": 4,
  "elapsed_seconds": 3.2
}
```

> **`sources[].label` 형식**: 청크가 속한 헤딩의 챕터 번호(H2~H6 기준, 예: `1.5.3`)가 있으면 `"파일명 | 1.5.3"`, 없으면(헤딩 이전 구간·PPTX·PDF는 항상 이 경우) `page_or_slide`로 폴백해 위 예시처럼 `"파일명 | p.12"`로 표시됩니다. 문서 버전은 라벨에 포함되지 않습니다 — 필요하면 업로드 시 지정한 `version`을 별도로 관리하세요.

**질문 유형 (`question_type`)**:

| 값 | 설명 |
|----|------|
| `concept` | 개념·이론 설명 |
| `usage` | 사용법·코드 예시 |
| `error` | 오류·트러블슈팅 |
| `version` | 버전·변경사항 |
| `meta` | 인사·잡담 (RAG 미사용, 직접 응답) |

```bash
curl "http://localhost:8080/api/v1/llm/usage/history?days=30"
```

## 4. 문서 인덱싱 동작

```
파일 업로드 or 폴더 동기화 (REST API)
  └─▶ SHA-256 계산 → doc_registry(SQLite, memory.db 공유)와 비교
        ├─ 신규 파일 → 로드 → [DOCX: MD 변환 → LLM 포맷 교정] → 청크 분할 → 키워드+맥락 추출 (LLM) → 벡터 스토어 추가
        ├─ 변경 파일 → 기존 청크 삭제 → 재인덱싱
        └─ 삭제 파일 → 벡터 스토어에서 제거

MD 재인덱싱 (/admin ↺ 버튼)
  └─▶ 저장된 교정 MD 읽기 → 결정적 정리(이미지 마커·소제목 번호·서식, LLM 미사용) → 청크 분할 → 키워드+맥락 추출 (LLM) → 기존 청크 삭제 → 벡터 스토어 추가
```

> **벡터 스토어**: `chroma`(기본) 또는 `sqlite-vec` 중 운영자가 선택한 백엔드로 저장됩니다(둘 다 동일한 사용자 경험).
>
> **DOCX 포맷 교정**: DOCX → Markdown 변환 직후 LLM이 섹션별로 잘린 문장·소제목 불일치·오타를 교정합니다. 원본(`{docId}.md`)과 교정본(`{docId}_corrected.md`) 모두 `data/converted/`에 저장됩니다.
>
> **키워드+맥락 추출**: LLM을 호출해 핵심 키워드 5개(`excerpt_keywords`)와 이 청크가 속한 맥락(`chunk_context` — 문서명·섹션 제목 + 짧은 설명, 검색 전용이며 화면에는 표시되지 않음)을 함께 생성합니다. 기본적으로 청크 여러 개(4개)를 한 번의 LLM 호출로 묶어 처리해 인덱싱 왕복 횟수를 줄입니다(운영자 설정, [PIPELINE.md §6.2](PIPELINE.md#62-단일-파일-인덱싱)).  
> 검색 품질(recall)이 높아지는 대신 인덱싱 시간이 늘어납니다.

### 4.1 형식별 청크 분할 전략

| 형식 | 로드 단위 | 분할 전략 | 이미지 처리 |
|------|----------|----------|------------|
| `.md` | `#` / `##` / `###` 헤더 단위 섹션 | 챕터(헤딩) 단위 — 짧은 챕터는 인접 챕터와 병합, 초과 시 슬라이딩 윈도우 (아래 주석) | URL 이미지 → alt 텍스트 유지, 로컬 이미지 → `[이미지: path]` 마커 |
| `.docx` | Word Heading 기준 섹션 → LLM 포맷 교정 후 MD 헤더 단위 재분할 | 챕터(헤딩) 단위 — 짧은 챕터는 인접 챕터와 병합, 초과 시 슬라이딩 윈도우 (아래 주석) | 인라인 이미지 추출 + EMF/WMF → PNG 변환 (설정 시) |
| `.pptx` | 슬라이드별 `[페이지: N]` 마커(제목이 있으면 `##` 헤딩 추가, 없으면 마커만) → LLM 포맷 교정 후 슬라이드 단위 재분할(1슬라이드=1섹션) | 섹션(슬라이드)이 `CHUNK_SIZE` 초과 시만 슬라이딩 윈도우 — 단, **서로 다른 슬라이드끼리는 병합되지 않음**("청크 1개=슬라이드 1개=정확한 인용" 유지) | 슬라이드 이미지 추출 + 본문에 `[이미지: ...]` 인라인(DOCX와 동일 — `addImageDescriptions` 적용됨) |
| `.pdf`(스캔 아님) | 페이지별 `[페이지: N]` 마커(합성 헤딩 없음) → LLM 포맷 교정 후 페이지 단위 재분할(1페이지=1섹션) | 섹션(페이지)이 `CHUNK_SIZE` 초과 시만 슬라이딩 윈도우 — 단, **서로 다른 페이지끼리는 병합되지 않음** | 임베드 이미지 추출 + 본문에 `[이미지: ...]` 인라인(DOCX와 동일 — `addImageDescriptions` 적용됨) |
| `.pdf`(스캔) | 페이지 1장 = 문서 1개 (텍스트 50% 이상 없으면 Tesseract OCR) | 슬라이딩 윈도우 (`CHUNK_SIZE` / `CHUNK_OVERLAP`, 섹션 병합 없음) | 임베드 이미지 추출; OCR 처리 (설정 시) |
| `.txt` | 전체 파일 = 문서 1개 → LLM 구조화 후 MD 헤더 단위 분할 | 챕터(헤딩) 단위 — 짧은 챕터는 인접 챕터와 병합, 초과 시 슬라이딩 윈도우 (아래 주석) | — |

> **슬라이딩 윈도우**: 청크 경계가 텍스트 중간이면 가장 가까운 줄바꿈(`\n`)으로 경계를 조정합니다.  
> `.docx` 헤딩이 없는 경우 전체 텍스트를 단일 문서로 처리한 뒤 슬라이딩 윈도우를 적용합니다.  
> **PPTX/PDF(스캔 아님)**: `[페이지: N]` 마커 자체가 슬라이드/페이지 단위 섹션 경계라, 제목이 없는 슬라이드/페이지는 합성 헤딩 없이 마커만으로 섹션이 나뉩니다(예전의 `"N번 슬라이드"`/`"N페이지"` 대체 헤딩은 페이지 번호가 이미 `page_or_slide`로 관리되어 본문에 노이즈만 남기므로 제거됨). 이미지만 있는 슬라이드/페이지도 유지됩니다 — 그래야 추출된 이미지가 청크에 붙을 자리가 남습니다. 제목·본문·이미지가 전부 없는 완전히 빈 슬라이드/페이지만 청크 자체가 생성되지 않습니다 — 상세는 [PIPELINE.md §6.3-bis](PIPELINE.md#63-bis-pptxpdf비스캔--md-변환--docx와의-차이점) 참고.

> **챕터 단위 청킹(MD·DOCX·TXT)**: 문서를 헤딩(챕터) 단위로 나눕니다. `MIN_CHUNK_SIZE`보다 짧은 챕터는 바로 다음 챕터와 합쳐지되, 다음이 더 상위(부모) 챕터면 합치지 않고 대신 이전 청크 쪽으로 붙습니다. 또한 하위 챕터(`###` 이상 — `##`보다 더 깊은 레벨) 청크의 맨 앞에는 그 챕터가 속한 바로 위 부모 헤딩 한 줄이 함께 붙어, 청크만 봐도 어느 챕터의 내용인지 알 수 있습니다(최상위 `##` 챕터에는 붙지 않음). 검색 정확도를 위한 동작이며 답변·출처 표시 방식에는 영향을 주지 않습니다. PPTX·PDF는 이 병합 대신 슬라이드/페이지 단위를 그대로 지킵니다.

> **PPTX 중복·목차·구분 슬라이드 자동 제거**(기본 켜짐): 이미지가 없는 슬라이드 중 ① 내용이 완전히 같은 반복 슬라이드, ② 다른 슬라이드 제목들을 나열한 목차/agenda 슬라이드, ③ 본문 없이 "PART 2"·"3장 개요"·"결제 시스템"처럼 구분용 제목만 있는 섹션 표지 슬라이드는 검색 인덱스에서 자동으로 제외됩니다(내용 없는 청크가 검색을 어지럽히는 것을 방지). 그래서 목차·표지 슬라이드 자체는 검색으로 찾지 못할 수 있으나, 각 항목의 실제 내용은 해당 섹션 슬라이드에서 그대로 검색됩니다. 단, "고객 만족을 최우선으로 합니다"처럼 문장형 제목만 있는 "키 메시지" 슬라이드는 내용으로 보아 유지됩니다. 이 동작이 원치 않으면 운영자가 끌 수 있습니다([OPERATOR_MANUAL.md `PPTX_REMOVE_DUPLICATE_SLIDES`·`PPTX_DROP_DIVIDER_SLIDES`](OPERATOR_MANUAL.md)).

### 4.2 메타데이터

| 메타데이터 | 적용 형식 | 설명 |
|-----------|----------|------|
| `doc_id`, `filename`, `version`, `sha256` | 전체 | 공통 식별 정보 |
| `page_or_slide` | PDF, PPTX | 페이지/슬라이드 번호 (PPTX·PDF[스캔 아님]은 `[페이지: N]` 마커 단위로 정확히 귀속됨) |
| `section`, `heading` | MD, DOCX, PPTX, PDF(스캔 아님) | 섹션 번호·헤더 텍스트 — PPTX는 슬라이드 제목(제목이 없는 슬라이드는 빈 값), PDF(스캔 아님)는 합성 헤딩을 만들지 않으므로 빈 값 |
| `chapter_no` | 전체 | 계층적 챕터 번호(H2~H6 헤딩마다 레벨별로 증가, 예: `1`·`1.1`·`1.5.3`) — 출처(Sources) 라벨에 표시됨(§3.6 참고) 및 `/admin` 청크 테이블의 챕터 열에도 표시됨(§2.5 참고). 헤딩 이전 구간과 헤딩이 없는 문서는 `0`(두 화면 모두 빈 칸/페이지 번호로 대체). **PPTX·PDF(스캔 아님)는 항상 `0`**(PPTX 슬라이드 제목은 챕터 구조가 아니고, 비스캔 PDF는 헤딩 자체가 없으므로) |
| `excerpt_keywords` | 전체 | LLM이 추출한 핵심 키워드 5개 |
| `chunk_context` | 전체 | 검색(임베딩+키워드) 전용 맥락 헤더 — "{파일명} > {heading}" + LLM 1~2문장. 화면 표시·저장 텍스트에는 포함되지 않음 (Contextual Retrieval) |

버전별로 격리 저장됩니다 — chroma는 `manual_{version}` 컬렉션 분리(예: `manual_latest`, `manual_1_0`), sqlite-vec는 `version` 파티션 키를 사용합니다.

## 5. 문제 해결

### 답변이 없거나 "문서에서 확인되지 않음"

```bash
# 인덱싱된 문서 확인
curl http://localhost:8080/api/v1/documents

# 폴더 동기화 실행
curl -X POST "http://localhost:8080/api/v1/documents/sync?version=latest"
```

- 문서 미업로드 → `/documents` 페이지 또는 API로 업로드
- `version` 불일치 → 업로드와 채팅의 `version` 값을 일치시킴
- 스캔 PDF → 텍스트 레이어가 있는 PDF 사용하거나 운영자에게 OCR 활성화 요청

### 답변 품질이 낮음

- 검색 문서 수(`SEARCH_TOP_K`) 또는 청크 크기(`CHUNK_SIZE`) 조정 필요 → 운영자 문의
- 라우팅 모드를 `QUALITY_FIRST`로 변경 (채팅 화면 드롭다운)

### 이미지가 답변에 표시되지 않음

이미지 처리는 운영자 설정(`app.image-description.enabled=true`)이 필요합니다.  
운영자 문의 또는 [OPERATOR_MANUAL.md](OPERATOR_MANUAL.md)를 참고하세요.

### 이미지 썸네일을 클릭하면 "연결할 수 없음"으로 표시됨

PPTX 문서에서 추출된 이미지 링크가 열리지 않으면 해당 문서를 재업로드해 재인덱싱해 보세요. 자세한 원인은 운영자에게 문의하거나 [OPERATOR_MANUAL.md §8](OPERATOR_MANUAL.md#8-문제-해결)를 참고하세요.

### "현재 요청이 몰려 있습니다" 메시지가 표시됨

다른 사용자들의 질문이 동시에 몰려 서버가 잠시 여유가 없는 상태입니다. 시스템 오류가 아니라 일시적인 혼잡 안내이며, 몇 초 후 다시 질문하면 대부분 정상 처리됩니다. 이 메시지가 자주 반복된다면 운영자에게 동시 사용자 규모를 알려 설정 조정을 요청하세요.

### 답변이 토큰 단위가 아닌 한 번에 표시됨

일부 환경에서는 LLM 프로바이더 설정(`stream=false`)에 따라 토큰이 하나씩 나타나는 대신 전체 응답이 완성된 후 한꺼번에 표시될 수 있습니다. 기능 자체는 정상이며, 설정은 운영자가 변경할 수 있습니다.

### 업로드 실패 (422)

파일 내용이 확장자와 일치하지 않을 때 발생합니다. 원본 파일을 다시 확인하거나 올바른 형식으로 저장 후 재시도하세요.

### 질문 오류 (400)

질문이 2,000자를 초과하거나 비어 있을 때 발생합니다. 질문을 간결하게 줄인 후 재시도하세요.

### 연결 오류 / 서비스 미응답

```bash
curl http://localhost:8080/api/v1/health
```

응답이 없으면 운영자에게 서비스 상태를 확인 요청하세요.
