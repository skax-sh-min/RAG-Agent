## 1. 개요

문서를 업로드하면 내용을 이해하고 질문에 답변하는 RAG(Retrieval-Augmented Generation) 서비스입니다.  
**Web UI**(`http://localhost:8080`)와 **REST API** 두 가지 방식으로 사용할 수 있습니다.

**주요 기능**:

| 기능 | 설명 |
|------|------|
| 질문 유형 분류 | concept / usage / error / version / meta 5종 자동 분류 |
| 멀티 쿼리 검색 | 원본 질문 + LLM 생성 변형 쿼리 2개(총 3개) 병렬 검색 후 중복 제거 |
| ReAct 재검색 | 증거 부족 시 자동 재검색 (최대 2회) |
| Critic 검증 | 답변이 문서에 근거하는지 이중 검증 (`S` 응답 모드는 스킵) |
| SSE 실시간 스트리밍 | 처리 단계 배지 + 토큰 실시간 출력. 전송 버튼이 스트리밍 중 **중지** 버튼으로 전환되어 즉시 중단 가능 |
| 업로드 취소 | 문서 업로드·인덱싱 진행 중 언제든 파일별로 취소 가능 |
| 멀티턴 대화 | 스레드 단위 대화 이력 유지 (재시작 후에도 유지) |
| 문서 버전 관리 | 버전별 독립된 검색 컬렉션 |
| 이미지 처리 | PDF·PPTX·DOCX 이미지 추출(PPTX는 SmartArt·차트 미리보기·첨부 파일 미리보기 포함) → 답변에 썸네일 표시; 스캔 PDF OCR 지원 |
| 이미지 분석 진행 표시 & 건너뛰기 | 답변에 필요한 이미지를 그 자리에서 분석해야 할 때 "이미지 분석 중 (2/5)"로 진행 상황 표시, **건너뛰기** 버튼으로 대기만 중단하고 답변을 계속 진행 가능(§2.2 참고). 업로드 시 이미 설명이 만들어진 이미지는 재분석하지 않음 |
| 방문자별 채팅 분리 | 로그인 없이 쓰는 배포에서, 운영자가 켜두면 접속한 사람마다 사이드바 대화 목록·이력이 따로 보임(기본은 모두 공유). 업로드된 **문서는 모두가 공유**합니다 — 자세한 동작·설정은 운영자 매뉴얼 §9.4.3 |
| 다크 모드 | 시스템 설정 자동 감지 + 사용자 override |
| 출처 hover 미리보기 & 원문 보기 | 출처 항목에 마우스를 올리면 관련 문서 청크 일부를 미리보기. **클릭하면 이미지를 포함한 전체 원문**을 팝업으로 확인 |
| 중복 질문 재사용 | 입력 중 질문 추천 목록 표시 → 선택 시 DB 검증 후 기존 답변 즉시 재사용(실패 시 일반 질의로 자동 전환). 범위는 항상 shared이며, Direct 모드 질문은 👍(좋아요)인 항목만 추천 대상 |
| 메시지 메타데이터 영속화 | 발송·수신 시간, 프로바이더, 토큰 수, LLM 호출 횟수를 DB에 저장 — 페이지 새로고침 후에도 유지 |
| DOCX 자동 포맷 교정 | DOCX → MD 변환 후 LLM이 섹션별 포맷(소제목·잘린 문장·오타)을 자동 교정 → 교정본으로 인덱싱 |
| 소제목 번호 매기기 | 업로드 시 "소제목 숫자 생성" 체크박스로 헤딩에 계층적 번호 부여(예: `1.1`, `1.2`) — **PPTX는 적용되지 않으며, PPTX를 선택하면 체크박스가 자동으로 해제됨**(PDF는 정상 적용되어 체크 유지). PPTX와 다른 형식을 함께 선택하면 나눠서 업로드하라는 경고가 표시됨. 재인덱싱 시 번호가 어긋나 있으면 자동으로 다시 계산 |
| 출처 챕터 번호 | 답변 출처(Sources)가 문서 구조(H2~H6 헤딩)에 따라 `p.12` 대신 `1.5.3` 같은 챕터 번호로 표시됨 — **위 체크박스와 무관하게 항상 자동 계산**(헤딩에 보이는 번호를 매기지 않아도 출처에는 챕터 번호가 붙음). 헤딩이 없는 구간과 PPTX·PDF는 페이지/슬라이드 번호로 표시 |
| 벡터 스토어 관리 | ChromaDB 컬렉션·청크 조회·편집·삭제 + 저장된 MD 파일 기반 재인덱싱 UI (`/admin`) |
| 문서 내보내기 | 인덱싱된 청크를 MD·TXT·DOCX 파일로 재구성해 다운로드(`/documents`, 관리자 전용) — 검색용으로 벌어진 청크 중복(반복 소제목·겹치는 문장 등)은 자동 정리됨. MD는 이미지가 있으면 ZIP으로 함께 받음. **PPTX는 아직 지원하지 않음** |
| 좋아요 기반 큐레이션 Q&A | 답변에 좋아요를 누르면 별도로 임베딩되어 이후 비슷한 질문의 검색 결과에 반영됨(운영자가 정한 가중치만큼 우선 노출). 본인은 채팅창에서, 관리자는 `/admin`에서 언제든 수정·취소 가능 |
| 지식 제안 (청크 직접 추가) | 문서에 없는 내용을 게시판 형식으로 직접 등록하면, 관리자가 검토 후 **임베딩 실행**하거나 **거부**함. 본문에 **이미지**를 넣을 수 있고(넣은 자리에 그대로 표시되며, 등록 시 이미지 내용도 자동으로 읽혀 검색에 반영됨), 처리 결과는 상단 메뉴 배지와 "내 제안" 목록에서 확인 ([§2.6](#26-지식-제안-청크-직접-추가)) |
| 인증 모드 | `app.auth.enabled=true`(기본): Spring Security 폼 로그인; `false`: guest/admin 자동 로그인 (로컬 전용) |

**인증 모드 요약**:

| 모드 | 설정 | 접근 방식 |
|------|------|-----------|
| **인증 활성화** (기본) | `app.auth.enabled=true` | `/login`으로 로그인; `/signup`으로 계정 생성 |
| **인증 비활성화** | `app.auth.enabled=false` | 로그인 불필요; 첫 실행 시 `/setup`에서 관리자 계정 생성 후 자동 로그인 |
| **관리 전용 인증** | `app.auth.enabled=false`<br>`app.auth.management-only=true` | 채팅·문서 조회는 로그인 불필요; 문서 업로드·삭제와 `/admin`만 로그인 필요 |

> 인증 모드 변경은 운영자 권한이 필요합니다. [OPERATOR_MANUAL.md §9.4](OPERATOR_MANUAL.md#94-인증-토글-no-auth-모드)를 참고하세요.

> 시스템 설치·배포·LLM 설정은 [OPERATOR_MANUAL.md](OPERATOR_MANUAL.md)를 참고하세요.

## 2. Web UI 사용법

### 2.0 로그인 및 계정

#### 인증 활성화 모드 (`app.auth.enabled=true`, 기본값)

서비스에 접속하면 `/login` 페이지로 리디렉션됩니다.

| 동작 | 경로 | 설명 |
|------|------|------|
| 로그인 | `/login` | 이메일 + 비밀번호 입력 |
| 계정 생성 | `/signup` | 이메일·표시 이름·비밀번호 입력 |
| 로그아웃 | Navbar **Logout** 버튼 | 세션 종료 |

> 5회 연속 로그인 실패 시 15분간 계정이 잠깁니다.

#### 인증 비활성화 모드 (`app.auth.enabled=false`)

로그인 없이 바로 사용할 수 있습니다. 모든 일반 접속은 **게스트(Guest)** 신원으로 자동 처리됩니다.

**첫 실행 시**: DB에 관리자 계정이 없으면 자동으로 `/setup` 페이지로 이동합니다.  
표시 이름·이메일·비밀번호를 입력하고 **관리자 계정 생성** 버튼을 클릭하면 설정이 완료됩니다.  
이후 `/admin` 경로는 이 관리자 계정으로 자동 로그인됩니다.

#### 관리 전용 인증 모드 (`app.auth.enabled=false`, `app.auth.management-only=true`)

채팅과 문서 조회는 로그인 없이 바로 사용할 수 있습니다. 다만 **문서 업로드·삭제와 벡터 스토어 관리(`/admin`)는 로그인이 필요**하며, 게스트 화면에는 해당 버튼·메뉴 자체가 보이지 않습니다.

**첫 실행 시**: DB에 관리자 계정이 없으면 자동으로 `/setup` 페이지로 이동합니다.  
표시 이름·이메일·비밀번호를 입력하고 **관리자 계정 생성** 버튼을 클릭하면 설정이 완료됩니다.  
**이 모드는 `/setup` 완료 후 자동 로그인되지 않습니다** — Navbar의 **Login** 링크에서 방금 만든 계정으로 로그인하세요.

로그인하면 Navbar에 관리자 메뉴와 문서 업로드/삭제 버튼이 나타나고, 다른 페이지로 이동해도 로그인 상태가 유지됩니다.

> 어떤 인증 모드로 배포됐는지는 운영자에게 문의하세요. 세부 동작은 [OPERATOR_MANUAL.md §9.4.2](OPERATOR_MANUAL.md#942-관리-전용-인증-management-only)를 참고하세요.

### 2.2 채팅

1. **`http://localhost:8080`** 접속 (새 스레드 자동 생성)
2. 이전 대화를 이어하려면 사이드바에서 해당 스레드 클릭
3. 좌측 상단 **version** 입력창에 검색할 문서 버전 입력 (기본: `latest`)
4. 필요하면 **응답 모드**(S/N/C)와 **태그**(아래 참고)를 고른 뒤
5. 하단 입력창에 질문 입력 후 **Enter** (줄바꿈: **Shift+Enter**)

**응답 모드 (S / N / C)**: 입력창 위 행 오른쪽 끝의 **S / N / C 토글 버튼**으로 답변의 성격을 고릅니다(버튼에는 글자만 표시되고, 마우스를 올리면 툴팁으로 설명이 뜹니다). 선택은 브라우저에 저장되어 다음 방문에도 유지됩니다.

| 모드 | 답변 성격 |
|------|----------|
| **S · 간단히** | 요약 하나로 — `## 요약` 섹션만, 1,000자 이내(문서 검색을 건너뛰는 **Direct** 모드에서는 1,500자). 배경·예시·참고 목록 없음 |
| **N · 자세히** (기본값) | 문서에 충실하게 — 5섹션 형식으로 배경·이유·전제·예외까지 |
| **C · 응용** | 문서를 **재료로** 코드·설정·예제를 만들어 줍니다 — "문서에서 찾아 달라"가 아니라 "만들어 달라"일 때 |

**보낸 질문 앞에는 그때 고른 설정이 두 글자로 표시됩니다** — `[RS] 로그 api 사용 예시` 처럼요. **앞 글자가 문서를 찾았는지**(`R` 문서 검색 / `D` 직답), **뒷 글자가 답변의 성격**(`S`/`N`/`C`)입니다. 그래서 `[RN]`은 문서를 찾아 자세히 답한 것, `[DS]`는 문서 없이 짧게 답한 것입니다. 답변 길이나 형식이 왜 다른지, 그리고 **왜 어떤 답변에는 출처가 없는지** 대화를 다시 열었을 때 바로 알아보기 위한 표시입니다. **전체 질문 보기** 목록과 화면 오른쪽 위에 뜨는 현재 질문 풍선에도 같은 표기가 붙습니다. 표기는 화면에만 붙고 질문 원문에는 섞이지 않으므로, 그 질문이 중복 질문 추천에 뜰 때는 대괄호 없이 나옵니다. 이 표시가 생기기 전에 저장된 예전 대화는 `[RN]`으로 보입니다 — 그때는 직답 여부를 따로 기록하지 않았으므로 기본값인 문서 검색으로 표시됩니다. `C`는 문서 검색에서만 고를 수 있어 항상 `[RC]`입니다.

**C(응용) 모드는 나머지 둘과 성격이 다릅니다.** S와 N은 "얼마나 자세히"의 차이지만, C는 **문서에 없는 것을 만들어도 되는가**의 차이입니다. 예를 들어 문서에 날짜 처리 함수가 설명돼 있을 때, N은 그 설명을 정리해 주고 C는 그 함수를 써서 요청하신 기능의 예제 코드를 새로 작성합니다.

C 답변은 네 섹션으로 나옵니다 — `## 요약` / `## 문서 근거`(사용한 문서 속 함수·옵션) / `## 구현`(본문) / `## 검증되지 않은 부분`(문서에서 확인하지 못해 일반 지식으로 채운 부분). **마지막 섹션을 꼭 확인하세요.** 무엇이 문서에서 왔고 무엇이 모델의 추정인지 구분하라고 만든 자리입니다.

> **C는 Direct(잡담) 토글과 함께 쓸 수 없습니다** — 검색된 문서가 재료이므로 검색을 건너뛰는 Direct에서는 성립하지 않습니다. Direct를 켜면 C 버튼이 비활성화됩니다.

**답변 아래 「컨텍스트 한도로 검색된 문서 N개 중 M개만 사용했습니다」가 보일 때**

AI 모델이 한 번에 읽을 수 있는 분량에는 한계가 있습니다. 찾아낸 문서가 그보다 많으면, 관련도가 **낮은 쪽부터** 빼고 답변을 만듭니다(그래도 가장 관련도 높은 문서는 항상 들어갑니다). 대화가 길어져 자리가 부족하면 **오래된 대화**부터 함께 뺍니다.

이때 **출처 목록은 찾아낸 문서를 전부 보여줍니다** — 답변에 쓰이지 않은 것도 함께요. 그래서 실제로 읽히지 않은 출처에는 `미사용` 표시가 붙습니다. 「응답 0%」와는 다른 뜻입니다:

| 표시 | 뜻 |
|------|-----|
| **응답 0%** | 모델이 읽었지만 답변에 쓰지 않음 — 검색은 제대로 됐다는 뜻 |
| **미사용** | 모델이 **읽지도 못함** — 그 내용이 답변에 빠졌을 수 있음 |

이 표시가 자주 보인다면 질문을 더 좁게 하시거나, 관리자에게 문의해 주세요(검색 문서 수 조정 또는 더 큰 모델).

> **C 버튼이 아예 보이지 않는다면 관리자가 이 모드를 꺼 둔 것입니다** — 고장이 아닙니다. C는 문서에 없는 내용을 만들어 내는 유일한 모드라, 그런 답변을 제공할지 자체가 운영 정책일 수 있어 관리자가 설정에서 끌 수 있습니다(끄면 비활성 회색 버튼이 남는 대신 버튼이 사라집니다). 이미 C로 받은 예전 답변은 기록에 그대로 남고 `[C]` 표시도 유지됩니다.
>
> **RAG ↔ Direct를 전환하면 응답 모드는 항상 `N`으로 돌아갑니다** — 어느 방향이든, 직전에 무엇을 골랐든 상관없이. 검색 여부와 답변의 성격은 서로 다른 축이라, 한쪽을 바꾼 뒤에도 남아 있는 다른 쪽 선택은 "내가 지금 고른 것"이라기보다 직전 대화에서 흘러온 설정에 가깝기 때문입니다. 특히 `S`는 버튼만 봐서는 눈에 잘 띄지 않아, 모드를 옮긴 뒤 답변이 짧게 나오는 이유를 알아채기 어려웠습니다. 필요하면 전환 후 다시 고르시면 되고, 그 선택은 평소처럼 저장됩니다.

> **C 답변에는 좋아요가 동작하지 않고, 나중에 재사용되지도 않습니다.** 만들어 낸 코드가 공유 지식으로 등록되면 다음 사람의 답변에 "문서"처럼 쓰이게 되고, "다시 만들어 줘"라는 요청에 저장된 코드를 그대로 돌려주면 요청하신 그 일을 하지 않는 셈이 되기 때문입니다.

> 예전에 있던 **L(원문 최대) 모드는 없어졌습니다.** 실제로는 M(현재의 N)과 답변 길이가 거의 같았기 때문입니다 — 두 모드가 같은 검색 결과를 받으므로 쓸 수 있는 재료가 같고, "더 길게"라는 지시만으로는 모델이 실제로 더 쓰지 않았습니다. 원문을 그대로 보고 싶다면 답변 아래 **출처 목록을 펼치거나**(청크 원문이 그대로 보입니다) [§1.6 문서 내보내기](#16-문서-내보내기)를 쓰는 편이 정확합니다. 기존 대화에 남아 있던 `M`·`L` 선택은 자동으로 `N`으로 읽히므로 따로 하실 일은 없습니다.

> `S` 모드에서는 속도/간결성 우선으로 Critic 근거 검증 단계를 생략합니다. 따라서 자동 재시도는 Answer 단계의 충분도 판단 기준으로만 동작합니다.

> **답변 위 검증 배지가 모드마다 다릅니다.** `N`은 통과 시 초록 **검증됨**(답변이 문서에 근거함), `C`는 파랑 **생성**입니다 — C에서 검사한 것은 "문서에 근거하는가"가 아니라 "문서에서 온 것처럼 적은 함수·옵션 이름이 실제로 문서에 있는가"이기 때문입니다. 지어낸 이름이 발견되면 노랑 **문서 밖 이름** 배지와 그 목록이 함께 표시되며, 이 경고는 **검증을 통과한 답변에도** 붙습니다. 배지는 저장되므로 새로고침해도 그대로 남습니다.

> **`S`와 `C`에서는 좋아요가 아무 일도 하지 않습니다** — S 답변은 이미 요약이라 공유 지식으로 등록해도 검색에 도움이 되는 내용이 남지 않고, C 답변은 만들어 낸 내용이라 공유 지식이 되면 다음 사람의 답변에 "문서"처럼 쓰이기 때문입니다(아래 §1.5 참고). 싫어요는 두 경우 모두 평소대로 동작합니다.

> 답변을 중간에 딱 잘라 제한하지는 않습니다. 분량은 모드별 지시문이 정하며, 숫자를 말하는 건 `S`뿐입니다 — 문서를 검색해 답하는 평소 경로는 "1,000자 이내", 검색을 건너뛰는 **Direct** 모드는 "1,500자 이내"로 조금 더 넉넉합니다(인용할 문서가 없어 답변이 스스로 풀어 써야 하기 때문). `N`·`C`는 숫자 대신 "무엇을 더 다룰지"(N은 배경·이유·전제·예외, C는 구현 의도·선택 근거·주의점)를 지시합니다 — 긴 답변에 글자 수 목표를 주는 방식은 실제로 효과가 없었습니다(옛 M/L이 그렇게 만들어졌고, 그래서 둘이 구분되지 않았습니다). 운영자 설정 `LLM_MAX_TOKENS`에서 파생되는 토큰 상한도 있지만 그것은 **폭주를 막는 안전판**이고, 게다가 실시간 스트리밍 답변에는 아예 적용되지 않습니다.

**검색 태그**: 별도 입력창 없이, 버전 셀렉터 옆에 표시되는 **태그 칩을 클릭**해 켜고 끕니다(다시 누르면 해제). 선택한 태그가 **모두** 포함된 문서만 검색합니다. 맨 앞의 **`All`** 칩은 "태그로 좁히지 않고 전체 문서 검색"을 뜻하며, 새 대화를 시작하면 기본으로 선택돼 있습니다. 다른 태그를 하나라도 고르면 `All`은 자동으로 꺼지고, `All`을 다시 누르면 골라둔 태그가 모두 해제됩니다. 모든 문서에 공통으로 붙은 태그(예: 전 부서 공통 태그)는 어차피 아무것도 걸러내지 못하므로 칩 목록에 아예 표시되지 않습니다 — 목록이 길어지는 걸 막기 위한 정리입니다. 등록된 태그가 없는 버전에서는 칩 영역 자체가 보이지 않습니다.

**중복 질문 추천/재사용**: 질문 입력창에 2글자 이상 입력하면 바로 아래에 기존 질문 추천 목록이 나타납니다. 추천 범위는 항상 **shared**(전체 사용자 기준)이며, 추천 목록에는 기존 질문 중 **50자 이하 질문만** 포함됩니다(51자 이상은 추천 제외).

- 추천 항목을 클릭하면 기존 답변을 즉시 재사용하지 않고, **반환 직전에 출처 청크 유효성(삭제/변경 여부)을 다시 1회 검증**합니다.
- 검증이 통과하면 새 turn이 `db-reuse` 제공자로 저장되고, 답변이 즉시 화면에 붙습니다.
- 검증에 실패하면(문서/청크 삭제, 재인덱싱으로 내용 변경 등) 토스트 안내 후 **동일 질문으로 일반 질의**를 자동 전송합니다.
- Direct 모드로 저장된 질문은 **👍(좋아요)** 인 항목만 추천/재사용 대상이 됩니다.
- "이거/그거" 같은 지시어 위주 질문은 추천에서 제외됩니다. 다만 `오류코드 404`, 파일명, 경로, API명처럼 구체 신호가 있으면 제외하지 않습니다.
- 재사용으로 붙은 답변에도 출처(Sources)와 hover 미리보기가 동일하게 표시됩니다. 스레드를 다시 열어 과거 turn을 복원했을 때도 같은 방식으로 표시됩니다.

**답변 실시간 표시**:
- 상단 배지에서 현재 처리 단계 확인 (질문 분류 → 문서 검색 → 답변 생성 → 검증)
- 토큰이 생성되는 즉시 화면에 출력
- 답변 아래 출처(Sources) — 마우스를 올리면 관련 문서 청크 일부 미리보기 팝오버 표시(PC 화면에서는 더 넓게 표시되어 읽기 편함), **클릭하면 이미지를 포함한 전체 원문이 별도 팝업 창으로 열림**(재사용된 답변·스레드를 다시 열어 복원한 과거 답변에서도 동일하게 동작)
- 검색된 이미지가 있으면 썸네일 그리드로 표시 (클릭 시 원본 확인)
- 소요 시간·토큰 수·사용 LLM·호출 횟수 메타정보 확인 가능 (재방문 시에도 유지)

**검증 결과와 미통과 사유**: 답변이 만들어지면 그 답변이 (1) 질문에 충분히 답했는지 (2) 검색된 문서에 근거하는지를 한 번 더 확인합니다. 통과하면 **검증됨** 배지가, 통과하지 못하면 **미검증** 배지가 붙습니다.

- 미통과 시에는 자동으로 다시 시도하며(최대 2회), 그동안 **왜 통과하지 못했는지**가 재시도 안내 아래 "사유: …" 한 줄로 표시됩니다 — 예: *"설치 절차는 있으나 질문한 포트 설정 값이 문서에 없음"*. 이 사유는 화면에만 남는 것이 아니라 **다음 시도에도 전달되어**, 같은 답을 그대로 반복하지 않고 그 부분을 다시 확인하게 합니다.
- **두 종류의 미통과는 다르게 처리됩니다.** (1) *질문에 충분히 답하지 못함* → 검색 범위를 넓혀 다시 찾습니다. 이때 직전 시도에서 **답변에 전혀 쓰이지 않은 관련도 낮은 문서 일부가 밀려나고** 그 자리에 새 문서가 들어옵니다(그냥 덧붙이면 새 근거가 이미 자리를 차지한 무관한 문서와 경쟁하게 되므로). (2) *문서에 없는 내용이 섞임* → 근거는 이미 충분하므로 다시 찾지 않고 **답변만 다시 씁니다**. 후자에서는 출처 목록이 그대로 유지되는 것이 정상입니다.
- 이전 시도의 답변은 지워지지 않고 **미검증**으로 접혀 남으므로, 펼쳐서 새 답변과 비교할 수 있습니다.
- 재시도를 다 쓰고도 통과하지 못한 답변은 그대로 전달되지만, 메타정보 줄에 **미검증** 배지와 함께 사유가 한 줄로 남습니다. 이 사유가 곧 **다음에 무엇을 해야 하는지**입니다 — 문서에 내용이 없다는 뜻이면 그 문서를 업로드하거나 [지식 제안](#26-지식-제안-청크-직접-추가)으로 내용을 추가하고, 질문이 모호하다는 뜻이면 질문을 구체화하세요.
- 사유는 검증을 수행한 LLM이 직접 쓴 것이라 항상 정확하지는 않습니다. 판단의 출발점으로 쓰고, 실제 근거는 답변 아래 **출처**에서 확인하세요.
- **배지가 아예 없는 답변도 있습니다** — 검증됨도 미검증도 아닌 경우입니다. 검증을 수행한 LLM이 응답을 내지 못했거나 형식이 깨져서 **판정 자체를 읽지 못했다**는 뜻이고, 이때는 재시도도 걸지 않고 답변을 그대로 전달합니다. "통과"가 아니라 "확인 못 함"이므로, 이런 답변은 **출처를 직접 펼쳐 확인**하세요. 매번 이렇게 나온다면 검증이 사실상 동작하지 않는 상태이니 운영자에게 알려 주세요. (`S` 모드는 원래 검증을 하지 않으므로 배지가 없는 것이 정상입니다.)

**환경에 따라 달라질 수 있는 값**: 설치 경로, 서버 주소·포트, 환경변수 값, 계정명 같은 값은 **문서를 쓴 환경과 내 환경이 다르면 달라지는 것이 정상**입니다. 그래서 이런 값이 문서와 다르다는 이유만으로는 검증이 실패하지 않고, 대신 답변 아래에 파란 안내 한 줄이 붙습니다.

> ℹ️ 환경에 따라 달라질 수 있는 값: 설치 경로 `/opt/app`과 포트 `8080`은 환경에 따라 다를 수 있습니다

- 이 안내는 **검증됨** 배지가 붙은 답변에도 나타납니다. 답변이 틀렸다는 뜻이 아니라, **그 값만큼은 내 환경 기준으로 바꿔 읽으라**는 뜻입니다.
- 값이 아니라 **절차나 동작 방식**이 문서와 다르면 그것은 환경 차이가 아니므로 여전히 미검증으로 판정됩니다.
- 답변에 이런 값이 없으면 안내 줄도 나타나지 않습니다.

**답변 중지**: 스트리밍 중에는 전송 버튼이 빨간 **중지** 버튼으로 바뀝니다. 잘못 보낸 질문이나 답변이 너무 길어질 때 클릭하면 즉시 중단되고, 그때까지 생성된 부분 답변은 그대로 남은 채 "사용자가 중단함" 표시가 붙습니다. 화면만 멈추는 것이 아니라 **LLM 쪽 생성도 함께 끊깁니다** — 중지한 답변이 뒤에서 계속 만들어지며 다음 질문의 순서를 밀어내는 일은 없습니다.

**이미지 분석 진행 표시 & 건너뛰기**: 검색된 문서에 아직 설명이 없는 이미지가 포함돼 있으면(예: 처음 검색되는 이미지), 답변을 만들기 전에 그 이미지를 분석하는 짧은 대기 구간이 생깁니다. 이 동안 상단 배지에 "이미지 분석 중 (2/5)"처럼 몇 번째 이미지까지 끝났는지 표시되고, 배지 옆에 작은 **건너뛰기** 링크가 함께 나타납니다.

- 이미지가 많거나 로컬 LLM이 느릴 때 대기가 길어질 수 있는데, **건너뛰기**를 누르면 남은 이미지를 기다리지 않고 그때까지 완료된 설명만으로 답변이 바로 진행됩니다.
- 건너뛴 나머지 이미지 분석은 화면에서만 안 기다릴 뿐, 서버에서는 백그라운드로 계속 완료되어 저장됩니다 — 다음에 같은 이미지가 다시 검색되면 이미 준비된 설명을 즉시 재사용합니다(다시 기다릴 필요 없음).
- 업로드할 때 "이미지 설명 추가"를 체크해 이미 문서에 설명이 포함된 이미지는 애초에 이 대기 자체가 생기지 않습니다(재분석하지 않음).

**질문 찾아가기 (긴 답변에서 길을 잃지 않기)**:

답변이 수십 줄인 경우가 많아 조금만 스크롤해도 "이게 무슨 질문에 대한 답이었지?"가 됩니다. 두 가지 도구가 있습니다.

| 도구 | 위치 | 하는 일 |
|------|------|--------|
| **현재 질문 풍선** | 대화 영역 **오른쪽 위** | 지금 읽고 있는 답변의 질문을 파란 풍선으로 계속 띄워 줍니다. 클릭하면 그 질문 위치로 돌아갑니다 |
| **전체 질문 보기** | **맨 아래로** 버튼 바로 **위**의 목록 아이콘(☰) | 이 대화의 질문 전체를 번호·시각과 함께 목록으로 열고, 항목을 클릭하면 그 질문으로 바로 이동합니다 |

- 질문 풍선은 **질문 버블이 화면에서 보이지 않을 때만** 나타납니다 — 질문이 이미 보이는 동안에는 같은 문구를 두 번 띄우지 않습니다.
- 목록에서 질문으로 이동하면 그 질문 버블이 잠깐 파랗게 깜빡여 어디로 왔는지 알려 줍니다.
- 질문 목록 창은 바깥을 클릭하거나 `Esc`를 누르거나 창 오른쪽 위 X로 닫습니다.
- 질문이 아직 하나도 없는 새 대화에서는 목록 버튼이 보이지 않습니다.
- 스레드를 다시 열어 복원한 과거 대화에서도 똑같이 동작합니다.

**메시지 메타데이터**:

| 표시 위치 | 정보 |
|----------|------|
| 사용자 버블 내부(오른쪽 하단) | 🕐 발송 시각 (HH:MM) |
| 어시스턴트 버블 하단 | 수신 시각 · 🤖 사용 프로바이더 · ⏱ 소요 시간 · 📥📤 입/출력 토큰 · 🔄 LLM 호출 횟수 |

> 모든 메타데이터는 DB에 저장되어 스레드를 다시 열어도 복원됩니다.

**싫어요 & 질문·답변 삭제**:

답변이 마음에 들지 않으면 👎(싫어요)를 누릅니다. 그러면 먼저 **"이 질문과 답변을 대화에서 삭제할까요?"** 라고 물어봅니다 — 지울 것인지, 화면에는 남기되 이후 참고 맥락에서만 뺄 것인지 두 선택지 중 하나를 고르는 것입니다.

- **예** → 그 질문과 답변 한 쌍이 대화에서 지워집니다. 같은 대화의 **다른 질문·답변은 그대로 남습니다**(대화 전체가 지워지는 것이 아닙니다 — 대화 전체 삭제는 사이드바의 휴지통 아이콘입니다). 되돌릴 수 없습니다.
- **아니오** → 삭제하지 않고 **싫어요만 기록**됩니다. 그 질문·답변은 화면에 그대로 남지만 **이후 대화의 참고 맥락에서 제외**되어, 다음 질문의 답변 품질에 더 이상 영향을 주지 않습니다.
- 이미 눌러둔 싫어요를 **취소**할 때(👎 다시 클릭)나 👍를 누를 때는 삭제 여부를 묻지 않습니다.

**좋아요 & 큐레이션 답변 편집**:

마음에 드는 답변에 👍(좋아요)를 누르면, 그 질문·답변이 별도로 저장·임베딩되어 **이후 비슷한 질문을 검색할 때 근거로 함께 활용**됩니다(반복 질문·FAQ성 질문의 정확도 향상 목적). 좋아요는 몇 초 안에 취소하면 저장이 아예 진행되지 않으니 실수로 누른 경우 바로 다시 누르면 됩니다.

| 동작 | 방법 |
|------|------|
| 좋아요 | 답변 하단 👍 클릭 (다시 누르면 취소) |
| 답변 내용 수정 | 좋아요 상태일 때만 나타나는 연필(✏) 아이콘 클릭 → 오른쪽 패널에서 텍스트 수정 후 저장 |

- 수정하면 검색용 데이터도 자동으로 다시 계산됩니다 — 별도 재저장 절차가 없습니다.
- **답변이 길면 검색용으로 여러 조각으로 나뉘어 저장됩니다**(문서를 인덱싱할 때와 같은 방식). 화면에 보이는 답변은 그대로 하나이고, 좋아요 취소·수정도 평소처럼 답변 단위로 동작합니다 — 나뉘는 것은 검색 색인 쪽뿐입니다.
- 답변 끝의 **출처(`## 참고`) 목록과 맨 앞 요약은 검색 색인에 넣지 않습니다** — 파일명·페이지 번호는 질문과 무관한 잡음이고 요약은 본문과 중복이기 때문입니다. 화면에 보이는 답변에는 그대로 남습니다.
- 좋아요를 취소하면 해당 답변은 검색 반영에서 즉시 제외됩니다.
- **`S`(간단히) 모드로 받은 답변은 좋아요를 눌러도 아무 일도 일어나지 않습니다** — 검색 색인에 넣을 때 요약·출처 섹션을 걷어내는데, S 답변은 전체가 요약이라 걷어내고 나면 남는 내용이 없기 때문입니다(질문만 담긴 항목이 만들어집니다). 그래서 등록 자체를 하지 않습니다. 공유 지식으로 남기고 싶은 답변은 `N` 모드로 다시 물어보신 뒤 좋아요를 눌러 주세요. 싫어요는 모드와 무관하게 평소대로 동작합니다.
- 본인이 좋아요한 답변만 이 방법으로 수정할 수 있습니다(다른 사용자의 대화는 애초에 보이지 않습니다). 전체 사용자의 큐레이션 답변을 관리하는 기능은 [§2.5](#25-벡터-스토어-관리) 관리자 화면에 별도로 있습니다.
- 대화(스레드) 자체를 삭제해도 이미 좋아요로 등록된 답변은 검색에 계속 반영됩니다 — 완전히 제외하려면 삭제 전에 좋아요를 먼저 취소하세요.

**스레드 관리**:

| 동작 | 방법 |
|------|------|
| 새 대화 시작 | 사이드바 **New Chat** 버튼 |
| 이전 대화 재개 | 사이드바에서 스레드 클릭 → 이전 메시지 버블 복원 |
| 대화 제목 변경 | 스레드 옆 연필 아이콘 클릭 → 인라인 편집 |
| 대화 삭제 | 스레드 옆 휴지통 아이콘 (되돌릴 수 없음 — 아래 참고) |

> **대화를 삭제하면 그 대화에서 👍를 눌러 공유 지식이 된 답변도 함께 회수됩니다** — 이후 검색 결과에 더 이상 반영되지 않습니다. 답변은 남기고 대화만 정리하고 싶다면, 그 답변을 [지식 제안](#26-지식-제안-청크-직접-추가)에 다시 등록해 두세요(승인되면 대화와 무관하게 유지됩니다).

> **라우팅 모드** (채팅 화면 드롭다운): `COST_FIRST` · `QUALITY_FIRST` · `PROGRESSIVE` · `LOCAL_ONLY`  
> 각 모드의 동작 방식은 [OPERATOR_MANUAL.md §5.3](OPERATOR_MANUAL.md)을 참고하세요.  
> 이 드롭다운이 아예 보이지 않는다면 운영자가 이 서비스를 로컬 LLM 전용으로 구성한 것입니다(어떤 모드를 골라도 결과가 같아 선택지 자체를 제공하지 않음) — 정상 동작입니다.

> **메시지 복원 제한**: 이전 turn의 토큰 수·출처 메타데이터는 DB에 저장되지 않으므로 새 turn에서만 표시됩니다.

### 2.3 문서 관리

`/documents` 접속 후:

| 기능 | 방법 |
|------|------|
| **업로드** | 드래그 앤 드롭 또는 영역 클릭 → 파일 선택 → Version 입력 → **Upload & Index** |
| **업로드 취소** | 진행 중인 파일 행의 **Cancel** 버튼 (업로드/인덱싱 중 언제든) |
| **목록 새로고침** | **Refresh** 버튼 |
| **문서 삭제** | 행 우측 **Delete** 버튼 |

**지원 형식**: PDF, PPTX, DOCX, TXT, MD / 최대 200 MB

> 관리 전용 인증 모드([§1](#1-개요) 참고)에서는 업로드 카드와 삭제 버튼이 관리자로 로그인했을 때만 보입니다. 게스트 화면에는 문서 목록 조회만 표시됩니다.

업로드 시 참고 사항:
- 같은 파일을 다시 올리면 SHA-256 기반 변경 감지로 변경된 경우에만 재인덱싱
- 파일 내용이 확장자와 일치하지 않으면 업로드가 거부됩니다 (예: .txt로 이름 바꾼 실행파일)
- 이미지 포함 문서(PDF·PPTX·DOCX)는 이미지도 함께 추출 (운영자 설정 필요)
- 스캔 PDF는 OCR로 텍스트 추출 (운영자 설정 필요)
- 소제목에 번호를 매기고 싶다면 업로드 시 **소제목 숫자 생성** 체크박스를 켜세요 — PPTX는 슬라이드 제목이 문서 목차 구조가 아니라서 이 옵션이 적용되지 않으며, **PPTX 파일을 선택하면 체크박스가 자동으로 해제**됩니다(PDF는 정상 적용되므로 체크된 채 유지됩니다). PPTX와 다른 형식을 같은 배치에 함께 선택하면 업로드는 배치 전체에 설정 하나만 적용되므로 화면에 나눠서 업로드하라는 경고가 뜹니다 — 업로드 자체를 막지는 않으니 그대로 진행해도 되고, PPTX만 따로 올려도 됩니다. 이 자동 설정은 어디까지나 기본값 제안이라 언제든 직접 체크/해제할 수 있습니다
- 대용량 파일 업로드를 잘못 시작했다면 **Cancel**로 즉시 중단할 수 있습니다. 취소 시점까지 이미 완료된 파일은 그대로 인덱싱되어 남고, 진행 중이던 파일만 취소됩니다
- 업로드/인덱싱 도중 오류가 나면 실패한 파일 행에 오류가 발생한 단계(문서 로드·구조화·이미지 분석·교정·청크 분할·키워드 추출·벡터 DB 저장)와 메시지가 표시됩니다. **로그 보기**를 클릭하면 해당 파일의 진행 이력을 확인할 수 있습니다 (다른 페이지로 이동하면 사라짐)
- 인덱싱이 오래 걸리는 도중(노트북 절전, 네트워크 전환 등으로) 브라우저 연결이 끊겼다가 다시 붙으면 대부분 실제 결과(완료/실패)를 그대로 이어받습니다. 아주 오래(4시간 이상) 끊겨 있었다면 실패가 아니라 **"⚠️ 상태 확인 불가 — 문서 목록에서 확인해 주세요"**로 표시될 수 있는데, 이 경우 실제로는 인덱싱이 정상 완료됐을 가능성이 높으니 **Refresh** 버튼으로 문서 목록을 새로고침해 확인하세요. 이 파일 다음에 올릴 예정이던 나머지 파일들도 계속 업로드됩니다
- "이미지 설명 추가"를 체크한 경우, 문서에 포함된 이미지를 LLM(Vision)이 분석하는 동안 파일 행에 **"이미지 분석 중 (N/M)"**로 진행 상황이 실시간 표시됩니다 — 이미지가 많은 PPTX·PDF 등에서 이 단계가 오래 걸릴 수 있습니다
- `data/documents/` 폴더를 직접 스캔해 신규·변경·삭제 파일을 일괄 반영하는 폴더 동기화는 REST API로만 제공됩니다 → [§3.3 증분 동기화](#33-증분-동기화)

**문서 내보내기** (관리자 전용):

문서 목록 각 행의 **내보내기** 버튼을 누르면 형식(MD/TXT/DOCX)과 옵션(이미지 설명 포함, 소제목 번호·목차 추가)을 고르는 창이 뜨고, **내보내기**를 누르면 바로 다운로드됩니다.

- 현재 벡터 스토어에 색인된 청크를 기준으로 문서를 다시 조립합니다 — `/admin`에서 청크를 편집·삭제했다면 그 내용이 그대로 반영됩니다.
- 검색을 위해 일부러 벌어진 청크 간 중복(반복된 소제목, 겹치는 문장 등)은 자동으로 정리되어 원문에 가까운 결과를 받습니다.
- MD로 내보낼 때 문서에 이미지가 있으면 이미지 파일을 함께 담은 ZIP으로 받습니다(이미지가 없으면 `.md` 파일 그대로). 원본 이미지 파일이 사라진 경우에는 깨진 링크 대신 `(이미지 없음: 파일명)` 안내가 들어갑니다.
- DOCX는 이미지를 실제 그림으로 넣습니다 — 글머리 기호 뒤나 문장 중간에 있던 이미지는 바로 아래 줄에 그림으로 들어가고, 표 안의 이미지는 그 칸 안에 칸 너비에 맞춰 들어갑니다.
- DOCX의 코드 블록은 1×1 표(테두리 상자) 안에 좌측 정렬·고정폭 글꼴로 들어가고, 주석(`//`, `#`, `/* */`)만 초록색으로 표시됩니다.
- **PPTX는 아직 지원하지 않습니다** — 형식 선택지에 없습니다.
- 소제목 번호·목차 옵션은 PPTX 원본 문서에는 적용되지 않아 체크박스가 자동으로 비활성화되며(이유가 함께 표시됨), 다른 형식에는 정상 적용됩니다.

### 2.4 LLM 사용량 통계

`/llm-usage` 접속 후:

| 영역 | 설명 |
|------|------|
| **프로바이더 카드** | 설정된 LLM 프로바이더별 상태 — 정상(초록) / 차단 중(빨강 + 남은 시간 카운트다운) |
| **임베딩 카드** | 문서 인덱싱·검색 시 사용되는 임베딩 모델의 토큰 사용량을 `EMBEDDING` 배지가 붙은 별도 카드로 표시 — 채팅 프로바이더와 분리 집계되며 항상 "정상" 상태 |
| **Orphan 카드** | 설정에서 완전히 제거된 프로바이더(또는 옛 임베딩 모델)의 과거 사용 기록을 회색 `ORPHAN` 배지 카드로 표시 — 관리자만 카드의 🗑 아이콘으로 삭제할 수 있습니다 |
| **일별 차트** | 누적 막대 차트 — 7일 / 30일 / 90일 기간 선택, 프로바이더별 색상 구분 (임베딩은 별도 막대로 구분 표시) |
| **기간별 테이블** | 오늘 / 이번 주 / 이번 달 탭 — 프로바이더별 입력/출력/합계 토큰 및 호출 수 |

카드 영역은 30초마다 자동 갱신됩니다.

> 키가 설정되지 않았고 한 번도 사용된 적 없는 프로바이더는 카드·차트·테이블 어디에도 표시되지 않습니다. 과거에 사용한 적 있는 프로바이더는 이후 키가 제거되어도 이력 확인을 위해 계속 표시됩니다 — 설정에서 완전히 제거되면 ORPHAN 카드로 전환됩니다.

### 2.5 벡터 스토어 관리

`/admin` 접속 후 벡터 스토어에 저장된 청크를 직접 조회·편집·삭제할 수 있습니다. 상단에는 **Vector Store 상태 카드**(백엔드 종류·정상 여부·문서/청크 수)가 표시됩니다.

> 관리 전용 인증 모드([§1](#1-개요) 참고)에서는 `/admin`이 로그인을 요구하며 Navbar에도 관리자로 로그인했을 때만 메뉴가 나타납니다.

> **벡터 스토어 백엔드**: 청크 브라우징/편집은 **ChromaDB·sqlite-vec 두 백엔드 모두** 지원됩니다. 레이아웃·기능은 동일하고 표시 지표·라벨만 백엔드에 맞게 바뀝니다(chroma=컬렉션 / sqlite-vec=버전, `vec_version`·차원 등). 자세한 차이는 [OPERATOR_MANUAL.md §7.4](OPERATOR_MANUAL.md) 참고.

**왼쪽 패널 — 컬렉션(chroma) / 버전(sqlite-vec) 목록**:
- 백엔드별 컬렉션(또는 버전)과 청크 수 표시
- 클릭 시 오른쪽 패널에 해당 청크 목록 로드

**오른쪽 패널 — 청크 테이블**:

표에는 ID·텍스트 미리보기·크기·파일명·페이지/슬라이드·**챕터**·키워드가 함께 표시됩니다. 챕터 열은 §4.2의 `chapter_no`(H2~H6 헤딩 기반 계층 번호)를 보여주며, 실제 챕터가 없는 청크(프롤로그·PPTX·PDF)는 빈 칸으로 표시됩니다. 청크는 문서별로 묶여 **문서 내 실제 순서 그대로** 표시됩니다(청크 ID 순서가 아닙니다).

| 기능 | 방법 |
|------|------|
| 문서 필터 | 드롭다운에서 특정 문서(docId) 선택 → 해당 문서 청크만 표시 |
| 페이지당 건수 | 드롭다운에서 20 / 50 / 100건 선택 (기본값: 20건) — 변경하면 첫 페이지부터 다시 조회 |
| 페이지 이동 | [이전 / 다음] 버튼으로 선택한 건수만큼 이동 |
| 청크 편집 | 행의 연필 아이콘 → 오른쪽 오프캔버스에서 메타데이터(JSON)·텍스트 수정 후 저장 |
| 청크 재인덱싱 | 편집 패널의 **이 청크만 재인덱싱** 버튼 → 저장된 텍스트 기준으로 그 청크만 재임베딩 + 키워드 검색(FTS) 인덱스 갱신 |
| 청크 삭제 | 행의 휴지통 아이콘 → 즉시 ChromaDB에서 제거 |

> **넓은 화면에서는 미리보기가 함께 표시됩니다**: 청크 편집 오프캔버스를 열 때 현재 창 폭이 충분히 넓으면(대략 PC 가로 화면 기준) 편집 패널이 왼쪽의 실시간 미리보기(마크다운 서식·표·이미지 포함)와 오른쪽의 기존 편집 입력창으로 나뉘어 표시됩니다. 텍스트를 수정하면 왼쪽 미리보기가 그대로 갱신되어 저장 전에 결과를 바로 확인할 수 있습니다. 창이 좁으면(모바일 등) 기존처럼 편집 입력창만 표시됩니다 — 오프캔버스를 여는 시점에 1회만 판정하므로, 열어둔 채로 창 크기를 바꿔도 즉시 반영되지는 않습니다(닫았다 다시 열면 재판정).

> **"요약 (맥락)" 필드**: 입력창 위에 회색 글씨로 표시되는 첫 줄(예: `문서명.docx > 소제목`)은 파일명·소제목에서 자동으로 계산되는 위치 정보로, **직접 편집할 수 없습니다**. 그 아래 입력창에 있는 문장만 실제 편집 대상이며, 검색(임베딩·키워드) 입력에는 이 위치 정보 뒤에 입력한 문장이 그대로 이어붙어 사용됩니다. 아직 문장이 없는 청크(키워드 재생성을 한 번도 하지 않은 경우 등)는 입력창이 비어 있으니 원하는 설명을 새로 적으면 됩니다.

**하단 — 문서 레지스트리**:
- 인덱싱된 전체 문서 목록 표시 (파일명·버전·청크 수·인덱싱 일시)
- **청크 보기** 버튼으로 해당 문서의 청크를 바로 필터링
- **↺ 버튼 (MD 재인덱싱)**: DOCX·TXT·PPTX·PDF(스캔이 아닌 경우) 문서는 서버에 저장된 교정 MD 파일(`{docId}_corrected.md`)을 기준으로 청크를 다시 생성하고 인덱싱합니다. MD 파일을 직접 수정한 뒤 이 버튼을 누르면 재업로드 없이 인덱싱을 갱신할 수 있습니다(스캔 PDF는 MD 파일 자체가 없어 미지원).
  - MD 파일이 가리키는 이미지가 실제로는 존재하지 않으면(수동 정리 등으로 파일이 사라진 경우) 해당 이미지 참조는 재인덱싱 시 자동으로 제거되고 MD 파일에도 반영됩니다.
  - 소제목에 이미 번호가 매겨져 있던 문서라면, 편집으로 헤딩이 늘거나 줄어 번호가 어긋난 경우 재인덱싱 시 자동으로 다시 계산되어 MD 파일에도 반영됩니다(PPTX 제외 — 애초에 번호가 붙지 않습니다).
  - 빈 줄 정리·프롬프트 마커 제거 같은 마크다운 서식 정리도 매번 다시 적용되어 MD 파일에 반영됩니다(LLM 미사용, 즉시 처리). 단, 코드 블록의 언어 태그 보정은 재인덱싱에서 다시 실행되지 않습니다 — MD 파일을 직접 편집한 뒤라면 코드 블록 안의 빈 줄이 의도와 다르게 정리될 수 있는 위험을 피하기 위한 설계입니다.

> **주의**: 청크 텍스트/메타데이터 **저장**만으로는 벡터 임베딩과 키워드(FTS) 인덱스가 갱신되지 않습니다 (원본 벡터 유지) — 편집한 내용은 표시·답변 프롬프트에는 바로 반영되지만, "이 텍스트/키워드로 검색되는지"는 그대로입니다.  
> 편집한 내용을 검색에도 반영하려면 편집 패널의 **이 청크만 재인덱싱** 버튼을 누르세요 — 저장된 텍스트를 기준으로 그 청크만 재임베딩하고, 키워드 검색 인덱스도 함께 갱신합니다. **키워드 재생성** 체크박스를 켜면 현재 키워드를 그대로 두는 대신 LLM으로 키워드·맥락을 새로 뽑습니다(LLM 호출 1회, 문서 전체 ↺ 재인덱싱과 동일한 품질). 문서 전체를 다시 인덱싱하려면 MD 파일 수정 후 ↺ 재인덱싱 버튼을 사용하거나, Documents 페이지에서 문서를 삭제 후 재업로드하세요.

> **키워드만 손보고 싶다면**: 메타데이터(JSON)의 `excerpt_keywords` 값을 직접 고친 뒤 저장하고, **키워드 재생성 체크를 해제한 채** 재인덱싱하면 됩니다(체크하면 LLM이 뽑은 값으로 덮어씁니다). 키워드는 **키워드(BM25) 검색 축에만** 쓰이고 벡터 임베딩에는 들어가지 않으므로, 특정 용어로 꼭 검색되게 하고 싶을 때 쓰는 수단입니다. 하이브리드 검색이 꺼져 있으면(`SEARCH_HYBRID_ENABLED=false`) 효과가 없고, 검색 색인이 3글자 단위라 **2글자 이하 키워드는 걸리지 않습니다**.

**큐레이션 Q&A 관리** (관리자 전용, §2.2 "좋아요 & 큐레이션 답변 편집" 참고):

`/admin` 페이지 **맨 아래** **큐레이션 Q&A** 카드는 기본적으로 접혀 있습니다 — 카드를 클릭해 펼치면 그때 사용자들이 좋아요한 답변을 최신순으로 불러와 확인할 수 있습니다. 확인할 필요가 없다면 그대로 접어 두면 됩니다. (위쪽 **청크 추가 제안** 카드가 처리해야 할 대기열이고, 이 카드는 이미 반영된 것을 확인하는 용도라 아래에 있습니다.)

| 기능 | 방법 |
|------|------|
| 페이지당 건수 | 드롭다운에서 20 / 50 / 100건 선택 (기본값: 20건) |
| 페이지 이동 | [이전 / 다음] 버튼으로 선택한 건수만큼 이동 |
| 답변 수정 | 행의 연필 아이콘 → 텍스트 수정 후 저장 (**청크 편집과 달리 저장 시 자동으로 재임베딩됨**) |
| 강제 삭제 | 행의 휴지통 아이콘 → 좋아요를 누른 사용자와 무관하게 즉시 검색에서 제외 |

부적절한 내용이 좋아요를 받아 검색에 반영된 경우, 사용자가 취소하지 않아도 관리자가 여기서 직접 제거할 수 있습니다.

> **화면이 넓으면 편집창 왼쪽에 미리보기가 함께 뜹니다** — 청크 편집과 똑같은 방식으로, 타이핑하는 대로 표·코드블록·이미지가 실제 보이는 모습으로 갱신됩니다. 이 답변의 마크다운이 그대로 검색 근거로 쓰이므로, 서식이 깨진 채 저장되지 않도록 확인하는 용도입니다. 화면이 좁으면(모바일 등) 기존처럼 편집창만 나옵니다.

**청크 추가 제안 검토** (관리자 전용, [§2.6](#26-지식-제안-청크-직접-추가) 참고):

`/admin` 페이지 하단 **청크 추가 제안** 카드에서 사용자들이 등록한 제안을 검토합니다. 큐레이션 Q&A 카드와 마찬가지로 기본적으로 접혀 있고, 펼칠 때만 목록을 불러옵니다. 카드 제목 옆에는 **검토 대기 건수**가 빨간 배지로 표시됩니다(0건이면 표시되지 않음).

| 기능 | 방법 |
|------|------|
| 상태 필터 | 드롭다운에서 검토 대기(기본) / 등록 완료 / 반려 / 철회됨 / 전체 선택 |
| 내용 확인·검토 | 행의 아이콘 클릭 → 오른쪽 패널에서 제목·본문 **전문** 확인. **미리보기** 탭으로 넘기면 본문에 들어간 이미지가 실제 그림으로 보입니다 |
| 내용 수정 후 등록 | 같은 패널에서 제목·본문을 직접 고친 뒤 **임베딩 실행** — 고친 내용이 그대로 색인되고, 작성자에게도 이 내용이 보입니다 |
| 거부 | **거부** 버튼 → 사유 입력(필수) → 작성자에게 사유가 그대로 표시됨 |

- **임베딩 실행**을 누르면 그 자리에서 큐레이션 Q&A 항목으로 등록되고, 실제 임베딩은 백그라운드로 진행됩니다. 임베딩에 실패하면 목록의 제목 앞에 ⚠ 배지가 붙습니다 — 큐레이션 Q&A 카드에서 본문을 줄여 저장하면 다시 시도됩니다.
- **본문에 이미지가 있으면 임베딩 실행이 그만큼 오래 걸립니다** — 누르는 시점에 각 이미지를 Vision 모델로 읽어 설명 문장을 본문에 넣기 때문입니다(이미지 내용까지 검색에 걸리게 하려면 설명이 색인되는 텍스트의 일부여야 합니다). 그동안 버튼은 잠기고 "등록 중..."으로 바뀝니다. 이미지가 여러 장이면 수십 초가 걸릴 수 있으니 창을 닫지 말고 기다리세요. 이미지 설명 기능이 꺼져 있거나 Vision 호출이 실패하면 설명 없이 그대로 등록됩니다(승인이 실패하지는 않습니다).
- 이미지 개수 상한(본문당 10장)을 넘긴 제안은 **임베딩 실행이 400 오류로 거부**되고 사유가 토스트로 표시됩니다. 본문에서 이미지를 줄인 뒤 다시 시도하세요.
- ⚠️ 검토 시 **본문 이미지도 함께 확인하세요.** 승인은 글뿐 아니라 그 이미지까지 검색 결과로 나가도 좋다는 허가이며, 이미지에서 생성된 설명 문장도 그대로 색인됩니다.
- 이미 처리한 제안은 읽기 전용으로만 열립니다. 등록한 뒤 마음이 바뀌면 **큐레이션 Q&A** 카드에서 해당 항목을 삭제하세요 — 작성자 화면에는 "회수됨"으로 표시됩니다.
- ⚠️ **검토는 사용자가 쓴 글이 검색 근거로 LLM 프롬프트에 들어가기 전 유일한 관문입니다.** 그래서 본문은 항상 잘리지 않고 전문이 표시되며, 일괄 승인·자동 승인 기능은 의도적으로 제공하지 않습니다. 등록 전에 내용을 반드시 읽어보세요.

### 2.6 지식 제안 (청크 직접 추가)

문서에는 없지만 검색으로 찾을 수 있으면 좋겠는 내용(사내 노하우, 자주 나오는 질문의 답 등)을 **직접 등록**할 수 있습니다. 상단 메뉴의 **지식 제안**을 클릭하면 등록 화면(`/curated/submissions`)이 열립니다.

등록한 내용이 바로 검색에 반영되지는 않습니다 — 관리자가 검토한 뒤 **임베딩 실행**을 해야 검색에 들어갑니다.

**등록 방법**:

1. **제목** — 이 내용이 무엇에 대한 것인지 한 줄로 (최대 200자)
2. **태그** (선택) — 쉼표로 구분. 입력창 아래 **기존 태그** 칩을 클릭하면 바로 추가됩니다(문서에 쓰인 태그와 다른 사람이 제안에 쓴 태그가 모두 나옵니다)
3. **본문** — 검색 결과로 제공되었으면 하는 내용. **마크다운**으로 쓰고, 오른쪽 위 **미리보기** 탭으로 렌더 결과를 확인할 수 있습니다
4. **이미지** (선택) — 아래 "본문에 이미지 넣기" 참고
5. **등록** 버튼

> **제목을 잘 쓰는 것이 중요합니다.** 제목은 검색할 때 질문과 맞춰보는 부분으로 쓰입니다. "VPN"보다 "사내 VPN 접속이 안 될 때 확인할 것"처럼 **질문에 가까운 제목**일수록 잘 검색됩니다.

**본문에 이미지 넣기**:

본문 라벨 옆 **이미지 추가** 버튼으로 스크린샷·다이어그램을 넣을 수 있습니다.

- 이미지를 넣고 싶은 자리에 **커서를 두고** 버튼을 누른 뒤 파일을 고르면, 그 자리에 `[이미지: ...]` 한 줄이 삽입됩니다. **이 줄이 있는 위치가 곧 이미지가 표시될 위치**입니다 — 줄을 잘라 다른 문단으로 옮기면 이미지도 따라갑니다. 지우면 이미지도 본문에서 빠집니다.
- **미리보기** 탭으로 넘기면 실제 그림으로 보입니다. 관리자 검토 화면도 같은 방식으로 보이므로, 미리보기에서 제대로 보인다면 관리자도 그대로 봅니다.
- png · jpg · gif · webp, 파일 하나당 **5MB**, 본문 하나당 **10장**까지.
- **이미지도 검색에 걸립니다.** 관리자가 임베딩을 실행할 때 각 이미지의 내용을 자동으로 읽어 설명 문장을 만들어 본문에 넣어 주기 때문에, 그림 안의 내용으로도 이 제안이 검색됩니다(등록 완료 후 "내 제안"에서 보이는 본문에 그 설명이 함께 들어가 있습니다). 그러니 이미지에만 담긴 핵심 내용도 **글로 한 번 더 적어 둘 필요는 없습니다** — 다만 이미지 분석이 항상 정확하지는 않으므로, 꼭 검색돼야 하는 용어는 본문에도 쓰는 편이 안전합니다.
- 이미지를 넣은 제안은 관리자의 **임베딩 실행**이 조금 더 오래 걸립니다(이미지를 읽는 시간). 등록하는 쪽에서는 기다릴 일이 없습니다.
- 올리기만 하고 **등록하지 않은 이미지**는 서버에 잠깐 남았다가 나중에 자동으로 정리됩니다. 제안이 **반려·철회**되면 그 제안의 이미지도 함께 정리됩니다.

> **본문 길이 제한은 없습니다.** 긴 본문은 관리자가 등록할 때 문서와 똑같은 방식으로 **여러 청크로 자동 분할**되므로, 길다는 이유로 거부되거나 검색에서 누락되지 않습니다. 입력창 아래에는 글자 수와 **예상 청크 수**가 표시됩니다(대략적인 추정이며, 정확한 개수는 소제목 위치에 따라 달라집니다). 다만 **주제가 다른 내용은 나눠서 등록**하는 편이 검색 정확도에 유리합니다 — 한 제안의 모든 청크는 같은 제목·같은 태그를 공유하기 때문입니다.

> **태그의 의미**: 태그를 지정하면 채팅에서 **그 태그를 고른 검색에만** 이 내용이 반영됩니다. 비워 두면 태그를 무엇으로 고르든 항상 반영됩니다(스코프를 지정하지 않은 것으로 봅니다).

> 검토 대기 중인 제안이 20건을 넘으면 더 등록할 수 없습니다. 관리자가 처리한 뒤 다시 등록하세요.

**처리 결과 확인**:

같은 화면 아래 **내 제안** 목록에 등록한 제안과 현재 상태가 표시됩니다.

| 상태 | 의미 |
|------|------|
| **검토 대기** | 아직 관리자가 확인하지 않음 — 이 상태에서만 **철회**할 수 있습니다 |
| **등록 완료** | 검색에 반영됨 (관리자가 내용을 다듬었다면 다듬어진 내용이 표시됨). 몇 개 청크로 나뉘어 등록됐는지 함께 표시됩니다 |
| **반려** | 등록되지 않음 — 관리자가 입력한 **거부 사유가 전문 그대로** 함께 표시됩니다 |
| **철회함** | 본인이 취소한 제안 |
| **회수됨** | 등록됐다가 이후 관리자가 검색에서 제거함. 청크가 여러 개였다면 **전부 함께** 회수됩니다(일부만 남는 상태는 없습니다) |

- 등록 완료됐지만 내용이 너무 길어 검색 색인에 실패한 경우 "임베딩에 실패했습니다" 경고가 함께 표시됩니다 — 내용을 줄여 다시 등록하거나 관리자에게 문의하세요.
- **처리 알림**: 등록·반려 등 처리가 끝나면 상단 메뉴의 **지식 제안** 옆에 빨간 숫자 배지가 나타납니다(최대 1분 이내 갱신). **내 제안** 화면을 열면 확인한 것으로 처리되어 배지가 사라집니다.

> **로그인 없이 쓰는 배포에서의 주의**: "내 제안"은 방문자를 구분할 수 있어야 동작합니다. 운영자가 방문자별 구분을 켜두지 않았다면(기본값) 모든 사람의 제안이 한 목록에 함께 보일 수 있습니다 — 운영자 매뉴얼 §9.4.3 참고. 또한 브라우저를 바꾸거나 쿠키를 지우면 이전에 등록한 제안이 목록에서 보이지 않을 수 있습니다(삭제되는 것은 아닙니다).

### 3.6 질의응답 (채팅)

```bash
curl -X POST http://localhost:8080/api/v1/chat \
  -H "Content-Type: application/json" \
  -d '{
    "question": "Spring Security에서 JWT 인증을 어떻게 설정하나요?",
    "version": "latest",
    "thread_id": "user-session-001"
  }'
```

**요청 필드**:

| 필드 | 필수 | 기본값 | 설명 |
|------|------|--------|------|
| `question` | ✅ | — | 사용자 질문 (최대 2,000자) |
| `version` | — | `latest` | 검색할 문서 버전 |
| `thread_id` | — | `default` | 멀티턴 대화 식별자 |
| `response_mode` | — | `N` | 답변 성격 — `S`(간단히) / `N`(자세히). 알 수 없는 값(옛 `M`·`L` 포함)은 `N`으로 처리 (§2.2 참고) |
| `selected_tags` | — | `[]` | 검색 스코프 태그 배열. 지정한 태그를 **모두** 가진 문서만 검색 |

**응답**:
```json
{
  "answer": "## 요약\n...",
  "question_type": "usage",
  "sources": [
    {
      "label": "spring-security-guide.pdf | p.12",
      "preview": "Spring Security에서 JWT 인증 필터를 구성하려면...",
      "doc_id": "spring-security-guide.pdf_a1b2c3d4",
      "page_or_slide": 12
    }
  ],
  "total_input_tokens": 1248,
  "total_output_tokens": 512,
  "llm_call_count": 4,
  "elapsed_seconds": 3.2
}
```

> **`sources[].label` 형식**: 청크가 속한 헤딩의 챕터 번호(H2~H6 기준, 예: `1.5.3`)가 있으면 `"파일명 | 1.5.3"`, 없으면(헤딩 이전 구간·PPTX·PDF는 항상 이 경우) `page_or_slide`로 폴백해 위 예시처럼 `"파일명 | p.12"`로 표시됩니다. 문서 버전은 라벨에 포함되지 않습니다 — 필요하면 업로드 시 지정한 `version`을 별도로 관리하세요.

**질문 유형 (`question_type`)**:

| 값 | 설명 |
|----|------|
| `concept` | 개념·이론 설명 |
| `usage` | 사용법·코드 예시 |
| `error` | 오류·트러블슈팅 |
| `version` | 버전·변경사항 |
| `meta` | 인사·잡담 (RAG 미사용, 직접 응답) |

```json
  "answer": "...",
  "sourceTurnId": 123,
  "provider": "db-reuse"
}
```

- 검증 실패(자동 일반 질의 폴백 대상)

```json
{
  "reused": false,
  "fallback": true,
  "question": "로그인 오류 401 원인",
  "message": "청크 내용이 변경되어 기존 답변을 재사용할 수 없습니다."
}
```

#### 오류/폴백 응답 요약

| API | HTTP | 형태 | 처리 가이드 |
|---|---|---|---|
| `/api/v1/questions/suggest` | 200 | `[]` (빈 배열) | 입력이 2글자 미만이거나 추천 후보가 없으면 정상 응답으로 빈 목록을 반환 (저장 질문이 51자 이상이면 후보에서 제외) |

| 공통(예외 발생 시) | 4xx/5xx | RFC 9457 ProblemDetail + `errorCode` | [ERROR_CODES.md](ERROR_CODES.md) 기준으로 처리 (`RAG-VAL-001`, `RAG-INT-001` 등) |

> 참고: `scope` 파라미터를 보내도 서버는 현재 항상 `shared` 기준으로 처리합니다(하위 호환용 입력).

### 3.9 청크 원문 조회

채팅 화면에서 출처(Sources) 배지를 클릭하면 뜨는 "원문 보기" 팝업이 내부적으로 호출하는 엔드포인트입니다. `/api/v1/chat` 응답의 `sources[].preview`는 항상 잘린 미리보기 텍스트인 반면, 이 엔드포인트는 **잘리지 않은 청크 전체 원문**(이미지 마커 포함)을 반환합니다.

```bash
curl "http://localhost:8080/api/v1/chunks/{chunkId}"
```

`{chunkId}`는 `/api/v1/chat` 응답의 `sources[].chunk_id` 값입니다.

응답:
```json
{ "content": "## 소제목\n청크 전체 내용...\n[이미지: images/abc123/img1.png]" }
```

청크가 삭제되었거나 재인덱싱으로 더 이상 존재하지 않으면 `404`가 반환됩니다.

> 로그인 여부와 무관하게(관리자 전용이 아님) 조회할 수 있습니다 — 문서·큐레이션 Q&A는 모든 사용자가 공유하며, 이 내용은 어차피 채팅 검색 결과로도 이미 노출되는 정보이기 때문입니다.

## 4. 문서 인덱싱 동작

```
파일 업로드 or 폴더 동기화 (REST API)
  └─▶ SHA-256 계산 → doc_registry(SQLite, memory.db 공유)와 비교
        ├─ 신규 파일 → 로드 → [DOCX: MD 변환 → LLM 포맷 교정] → 청크 분할 → 키워드+맥락 추출 (LLM) → 벡터 스토어 추가
        ├─ 변경 파일 → 기존 청크 삭제 → 재인덱싱
        └─ 삭제 파일 → 벡터 스토어에서 제거

MD 재인덱싱 (/admin ↺ 버튼)
  └─▶ 저장된 교정 MD 읽기 → 결정적 정리(이미지 마커·소제목 번호·서식, LLM 미사용) → 청크 분할 → 키워드+맥락 추출 (LLM) → 기존 청크 삭제 → 벡터 스토어 추가
```

> **벡터 스토어**: `chroma`(기본) 또는 `sqlite-vec` 중 운영자가 선택한 백엔드로 저장됩니다(둘 다 동일한 사용자 경험).
>
> **DOCX 포맷 교정**: DOCX → Markdown 변환 직후 LLM이 섹션별로 잘린 문장·소제목 불일치·오타를 교정합니다. 원본(`{docId}.md`)과 교정본(`{docId}_corrected.md`) 모두 `data/converted/`에 저장됩니다.
>
> **키워드+맥락 추출**: LLM을 호출해 핵심 키워드 5개(`excerpt_keywords`)와 이 청크가 속한 맥락(`chunk_context` — 문서명·섹션 제목 + 짧은 설명, 검색 전용이며 화면에는 표시되지 않음)을 함께 생성합니다. 기본적으로 청크 여러 개(4개)를 한 번의 LLM 호출로 묶어 처리해 인덱싱 왕복 횟수를 줄입니다(운영자 설정, [PIPELINE.md §6.2](PIPELINE.md#62-단일-파일-인덱싱)).  
> 검색 품질(recall)이 높아지는 대신 인덱싱 시간이 늘어납니다.

### 4.1 형식별 청크 분할 전략

| 형식 | 로드 단위 | 분할 전략 | 이미지 처리 |
|------|----------|----------|------------|
| `.md` | `#` / `##` / `###` 헤더 단위 섹션 | 챕터(헤딩) 단위 — 짧은 챕터는 인접 챕터와 병합, 초과 시 슬라이딩 윈도우 (아래 주석) | URL 이미지 → alt 텍스트 유지, 로컬 이미지 → `[이미지: path]` 마커 |
| `.docx` | Word Heading 기준 섹션 → LLM 포맷 교정 후 MD 헤더 단위 재분할 | 챕터(헤딩) 단위 — 짧은 챕터는 인접 챕터와 병합, 초과 시 슬라이딩 윈도우 (아래 주석) | 인라인 이미지 추출 + EMF/WMF → PNG 변환 (설정 시) |
| `.pptx` | 슬라이드별 `[페이지: N]` 마커(제목이 있으면 `##` 헤딩 추가, 없으면 마커만) → LLM 포맷 교정 후 슬라이드 단위 재분할(1슬라이드=1섹션) | 섹션(슬라이드)이 `CHUNK_SIZE` 초과 시만 슬라이딩 윈도우 — 단, **서로 다른 슬라이드끼리는 병합되지 않음**("청크 1개=슬라이드 1개=정확한 인용" 유지) | 슬라이드 이미지 추출 + 본문에 `[이미지: ...]` 인라인(DOCX와 동일 — `addImageDescriptions` 적용됨) |
| `.pdf`(스캔 아님) | 페이지별 `[페이지: N]` 마커(합성 헤딩 없음) → LLM 포맷 교정 후 페이지 단위 재분할(1페이지=1섹션) | 섹션(페이지)이 `CHUNK_SIZE` 초과 시만 슬라이딩 윈도우 — 단, **서로 다른 페이지끼리는 병합되지 않음** | 임베드 이미지 추출 + 본문에 `[이미지: ...]` 인라인(DOCX와 동일 — `addImageDescriptions` 적용됨) |
| `.pdf`(스캔) | 페이지 1장 = 문서 1개 (텍스트 50% 이상 없으면 Tesseract OCR) | 슬라이딩 윈도우 (`CHUNK_SIZE` / `CHUNK_OVERLAP`, 섹션 병합 없음) | 임베드 이미지 추출; OCR 처리 (설정 시) |
| `.txt` | 전체 파일 = 문서 1개 → LLM 구조화 후 MD 헤더 단위 분할 | 챕터(헤딩) 단위 — 짧은 챕터는 인접 챕터와 병합, 초과 시 슬라이딩 윈도우 (아래 주석) | — |

> **슬라이딩 윈도우**: 청크 경계가 텍스트 중간이면 가장 가까운 줄바꿈(`\n`)으로 경계를 조정합니다.  
> `.docx` 헤딩이 없는 경우 전체 텍스트를 단일 문서로 처리한 뒤 슬라이딩 윈도우를 적용합니다.  
> **PPTX/PDF(스캔 아님)**: `[페이지: N]` 마커 자체가 슬라이드/페이지 단위 섹션 경계라, 제목이 없는 슬라이드/페이지는 합성 헤딩 없이 마커만으로 섹션이 나뉩니다(예전의 `"N번 슬라이드"`/`"N페이지"` 대체 헤딩은 페이지 번호가 이미 `page_or_slide`로 관리되어 본문에 노이즈만 남기므로 제거됨). 이미지만 있는 슬라이드/페이지도 유지됩니다 — 그래야 추출된 이미지가 청크에 붙을 자리가 남습니다. 제목·본문·이미지가 전부 없는 완전히 빈 슬라이드/페이지만 청크 자체가 생성되지 않습니다 — 상세는 [PIPELINE.md §6.3-bis](PIPELINE.md#63-bis-pptxpdf비스캔--md-변환--docx와의-차이점) 참고.

> **청크 분할 전략 두 가지**(운영자가 `/settings`에서 전환, 재기동 불필요): 기본은 아래에 설명된 **크기 기준 병합**입니다 — `MIN_CHUNK_SIZE`보다 짧은 챕터를 인접 챕터와 묶어 청크 크기를 채웁니다. **소제목 최대 분할**로 바꾸면 `MIN_CHUNK_SIZE`를 아예 보지 않고 소제목마다 잘라, 짧은 소절도 독립 청크로 남습니다("이 항목만 정확히 찾고 싶다"에 유리하고, 대신 청크 수가 늘어 인덱싱 시간·임베딩 호출이 증가합니다). 최대 분할에서도 **"제목 + 2문장 이내"인 도입부 챕터**는 바로 아래 하위 챕터와 합쳐지고(그것만 홀로 검색되면 쓸모가 없으므로), 표·코드 블록이 청크 경계에 걸리면 경계를 옮겨 최대한 통째로 유지하며, PPTX·PDF는 슬라이드/페이지를 넘어서는 병합을 하지 않습니다(1슬라이드 = 1청크 유지). **설정을 바꿔도 이미 인덱싱된 문서는 그대로**이고, `/admin`에서 ↺ 재인덱싱한 문서만 새 전략으로 다시 잘립니다 — 그래서 두 전략을 문서별로 바꿔가며 비교해 볼 수 있습니다. 자세한 내용은 [OPERATOR_MANUAL.md §6.10](OPERATOR_MANUAL.md#610-청크-분할-전략-크기-기준-병합--소제목-최대-분할).
>
> **챕터 단위 청킹(MD·DOCX·TXT)**: 아래는 기본(크기 기준 병합) 전략의 동작입니다. 문서를 헤딩(챕터) 단위로 나눕니다. `MIN_CHUNK_SIZE`보다 짧은 챕터는 바로 다음 챕터와 합쳐지되, 다음이 더 상위(부모) 챕터면 합치지 않고 대신 이전 청크 쪽으로 붙습니다. 또한 하위 챕터(`###` 이상 — `##`보다 더 깊은 레벨) 청크의 맨 앞에는 그 챕터가 속한 바로 위 부모 헤딩 한 줄이 함께 붙어, 청크만 봐도 어느 챕터의 내용인지 알 수 있습니다(최상위 `##` 챕터에는 붙지 않음). 검색 정확도를 위한 동작이며 답변·출처 표시 방식에는 영향을 주지 않습니다. PPTX·PDF는 이 병합 대신 슬라이드/페이지 단위를 그대로 지키되(아래 PPTX 동일 헤딩 슬라이드 병합 항목 참고), 그 외에는 슬라이드/페이지 경계를 넘어 병합되지 않습니다.

> **PPTX 동일 헤딩 슬라이드 병합**: 연속된 두 슬라이드가 같은 소제목(`##`+`###` 두 줄 모두)을 완전히 똑같이 달고 있으면 — 긴 내용을 두 슬라이드에 나눠 이어 쓴 경우 — 청크 크기를 넘지 않는 한 하나의 청크로 합쳐집니다. 두 번째 슬라이드의 반복되는 소제목 줄은 빠지지만, 그 자리에 페이지 표시가 남아 어느 슬라이드의 내용인지 계속 구분할 수 있습니다. 한 청크는 최대 2장까지만 합쳐집니다 — 같은 소제목이 3장 이상 이어져도 앞의 2장만 합쳐지고, 그다음 슬라이드부터는 새로 2장씩 묶입니다. 소제목이 하나라도 다르거나 합친 크기가 청크 크기를 넘으면 이 병합은 적용되지 않고 슬라이드별로 그대로 유지됩니다.

> **PPTX 중복·목차·구분·예고·종료 슬라이드 자동 제거**(기본 켜짐): 이미지가 없는 슬라이드 중 ① 내용이 완전히 같은 반복 슬라이드, ② 다른 슬라이드 제목들을 나열한 목차/agenda 슬라이드, ③ 본문 없이 "PART 2"·"3장 개요"·"결제 시스템"처럼 구분용 제목만 있는 섹션 표지 슬라이드, ④ 제목 한 줄만 있고 그 내용이 바로 다음 슬라이드에 그대로 반복되는 "예고 제목" 슬라이드, ⑤ 덱의 마지막 슬라이드가 "끝"·"END"·"The End"·"감사합니다"·"Thank you"처럼 종료 표시만 있거나 짧은 서명 정도만(종료 표시 외 10자 이내) 덧붙은 경우는 검색 인덱스에서 자동으로 제외됩니다(내용 없는 청크가 검색을 어지럽히는 것을 방지). 그래서 목차·표지·예고·종료 슬라이드 자체는 검색으로 찾지 못할 수 있으나, 각 항목의 실제 내용은 해당 섹션 슬라이드에서 그대로 검색됩니다. 단, "고객 만족을 최우선으로 합니다"처럼 문장형 제목만 있는 "키 메시지" 슬라이드나, 이메일·전화번호 등 종료 표시 외 내용이 10자를 넘는 마무리 슬라이드는 내용으로 보아 유지됩니다. 이 동작이 원치 않으면 운영자가 끌 수 있습니다([OPERATOR_MANUAL.md `PPTX_REMOVE_DUPLICATE_SLIDES`·`PPTX_DROP_DIVIDER_SLIDES`·`PPTX_DROP_REDUNDANT_TITLE_SLIDES`·`PPTX_DROP_ENDING_SLIDE`](OPERATOR_MANUAL.md)).

### 4.2 메타데이터

| 메타데이터 | 적용 형식 | 설명 |
|-----------|----------|------|
| `doc_id`, `filename`, `version`, `sha256` | 전체 | 공통 식별 정보 |
| `page_or_slide` | PDF, PPTX | 페이지/슬라이드 번호 (PPTX·PDF[스캔 아님]은 `[페이지: N]` 마커 단위로 정확히 귀속됨) |
| `section`, `heading` | MD, DOCX, PPTX, PDF(스캔 아님) | 섹션 번호·헤더 텍스트 — PPTX는 슬라이드 제목(제목이 없는 슬라이드는 빈 값), PDF(스캔 아님)는 합성 헤딩을 만들지 않으므로 빈 값 |
| `chapter_no` | 전체 | 계층적 챕터 번호(H2~H6 헤딩마다 레벨별로 증가, 예: `1`·`1.1`·`1.5.3`) — 출처(Sources) 라벨에 표시됨(§3.6 참고) 및 `/admin` 청크 테이블의 챕터 열에도 표시됨(§2.5 참고). 헤딩 이전 구간과 헤딩이 없는 문서는 `0`(두 화면 모두 빈 칸/페이지 번호로 대체). **PPTX·PDF(스캔 아님)는 항상 `0`**(PPTX 슬라이드 제목은 챕터 구조가 아니고, 비스캔 PDF는 헤딩 자체가 없으므로) |
| `excerpt_keywords` | 전체 | LLM이 추출한 핵심 키워드 5개 |
| `chunk_context` | 전체 | 검색(임베딩+키워드) 전용 맥락 헤더 — "{파일명} > {heading}" + LLM 1~2문장. 화면 표시·저장 텍스트에는 포함되지 않음 (Contextual Retrieval) |

버전별로 격리 저장됩니다 — chroma는 `manual_{version}` 컬렉션 분리(예: `manual_latest`, `manual_1_0`), sqlite-vec는 `version` 파티션 키를 사용합니다.

## 5. 문제 해결

### 답변이 없거나 "문서에서 확인되지 않음"

```bash
# 인덱싱된 문서 확인
curl http://localhost:8080/api/v1/documents

# 폴더 동기화 실행
curl -X POST "http://localhost:8080/api/v1/documents/sync?version=latest"
```

- 문서 미업로드 → `/documents` 페이지 또는 API로 업로드
- `version` 불일치 → 업로드와 채팅의 `version` 값을 일치시킴
- 스캔 PDF → 텍스트 레이어가 있는 PDF 사용하거나 운영자에게 OCR 활성화 요청

### 답변 품질이 낮음

- 검색 문서 수(`SEARCH_TOP_K`) 또는 청크 크기(`CHUNK_SIZE`) 조정 필요 → 운영자 문의
- 라우팅 모드를 `QUALITY_FIRST`로 변경 (채팅 화면 드롭다운)

### 이미지가 답변에 표시되지 않음

이미지 처리는 운영자 설정(`app.image-description.enabled=true`)이 필요합니다.  
운영자 문의 또는 [OPERATOR_MANUAL.md](OPERATOR_MANUAL.md)를 참고하세요.

### 이미지 썸네일을 클릭하면 "연결할 수 없음"으로 표시됨

PPTX 문서에서 추출된 이미지 링크가 열리지 않으면 해당 문서를 재업로드해 재인덱싱해 보세요. 자세한 원인은 운영자에게 문의하거나 [OPERATOR_MANUAL.md §8](OPERATOR_MANUAL.md#8-문제-해결)를 참고하세요.

### "현재 요청이 몰려 있습니다" 메시지가 표시됨

다른 사용자들의 질문이 동시에 몰려 서버가 잠시 여유가 없는 상태입니다. 시스템 오류가 아니라 일시적인 혼잡 안내이며, 몇 초 후 다시 질문하면 대부분 정상 처리됩니다. 이 메시지가 자주 반복된다면 운영자에게 동시 사용자 규모를 알려 설정 조정을 요청하세요.

### 답변이 토큰 단위가 아닌 한 번에 표시됨

일부 환경에서는 LLM 프로바이더 설정(`stream=false`)에 따라 토큰이 하나씩 나타나는 대신 전체 응답이 완성된 후 한꺼번에 표시될 수 있습니다. 기능 자체는 정상이며, 설정은 운영자가 변경할 수 있습니다.

### 업로드 실패 (422)

파일 내용이 확장자와 일치하지 않을 때 발생합니다. 원본 파일을 다시 확인하거나 올바른 형식으로 저장 후 재시도하세요.

### 업로드 실패 — "저장 공간이 부족합니다" (413)

운영자가 정해 둔 이 서버의 저장 총량을 다 쓴 상태입니다. 올린 파일 하나가 큰 것이 아니라 **더 넣을 자리가 없다**는 뜻이라, 잠시 기다렸다 다시 시도해도 결과는 같습니다. 안 쓰는 문서를 `/documents`에서 삭제하면 곧바로 자리가 나며(삭제한 문서의 원본은 복구용으로 잠시 보관되지만 이 사용량에는 잡히지 않습니다), 지울 것이 없다면 운영자에게 상한 조정을 요청하세요. 파일 하나가 너무 큰 경우(기본 200MB 초과)는 이것과 다른 안내가 뜹니다.

> 문서를 하나 올렸는데 사용량이 그보다 훨씬 많이 늘어나는 것은 정상입니다 — 인덱싱이 변환 마크다운과 슬라이드·페이지 이미지를 함께 만들고, 그쪽이 원본보다 클 때가 많습니다.

### 지식 제안 등록이 거부됨

[§2.6](#26-지식-제안-청크-직접-추가) 화면 상단에 빨간 안내가 뜨며, 입력하던 내용은 그대로 남아 있습니다.

- "제목이 너무 깁니다" → 제목은 200자까지입니다.
- "태그는 최대 …" → 태그는 10개까지, 각 32자까지입니다.
- "검토 대기 중인 제안이 이미 20건입니다" → 관리자가 처리한 뒤 다시 등록하세요.
- "본문에 넣을 수 있는 이미지는 최대 10개입니다" → 이미지 줄(`[이미지: ...]`)을 지워 개수를 줄이세요. 같은 그림을 두 번 넣었다면 그것도 2개로 셉니다.

> **본문 길이로는 거부되지 않습니다** — 긴 본문은 등록 시 자동으로 여러 청크로 나뉩니다.

### 지식 제안에 이미지를 올릴 수 없음

**이미지 추가** 버튼을 눌러 파일을 골랐는데 오류 토스트가 뜨는 경우입니다.

- "지원하지 않는 이미지 형식입니다" → png · jpg · gif · webp만 됩니다. SVG·BMP·HEIC 등은 png로 변환해 올리세요.
- "이미지 내용이 확장자와 일치하지 않습니다" → 파일 이름만 `.png`로 바꾼 파일입니다. 이미지 편집기에서 실제 png/jpg로 저장한 뒤 올리세요.
- "이미지가 너무 큽니다" → 파일 하나당 5MB까지입니다. 스크린샷은 보통 png로 저장하면 충분히 작아집니다.
- "저장 공간이 부족합니다" → 서버 전체 저장 상한에 걸린 것으로, 이미지 크기 문제가 아닙니다. 위의 "업로드 실패 — 저장 공간이 부족합니다"를 참고하세요.

> 이미지가 본문에는 `[이미지: images/submissions/…]` 한 줄로만 보이는 것은 정상입니다 — **미리보기** 탭에서 실제 그림으로 확인하세요.

### 등록한 지식 제안이 목록에서 사라짐

로그인 없이 쓰는 배포에서는 브라우저 쿠키로 방문자를 구분하므로, 브라우저를 바꾸거나 쿠키를 지우면 이전 제안이 조회되지 않습니다(서버에서 삭제된 것은 아니며, 이미 등록 완료된 내용은 검색에 계속 반영됩니다). 운영자에게 문의하세요.

### 질문 오류 (400)

질문이 2,000자를 초과하거나 비어 있을 때 발생합니다. 질문을 간결하게 줄인 후 재시도하세요.

### 연결 오류 / 서비스 미응답

```bash
curl http://localhost:8080/api/v1/health
```

응답이 없으면 운영자에게 서비스 상태를 확인 요청하세요.

서비스 첫 사용 시 순서대로 확인하세요.

- [ ] `GET /api/v1/health` → `{"status":"ok"}` 응답 확인
- [ ] `http://localhost:8080` 접속 확인
  - 인증 모드: `/login` 페이지로 리디렉션 → 로그인 또는 `/signup` 계정 생성
  - 비인증 모드 + 첫 실행: `/setup` 페이지로 리디렉션 → 관리자 계정 생성
- [ ] 샘플 문서 1개 업로드 성공 (`/documents` 또는 `POST /api/v1/documents`)
- [ ] 문서 목록에 업로드 문서 표시 확인
- [ ] 업로드 문서 관련 질문 응답 성공 + Sources 포함 확인
- [ ] 후속 질문 시 이전 맥락 반영 확인 (멀티턴)
- [ ] 대화 재진입 시 이전 메시지 버블 복원 확인 (`/chat/{threadId}`)
- [ ] KO/EN 언어 전환 동작 확인
- [ ] `/admin` 접속 → ChromaDB 컬렉션 및 청크 목록 표시 확인
