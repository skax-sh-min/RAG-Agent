# PITFALLS — 결정 근거 · 함정 · 실패 기록

`CLAUDE.md` 는 **자주 바뀌지 않는 것**만 담는다 — 스택, 구조, 파일의 역할, 규약, 하드 제약.
이 파일은 그 뒤에 있는 것을 담는다: **왜 그렇게 만들었는가**, **무엇을 시도했다가 틀렸는가**,
**무심코 고치면 무엇이 조용히 깨지는가**.

> **언제 읽나.** 여기 나온 파일을 고치기 **전에** 해당 항목을 읽는다. 대부분의 항목은 실제로 한 번
> 깨졌던 것의 기록이고, 겉으로는 불필요해 보이는 코드가 왜 거기 있는지를 설명한다. 규칙 자체는
> `CLAUDE.md` 에 한 줄로 남아 있으므로, **규칙만 필요하면 그쪽으로 충분하다.**

> **왜 나눴나.** `CLAUDE.md` 는 모든 세션 컨텍스트에 통째로 실린다. 사고가 날 때마다 그 기록을
> 거기 덧붙이면 파일이 무한정 자라고, 정작 매번 필요한 규칙이 서사에 묻힌다. 서사는 필요할 때만
> 읽으면 된다.

## 파일별 결정 근거와 함정

### `agent/AgentGraph.java`

State machine; skips CLASSIFIER when `questionType != null`; `run()` (blocking) + `runStreaming()`. **두 재시도 게이트는 다른 노드로 간다** — `sufficient=false`(질문에 답하지 못함) → RETRIEVAL(+`incrementRetrievalRetry()`), `grounded=false`(문서 밖으로 나감) → **ANSWER**. 후자에서 재검색은 임베딩 + MultiQuery 확장 호출을 쓰고 사실상 같은 집합을 받아오는 낭비이고, 근거가 아니라 답변이 문제이므로 답변만 다시 쓴다. **이 분기는 `AnswerService`의 `[직전 시도 메모]`가 있어야만 성립한다** — 프롬프트가 그대로면 온도 0에서 같은 답변이 그대로 재생성된다

### `agent/AgentState.java`

Immutable state record (`userId`, `locale`, `routingMode`, `premiumUpgraded`, `usedProvider`, `grounded`, `evalReason`, `envNote`, `directMode`, `selectedTags`, `responseMode`, `usedDocIndices`, `inventedSymbols`, `retrievalRetries`, `excludedDocIds`). **`retrievalRetries`는 `retryCount`와 별개다** — grounded 재시도가 RETRIEVAL을 건너뛰므로, 검색 escalation의 입력은 "몇 번 재시도했나"가 아니라 "검색을 몇 번 다시 했나"여야 한다. `excludedDocIds`는 턴 단위 누적이라야 교체가 전진한다(재시도마다 새로 계산하면 직전에 뺀 청크가 다시 올라온다). **레코드 컴포넌트를 추가하면 `AgentState.of()`의 위치 기반 생성자 호출도 함께 고쳐야 한다** — 빌더만 고치면 컴파일이 그 한 줄에서만 깨지고, 그 여파로 `AgentState`를 쓰는 모든 파일에 오류가 번져 원인이 묻힌다

### `controller/AdminController.java`

`/admin`, `/admin/chunks`; document re-index endpoint (async, SSE-tracked); `POST /admin/chunks/{id}/reindex` per-chunk re-embed+FTS (sync); §6.25 대화 목록 — `GET /admin/threads` (패널), `/admin/threads/{id}/turns` (드릴다운), `/admin/threads/{id}/delete-preview` + `DELETE /admin/threads/{id}` (삭제), `/admin/threads/turns/{turnId}/content` (원문 열람, 감사), `/admin/retrieval-metrics/turns/{turnId}/sources` (공용 출처 표). **전부 `/admin/**` 아래여야 한다** — `/api/v1/**` 는 CSRF 면제 + management-only 에서 게스트 개방이라 전 사용자 대화가 그대로 열린다

### `controller/SettingsController.java`

§6.13 — `GET /settings` (read view, guest-open, edit gated by `isAdmin`); `POST /admin/settings/update`/`reset` (inherit `/admin/**` ROLE_ADMIN gating) return the updated `fragments/settings-item :: item` HTMX fragment; `POST /admin/settings/context-window/reprobe` (§6.26 A5) re-asks every registered LOCAL provider for its context window and returns the whole providers table

### `service/SettingsService.java`

§6.13 (below); `providerRows()`/`setProviderEnabled()` filter to `LOCAL`-role providers only when `app.llm.default-routing-mode=LOCAL_ONLY` (`visibleProviders()`) — NORMAL/PREMIUM entries can still sit in `application.properties` for a future mode switch but routing never selects them in LOCAL_ONLY, so hiding them (with an explanatory hint on `/settings`) avoids config-vs-reality confusion; a hidden provider is also rejected as "unknown" by the toggle endpoint, not just invisible

### `controller/OperationsController.java` (턴 삭제)

`DELETE /ui/threads/{threadId}/turns/{turnId}` — 싫어요 확인 대화상자 전용. `clearHistory()`와 **같은 테이블 집합**(`turn_source_ref`/`turn_image_ref`/`conversation_turns`)을 `turn_id` 하나로 좁혀 지우므로, 그 세 테이블에 턴 단위 데이터를 새로 추가하면 `SqliteMemoryRepository.deleteTurn()`도 함께 고쳐야 한다. 삭제된 턴을 가리키는 `reused_from_turn_id`는 일부러 남긴다 — 그 컬럼을 읽는 SQL이 전부 LEFT JOIN + `"참조 원문 삭제됨"` 폴백이다. 확인이 피드백 저장보다 **먼저**라 삭제와 싫어요는 배타적이다 — 삭제를 고르면 피드백 PATCH 자체를 보내지 않는다. 이 엔드포인트가 부르는 `onTurnDeleted()`가 큐레이션 고아 행을 막는 유일한 장치이며, §10.11 이후 **좋아요 여부를 보지 않고 무조건** 부른다 — 엔트리의 존재가 피드백 값과 무관해졌으므로 `LIKE`를 확인하고 들어가면 나중에 마음이 바뀐 저자의 엔트리를 전부 놓친다

### `security/GuestIdentityResolver.java`

Per-visitor `userId` for no-auth mode (`app.auth.guest-identity` = `shared`/`ip`/`cookie`/`hybrid`), so separate visitors get separate chat threads instead of sharing one guest. **The only change personalization needed**: `thread_meta`/`conversation_turns`/`curated_qa.source_user_id` are already `userId`-keyed and every repository method already takes it (Phase 1 Step 1.4) — the isolation machinery was just being fed a constant. Ids are `guest-<12 hex>` = HMAC-SHA256(persisted secret, visitor key) — hashed so raw IPs never reach `thread_meta`/audit rows, prefixed so guest rows stay greppable (`WHERE user_id LIKE 'guest-%'`) for a later cleanup or hand-off to real accounts. `hybrid` reads the `rag_visitor` cookie (HttpOnly/SameSite=Lax/1y) when present, else derives from IP and bakes that as the cookie — surviving both an IP change (cookie wins) and a cookie wipe (same IP re-derives the same id). IPv6 keys off the /64 prefix (privacy extensions rotate the low 64 bits). `@ConditionalOnProperty` on the same `app.auth.enabled=false` flag as the filter, so real auth removes it from the context entirely — a derived guest id and a real login can never both be live. Document storage stays shared (`DocRegistry.SHARED`), unaffected

### `security/ClientIpResolver.java`

PLAN §6.19.3 — the single place deciding "this request's client IP" for both `RateLimitFilter` and `GuestIdentityResolver`. `X-Forwarded-For` is honored only when `app.trust-forwarded-for=true` (default false): the header is client-supplied on a direct-exposure deployment, so trusting it would let an attacker rotate it to refill their own rate-limit bucket or — once identity derives from IP — impersonate another visitor. Behind a proxy the flag must be ON or every visitor collapses into the proxy's own address

### `llm/IndexingOutputCap.java`

인덱싱/백그라운드 호출의 **출력 예약**을 작업 크기에 맞춰 좁힌다. 이 호출들은 per-call 옵션에 온도만 실어 와서 프로바이더 빈에 구워진 `app.llm.max-tokens` **전체**가 예약됐다 — `max_tokens` 는 상한이 아니라 예약이라(`프롬프트 + max_tokens ≤ n_ctx`) 그만큼 입력 자리가 사라진다. 창 20,480·`max-tokens=10000` 에서 MD 교정이 초과로 실패한 것이 이 조합이었고, **같은 프로퍼티가 `maxSectionChars` 까지 정하므로 입력과 예약이 함께 커진다**. `forRewrite()` 는 출력이 입력에 묶인 작업(MD 교정·txt→md)에 `TokenEstimator` 추정 × 1.5, `forFixed(ratio)` 는 응답 모양이 정해진 작업(키워드+맥락, 이미지 설명)에 `max-tokens` 의 비율. **모든 값이 `app.llm.max-tokens` 에서 파생된다** — 여기만 독립 상수를 두면 운영자가 그 값을 내려도 인덱싱 예약만 안 따라온다(절대값은 `MIN_OUTPUT_TOKENS` 하나뿐, `ResponseMode.maxTokens()` 의 256 바닥과 같은 성격). **너무 조이면 안 된다**: 재작성 응답이 잘리면 `MarkdownCorrectionService` 의 마커·펜스 검사에 걸려 그 섹션이 원문 그대로 남는다(우아한 폴백이지만 교정이 조용히 사라진다)

### `llm/PromptBudget.java`

입력 토큰 예산 = `창 − 출력 예약 − 여유(창의 10%, 최소 256)`. **`max_tokens` 가 상한이 아니라 예약**이라 창 크기만으로는 부족하다 — 서버가 `프롬프트 + max_tokens ≤ n_ctx` 를 검사한다. 여유를 두는 이유는 `TokenEstimator` 가 추정이고 한글 1토큰/글자는 실제 범위(1~2)의 아래쪽이라 **과소평가할 수 있기** 때문 — 예산에서 과소평가는 곧 초과다. `fitByPrefix()` 는 뒤에서부터 덜어낸다(검색 결과가 RRF 내림차순이라 뒤가 최저 관련도) **단 첫 항목은 예산을 넘어도 남긴다** — 문서를 다 버리면 프롬프트가 "문서를 찾을 수 없습니다" 가 되어 검색이 성공했는데도 모른다고 답한다. **창을 모르는 경우는 이 클래스가 다루지 않는다** — 호출부가 먼저 판단해 아무것도 자르지 않아야 한다(추측으로 근거를 버리는 것이 초과보다 나쁘다). `rewriteInputChars(창, 지시토큰)` 는 **재작성 작업**(MD 교정·txt→md 구조화)용 별도 식이다 — 그쪽은 출력 예약이 입력에 비례해(`IndexingOutputCap.forRewrite()` = 입력×1.5) 예산을 "예약을 먼저 빼고 남은 것"으로 잡으면 순환이 된다. `지시 + S + 1.5S + 여유 ≤ 창` 을 풀어 `S ≤ (창 − 지시 − 여유) / 2.5` 로 계산하며, 1.5 는 `IndexingOutputCap.REWRITE_HEADROOM_PERCENT` 를 그대로 읽는다(두 값이 갈라지면 예약과 입력이 서로 다른 비율을 믿는다)

### `llm/TokenEstimateCalibration.java`

`TokenEstimator` 의 추정을 **서버가 실제로 센 토큰 수**와 대조하는 관측 계층. 컨텍스트 입력 예산(`PromptBudget`)과 인덱싱 출력 상한(`IndexingOutputCap`)이 모두 "한글 1글자 ≈ 1토큰" **가정** 위에 서 있는데, 어휘가 큰 최신 토크나이저는 0.5~0.7 로 처리하기도 해 그러면 예산이 30~50% 빡빡해진다(멀쩡한 근거를 버린다). 반대로 1보다 크면 초과를 못 막는다. **데코레이터인 이유**: 프롬프트와 usage 를 동시에 보는 자리가 여기뿐이다 — `LlmRouter` 는 호출을 불투명한 클로저로 받아 프롬프트를 못 보고, 호출부는 서버가 센 토큰 수를 못 본다. **블로킹만 관측된다**(스트리밍은 usage 미제공) — 계수는 경로가 아니라 텍스트·토크나이저의 성질이라 그 표본으로 충분하다. **관측만 하고 예산을 자동 보정하지 않는다**: 표본 수에 따라 같은 질문이 다른 양의 근거를 받으면 재현이 안 된다

### `llm/TokenEstimator.java`

실제 토큰 수를 알 수 없을 때 쓰는 **단 하나의** 추정 가정: `CJK 글자수 × 1 + 나머지 글자수 / 4`. 예전에는 `LlmRouter.approxTokens()`·임베딩 폴백이 chars/4(영어 경험칙), `ResponseMode` 예산·`MAX_EVAL_EXCERPT_CHARS` 산정이 "한글 1토큰≈1글자"를 써서 **4배 차이 나는 두 가정이 공존**했고 한국어 스트리밍 사용량이 그만큼 적게 기록됐다. 지금 식은 그 둘을 **특수 케이스로 갖는다** — 순수 영어면 옛 chars/4 와 정확히 같아 회귀가 없고, 순수 한국어면 글자 수와 같다. 공백·구두점은 CJK 로 세지 않는다(세면 추정이 부풀어 예산을 과하게 깎는다). codePoint 단위라 이모지가 두 글자로 세어지지 않는다. **실제 usage 를 주는 경로(블로킹 호출의 `ChatResponse` 메타데이터)는 반드시 그 값을 쓴다** — 이건 스트리밍·usage 미보고 임베딩 서버처럼 그것을 얻을 수 없는 자리의 폴백이다

### `service/SettingsService.reprobeContextWindows()`

§6.26 A5 — 기동 시 한 번 탐지한 창은 낡는다(서버를 다른 `-c` 로 재시작, LM Studio 의 JIT 로딩). **버튼이지 타이머가 아니다**: 주기적으로 다시 물으면 같은 질문이 시각에 따라 다른 양의 근거를 받아 재현이 안 된다 — `TokenEstimateCalibration` 이 "관측만 하고 예산을 자동 보정하지 않는다"고 정한 것과 같은 이유이고, 창을 바꾼 사람은 자기가 바꾼 것을 알고 있다. **세 가지를 하지 않는다**: ① `context-size` 선언된 프로바이더는 묻지 않는다(관측이 의도를 덮어쓰면 못 박은 값이 버튼 한 번에 사라진다) ② 탐지 실패 시 이전 값을 **지우지 않는다** (알던 값을 "모름"으로 되돌리면 그 순간부터 입력 예산이 통째로 꺼져, 고치러 누른 버튼이 상황을 악화시킨다) ③ LOCAL 이 아닌 프로바이더는 대상이 아니다. **고치는 것은 입력 예산뿐** — 출력 예약은 `ProviderContextWindows.cappedMaxTokens()` 로 빈 생성 시점에 굳어 `MaxTokensCappingChatModel` 안에 들어가므로 새 창에서 그 값이 달라져야 하면 재기동이 필요하고, 그 사실을 `restartNeeded` 로 함께 돌려준다(조용히 넘기면 "재탐지했으니 괜찮겠지"라는 잘못된 안심이 남는다)

### `llm/ContextWindowProbe.java`

### `llm/MaxTokensCappingChatModel.java`

프로바이더별 `max-tokens` 상한을 호출자 옵션 위에 씌우는 데코레이터. **이게 없으면 프로바이더별 설정이 채팅 경로에서 무효다** — 빈의 `defaultOptions` 는 호출자가 옵션을 안 줬을 때만 쓰이는데, 블로킹 호출부(`AnswerService.answerOptions`/`evalOptions`, `DirectAnswerService`)는 매번 자기 `maxTokens` 를 실어 보낸다. 호출부를 고쳐 프로바이더를 알게 하는 방법은 안 된다: 누가 받을지는 `LlmRouter` 가 나중에 정하므로(역할·우선순위·차단·최소 부하) 미리 물어본 답은 낡을 수 있다. **내리기만 한다** — 더 작은 값은 그대로 두고(검증 호출의 2,048), 없던 상한을 만들지 않으며, 호출자의 옵션 객체를 복사해 쓴다. **상한은 `int` 가 아니라 `IntSupplier` 로 받아 호출마다 다시 계산한다**(§6.26 A6) — `app.llm.max-tokens` 가 핫 편집 대상이고 그 상한의 다른 입력인 컨텍스트 창도 `/settings` 재탐지(§6.26 A5)로 바뀌므로, 생성자에서 값을 받아 두면 둘 다 재기동 전까지 반영되지 않는다. 스트리밍은 `OpenAiApi.chatCompletionStream()` 직행이라 여기를 지나가지 않는다

### `llm/LlmRouter.java`

Provider selection by TaskType × RoutingMode; `route()`, `executeWithTracking()` (ungated, indexing/background), `executeGated()`/`acquirePermit()` (§6.12 — per-provider `Semaphore` concurrency gate for the interactive chat/query path; `tryAcquire` up to `app.llm.permit-wait-timeout-seconds` then throws `LlmBackpressureException`, HTTP 429, no circuit-breaker block); `executeGatedWithUsage()` — same gating, additionally returns `LlmResult(text, inputTokens, outputTokens)` read from `ChatResponse.getMetadata().getUsage()` so blocking per-turn callers (`AnswerService`, `ClassifierService.execute()`, `DirectAnswerService.execute()`) can accumulate real token counts into `AgentState` instead of `accumulateTokens(0, 0)`; streaming callers still can't read real usage and instead fold `LlmRouter.approxTokens()` (chars/4, same estimate `recordApproxUsage()` writes to `/llm-usage`) into the per-turn total; `localTier1Concurrency()` — summed in-use/capacity (`ConcurrencySnapshot`) across every `role=LOCAL, priority=1` provider not runtime-disabled via `/settings` — the "main" answer-serving local tier, excluding the `priority=0` MICRO_TEXT offload model (e.g. `local-fast`); `Optional.empty()` only when none are registered/enabled at all. A circuit-broken provider still contributes its full `concurrency` to `capacity` but that whole amount counts as in-use (not accepting anything right now) rather than being excluded — so a lone blocked LOCAL provider shows fully-saturated (e.g. `3/3`) instead of making the indicator vanish. Otherwise in-use is `capacity - Semaphore.availablePermits()` against a fixed `providerCapacity` map recorded at construction (concurrency is restart-required, never changes at runtime). Backs the header's `GET /api/v1/llm/concurrency` indicator (`OperationsController.getLlmConcurrency()`), which additionally folds in `EmbeddingConcurrencyTracker.get()` — embedding calls never acquire this gate at all (separate `EmbeddingModel` decorator chain), so without that the indicator would sit at 0 during indexing/search embedding regardless of load — and clamps the combined total to `capacity` (embedding concurrency is governed by separate limits, e.g. `EMBED_MAX_CONCURRENT_BATCHES`, that don't share this budget, so an unclamped sum could otherwise exceed it). The header JS bold-reds the number once in-use reaches capacity

### `llm/EmbeddingConcurrencyTracker.java`

Plain `AtomicInteger` in-flight counter for genuine outbound embedding calls (never negative, `get()` floors at 0). Incremented/decremented by `TrackingEmbeddingModel.call()` — the one decorator layer common to both the query-time cached path (`CachingEmbeddingModel`'s cache-miss/"owner" call) and the index-time path, which bypasses the cache entirely (`CachingEmbeddingModel.unwrapForIndexing()`) — so it observes every real embedding call regardless of which path triggered it

### `ingestion/ChunkSplitter.java`

Pure chunk-splitting/merging algorithm; no Spring bean deps, extracted from `DocumentIndexer`. **Two chunking strategies selected by `app.chunk-split-granular` (hot, applies on the next indexing / ↺ re-index)**: `false` (default) = everything described below — size-driven merging toward `chunkSize`; `true` = **최대 분할** (`splitChapterGranular()`), which splits at every heading and **never consults `minChunkSize`** (neither `mergeSectionsByChapter()` nor `backwardMergeShortChunks()` runs), so a short subsection stays its own chunk. Its one merge rule is `groupLeadInSections()`: a section that is a heading plus ≤2 content units (`isLeadInSection()` — units = `max(sentence-terminator count, non-blank line count)`, and any table row or code fence disqualifies it outright) folds forward into **strictly deeper** headings only, re-evaluated after each step so a heading ladder collapses only while every level so far is still lead-in text, never across a sibling/parent heading, a `PAGE_OR_SLIDE` boundary, or `chunkSize`. For pptx/pdf, granular skips only the **cross-slide** merges (`mergeIdenticalHeadingSlides()` + `mergeShortSections()`) and instead runs `joinSectionsWithinPage()`, which collapses each `PAGE_OR_SLIDE` group into one Document — heading lines are section boundaries in the loader too, so a titled slide arrives as a `"## 제목"` section plus a `"### 소제목"`+body section, and emitting those separately would produce a body-less title-only chunk. Net effect is a true 1 slide = 1 chunk; heading-based splitting never applies to these formats since their headings are slide titles, not chapter structure. Boundary handling is shared but parameterized: `blockToleranceFor(granular, chunkSize, overlap)` feeds `adjustEndForCodeBlock()`/`adjustEndForTableBlock()` — the default path passes `overlap` (unchanged, but note `app.chunk-overlap` now defaults to **0**, which makes both block guards no-ops and lets every straddling table/fence get cut), granular passes `max(overlap, chunkSize/2)` so a chunk may reach ~1.5×`chunkSize` to finish a block or end early to let one start the next chunk. **Two section-aware strategies** routed by filename (**and**, for PDF, `MetaKey.SOURCE_TYPE != "ocr"`): **chapter-structured** (md/docx/txt) → `splitChapterStructured()`/`mergeSectionsByChapter()`; **page-structured** (pptx/non-scanned pdf) → `mergeIdenticalHeadingSlides()` pre-pass then legacy `mergeShortSections()`; scanned PDF and any other extension get plain sliding window. **`mergeSectionsByChapter()`** (md/docx/txt): only a section still below `minChunkSize` (normalized length) forward-merges into the next, and **never into a higher/parent heading** (`next.level < accLevel`, level = leading `#` count) — then the next section's size decides: 규칙1 combined ≤ chunkSize → merge; 규칙2 next alone ≤ chunkSize → stop; 규칙3 next > chunkSize → merge only if prepending keeps the sliding-split's last piece ≥ `minChunkSize*1.5` (`rawSlidingPieces()` look-ahead, extracted from `slidingWindow()` so simulation and real split share boundaries). Each `SectionGroup` keeps the first section's metadata + original index — **except `MetaKey.CHAPTER_NO`**: if the starting section's chapter number is still the `"0"` prologue placeholder (no real H2+ heading seen yet — chapter counting in `DocumentLoaderService` only starts at H2, so a leading H1-title-only or heading-less section stays `"0"`) but the merge absorbed a later section that already carries a real chapter number, the group reports that first real number instead of `"0"` (`firstRealChapterNo()`) — otherwise a document opening with a short H1 title/intro would mislabel its first chunk as chapter `"0"` even though the merged content actually starts inside chapter 1. No-op (keeps `"0"`) when every merged section is still `"0"`, and no-op when the starting section already has a real chapter number (ordinary "first section's metadata wins" applies). `splitChapterStructured()` then sliding-splits oversized groups (+ `reinjectHeadingForSplitPieces()`), `prependParentBreadcrumb()` prepends the immediate parent heading (one level up) to the **first (non-tail) piece** of a child chapter (heading level ≥ 3; `##`/heading-less skipped), and `backwardMergeShortChunks()` folds any still-sub-`minChunkSize` chunk into the previous one (cross-section analog of `mergeTinyChunks()`). **`mergeIdenticalHeadingSlides()`** (pptx/pdf, runs first): groups raw sections into per-slide bundles by `MetaKey.PAGE_OR_SLIDE`, then merges consecutive slides whose assembled `##`+`###` heading pair is **exactly identical** (both levels must be present — never true for non-scanned PDF, which emits no headings) into one chunk, up to `MAX_IDENTICAL_HEADING_MERGE_SLIDES` (default **2**) slides per group, as long as the combined normalized size stays `≤ chunkSize` — once a group hits the cap the next slide starts a fresh group of its own (4 identical-heading slides in a row → two 2-slide chunks, not one 4-slide chunk). Every slide after the first in a group has its duplicate `##`/`###` lines stripped (`stripDualHeadingLines()`) but gets a `[페이지: N]` text marker inserted in their place so the merged chunk still shows where each slide's content began (the merged `Document`'s `PAGE_OR_SLIDE` metadata itself still only reflects the first slide, same "first section's metadata wins" convention as everything else here). **`mergeShortSections()`** (pptx/pdf) then merges by 40%/75%-of-chunkSize thresholds and refuses to merge across a `MetaKey.PAGE_OR_SLIDE` mismatch (no-op for md/docx/txt) so PPTX/PDF keep a "1 chunk = 1 slide/page = exact citation" guarantee. Size-budget checks (`mergeSectionsByChapter`/`mergeShortSections`/`enforceMaxChars`) measure normalized length (`MarkdownNoiseNormalizer`) — `slidingWindow()`/`rawSlidingPieces()` and offset-based helpers stay on raw text. `mergeTinyChunks(chunks, minLength, maxOverlap)`'s **`maxOverlap` must be the real sliding-window `overlap`**, not `minLength` — it is how many characters of a join `mergeAdjacentText()` may treat as duplicated and delete, and only the overlap region can legitimately be duplicated. Passing `minLength` (as it did before) made the join scan up to `min-chunk-size` (default 500) chars for a matching suffix/prefix even at `chunk-overlap=0`, where pieces are disjoint — on repetitive content (repeated table rows, uniformly formatted list items) that match is coincidence and the text was silently lost. `maxOverlap <= 0` now joins verbatim. When `slidingWindow()` cuts a fenced code block across pieces, `reopenTruncatedBlock()`/`reopenCodeFence()` re-wrap each piece with the opening/closing fence plus a `CODE_CONTINUATION_BEFORE`/`CODE_CONTINUATION_AFTER` marker line (plain text **outside** the fence, never inside it) — these markers live in `Document.getText()` itself, so they're searchable (flow into `SearchTextBuilder`) and visible as-is in the `/admin` chunk view

### `model/SourceRef.java`

출처 1건. 뒤 5개 컴포넌트 중 `similarity`/`retrievalShare`/`axisRanks`는 **검색 진단 수치**(1단계, RETRIEVAL 시점 확정), `answerShare`는 **응답 참여도**(2단계, FINALIZE에서 사후 부착 — 검색 시점엔 존재할 수 없다), `staleStatus`는 **청크 변경 상태**(3단계, 대화 기록을 다시 열 때만 채워짐). 전부 nullable — `null`은 "측정 안 됨"이지 0이 아니다(BM25/큐레이션 축에만 걸린 청크엔 유사도가 없고, DB 재사용·복원된 히스토리·확장 실패 폴백 경로엔 융합 상태 자체가 없다). 그 경로들을 위해 5-인자/8-인자 편의 생성자를 둔다; Jackson은 항상 canonical(10-인자)을 쓰므로 필드 추가 이전에 저장된 레코드는 null로 역직렬화된다. **`staleStatus`만은 `retrieval_metrics` blob에 저장되지 않는다** — "지금 이 순간의 DB 상태"라 굳혀두면 그 뒤 삭제된 청크를 영원히 정상으로 표시하게 되므로, 대화를 열 때마다 `turn_source_ref`에서 새로 계산한다(`RetrievalMetricsService.enrich()`가 병합 시 이 필드만 live 값을 보존). 배지 표시 여부·문구 판단은 전부 `staleBadge()` 하나에 있다 — 삭제는 항상, 수정은 `answerShare > 0`일 때만(§ 청크 변경 표시). 템플릿이 `${src.staleBadge}`로 읽는데 이건 레코드 컴포넌트가 아닌 일반 메서드라 SpEL 접근 가능 여부를 `SourceRefStaleBadgeTest`가 고정한다. **표시 순서는 `DISPLAY_ORDER`/`sortedForDisplay()` 하나에 있다** — 1순위 응답 참여도, 2순위 유사도, 둘 다 내림차순이고 `null`(미측정)은 뒤로. 검색 랭킹 1위가 답변에 한 글자도 기여하지 않는 일이 흔해 RRF 순서로 보여주면 목록 앞머리가 근거와 무관해진다. 적용 지점은 `FinalizeService`(참여도 부착 직후 — 1순위 키가 그때 생긴다)와 `RetrievalMetricsService.enrich()`(대화 기록, 병합 직후). **스트리밍만 예외**로 클라이언트가 같은 규칙을 한 번 더 구현한다(`chat-stream.js`의 `compareSourceOrder()`/`reorderSources()`) — 출처 이벤트가 답변보다 먼저 도착해 그 시점엔 참여도가 존재할 수 없으므로 유사도 순으로 먼저 그리고 `done`의 attribution이 붙는 순간 재정렬한다. 규칙을 바꾸면 양쪽을 함께 고쳐야 하며 자바 쪽은 `SourceRefDisplayOrderTest`가 고정한다

### `service/QuestionReuseService.java`

§ 질문 재사용 — 과거 턴의 답변을 LLM 호출 없이 재사용(`/api/v1/questions/reuse`)하고, 그 답변이 아직 유효한지 판정한다. 턴 저장 시 `recordTurnSources()`가 검색된 청크의 `(chunk_id, sha256(chunk_fts.content), answer_share)`를 `turn_source_ref`에 스냅샷하고, 재사용 직전 `validateTurn()`이 현재 해시와 대조한다. **검증 대상은 검색된 청크 전부가 아니라 답변에 지분이 있었던 청크**(`answer_share > 0`) — topK개가 검색돼도 답변을 실제로 떠받친 건 보통 두세 개라, 한 글자도 반영 안 된 청크의 수정으로 멀쩡한 답변을 폐기하면 문서를 손볼 때마다 재사용이 통째로 무력화된다. 지분을 아는 행이 하나도 없으면(컬럼 추가 이전 기록, 귀속이 `Method.NONE`) 예전처럼 전체를 검증한다 — 차단의 폴백은 항상 엄격한 쪽

### `repository/QuestionReuseRepository.java`

`turn_source_ref` 테이블(런타임 멱등 DDL + 방어적 `ALTER TABLE`로 `answer_share`/`invalidated_at` 추가). `status`는 `active`/`deleted`/`modified`(옛 버전은 무효화에 `inactive` 하나만 썼다 — 상태 판정이 전부 `= 'active'` 비교라 남아 있는 레거시 행도 자동으로 무효 쪽으로 읽히고, 그래서 마이그레이션이 없다. 쓰는 메서드는 `markSourceRefsStaleByChunkIds()`이고 이름이 값과 어긋나 있던 옛 이름 `markSourceRefsInactiveByChunkIds`에서 바뀌었다) — 재사용 차단에는 둘 다 같게 작용하지만 배지 규칙이 다르다. `modified`는 `active` 행만 갱신하고 `deleted`는 무조건 덮어쓴다(수정 후 삭제된 청크의 최종 상태는 삭제여야 하므로). `findAllSourceRefs()`가 `findSourceRefs()`와 별도로 있는 이유: 후자는 `status='active'`만 주는데, 지분 없는 청크를 무효화하면 그 목록이 줄어들고 빈 목록은 "출처 없음 → 재사용 불가"로 읽혀 지분 스코프가 막으려던 차단이 그대로 일어난다. `findSourcePreviewRows()`에는 **status 필터가 없다** — 무효화된 출처를 걸러내면 대화 기록에서 배지가 아니라 출처 자체가 조용히 사라진다. 반대로 **`hidden_at`은 걸러낸다** — 채팅 원문 보기 모달의 "현재 대화에서 이 청크 제거"(응답 참여도 0%인 출처에만 노출, `PATCH /ui/threads/{threadId}/turns/{turnId}/sources/exclude`)가 세우는 컬럼으로, 사라지는 것이 사용자가 직접 요청한 결과다. `status`와 별도 컬럼인 이유: `status`는 "청크가 그 뒤 바뀌었나"라는 사실 관측이고 재사용 검증이 그 값에 의존하는데, 숨김은 표시 취향이라 같은 컬럼에 섞으면 화면에서 치웠다는 이유만으로 재사용 판정이 달라진다 — 그래서 `findSourceRefs()`/`findAllSourceRefs()`는 `hidden_at`을 보지 않는다(`QuestionReuseSourceHideTest`가 고정)

### `service/DocumentBackupCleaner.java`

§6.15 — retention for `data/documents/backup/`, where `RagService.archiveSourceFile()` moves a deleted document's original (deleting never removed the source, and nothing ever cleaned this up). The other half of `StorageQuotaService`'s decision to exclude that directory: the cap can only ignore those bytes safely if something bounds them. **Three rules in order**, each seeing what the previous left: (1) newest archive per original filename — this is what actually bounds a repeated upload→delete loop, the other two are backstops; (2) older than `app.upload.backup-retention-days` (default 30); (3) still over `app.upload.backup-max-size` (default 2GB) → oldest first. **These two are the only settings in the app whose unset value is a default rather than "unlimited"** — the cap itself is safest off by default, but a backup directory nobody can see or delete from any screen fills silently. **Only names matching `{base}_{yyyyMMdd_HHmmss}{ext}` are ever deleted**; a file the operator put there counts toward rule 3's measurement but is never removed (an unreachable cap is logged, not force-resolved). Timestamps are parsed from the filename, not `lastModifiedTime`, so a copy or restore can't reset them. Runs on `ApplicationReadyEvent` and after each archive; every failure is swallowed — retention must never fail the delete that triggered it

### `service/StorageQuotaService.java`

§6.15 — the deployment-wide storage cap (`app.upload.max-total-size`, **0 = unlimited, the default**). Consulted by both document upload entry points (`DocumentController.uploadDocument`/`uploadDocumentApi`, before `stageToTemp()` so a refused upload writes nothing) and by `CuratedImageStore.store()` — that one is the only path where an unauthenticated caller writes a binary to disk, so leaving it out would be the obvious way around the cap. **Measures three trees, not one**: `{dataDir}/documents`, `converted/`, `images/` — indexing's converted MD and extracted images routinely dwarf the uploaded original (PPTX, scanned PDF), so a cap that counted only `documents/` would miss most of what an upload actually consumes. Everything else under `data/` (SQLite files, audit logs, the Chroma volume) is not upload-driven and is excluded. **A soft cap by design**: only the incoming file's size is knowable at admission (the derived artifacts don't exist yet and can't be predicted), so one upload can finish over the line and the *next* one is refused — the alternative is aborting mid-index or guessing an expansion factor, and a wrong guess rejects uploads that would have fit. Usage is a disk walk, never a counter column, so any deletion (admin, sync, manual `rm`) frees space without knowing quotas exist; the walk is **skipped entirely when no limit is set**, so the default deployment pays nothing. `/settings` renders 사용량/상한 read-only (view-only like `max-tokens` — it's deployment policy, and `Spec`'s numeric kind is `int`, which can't hold a GB-scale byte count) and reads `usedBytesCached()` (30s TTL), **not** `usedBytes()`: that page is guest-open in every auth mode, so rendering it must not give an unauthenticated visitor an unbounded directory walk per request. `checkCanAccept()` deliberately does not share that cache — a multi-file upload arrives back-to-back and a stale figure would wave several past the cap in a row. **The one excluded subtree is `documents/backup/`** (where deleting a document archives its original): counting it breaks the only remedy the cap's own error names, since deleting moves bytes *within* `documents/` and usage barely drops, with no screen able to reclaim the difference. That exclusion is only safe because `DocumentBackupCleaner` bounds the directory — change one and you must change the other

### `service/AnswerAttribution.java`

2단계 응답 참여도 — 답변 문장을 가장 닮은 청크에 배정하고 글자수 비율을 몫으로 낸다. 순수 클래스(Spring 의존 없음, `ChunkReassembler` 선례), 추가 LLM/임베딩 호출 0회. **한국어라 문자 4-gram**(공백 토큰화는 조사/어미를 잘못 끊어 "포트를"↔"포트는"이 안 잡힌다) + **희소도 가중 `1/문서빈도`**(없으면 같은 문서 청크들이 머리말·breadcrumb 같은 보일러플레이트로 비슷해져 몫이 "가장 긴 청크"로 쏠린다). 매칭 안 된 문장·마크다운 헤딩 줄은 **분모에서 제외** — 모델이 자기 말로 쓴 연결 문장을 억지로 배정하지 않는다. `usedDocs` 인용 신호는 **후보를 좁히기만** 하고 몫을 만들지 않는다(인용했어도 답변이 안 닮았으면 0). **추정이지 측정이 아니다** — 인과적 기여도는 leave-one-out뿐이며 오프라인 하네스(OPERATOR_MANUAL §6.6) 영역

### `service/AnswerService.java` (축소 재시도)

**사전 예산이 빗나가면 문서를 조금씩 덜어내 다시 시도한다** (`withShrinkRetry()`, 초과 1회당 `app.llm.shrink-step` 개(기본 **1**), 상한 `MAX_SHRINK_ATTEMPTS`=5 → 기본 조합에서 topK=10 이면 10→9→8→7→6→5). **처음엔 이진 축소였다가 선형으로 바꿨다** — log(n) 왕복은 왕복만 세고 버려지는 근거를 세지 않는다. 사전 예산이 이미 창에 맞춰 놓은 뒤라 여기까지 오는 초과는 대개 아슬아슬하고(`TokenEstimator` 오차의 정상 범위가 0.75~1.35), 그런 초과에 반을 자르면 한 개면 됐을 자리에서 다섯 개를 버린다. 대신 왕복이 늘어 상한이 필요하고, `shrink-step × MAX_SHRINK_ATTEMPTS` 가 **도달 가능한 최대 축소폭**이다. 이력은 여전히 반씩 줄인다 — 턴 길이가 제각각이라 "몇 개"라는 단위가 없다. **여기 있는 이유**: `LlmRouter` 는 호출을 불투명한 클로저로 받아 프롬프트 안을 못 보므로 무엇을 버릴지 아는 곳이 여기뿐이다 — 라우터의 프로바이더 순회("다른 곳에 물어본다")와 층이 달라 서로 방해하지 않는다("더 작게 물어본다"). **초과 판정은 두 모양을 다 본다** — 블로킹은 라우터가 `LlmContextOverflowException` 으로 바꿔 주지만 스트리밍은 `OpenAiApi` 직행이라 날것이 올라오므로 `LlmRouter.isContextOverflow()` 가 `public` 이다(마커 목록을 복사하면 한쪽만 고쳐진다). **지켜야 할 세 가지**: (a) 성공한 단계로 `withBudgetNote(state, level)` 를 **다시** 세운다 — 안 그러면 화면은 0단계 기준으로 안내하고 모델은 그보다 적게 봤다는 상태가 남는다. (b) 검증 축소는 `buildEvalExcerpts(..., totalAvailable)` 로 **원본 문서 수**를 넘겨 `trimmed()` 를 참으로 유지한다 — 그래야 `unreliableNegative()` 가 그 `grounded=false` 를 판정 없음으로 떨어뜨린다(줄인 목록 크기를 전체로 쓰면 `.limit(5)` 사고가 되살아난다). (c) 스트리밍은 **토큰이 하나라도 나갔으면** 재시도하지 않는다(화면에 앞부분이 두 번 찍힌다). 초과가 아닌 예외는 절대 재시도하지 않는다

### `service/CancellableTokenStream.java`

두 스트리밍 경로(`AnswerService.streamDirect()`, `DirectAnswerService.callOrStream()`)가 LLM 토큰을 소비하는 **유일한** 방법. `flux.toIterable().forEach(sink)` 를 **예외로 벗어나도 업스트림 구독은 취소되지 않는다** — 반복자를 버릴 뿐이라 LLM 쪽 HTTP 응답은 계속 소비되고, 로컬 LLM 은 화면이 "사용자가 중단함"을 띄운 뒤에도 계속 생성한다(관찰된 증상). 실측: 5ms 간격 스트림을 3번째 토큰에서 던지는 소비자로 받으면 `doOnCancel` 이 끝내 안 불리고 생산이 63개까지 계속 늘었다; 구독을 붙잡아 두고 실패 시 `cancel()` 하면 4개에서 멈춘다. **중단 신호가 두 갈래인 것이 함정** — 클라이언트 abort 는 `emitter.send()` 실패와 `worker.interrupt()` 를 동시에 일으키는데, 인터럽트만으로는 부족하다(반복자가 *대기 중*일 때만 Reactor 가 그걸 보고 취소하는데, 토큰이 계속 도착하는 동안엔 대기하지 않고, 애초에 send 실패가 먼저 터져 스레드는 이미 반복자 밖이다). 그래서 예외 경로에서 직접 취소하고 토큰 사이 인터럽트 플래그도 함께 본다. 호출부의 예외 처리는 예전과 동일 — 달라지는 건 LLM 연결이 실제로 끊긴다는 점뿐. `CancellableTokenStreamTest` 가 실제 `doOnCancel` 발화를 확인하고, 같은 파일의 규약 가드가 운영 코드의 `toIterable()` 재등장을 막는다(이 클래스만 예외)

### `service/RetrievalService.java`

Batch MultiQuery search → RRF fusion; **retry escalation은 두 축이며 `app.search-retry-escalate` 플래그 하나가 둘 다 켜고 끈다** — 후보 풀 `candidateK = min(round(topK×(1+0.5×retrievalRetries)), topK×3)`, 최종 컷 `effectiveTopK = topK + retrievalRetries`. **escalation 의 입력은 `retryCount` 가 아니라 `retrievalRetries` 다** — grounded 재시도는 RETRIEVAL 을 건너뛰므로(`AgentGraph`), retryCount 를 쓰면 검색하지도 않은 만큼 escalation 이 앞서 나간다. 후보 풀 배수를 ×2 → **×1.5** 로 낮춘 것은 `RetrievalEviction` 이 최종 컷의 1/3 을 비워 주기 때문이다(그 자리를 채울 만큼 ≈×1.3 이면 되고, 풀을 키우는 것도 공짜가 아니다 — 융합·태그 필터·리랭크가 그 위에서 돈다). **최종 컷 +1 은 컨텍스트 여유가 있을 때만 적용된다**(`hasContextHeadroomFor()`). 기준이 답변 호출이 아니라 **검증 호출**인 이유는 넘칠 때 나는 사고가 컨텍스트 초과가 아니라 조용한 품질 저하이기 때문 — 발췌가 잘리면 `unreliableNegative()` 가 `grounded=null` 로 떨어뜨려 **재시도를 거듭할수록 판정이 사라진다**. 직전 답변(`state.answer()`)을 실측 재료로 쓰고, 창을 모르면 늘린다(늘리는 쪽이 기존 동작이라 모르는 상태에서 동작을 바꾸지 않는다 — "창을 모르면 아무것도 하지 않는다"는 추측으로 *줄이지* 말라는 뜻이다). 재시도에는 `evalReason` 이 **검색 축 하나로 추가**된다(LLM 왕복 0회 — 확장기는 빈 생성 시점에 프롬프트가 고정돼 per-request 로 바꿀 수 없지만, 사유 문장 자체가 '못 찾은 것'을 이름으로 부르고 있어 질의로 쓸 만하다). 원 질문 축은 그대로라 사유가 엉뚱해도 그 축 순위만 나빠진다. 밀려난 청크(`state.excludedDocIds()`)는 **최종 컷 전에** 제거된다 — 자리를 비우는 것이 목적이라 컷 뒤에 걸면 다음 후보가 올라오지 못한다. 후보 풀만 키우면 최종 자리를 놓고 경쟁하는 문서만 바뀔 뿐 답변 노드가 받는 문서 수는 매번 topK 그대로라, 재시도가 끌어올리려던 근거가 컷 바로 뒤에 있으면 재시도가 같은 이유로 다시 실패한다. 최종 컷은 답변/평가 프롬프트가 실제로 나르는 양이므로 후보 풀처럼 배수가 아니라 **가산**이다. `candidateK`는 `max(candidateK, effectiveTopK)`로 보정되고(topK=1 같은 극단 설정 방어), expansion 실패 폴백 경로도 같은 `effectiveTopK`로 자른다 — 안 그러면 expansion LLM 호출을 놓친 시도만 조용히 강등된다; optional rerank via injected `Optional<RerankerService>`; `execute(state, listener)` overload (blocking path uses `execute(state)` → `GraphListener.NOOP`) drives query-time Lazy Vision — `hasEmbeddedDescription()` filters out any image whose `[이미지: ...]` marker is already immediately followed by `[이미지 설명: ...]` in the chunk text (indexed with "이미지 설명 추가" checked) before calling `LazyVisionService.describeIfNeeded()`, so an already-described image is never re-analyzed and never gets a duplicate description appended by `augmentWithDescriptions()`. **검색 진단 수치(1단계)**: `mergeRrfScored()`가 융합 부산물로 `RrfMetrics(rrfScore, vectorSimilarity, axisRanks)`를 남기고(추가 LLM/임베딩 호출 0), 기존 `mergeRrf()` 오버로드들은 여기 위임 후 메트릭만 버려 랭킹은 비트 단위로 동일하다. 메트릭은 `Document` 메타데이터가 **아니라** `docKey` 기준 사이드 맵으로 나른다 — 검색 결과 문서는 답변 프롬프트와 벡터 스토어로 다시 흘러가므로 `MetaKey.SEARCH_TEXT`류의 "영속 전 stripping 필요한 임시 키"를 늘리지 않기 위함이고, 태그 필터·리랭크가 목록을 재구성해도 살아남는다. `addRrfAxis()`의 문서 선택은 `putIfAbsent`가 **아니다** — score를 가진 Document를 우선 보존한다(BM25 축 Document에는 score가 없어, 키워드 축이 먼저 도달한 청크의 유사도가 통째로 사라지던 버그)

### `service/QuestionCondenser.java`

§10.12 — 맥락에 기댄 **짧은 후속 질문**을 자립적인 검색어로 다시 쓴다. 검색 축 셋(벡터·BM25/FTS·큐레이션)이 전부 질문 원문을 보는데 이력은 답변 단계에서만 쓰이므로 `"그 설정은 어디야?"` 는 검색어로 의미가 없었고, 하필 그 길이 구간이 MultiQuery 확장에서도 빠져(`shouldExpand()`) **확장도 맥락도 없는** 최악의 조합이 거기 몰려 있었다. **MultiQuery 만 고치는 것으로는 안 된다** — 그러면 벡터 축만 나아지고 BM25·큐레이션은 여전히 원문을 토크나이즈해 절반이 틀린 채 남는다. 질문 자체를 다시 써서 `AgentState.searchQuestion` 에 실으면 한 번의 재작성이 세 축과 분류기를 함께 고친다.

**재료는 이전 *질문*들뿐이고 답변은 절대 넣지 않는다** — 이 파일에서 가장 쉽게 되돌려질 결정이고, 되돌리면 세 가지가 한꺼번에 깨진다: ① 답변은 2~3천 자라 `MICRO_TEXT` 계층에 무겁다 ② 답변의 표현이 질문에 섞이면 **검색이 자기 답변을 다시 찾는** 쪽으로 기운다(§10.11 이 큐레이션에서 경계하는 순환과 같은 모양) ③ **§10.13 이후 Direct 답변이 캡 없이 이력에 들어간다** — 모델이 지어낸 용어가 검색어가 되고, 그 위에 세운 답변이 다시 이력이 되어 용어를 굳힌다. 사용자가 직접 쓴 질문만 쓰면 그 오염 경로가 **구조적으로** 닫히므로 Direct 턴을 따로 걸러낼 필요가 없다 — 계획에 있던 `direct_mode`/`response_mode` 필터는 그래서 만들지 않았다.

**게이트가 순수한 것(길이만 본다)이 병렬성을 지킨다.** 분류는 독립화된 질문을 기다려야 하는데, 이력 로딩과 분류는 오늘 병렬로 돈다(`AgentService.chat()`). 게이트를 이력 없이 판단할 수 있으면 **긴 질문에서는 이미 완료된 future** 라 분류가 즉시 출발하고, 실제로 직렬화되는 것은 독립화가 필요한 짧은 질문뿐이다. 게이트가 이력을 읽어야 하는 모양으로 바뀌면 모든 턴의 분류가 DB 읽기 뒤로 밀린다.

**확장 게이트는 반드시 *원문* 길이로 잰다**(`shouldExpand(state.question())`). 독립화된 질의는 원문보다 길어지는 것이 정상이라 재작성 결과로 재면 확장까지 함께 돌아 **한 턴에 질의 전처리 LLM 호출이 둘**이 된다 — 이 항목이 "호출 순증 0"으로 성립하는 이유가 두 게이트가 정확한 여집합이라는 것 하나뿐이다.

on/off 스위치를 새로 만들지 않고 `app.search-multiquery-enabled` 를 공유한다(길이 임계값도 `app.search-multiquery-min-length` 를 그대로 쓴다) — 둘은 같은 성질의 호출이고 임계값은 이미 그 쌍의 경계다. 별도 임계값이 필요한지는 오탐 빈도를 본 뒤 판단한다(§10.12 열린 항목 (a)). 출력은 `MAX_OUTPUT_TOKENS`(256)로 따로 조인다 — 한 줄짜리 응답에 프로바이더의 `app.llm.max-tokens` 전체를 예약하면 좁은 창에서 `n_ctx` 를 넘기는 것은 프롬프트가 아니라 그 예약이다(§6.26, `AnswerService.MAX_EVAL_OUTPUT_TOKENS` 와 같은 이유). 응답이 상한(`MAX_CONDENSED_CHARS` 400자)을 넘으면 **잘라 쓰지 않고 버린다** — 그 길이는 모델이 질문 한 줄이 아니라 설명·목록을 냈다는 뜻이고, 앞부분만 잘라 쓰면 원문보다 나쁜 질의가 된다. 재료가 없거나·모델이 원문을 그대로 돌려주거나·호출이 실패하면 **원문으로 검색한다**(`withoutVerdict()`·`ProviderContextWindows` 와 같은 "모르면 아무것도 하지 않는다").

### `service/RetrievalEviction.java`

§ 재시도 개선 — 검증 실패 재시도에서 **어떤 청크를 밀어낼지** 정하는 순수 클래스(`AnswerAttribution`/`ChunkReassembler` 선례). escalation이 최종 컷을 재시도당 1개만 늘리므로, 관련 없는 청크를 그대로 둔 채 하나를 덧붙이면 새 근거가 죽은 무게와 경쟁한다 — 자리를 **비우는** 편이 낫다. **신호 둘이 동의할 때만 민다**: `usedDocIndices`에 없고(평가가 근거로 안 썼다고 보고) + RRF 하위 절반. 하나만으로는 안 되는 이유는 `usedDocs`가 방금 반려된 시도의 **자기 보고**이기 때문. **세 가드가 본체다** — ① 빈 `usedDocIndices`는 "전부 미사용"이 아니라 **"모른다"**(판정 실패·발췌 축소 경로가 그 값을 비운다) → 아무것도 안 민다 ② 발췌가 잘린 시도(`EvalExcerpts.trimmed()`)에서는 안 민다 — 잘린 문서는 `[Dn]` 번호를 못 받아 "안 쓰인 것"과 **"보이지도 않은 것"**이 구별되지 않는다 ③ 1순위는 절대 안 민다(`PromptBudget.fitByPrefix`가 첫 항목을 남기는 것과 같은 이유). 최대 1/3. **`sufficient=false` 전용** — `grounded=false`는 답변이 문서 밖으로 나간 경우라 근거를 빼는 것이 방향상 반대다. 판정은 `AnswerService.evaluate()`에서 내린다(세 입력이 거기에만 모여 있다)

### `service/HistoryPolicy.java`

§10.13 — `[이전 대화]` 에 **얼마나** 넣고 각 턴을 **무엇으로** 렌더할지 정하는 순수 클래스(`RetrievalEviction`/`AnswerAttribution` 선례). **한 곳에 모은 것이 요점이다**: 이력을 만드는 길이 둘(요약 경로의 `[Recent]` 블록, 폴백 경로의 `MemoryRepository.getHistory()`)이고 둘은 이미 서로 다르게 동작했다 — 그래서 같은 스레드가 **요약 캐시가 있느냐에 따라 다른 맥락을 보고**, 새 규칙을 한쪽에만 넣으면 캐시 TTL 이 지나는 순간 이력이 갑자기 달라진다. 예산 규칙은 **"Direct 라서"가 아니라 "문서 자리가 비어서"** 다: `이력 상한 = 입력 예산 − 문서가 차지할 자리`. 모드별 상수를 두 개 만들면 `topK` 를 낮춘 배포나 검색 결과가 적게 나온 턴으로의 일반화가 막힌다. **1차 적용이 Direct 뿐인 이유는 모드가 아니라 타이밍**이다 — 이력은 검색보다 **먼저** 로딩되고(`AgentService.chat()` 이 이력 로딩과 분류를 병렬로 돌린다) 그 시점에 문서가 몇 개 올지 모르는데, Direct 만 검색이 아예 안 돌아 0 이 확정이다(RAG 쪽 불확실성은 검색 후 도는 `AnswerService.fitToBudget()` 담당). 같은 이유로 **`meta` 분류는 여기서 Direct 로 세지 않는다** — 그 판정은 아직 병렬 스레드에서 계산 중이다. **확대만 하는 것이 아니다**: 좁은 창에서는 오늘의 고정 5,000자보다 작게 나오고 그것이 옳다(Direct 경로에는 예산 가드가 없어 그 5,000자가 이미 창을 넘기고 있었다) — 줄였으면 `budgetNote` 로 말한다. 렌더 규칙은 **두 축의 조합**이다: `askingDirect`(지금 묻는 턴)가 *얼마나*를, 이전 턴의 `response_mode` 가 *무엇을* 정한다 — S→`## 요약`(그게 답변 전부), N·C→`## 요약`·`## 참고` 뺀 본문, **DN→전문**(뺄 섹션이 없어 순효과가 캡 제거뿐이고 그것이 이 항목의 노림수). C 의 `## 검증되지 않은 부분` 은 남는다(`stripStructuralSections` 가 요약·참고만 건드린다). 분기는 `summaryOnly()` 로 한다 — 마침 정확히 S 만 참이라 새 성질을 만들지 않으며, `ResponseModeBranchConventionTest` 는 **텍스트 검사**라 주석에 모드 값 비교 패턴을 적는 것조차 빌드를 깬다. `RECENT_ANSWER_CAP`(1,200)은 RAG 로 물을 때만 걸리고 지우지 않는다 — §10.13 1단계(DN 도 `## 요약` 을 낸다)가 정상 경로에서 뺐을 뿐, 형식을 안 따른 긴 답변의 안전판이다. `trimToBudget()` 은 §6.26 에서 `AnswerService` 에 있던 것을 옮긴 것이고, Direct 경로도 같은 절단을 쓰게 되면서 구현이 하나로 모였다

### `export/ExportPreprocessor.java`

§ 문서 내보내기 — rewrites indexing markers into reader-facing markdown: `[이미지: ...]`/`[이미지(변환불가): ...]` → caller-supplied `(imagePath, ImageSpot) -> ImageReplacement` (bracket-depth scan, not line regex, since `[이미지 설명: ...]` spans multiple lines/paragraphs and can sit inline after a `<br>` inside a table cell). `ImageSpot` classifies the marker's position from the current line's prefix — `TABLE_CELL` (prefix starts with `|`, replacement must stay strictly inline or the row splits), `LINE_START`, or `INLINE` (a bullet, a half-written sentence). A rewriter answering `ImageReplacement.ownLine(...)` gets its replacement moved onto a line of its own everywhere except `TABLE_CELL`, with a bare `- `/`> ` prefix dropped (it would render as an empty bullet) and trailing whitespace trimmed — the earlier boolean `atLineStart` lumped bullets in with table cells, so a `- [이미지: ...]` line silently degraded to a `(이미지: 파일명)` text note in DOCX. `[페이지: N]`/`[도형 그룹]`/`[다이어그램]` dropped, `[차트: 라벨]` label kept; optional `applyHeadingNumbers()` (idempotent — strips any existing number first) + `buildToc()`

### `service/CuratedQaService.java`

§10.10 — a shared curated-Q&A knowledge axis (embedded under a reserved `"curated"` vector-store version namespace, survives doc re-indexing); fused into search via weighted RRF as **one axis** at `app.search-curated-qa-weight` (default **1.0**). §10.11 merged what used to be two axes split by `MetaKey.CURATED_ORIGIN` (`like` vs `manual`, each with its own weight): that split expressed "the app's own unreviewed output" vs "text a person wrote", and every entry now goes through the same human edit and admin approval, so `app.search-submission-weight` and the partition are gone. `CURATED_ORIGIN` itself stays — audit/statistics, not a search weight. `app.search-curated-qa-enabled` still gates the whole search; the admin moderates all entries from `/admin`'s curated card (page bottom, below the submission card) — `openCuratedEdit()` mirrors `openChunkEdit()`: same `EDIT_BASE_WIDTH * 2` threshold, same `renderChunkPreview()`, same 200 ms debounce, so the wide-screen live preview is one implementation used by both editors. **§10.11 — `onLike()` is gone.** Liking an answer wrote a `curated_qa` row on the spot and embedded it three seconds later, so the app had two doors into the search corpus guarded oppositely: a written proposal needed admin approval, a 좋아요 needed nothing, and a Direct answer grounded in no document could become everyone's search knowledge on one click. The chat now offers to open a 지식 제안 instead, and **the only writers are `createFromSubmission`/`createFromLikedTurn`, both reached only from `CuratedSubmissionService.approve`**. The debounce, the like re-check before embedding and the compensating delete after it went with `onLike` — all three made an accidental like cheap to undo before it became public, and an approval is an explicit one-way action with nothing to race. `onUnlike` became `onTurnDeleted` and fires only on turn deletion (unliking must not retract reviewed knowledge; deleting the turn still must, since the row is linked by a copy of the id, not a foreign key) — and that retraction is now **unconditional**, because checking for `LIKE` first would miss every entry whose author later changed their mind. `ResponseMode.allowsSubmission()` (ex-`allowsCuration()`) now means "does 좋아요 open the proposal form here", and only **S** is false — C was opened in §10.11 (what stops model-invented code from becoming the next turn's "document" is the review, not the mode exclusion) and S's own reason changed: not "stripping structural sections leaves nothing" (nothing is stripped from hand-edited text) but "S is deliberately abridged, so it is the wrong source to keep". **LIKE's second reader** is `QuestionReuseRepository`'s `DIRECT_NEEDS_LIKE_PREDICATE` — a Direct turn's answer may only be reused if its asker liked it — so declining the proposal dialog (which leaves no like) also keeps that turn out of reuse; accepted, since a like meaning two things depending on a dialog would be worse. The old rule — skip only the embed thread when `response_mode` is `L` — is gone with L itself (§6.24). the default embed text (`defaultSearchText()`) already excludes both the trailing `## 참고` (citation noise) and the leading `## 요약` (redundant once `## 상세 설명` carries the same content) sections via `CuratedTextUtils.stripStructuralSections()` (= `stripSummarySection()` ∘ `stripReferenceSection()`, both no-ops when their heading is absent, so a Direct-mode/meta answer with no fixed-section format passes through untouched). **긴 답변은 임베딩 시점에 분할된다** — `splitForEmbedding()`(문서와 같은 `ChunkSplitter`, `app.chunk-split-granular`까지 적용, 단 청크 크기는 `EMBED_CHUNK_SIZE_MULTIPLIERS`=**2.0→1.5→1.0**을 순서대로 시도하며 임베딩 실패 시에만 줄인다 — 큐레이션 텍스트는 하나의 논증이라 서버가 받아주는 한 크게 유지하는 편이 근거로 읽힌다; `minChunkSize`도 같은 배수로 함께 스케일해야 tiny-chunk 병합이 분할을 되돌리지 않는다)로 나눠 **DB 행 하나 → 벡터 N개**를 만든다. 제안 게시판(행 N개)과 달리 좋아요 출신이 행을 쪼개지 않는 이유는 `UNIQUE(source_turn_id)`·대화/턴 삭제 회수·재승인이 모두 turn 단위이기 때문 — `insertManual` 을 태우면 `source_turn_id` 가 `NULL` 로 박혀 그 셋이 조용히 함께 죽는다(§10.11 함정 ①). 승인은 또한 `source_submission_id` 를 반드시 실어야 한다(함정 ②): 제안의 상태가 전부 그 컬럼으로만 세어지므로 빠지면 오류 없이 제안이 현실과 끊긴다. 벡터 id는 첫 청크가 기존 `curated-<id>`(하위 호환, 제자리 덮어쓰기), 이후가 `curated-<id>-<i>`이고 개수는 `curated_qa.chunk_count`에 저장되어 de-index/재임베딩이 전부를 찾는다(재임베딩은 **새 벡터를 먼저 쓰고** 남은 것을 지운다 — 실패 시 기존 벡터가 살아 있도록). 질문은 모든 청크의 검색 텍스트에 반복 부여된다. **`stripStructuralSections()`는 자르기 '전'에 적용**된다 — 뒤로 미루면 인용 목록이 청크 경계를 넘을 때 뒤 조각에 `## 참고` 헤딩이 없어 스트립이 실패하고 인용만 담긴 벡터가 생긴다. 그 결과 **벡터의 저장 텍스트에는 요약/참고 섹션이 없다**(원문 전체는 `curated_qa.answer`에 그대로 남아 채팅·관리자 화면이 보여줌). `tryEmbedWithFallback()`는 3단 폴백 — 청크 → 답변 전체 1벡터 → 핵심 섹션만: 실패 시 좁혀 재시도하는 `상세 설명`/`예시·코드`/`설정·주의사항`-only slice (`CuratedTextUtils.extractCoreSections()` — same `stripStructuralSections()` pipeline plus emphasis-marker stripping, gated on a `## 상세 설명` heading actually existing) before giving up and marking `curated_qa.embed_status='failed'` — surfaced as a badge on the proposal (`/curated/submissions`) and in `/admin`'s curated panel — §10.11 removed the chat-side badge and the inline-edit pencil along with every other curation state in the chat window. The stored/displayed answer (`Document.getText()`) is never touched by any of this — only the derived `MetaKey.SEARCH_TEXT` override used for embedding. All three heading regexes (`참고`/`상세 설명`/`요약`) tolerate common LLM phrasing variants (e.g. `## 참고자료`, `## 상세 설명 및 배경`) as long as a `#` marks them as an actual heading — the hash-less bare-heading fallback for `참고` stays an exact match only, to avoid mistaking ordinary prose that starts a line with that word for a heading. Backed by `repository/CuratedQaRepository.java`

### `service/CuratedSubmissionService.java`

지식 제안 게시판 — users post a proposal (제목 + 본문), an admin later runs 임베딩 실행 or 거부. **§10.11 made this the only way into the search corpus**: a 좋아요 in chat opens this form prefilled from that answer (`?fromThread=&fromTurn=`) rather than publishing anything itself. Deliberately a **separate table** (`curated_submission`) from `curated_qa` rather than an extra status there: `curated_qa.status='active'` means "currently contributing to search", an invariant retrieval/moderation already relies on, and `UNIQUE(source_turn_id)` collides with turn-less manual rows. Approval copies the (admin-editable) text into real `curated_qa` rows and links them back — **through one of two paths, and picking the wrong one breaks things silently** (§10.11 함정 ①): a hand-written proposal goes to `createFromSubmission()` (N pre-split rows), a 좋아요 출신 one to `createFromLikedTurn()` (one row keyed by its turn, split into vectors at embed time). Pushing the latter through `insertManual` writes `source_turn_id = NULL`, which kills `UNIQUE(source_turn_id)`, the conversation/turn-delete retraction and the row's identity across a re-approval, all at once and with nothing failing. **The admin approval is the only gate between user text and the `[검색된 문서]` block of an answer prompt** (`PromptInjectionGuard.wrap()` delimits the user *question*, never search results) — hence no auto-approve/bulk-approve path anywhere and the review offcanvas always shows the body in full. 제목 lands in `curated_qa.question` because `defaultSearchText()` embeds `question + answer`; a body-only submission would barely match a question-shaped query. **No body length limit**: `approve()` runs the body through `ChunkSplitter` (`splitBody()`, a one-`.md`-document call, so `app.chunk-split-granular` and the table/code-block boundary protection apply) and creates **N** `curated_qa` rows, the same way a document is indexed — which is what removes the "임베딩 불가능한 본문" failure mode structurally rather than by rejecting input. The title is repeated on every chunk (`defaultSearchText()` embeds question+answer, so a chunk without it barely matches a question-shaped query). `chunkSizeForBody()` is only the form's "약 N개 청크" hint. Consequence: submission↔curated is **1:N**, so `Submission.displayStatus()` derives 회수됨 from an active-row **count** (전부/전무 — `CuratedQaService.forceRemove()` on any manual row takes down the whole submission via `forceRemoveBySubmission()`), and `curated_submission.curated_qa_id` is just the first chunk's pointer for the admin panel. Tags (`curated_submission.tags` → every chunk's `curated_qa.tags`) are validated by `TagUtils.normalize()` and admin-editable at review time. `MAX_TITLE_LEN`=200 (a chat question runs to 2,000, so the prefill **truncates** — otherwise the form dies on an exception). `MAX_PENDING_PER_USER`=20, **skipped for a 좋아요 출신 proposal** (함정 ④): under the default `guest-identity=shared` that cap is one shared counter for every visitor, and a 좋아요 is one button press with nowhere to render a "20건이 밀려 있습니다" form error — `findLiveProposalForTurn` (one live proposal per turn) bounds it instead. **저자 수정·철회** (§10.11): editing lands the proposal back in `pending` whatever it came from, and the curated rows are deliberately **left alone** — an approved entry keeps serving search until the new text is approved, which then replaces it, since losing an entry for the days a typo fix takes to review is the worse trade. That needs no new status: `displayStatus()` derives 회수됨 from "approved with no active rows", so "pending with active rows" simply reads as pending. Replacement is per-origin — a hand-written proposal's previous rows come down first (new ids each approval, else the same proposal is searched twice), a 좋아요 출신 one is upserted in place (retracting first would let the background vector delete race the vectors just written, same id). Withdrawal now covers **approved** too and retracts with it; before, contributed knowledge was irretrievable except through an admin. `approve()`/`reject()` are audited (`curated.submission.approve`/`.reject`/`.create`)

### `repository/CuratedSubmissionRepository.java`

청크 추가 게시판 table + queries. `markApproved`/`markRejected` are **compare-and-set** (`WHERE ... AND status='pending'`); `markWithdrawn` and `updateByAuthor` widen that to `IN ('pending','approved')` (§10.11 — the author can take back and rewrite knowledge they contributed) so two admins clicking 임베딩 실행 at once produce one approval — the loser's already-created curated row is rolled back by `CuratedSubmissionService.approve()`. Every read LEFT JOINs `curated_qa`, so `Submission.displayStatus()` derives `revoked` (approved but the curated row was later deactivated from the curated panel) and `embedFailed()` at read time — no write-side hook back into this repository, and no service cycle. `author_read_at` drives the author's header badge; stamped by opening "내 제안", never by the badge poll itself. `source_turn_id`/`source_thread_id` (defensive `ALTER`, `tags` 선례) record a 좋아요 출신 proposal's origin — they drive the review screen's `[RN]`/`[DN]` label and conversation link and `findLiveByTurn`'s duplicate check (a **plain** index, not UNIQUE: rejected/withdrawn rows for the same turn are normal, and "live" means pending-or-approved). The read also aggregates `SUM(chunk_count)` separately from `COUNT(*)`: rows are the 전부/전무 unit, vectors are what "N개 청크로 등록됨" means, and those differ for a 좋아요 출신 row

### `controller/CuratedSubmissionController.java`

청크 추가 게시판 (사용자) — `/curated/submissions` page (form + 내 제안 목록, guest-open in every auth mode), plain form POST + flash redirect (an HTML form, so validation errors must not come back as `GlobalExceptionHandler` JSON), `POST /{id}/withdraw`, `GET /{id}/detail` + `POST /{id}` for the author's edit offcanvas (real API calls — the offcanvas renders 400/409 inline), `GET /unread-count` for the header badge, and `POST /images` (본문 이미지 업로드 — a real API call, so a JSON error body *is* right there, unlike the form POST above). ### `service/CuratedImageStore.java`

지식 제안 본문 이미지 — upload, marker bookkeeping, approval-time Vision description, cleanup. Images land at `{dataDir}/images/submissions/{sha16}.{ext}` and are referenced from a body by the **same `[이미지: …]` marker the document pipeline emits**, which is what makes every downstream consumer work unchanged: `GET /api/v1/images/{docId}/{filename}` already serves the path (the literal directory name `submissions` can never collide with a document's imageId — those are 16-hex hashes), `base.html`'s `renderMarkdownWithImageMarkers()` already renders it, and `RetrievalService` already turns `image_paths` metadata into answer thumbnails. **Marker position = image position**: the form uploads eagerly and splices the returned marker in at the caret, so everything after that is ordinary text editing and an image travels with the paragraph it illustrates when `approve()` splits the body. `store()` layers extension allowlist → 5MB cap → magic bytes (`FileTypeDetector`, extended with png/jpg/gif/webp) → content-hash filename, because the board is guest-open in every auth mode and this is the one place an unauthenticated caller writes a binary to disk; the client never picks a path component, and re-uploading the same picture is idempotent rather than duplicating bytes. `describeImages()` (called by `approve()` **before** `splitBody()`, so a marker and its description can't land in different chunks) delegates to `LazyVisionService` — the description therefore also lands in the shared `image_descriptions` cache, and `RetrievalService.hasEmbeddedDescription()` sees the injected line and skips re-analyzing on every later turn. No-op when `app.image-description.enabled=false`, and a Vision outage is caught and logged rather than failing the approval. `MAX_IMAGES_PER_SUBMISSION`=10 bounds the fan-out one approval can trigger (checked at both submit and approve). Cleanup is reference-counted, not ownership-based — filenames are content hashes, so two posts can share one file: `releaseImages()` (reject/withdraw) and `sweepOrphans()` (`ApplicationReadyEvent`, 24h grace, collects images from drafts that were never posted) both delete only what no live submission or active curated row still references

### PPTX · 스캔본 아닌 PDF 의 마크다운 변환

- PPTX / non-scanned PDF → Markdown: the `[페이지: N]` marker (NOT a synthetic heading) is the per-slide/page section boundary — `PptxToMarkdownConverter`/`PdfToMarkdownConverter` no longer emit `## N번 슬라이드`/`## N페이지`, and both `DocumentLoaderService.splitMarkdownBySections()` and `MarkdownCorrectionService.splitBySections()`/`splitByPages()` split on the marker. Only PPTX/PDF emit `[페이지: N]`; DOCX/TXT/MD never do (so the marker-as-boundary logic is a no-op for them). At PPTX conversion time, image-less duplicate + agenda/TOC slides are dropped (`app.pptx-remove-duplicate-slides`, default on), title-only section-divider slides are dropped (`app.pptx-drop-divider-slides`, default on, keeping sentence-like key-message titles), a title-only slide (no image, no group/diagram/chart/table text) whose exact title also appears in the immediately following slide is dropped as a "preview title" slide (`app.pptx-drop-redundant-title-slides`, default on — last slide never affected, no next slide to compare against), and the very last slide is dropped when its image-less normalized content contains an ending marker (끝/END/The End/감사합니다/Thank you) with at most 10 other normalized characters left over (`app.pptx-drop-ending-slide`, default on); dropped slides never shift `page_or_slide` numbering (`slideNum = i+1`). `MetaKey.CHAPTER_NO` stays `"0"` for PPTX/PDF (`skipChapterNumbers=true`) — real hierarchical chapter numbers come only from DOCX/MD/TXT H2–H6 headings
- PPTX multi-line shape text → code fence or block separation, in **both** shape paths: `appendShapeTextBlock()` for a text shape inside a group/diagram, `appendSlideBodyShape()` for a standalone slide-body text box (code lives in standalone boxes more often than in groups). Single-line shapes are unchanged (group: tight `\n` for short node labels; body: `appendBodyLine()`'s `\n\n`). **Multi-line** shapes get fenced with ``` when `looksLikeCodeBlock()` says code — the fence body uses `rawParagraphText()` (`stripTrailing()`, never `trim()`, so indentation survives) with interior blank lines preserved, and no emphasis markers, so code is reproduced verbatim and `MarkdownNoiseNormalizer`/`splitMarkdownBySections()` both leave the interior alone. The converter emits a **bare** ``` fence; `MarkdownCorrectionService.correct()` then finishes the job — `normalizeCodeContent()` strips the interior blank lines except one before a multi-line-comment or function/class signature (which is why preserving them in the converter matters), and `postProcessMarkdown(md, isPptx=true)` guarantees a blank line around the fence. The same pass also infers the fence's language tag from its content (`inferLanguage=true`), which is deliberately **decoupled from the `addHeadingNumbers` checkbox** so PPTX (which always forces it `false`) and any file uploaded with the box unchecked still get tagged fences — the `addHeadingNumbers` branch now only runs `addHierarchicalHeadingNumbers()` (fence-aware, so it never needs a code re-polish). Non-code multi-line text is blank-line separated in the group path only; the body path already separates paragraphs via `appendBodyLine()`. `appendSlideBodyShape()` collects a shape's surviving `BodyLine`s before emitting (a whole-shape fence can't be decided line-by-line) but runs heading promotion + consecutive-dup skipping in the original paragraph order, so those verdicts are unchanged. `looksLikeCodeBlock()` is deliberately conservative: **blank lines count toward neither the numerator nor the denominator** (a snippet's interior blank lines must not dilute the ratio), any `-`/`*`/`1.`-prefixed line (or a native `para.isBullet()`) means **not** code, an existing ``` means not code, and otherwise ≥`CODE_LINE_RATIO_PERCENT` (60%) of non-blank lines must hit `CODE_LINE_SIGNAL`. Arrows (`->`/`=>`) are excluded from the signal set on purpose — "요청 -> 응답" flow labels are far more common in diagrams than code
- PPTX shape-group text: a group-member shape whose entire text is a bare counter/step-badge label (`"1"`, `"1."`, `"(2)"` — `BARE_NUMBER_LABEL` regex in `PptxToMarkdownConverter.appendGroupText()`) is skipped from the extracted `[도형 그룹]` text — the group is already rasterized to an image separately, so a lone digit with no context is noise, not content. A label with trailing text (`"1단계"`) is unaffected — the regex only matches when the **entire** trimmed text is numeric (with optional surrounding `()`/`[]`/`.`/`)`). If filtering leaves a group with no other text, `appendShapeGroup()`'s existing empty-check suppresses the whole `[도형 그룹]`/`[/도형 그룹]` block, same as a purely decorative group with zero text shapes.

### MarkdownCorrectionService — 코드 펜스 짝 불변식과 표 보호

- **Code-fence parity is a pipeline invariant** in `MarkdownCorrectionService`: every pass after the LLM assumes fence lines pair up 1-2, 3-4, … and `normalizeCodeBlocks()` *writes* `"```" + resolvedLang` onto whatever it treats as an opener — so one unpaired fence makes it stamp a language tag onto a **closing** fence (the observed ```` ```java … ```java ```` corruption), and mispair prose into code blocks. Three guards keep it: (1) `correctSection()` discards an LLM response whose kept span (post-`cutOverlap`) has an odd fence-line count and keeps the original section — input sections are balanced by construction, and `cutOverlap()` can otherwise take half a pair with it when the model wraps marker-spanning code in one fence; (2) `fixClosingFences()` heals an unclosed fence at an H2–H7 heading, at a `[페이지: N]` marker (PPTX/non-scanned PDF emit **no** `##` headings, so a heading is never reached there), and at end of input; (3) `normalizeCodeBlocks()` refuses the whole document — no tagging, no `normalizeCodeContent()` — when the fence count is odd or when `fenceLineCount() != fenceMarkCount()` (a mid-line ```` ``` ````, e.g. prose ending in "…감쌉니다: ```" or a table cell, is invisible to the line-based passes but counted by the anchorless `FENCED_BLOCK` regex, so the two views disagree on pairing). Any new fence-touching pass must preserve this invariant. The re-index path (`DocumentIndexer.postProcessIfNeeded()`) deliberately runs only `postProcess()`, so a file already saved in a broken state is **not** self-healed by ↺ re-index — instead `POST /admin/documents/{docId}/reindex` runs a read-only pre-flight (`RagService.checkReindexFenceHealth()` → `DocumentIndexer.checkFenceHealth()` → `MarkdownCorrectionService.findFenceProblems()`) and returns **409** with `{status:"fence_problems", problems:[{line,kind,message}]}` **without starting any work**; the admin UI lists the line numbers and offers 무시하고 진행 (re-POST with `?force=true`) or 중지. `findFenceProblems()` is the read-only counterpart of `fixClosingFences()` and must stay in sync with it (same line-based scan, same three defect kinds)
- `MarkdownCorrectionService.postProcessMarkdown()`'s Pass B guarantees a blank line **before and after** three line kinds, all fence-aware (code-block *contents* are never touched): a fenced code block, a GFM table block (`markTableRows()`), and an H2–H7 heading (`looksLikeChapterHeadingNotComment()` — so `### 주석 ###`-style banner comments and any `#` line inside a fence are excluded). The heading rule deliberately matches the **raw** line (no `stripLeading()`, unlike the fence check), so an indented `##` inside a list item or indented code block is left alone; H1 is also out of scope (document-title line). Blank-line *collapsing* runs in the same pass, so the inserted blanks are never doubled and a trailing blank at EOF is trimmed. This pass also runs on re-index and on document export (`DocumentExportService` → `postProcess()`), so hand-edited MD files get the same guarantees
- `MarkdownCorrectionService.correctSection()` never sends GFM table content to the LLM: `extractTables()` (uses the same `markTableRows()` the table-aware blank-line pass in `postProcessMarkdown()` already relied on) replaces each table block with a `[TABLE_PLACEHOLDER_N]` marker before building the prompt, and `restoreTables()` substitutes the original table text back into the response afterward — a prose "표는 변경 금지" instruction alone wasn't reliable (local models were observed replacing `:` with `|` inside cells). If a placeholder is missing from the response (model dropped/mangled it), the whole section falls back to its untouched original text rather than guessing where the table belongs — same discipline as the `<<<SECTION_START/END>>>` overlap-marker check in `cutOverlap()`.

### 응답 모드 (S / N / C)

- Response mode (**S/N** in the chat input bar + **C** server-side only, default `N` — PLAN §6.24, PIPELINE §3.1): the per-message **답변의 성격** axis, orthogonal to routing mode. S/N are the *length* axis; **C (응용) is a different axis — 근거 엄격도**: it builds new code/config *using* the retrieved documents as material, so it gives up "nothing outside the documents". All three are selectable in the chat input bar. **C and Direct are mutually exclusive** — the client disables the C button while Direct is on, and **any RAG↔Direct toggle resets the response mode to `N`** (either direction, whatever was selected, stored preference included — the reset lives in the toggle's `change` handler, deliberately *not* in `updateResponseModeAvailability()`, which also runs on page load and would wipe the stored choice every time), and the server enforces it independently in `ChatRequest`'s compact constructor (REST) and `ChatForm.responseModeOrDefault()` — the one point the HTMX form path and the SSE path share, since `ChatController.normalizeResponseMode()` is not on the SSE path. `AgentGraph`'s guard (Step 2-c) is separate: it stops a null Direct prompt key from throwing, while these two also keep the stored `response_mode` honest. `L` was removed and `M` renamed to `N`; `ResponseMode.parse()` is lenient so legacy `"M"`/`"L"` in `conversation_turns.response_mode` and in the browser's `localStorage['chatResponseMode']` both degrade to `N` — **no migration**. **Each mode owns a whole system prompt** (`prompt.answer.system.{s,n,c}`, and `prompt.direct.system.{s,n}` for the Direct path; meta keeps `prompt.direct.meta.system` regardless of mode). **C has no Direct prompt on purpose** (`directSystemPromptKey=null` → `allowsDirect()=false`): retrieval is its premise, so `AgentGraph` sends neither a `directMode=true` request nor a `"meta"` classification to DIRECT_ANSWER for it — the first would NPE on the null key, the second would skip retrieval entirely and silently neuter the mode ("문서에 있는 날짜 함수로 예제 만들어줘" classifies as meta). The old approach — one shared prompt plus a `prompt.answer.style.*` instruction appended to the *user* message to override it — is gone, because it failed for S: the system prompt's list of five section headers beat the one-line negative instruction, the model emitted all of them, and the server truncated afterwards so the screen and the stored answer disagreed. **S's prompt therefore never names the section headers at all** — listing them to forbid them is enough for a weak local model to follow the list (`ResponseModeSystemPromptTest` pins this, plus S's character cap and N's absence of any number). **S's cap is per path, not per mode**: the RAG prompt says 1,000자, the Direct one 1,500자 — Direct has no document excerpts to cite, so the answer has to spell itself out. The number itself is not the invariant the guard holds; what it holds is that the ko and en bundles name the *same* number, since a mode that answers at two different lengths depending on UI language is the failure that actually shipped. **Length policy is asymmetric on purpose**: a cap on short output sits *before* where the model stops on its own and binds; a target on long output sits *after* it and does nothing (old M asked ~5,000 chars → 3,047 actual; L asked ~10,000 → 3,187 — that measurement is why L died). So N names no number and instead says what to cover. **Branch on capabilities, never on the enum value** — `skipsVerification()` (S: no eval call, no CRITIC), `summaryOnly()` (deliberately separate from the former: same value on S today, different questions), `allowsDirect()`, `allowsSubmission()`, `retrievalBoost()`, `usesCreativeTemperature()` (which temperature knob), `usesCreativeEval()` (which record the returned JSON is read into); `ResponseModeBranchConventionTest` fails the build on a `== ResponseMode.X` in main. The last two always move together today but answer different questions, so they stay apart — and picking the parser by comparing the *prompt key string* is deliberately avoided: renaming the key would silently select the wrong parser. **`maxTokens(configured)` = `min(configured, max(256, max(round(configured*ratio), minChars)))`** — S 0.15/2,000, N and C both 0.70/5,000 (C's length policy is N's, so its budget is too). The `min` is what stops a mode floor from punching through the operator's ceiling (default 6,000 used to hand L 10,000). It applies to **blocking calls only**; streaming has no cap, and this budget is a runaway guard, not a length target — it must stay comfortably *above* the prompt's own cap (S: prompt 1,000자 — 1,500 on the Direct path — vs budget 2,000+), so raising S's prompt cap means raising `minChars` too. `/settings` renders a read-only 응답 예산 row per mode showing which term won (`2,000 (최소 보장)` / `8,400 (상한의 70%)` / `3,000 (설정 상한)`) since the crossover differs per mode (S 13,334, N/C 7,143). **S cannot be proposed as knowledge** (`allowsSubmission()=false`): its 좋아요 button renders disabled with the reason in its tooltip. §10.11 replaced that reason — the old one ("stripping structural sections leaves nothing to embed") stopped holding once the text reaching the corpus is hand-edited; the real one is that S is *deliberately abridged*, a 1,000자 `## 요약` whose prompt tells the model to leave out background, reasoning, premises and exceptions. That is a format chosen to read something quickly, not a source worth keeping. 싫어요 is unaffected. **`SummaryOnlyGuard` is a conditional safety net, not a rewriter**: it returns a compliant answer by identity and only salvages the first section when the model emitted 2+ headings (fence-aware); it never cuts by character or line count, and it logs at INFO when it fires — that frequency is the only measurement of whether the S prompt is working. **When the server changes the answer after streaming** (that guard, `truncate()`'s 20,000-char cut, a PROGRESSIVE re-generation), the SSE `done` payload carries `finalAnswer` and `chat-stream.js` replaces the bubble — omitted when unchanged so a 20,000-char answer isn't sent twice. Without it the screen kept the streamed text while the DB held the corrected one, surfacing only on refresh (and 좋아요 saved a different text than the user saw). **C는 운영자가 끌 수 있다** (`app.llm.creative-mode-enabled`, 기본 ON — 이 스위치가 생기기 전에는 늘 열려 있었으므로 미설정 시 동작이 변하지 않는다). 판정은 둘로 나뉜다 — enum은 "끌 수 있는 모드인가"(`ResponseMode.operatorToggleable()`, 지금은 C만 `true`)만 알고, "지금 꺼져 있는가"는 설정 계층이 알며, 둘을 합치는 곳은 **`SettingsService.effectiveResponseMode()` 하나다**. 모든 채팅 진입점이 그것을 거쳐야 한다 — `ChatController.normalizeResponseMode()`(HTMX·SSE 공유. 라디오 파라미터가 없어도 hidden 필드값을 같은 판정에 통과시킨다 — 예전의 조기 반환이 그 경로를 통째로 비껴갔다)와 `withAvailableResponseMode()`(REST — 화면을 거치지 않아 버튼 감추기가 존재하지 않는 경로). 강등을 **진입점에서** 하는 이유는 Direct 배타 가드와 같다: 그래프 안쪽에서만 바꾸면 저장된 `response_mode`는 C인데 실제로는 N으로 답한 턴이 남는다. 꺼지면 채팅 입력창의 C 버튼을 **비활성이 아니라 아예 렌더하지 않고**(`creativeModeEnabled` 모델 속성 → `chat.html`의 `th:if`, 그리고 JS의 `RESPONSE_MODES` 화이트리스트에서도 빠진다 — 그래야 localStorage에 남은 `'C'`가 되살아나 어느 라디오도 체크되지 않은 입력창을 만들지 않는다), 과거에 C로 답한 턴의 `[C]` 표기·배지는 그대로 남는다. **C specifics**: (a) it uses `app.llm.creative-temperature` (default 0.7, clamp [0,1.0], hot) instead of `app.llm.temperature` — that one is clamped to [0,0.3], which makes creative generation impossible on it; `AnswerService.answerTemperature()` picks between them and must be honored on **both** the blocking and the `streamDirect()` streaming path, since the chat UI only ever streams. (b) Verification is **replaced, not disabled** — `prompt.answer.eval.creative` returns `sufficient`/`apiGrounded`/`inventedSymbols`/`envNote` into a separate `CreativeEvalOutput` record (a second `BeanOutputConverter`; folding `inventedSymbols` into the shared `EvalOutput` would put it in N's generated JSON schema too). `apiGrounded` rides in `AgentState.grounded`, so `CriticService` still reads one boolean (its `null` handling did change once — see the '판정 없음' bullet below). The ordinary `grounded` gate is false *by definition* for a creative answer, which would burn ANSWER×3 + EVAL×3 + RETRIEVAL×3 and still end in a 미검증 badge. `inventedSymbols` never triggers a retry — inventing a name is not the failure, presenting it as document-sourced is — and lands in `AgentState.inventedSymbols` for the Phase 4-b badge. (c) **Its passing badge is blue `생성`, not green `검증됨`** (`generative()`) — the two modes passed different questions (is this grounded in the documents? vs do the names it presented as document-sourced exist?), and one green badge for both invites the reader to take the second for the first. Any flagged `inventedSymbols` get their own amber badge plus an expanded line, shown **even on a passing answer**. All of this is decided in `model/VerificationSnapshot`, which is both the stored shape (`conversation_turns.verification`, JSON, defensive ALTER) and the display rule — there are three renderers (the no-JS HTMX fragment, `chat.html`'s history loop, and `chat-stream.js`), the two server-side ones read that record, and the JS implements the rule a second time because SSE never touches a template. `generative` is **stored, not derived** from `response_mode`: it records what was actually verified on that turn, so redefining the flag later must not relabel old answers. Parsing is lenient (`FAIL_ON_UNKNOWN_PROPERTIES` off, one bad blob skips only its own turn) because these rows outlive the code that wrote them. A NULL column means "no verification record" — every pre-existing turn plus meta/Direct/S — and renders no badge, exactly as before. (d) **Never reused** (`allowsReuse()=false`): C's request is "build me one", so returning a stored answer to 다시 만들어줘 declines the only thing that was asked. The rule lives in `QuestionReuseRepository`'s WHERE predicate, shared by the suggestion and the reuse query and **generated from the enum** — it used to be a `<> 'S'` literal in both, where a mode value comparison is invisible to `ResponseModeBranchConventionTest`. It is `NOT IN` over the excluded modes, never `IN` over the allowed ones, so NULL/blank/legacy `'M'`/`'L'`/unknown all stay eligible exactly as `ResponseMode.parse()` would read them. (e) **May be proposed as knowledge** (`allowsSubmission()=true`, flipped in §10.11): a C answer in `curated_qa` is searched back at the curated axis's RRF weight, so model-invented code would become the next turn's "document" — hallucination hardening into doctrine over generations, and unwinding it means hunting down vectors. What made that fatal was the *absence of a gate*: one click, three seconds, shared knowledge. Now that a person edits the text and an admin approves it, a C answer gets the same review as anything else, and the review — not the mode exclusion — is what stops the loop. (f) `retrievalBoost()` is wired into `RetrievalService` (added to the retry escalation, not replacing it) but is **0 for every mode**; raising it requires lifting `AnswerService.MAX_EVAL_EXCERPT_CHARS` first (PLAN §6.24 Step 4-c), otherwise lower-ranked documents drop out of the verification window and the `grounded=false` false-positive the `.limit(5)` removal fixed comes back.

### 검증 판정의 신뢰도 — 축소·실패 시 '판정 없음'

- **프롬프트가 창에 맞춰 축소되면 사용자에게 말해야 한다** (`AgentState.budgetNote`): 축소는 프롬프트에만 걸리고 `state.sources()` 는 검색된 전부를 그대로 들고 있어서, 안내가 없으면 사용자는 화면의 출처 10개를 모델이 다 읽고 답한 것으로 읽는다. `AnswerService.withBudgetNote()` 가 **두 진입점에서 한 번** 세우면 아래 모든 `toBuilder()` 복사(PROGRESSIVE 업그레이드 포함)를 타고 흐르므로 경로마다 심을 필요가 없고, `fitToBudget()` 은 여전히 계산이 한 곳이다(프롬프트 조립부가 같은 함수를 다시 부를 뿐 규칙을 복제하지 않는다). **검증 결과가 아닌데도 `VerificationSnapshot` 에 저장한다** — `envNote` 와 같은 이유로 새로고침 후에도 남아야 하기 때문이고, 저장하지 않으면 대화를 다시 열었을 때 출처 목록만 단서 없이 복원되어 이 기능이 막으려던 상태가 그대로 재현된다. 그래서 `isEmpty()` 도 이 값을 센다(안 세면 검증을 안 돌린 턴의 안내가 저장에서 통째로 빠진다). 렌더러는 늘 그렇듯 셋이고, **문구는 서버가 통째로 만들어 내려보낸다**(숫자 포함) — JS 가 조립할 것이 없어야 세 렌더러가 문구로 갈라지지 않는다. 메시지 번들을 쓰지 않는 것도 의도적이다: 저장돼 나중에 다시 렌더되는 문자열이라 그때의 로케일이 답변 시점과 다를 수 있다(`evalReason`·`envNote` 가 모델의 한국어를 그대로 저장하는 것과 같은 자리)
- **축소된 근거로 내려진 `grounded=false` 도 판정으로 삼지 않는다** (`AnswerService.unreliableNegative()`): 검증 호출은 검색 문서 위에 **답변 전문**이 통째로 얹히는 이 앱 최대의 요청이라, **답변이 길수록 발췌 자리가 줄어든다** — 답변 호출은 통과했는데 검증만 좁아지는 구간이 실제로 있다. 이때 판정의 신뢰도는 **비대칭**이다: `grounded=true` 는 본 것만으로 근거를 찾았다는 뜻이라 문서를 더 봐도 뒤집히지 않지만, `grounded=false` 는 "못 찾았다"이고 빠진 그 문서에 있었을 수 있다(`.limit(5)` 사고의 정확한 모양). 그래서 발췌가 잘린 채 나온 부정 판정은 `grounded=null`(판정 없음)로 떨어뜨린다 — 배지도 재시도도 없다. **재시도를 안 거는 것이 핵심**: 답변 길이와 창이 그대로라 재시도해도 같은 축소가 반복되고 예산만 탄다. **비우는 것은 `grounded` 뿐이고 `sufficient` 는 살린다** — 그건 답변과 질문을 견주는 판단이라 발췌 완전성에 거의 의존하지 않고, 그것까지 버리면 정당한 PROGRESSIVE 업그레이드(창이 더 큰 프로바이더로 가는, 이 상황에 도움 되는 쪽) 신호가 사라진다
- **검증 결과를 읽지 못하면 '통과'가 아니라 '판정 없음'이다** (`AnswerService.withoutVerdict()`): 검증 호출이 빈 응답을 주거나(`isEmptyVerdict()`) 반환 JSON 파싱이 실패하면 `grounded=null` + `needsRetry=false`로 내려간다. **재시도를 걸지 않는 것까지가 fail-safe이고, `grounded=true`로 위조하는 것은 fail-safe가 아니다** — 예전 폴백이 그 `true`를 써넣었고, 그 값이 그대로 `VerificationSnapshot`으로 흘러가 **검증한 적 없는 답변에 `검증됨`(N)/`생성`(C) 배지**가 붙었다(같은 사고에서 `sufficient=false`로 걸렸어야 할 재시도도 함께 사라진다 — C에서 "만들다 만" 답변이 그대로 나간 경로가 이것이다). `grounded=null`은 이 앱이 이미 "검증 미실행"으로 취급하는 값이라 새 UI 상태가 아니다: `CriticService`가 덮어쓰지 않고(예전에는 `null → true` 폴백이 **거기**에 있었다 — `AnswerService`만 고치면 CRITIC이 도로 위조한다), `VerificationSnapshot.isEmpty()`가 참이 되어 `MemoryService.saveVerification()`이 저장을 건너뛰며(컬럼 NULL), `verdictLabel()`과 `chat-stream.js`의 `=== true`/`=== false` 비교가 둘 다 배지를 그리지 않는다. 빈 응답 로그(`[EVAL]`/`[EVAL-C] 검증기가 빈 응답을 반환했다`)가 `inputTokens`/`outputTokens`를 함께 찍는 이유는 그 둘이 원인을 가르는 유일한 단서이기 때문 — `outputTokens=0`이면 모델이 아무것도 내지 못한 것(**검증 호출은 질문 + 답변 전문 + `buildEvalExcerpts()` 발췌 + 응답 스키마가 한 번에 들어가는 이 앱 최대 단일 요청**이라 컨텍스트 초과가 유력), 0보다 크면 content가 아닌 곳(reasoning 필드)으로 나온 것이다.

### 질문 버블의 두 글자 표기

- 질문 버블의 표기(`[RS] 질문`)는 **두 글자**다 — 앞이 검색 축(`R` RAG / `D` Direct), 뒤가 답변의 성격(`S`/`N`/`C`). 규칙의 출처는 **둘**이고 그 이상으로 늘려선 안 된다: 서버는 `MemoryRepository.Turn.responseModeLabel()`, 클라이언트는 `layout/base.html` 의 전역 `bubbleModeLabel(responseMode, directMode)`. **렌더러가 넷**이라 그렇다 — 대화 기록(`chat.html` 루프, 서버) · 스트리밍(`chat-stream.js`) · 재사용(db-reuse) · HTMX 낙관적 버블(뒤 셋은 클라이언트). JS 셋이 파일 둘에 흩어져 있어 각자 복사하면 같은 대화가 새로고침 전후로 다른 표기를 단다. **두 축을 다 적는 이유**: 성격만 적으면(옛 `[N]`) 같은 질문을 문서로 물었는지 모델 지식으로 물었는지가 화면 어디에도 없다. 두 축은 직교하므로 — "N 대신 Direct"가 아니라 "Direct 이면서 N" — 한 글자로 뭉칠 수 없고, 특히 **`DS`와 `DN`은 프롬프트(`prompt.direct.system.s`/`.n`)도 후처리(`SummaryOnlyGuard`)도 다른 별개의 조합이다**. `C`는 RAG 전용이라 `RC`의 `R`은 정보를 안 나르지만 그대로 둔다(혼자 `[C]`면 렌더링 오류로 읽힌다). **`direct_mode`는 "무엇을 요청했나"이지 "검색이 실제로 돌았나"가 아니다** — RAG로 물어도 분류기가 `meta`로 판정하면 검색을 건너뛰므로 출처 없는 `R` 턴이 있을 수 있고, 컬럼이 생기기 전 턴은 전부 `R`로 읽힌다(`DEFAULT 0`). 표기는 `.bubble-user-mode` span 으로 **본문과 분리해** 넣고, **`data-question` 에는 절대 섞지 않는다** — 그 속성은 질문 '원본'이고 중복 질문 추천·재사용이 그대로 쓰는 값이라, 대괄호가 끼면 그 소비자들에게 딸려간다. 질문 내비게이션(전체 질문 보기 목록 · 현재 질문 풍선)은 `data-question` 을 우선 읽으므로 표기를 **`data-response-mode` 로부터 다시 만든다**(`qnavModePrefix()`); 그 속성에도 두 글자가 그대로 들어가 있어 그쪽은 고칠 것이 없다. 서버 렌더 경로의 성격 글자는 `ResponseMode.parse().name()`이라 구 `M`/`L`·NULL 이 **실제 동작과 같은 `N`**으로 표기된다 — 저장 문자열을 그대로 쓰면 화면과 그 턴이 답한 방식이 어긋난다. `TurnResponseModeLabelTest` 가 서버 쪽 규칙을 고정하고, `ChatControllerHtmxTest.historyQuestionsCarryTheResponseModePrefix` 가 한 글자 표기가 되살아나지 않는지 본다
- `fragments/message-user.html` 은 **현재 어떤 컨트롤러도 렌더하지 않는다**(README/UI.md 구조 목록에만 남아 있음). 배선한다면 `modeLabel` 모델 속성(두 글자 완성본)이 필요하고, 없을 때 `[null]` 이 찍히지 않도록 `th:if` 가 걸려 있다 — **두 축을 따로 받지 않는 이유**는 조립 규칙이 이미 서버와 클라이언트 두 곳에 있어서다(위 항목). 세 번째 사본을 만들지 말 것

### thread_meta.tags

### 벡터 스토어 백엔드와 vec/FTS DataSource

- Vector store backend (Phase 5): `app.vectorstore.type=chroma|sqlite-vec`, wired by `VectorStoreProviderConfig` (one `VectorStoreProvider` bean per mode). Chroma-only beans — `ChromaConfig`/`ChromaApi`, `VectorStoreRegistry`, `ChromaHealthChecker`, `VectorStoreWarmup`, `chromaVectorStoreProvider` — are `@ConditionalOnProperty(name="app.vectorstore.type", havingValue="chroma", matchIfMissing=true)`, so sqlite-vec mode starts without ChromaDB. sqlite-vec requires an operator-provided `vec0` native binary (`SQLITE_VEC_EXTENSION_PATH`, loaded via `DataSourceConfig.configureSqliteVec`) + `app.embedding.dimensions`; `AdminService` injects `Optional<ChromaApi>` + `JdbcTemplate`/`AppProperties`/`ObjectMapper` and serves `/admin` for both backends (chroma via `ChromaApi`, sqlite-vec via the `vec_document_chunks` table) plus a backend-agnostic status view (`vectorStoreView()` → `VectorStoreAdminView`); on sqlite-vec the UI "collection" identifier is the version string. Switching backends needs full re-indexing (vectors are not shared)
- Vector/FTS DataSource: `app.vectorstore.sqlite-vec.db-path` (`SQLITE_VEC_DB_PATH`) is an opt-in feature switch — empty (default) keeps `vec_embeddings`/`vec_document_chunks`/`chunk_fts` in `memory.db`; set (sqlite-vec only) puts them in a separate `vector.db` with its own pool=1 DataSource + vec0 extension. `DataSourceConfig` always exposes a `vectorJdbcTemplate` bean (separate `vector.db` when the switch is on, else an alias of the `@Primary` memory.db template). **Any component touching vec/FTS tables must inject `@Qualifier("vectorJdbcTemplate")`** — currently `SqliteVecSchemaInitializer`/`SqliteVecVerifier`/`SqliteVecVectorStoreProvider`/`KeywordSearchRepository`/`AdminService`. `SqliteVecSchemaInitializer.init()` applies WAL+busy_timeout PRAGMAs (after the dimension fail-fast) on that template. Indexing must keep the vectors→FTS→registry write order (memory.db registry committed last) since the two files are not transactionally atomic

### 청크 추가

- 청크 추가 (user-submitted chunks): `curated_qa` gained `origin` (`like`/`manual`) + `source_submission_id`, and `source_turn_id` became **nullable** — SQLite can't `ALTER` that, so `CuratedQaRepository.init()` rebuilds the table once (guarded by the absence of `origin`, inside one transaction) and recreates `idx_curated_qa_turn` as a **partial** UNIQUE index (`WHERE source_turn_id IS NOT NULL`) so the many NULLs of manual rows can't collide while like→unlike→like idempotency is preserved. Consequence: **`deactivate(turnId)` silently no-ops on a manual row** — `forceRemove()`/`onThreadDeleted()` must use `deactivateById()`, and any new de-activation path must too

### 대화

**대화(스레드) 삭제도 큐레이션을 회수해야 한다** (§6.25): `curated_qa` 행은 turn/thread id의 **복사본**으로만 연결돼 있어(FK가 아니다 — 그래서 이 테이블이 대화 삭제를 견디도록 설계됐다) 대화를 지워도 행과 벡터가 남아 검색에 계속 기여한다. 턴 단위는 `deleteTurn` → `onTurnDeleted()`(§10.11 이전 이름 `onUnlike`)가 막고 있었지만 대화 단위 `deleteThread`는 아무 처리도 하지 않던 버그였다. 이제 `CuratedQaService.onThreadDeleted(userId, threadId)`가 `findActiveByThread()`로 그 대화의 활성 좋아요 행을 모아 `deactivateById()` 하고 **벡터는 한 번의 배치 호출**로 지운다(`forceRemoveBySubmission`의 행별 fan-out과 달리 — 긴 대화는 좋아요 턴이 많아 스레드·왕복이 행 수만큼 늘어난다). 회수 건수를 반환해 감사 로그(`thread.delete`의 `curatedRetracted`)에 남긴다. **`findActiveByThread()`는 `source_turn_id IS NOT NULL`로 제안(manual) 행을 구조적으로 배제한다** — 제안은 전부/전무 단위(`forceRemoveBySubmission`)라 대화 삭제가 그 일부를 내려서는 안 된다. 대화 삭제 경로를 새로 만들면(관리자 삭제 등) 반드시 이 메서드를 함께 호출해야 하며, 그러지 않으면 어느 버튼을 눌렀느냐에 따라 결과가 갈린다

### Header badges

- Header badges (청크 추가 알림) poll every **60 s** from `layout/base.html`, not 3 s like the LLM indicator — a board post has no second-level freshness need. The admin count endpoint lives at `GET /admin/submissions/pending-count`, deliberately **not** under `/api/v1/**`: that prefix is CSRF-exempt and guest-open in management-only mode (§6.17), so it would hand the pending count to anyone; under `/admin/**` it inherits the `ROLE_ADMIN` gate. The badge elements are rendered only when `isAdmin`, and the poll starts only if its element exists

### 정적 자산

- 정적 자산(`/css/**`, `/js/**`)은 **내용 해시 URL**로 나간다 (`spring.web.resources.chain.strategy.content.*`) — `/js/chat-stream.js` → `/js/chat-stream-<md5>.js`. 이 재작성은 타임리프 `@{...}` 링크가 `ResourceUrlEncodingFilter`(Thymeleaf 오토컨피그가 체인 활성 시 등록)를 거칠 때만 일어나므로, **템플릿/JS에서 정적 경로를 문자열로 직접 쓰면 해시가 붙지 않아 캐시 무효화에서 빠진다**(예: `base.html`의 hljs 테마 전환은 `/webjars/...`를 문자열로 만든다 — webjars는 의존성 버전으로 고정돼 있어 범위에서 뺐기 때문에 무해). 해시 없는 원래 경로도 200으로 응답하므로(`VersionResourceResolver`가 실제 파일을 먼저 찾는다) 기존 링크는 깨지지 않는다. `SecurityConfig`/`NoAuthAutoLoginFilter`의 `permitAll` 매처가 `/css/**`·`/js/**` 접두사 기준이라 해시 파일명도 그대로 통과한다

### § 청크 변경 표시/차단

- § 청크 변경 표시/차단: 청크를 삭제·수정하는 **모든** 경로가 `QuestionReuseService`에 사유와 함께 통지해야 한다 — `AdminService.deleteChunk()`/`DocumentIndexer`(문서 재인덱싱·삭제) → `markChunkDeleted`/`markChunksDeleted`(=`deleted`), `AdminService.updateChunk()` → `invalidateChunk`(=`modified`), `AdminService.reindexChunk()` → `invalidateChunkIfHashChanged`(해시 변경이면 `modified`, FTS에서 사라졌으면 `deleted`). **`updateChunk()`가 특히 함정**: 재임베딩 없이 저장 텍스트만 고치므로 `chunk_fts`를 건드리지 않고, 해시는 그 테이블에서 계산되어 **원문이 바뀌었는데 해시는 그대로**다 — 명시적으로 통지하지 않으면 재인덱싱 전까지 옛 원문 기준 답변이 계속 재사용된다(해시 대조만으로는 절대 못 잡는 유일한 경로)

### 큐레이션 태그 스코프

- 큐레이션 태그 스코프: `filterByTags()`는 벡터·키워드·큐레이션이 합쳐진 **병합 후보 풀 전체**에 걸리는데 `CuratedQaService.buildDocument()`가 `MetaKey.TAGS`를 안 실어서, 태그 칩을 하나라도 켜면 좋아요 답변·승인된 제안이 **전부 탈락**했다(`TagUtils.matchesAnd(빈 태그, 선택)` = false). 이제 태그가 `conversation_turns.selected_tags`(`response_mode`와 같은 방어적 ALTER로 추가, `AgentService`/`StreamingAgentService`가 저장) → 제안 폼 프리필 → `curated_qa.tags` 로 이어지고 `buildDocument()`가 그 값을 `MetaKey.TAGS`로 싣는다(§10.11 이후 저자와 관리자가 등록 전에 고칠 수 있다). 태그가 비면 **키 자체를 넣지 않으며**, `filterByTags()`의 큐레이션 면제(`DOC_TYPE=curated_qa` + 태그 없음 → 항상 통과)가 이를 "스코프 미상 = 전 스코프 소속"으로 취급한다 — 문서 청크는 엄격 AND 그대로라 태그 없는 문서는 여전히 탈락한다

### 지식 제안 본문 이미지

- 지식 제안 본문 이미지: `CuratedQaService.buildDocument()` sets `MetaKey.IMAGE_PATHS` from the markers **still present in that chunk's stored text**, computed after the split — so a proposal with 3 images cut into 2 chunks gives each chunk only its own (same rule as `DocumentLoaderService.loadFromMarkdown()`). Without this key a curated chunk gets no answer thumbnail at all, since `RetrievalService` builds `imageRefs` purely from `image_paths` metadata. Marker parsing lives in exactly one place, `CuratedImageStore.markerPaths()` (static, so `buildDocument()` needs no dependency on the service); the browser-side counterpart is `layout/base.html`'s `renderMarkdownWithImageMarkers()` — **do not re-declare `CHUNK_IMAGE_MARKER`/`PREVIEWABLE_IMAGE_EXT` in a page script**, they are globals now and a second top-level `const` is a page-breaking `SyntaxError`

### RetrievalService.hasEmbeddedDescription

- `RetrievalService.hasEmbeddedDescription()` must accept **both** injection forms — `[이미지: …]\n[이미지 설명: …]` and the table-row `[이미지: …]<br>[이미지 설명: …]` (a raw newline inside a `|…|` cell shatters the table, so `MarkdownCorrectionService` and `CuratedImageStore` both use `<br>` there). Miss the `<br>` form and every table-embedded image reads as a cache miss on every turn, and `augmentWithDescriptions()` appends a duplicate description next to the one already in the text

### MetaKey.CHUNK_CONTEXT 는 일반 영속 메타데이터 키다

- `MetaKey.CHUNK_CONTEXT` is a normal persisted metadata key (like `MetaKey.EXCERPT_KEYWORDS`) — set by `KeywordExtractor`, consumed by `SearchTextBuilder`, and written to Chroma metadata / the `vec_document_chunks.metadata` JSON blob same as any other key. Only `MetaKey.SEARCH_TEXT` (the fully-computed context+normalized embedding/FTS text, §10.8.5 — cheaply re-derivable from `CHUNK_CONTEXT` + the stored text) stays transient and is stripped before persistence in both `ChromaVectorStoreProvider.add()` and `SqliteVecVectorStoreProvider.add()`. Because `CHUNK_CONTEXT` round-trips, `AdminService.reindexChunk(regenerateKeywords=false)` genuinely "keeps" whatever keywords/context are currently stored, including a value the operator hand-edited via `updateChunk()`. The `/admin` 청크 편집 offcanvas exposes 키워드/요약(맥락) as dedicated fields (`edit-keywords`/`edit-context`, pulled out of the raw metadata JSON box via `metaJsonExcludingInlineFields()` so there's one editable copy of each) — edit them, 저장 (`updateChunk`), then 이 청크만 재인덱싱 (`reindexChunk(regenerateKeywords=false)`) to hand-correct a chunk's search-time context without an LLM call; checking 키워드·요약 재생성 instead re-runs `KeywordExtractor.enrichSingle()` and overwrites both. Pre-existing chunks indexed before this change have no `chunk_context` key at all (blank field until a keyword-regenerate or full re-index backfills it)

### AdminService.reindexChunk

- `AdminService.reindexChunk()` re-embeds by constructing the `Document` with the SAME id as the existing chunk (`chunkId`, not a fresh one) before calling `VectorStoreFacade.add()` — both providers upsert-by-id (Chroma: `upsertEmbeddings` overwrites; sqlite-vec: `add()` deletes-then-inserts by id), so this updates the chunk in place instead of creating a duplicate. `KeywordExtractor.enrichSingle()`'s returned `Document` carries an unrelated fresh id (same as `enrichKeywords()` during indexing) — callers must read only its metadata, never its id

### ChromaVectorStoreProvider.add

- `ChromaVectorStoreProvider.add()` does **not** delegate to Spring AI's `VectorStore.add()` (that API embeds and stores the exact same string, which breaks the §10.1 embed≠store split) — it manually embeds `SearchTextBuilder`-derived text in `TokenCountBatchingStrategy` sub-batches, then upserts via `chromaApi.upsertEmbeddings()` with the original text as the stored document

### chunk_fts 의 trigram 토크나이저는 3글자 이상이어야 토큰이 나온다

- `chunk_fts`'s `trigram` tokenizer requires 3+ characters to produce any trigram — `KeywordSearchRepository.toMatchQuery()` drops shorter terms, so a 2-char query (very common in Korean — e.g. "오류", "문서") gets zero contribution from the BM25 axis while the vector axis is unaffected; this is expected, not a bug

### §6.12 동시성 게이트 · 단일 비행 · 과부하 차단 · 부하 분산

- §6.12 concurrency gate: `LlmRouter.executeGated()`/`acquirePermit()` (per-provider `Semaphore`, sized `app.llm.providers[].concurrency` else `app.llm.default-provider-concurrency` default 3) is used ONLY on the interactive chat/query path (`ClassifierService`, `AnswerService`, `DirectAnswerService`, `RerankerService`, `RetrievalService`'s MultiQuery model via `ConcurrencyLimitingChatModel`). Indexing/background callers (`KeywordExtractor`, `MarkdownCorrectionService`, `TextToMarkdownService`, Vision/title/summary services, etc.) deliberately keep the ungated `executeWithTracking()` — they already have their own semaphore (`app.indexing.max-concurrent-llm-calls`) and no synchronous HTTP caller waiting on a deadline. A timed-out gate wait throws `LlmBackpressureException` (`RAG-LLM-002`, HTTP 429 + `Retry-After`) — never caught by `LlmRouter`'s generic retry/circuit-breaker logic, since capacity pressure isn't a provider failure
- §6.12 in-flight single-flight: `CachingEmbeddingModel` holds a `ConcurrentHashMap<String, CompletableFuture<float[]>>` alongside its existing Caffeine `Cache` — a text miss either becomes the "owner" (batched into one delegate call with other new-this-call misses, same as before) or a "joiner" that `join()`s another concurrent call's in-flight future for the same (post-normalization) text instead of recomputing. Owner failure propagates to joiners and clears the in-flight entry so the next call retries fresh. Only exact-text collisions merge — near-duplicate questions still miss (§10.5 semantic cache, deferred)
- §6.12 overload-aware circuit breaking: `LlmRouter` catches `HttpStatusCodeException` (covers both 4xx `HttpClientErrorException` and 5xx `HttpServerErrorException`) for 429/402/503 and routes through `blockForOverload()` before calling `CircuitBreaker.block()` — if `findFirst(taskType, roleOrder, tried)` still finds a fallback provider, block normally (Retry-After header or `circuit-breaker-minutes` default); if there's no fallback (the common lone-LOCAL-provider deployment) AND no explicit Retry-After header, block for a short fixed duration (`SHORT_BLOCK_SECONDS`, "30") instead — a full multi-minute block on the only viable provider just turns a transient capacity blip into a total outage until the block expires. An explicit Retry-After header is always honored regardless of fallback availability (authoritative provider/operator guidance, never second-guessed). Other status codes (500/502/504/etc.) keep the pre-existing flat 30s block, now expressed via the same `SHORT_BLOCK_SECONDS` constant. **Four failures never block**, all for the same reason (the provider isn't sick): `isTimeoutLike` (client-side interrupt, rethrown), `isVisionUnsupported` (mmproj — a *permanent* provider limit, so it's remembered and image tasks skip it afterwards), `isContextOverflow` (the prompt outgrew the server's window — a property of *this request*, so nothing is remembered and the next short question must still go through), and `isRequestTerminatedByServer` (`{"error":"terminated"}` — the server killed the in-flight request while restarting or reloading its model; **the mirror image of `isTimeoutLike`**, and blocking here is actively harmful because the failure only occurs as the server goes *down* while the block outlives its coming back up, producing the operator-visible "restarted it and it still fails". The marker is the JSON fragment, not the bare word — `connection terminated by peer` is a real network fault and must still block). **The exhausted message is user-facing** — it is sent as the SSE `error` event and `chat-stream.js`'s `onError` prints it verbatim into the chat bubble, so `LlmRouter.exhausted()` writes it in Korean and names the wait: `AI 서버가 일시적으로 응답하지 않아 20초 후 다시 시도할 수 있습니다. (task=TEXT)`. The seconds come from `CircuitBreaker.secondsUntilUnblocked()` (floors at 1 — 0 reads as "it works now") over every provider that would be eligible **but for the block**, deliberately *not* excluding the one just tried, since that is exactly what the user is waiting on. **The wait is only stated when a block is the reason**: when the candidates ran out because they were tried and failed this request, waiting fixes nothing and naming a time would be a lie. The same value rides out as `Retry-After` through the existing `RagException.retryAfterSeconds()` branch, and `LlmContextOverflowException` keeps -1 (a smaller prompt, not time, is the fix). `routeProvider()` — the streaming path — shares the helper, or the same outage would read differently depending on whether the answer streamed. **Blocking is also shorter when the provider has no fallback**: `blockForFailure()` mirrors `blockForOverload()`'s no-fallback rule for ordinary failures (connection refused, non-overload HTTP) — with one provider a block is not a detour but a total outage, so it uses `NO_FALLBACK_BLOCK_SECONDS` (5) instead of `SHORT_BLOCK_SECONDS` (30). The block is kept rather than removed because a genuinely dead server would otherwise make every request pay its own connect timeout. The last one matters most on a lone LOCAL provider: the error is deterministic, so a 30s block buys nothing and takes down the smaller requests that would have fit. Detection is substring matching over `CONTEXT_OVERFLOW_MARKERS` because the wording is per-server, and LM Studio's `Context size has been exceeded.` arrives *inside* an HTTP 400 body wrapped as a `NonTransientAiException`, so it never reaches the `HttpStatusCodeException` catch. `too many tokens` is deliberately excluded — it collides with rate-limit wording, and misreading a real 429 here would skip `blockForOverload()`'s Retry-After handling
- §6.12 same-priority load balancing: `LlmRouter.findFirst()` groups eligible candidates within a role by the lowest priority present (unchanged tie-break/failover semantics — a different priority always wins over load); when multiple providers tie at that priority (e.g. two LOCAL providers registered for horizontal throughput), `selectWithinTopPriority()` picks the one with the most free permits on its concurrency-gate `Semaphore` (`availablePermits()`) — a "least-connections" balancer that reuses item 1's semaphores with zero new bookkeeping. Ties (both fully idle) deterministically keep the first-registered provider. Pure deployment-config feature: register two `providers[]` entries with the same `role`+`priority` and a different `base-url` — no schema/code changes needed. Not yet applied to embedding providers (different routing point, `EmbeddingModel` decorator chain)

### §6.13 설정 오버라이드 계층 (핫 편집)

- §6.13 settings override layer: `/settings` shows the effective LLM/RAG config; three families of values are **hot-editable** without a restart via a process-wide **static** `OverrideSource` on `AppProperties` (it's an immutable `@ConfigurationProperties` record, so the store can't be a ctor arg or injected field) — `SettingsService` binds itself via `AppProperties.bindOverrides(this)` at `@PostConstruct`, unbinds at `@PreDestroy`. Hot accessors read **override → else property default** then apply existing clamping; unbound (unit tests) = old behavior, regression 0. Full key list: `SettingsKeys`/`SettingsService.SEARCH_HOT_SPECS`/`INDEXING_HOT_SPECS`/`LLM_HOT_SPECS`.
  - **search** (apply on next search): similarity-threshold, RRF weight/k, candidate/tag multipliers, multiquery min-length/enabled, retry-escalate, topK, hybrid-enabled, `search-curated-qa-weight`(큐레이션 축 — §10.11 에서 좋아요/제안 두 축이 하나로 합쳐졌다). `RetrievalService` reads all of these fresh via `props.xxxSafe()` per `execute()`/`shouldExpand()` (topK/multiquery/hybrid used to be ctor-cached, which defeated hot-reload); only `rerank-enabled` stays cached (structural `@ConditionalOnProperty` bean, can't hot-swap).
  - **indexing/chunking** (apply on next indexing/↺ re-index, not next search): chunk size/overlap/min, `chunk-split-granular` (§ 청크 분할 전략 — flipping it changes nothing until a document is re-indexed, so the two strategies coexist in one collection and ↺ re-index is the supported way to move one document across), `indexing.max-concurrent-files`/`max-concurrent-llm-calls` (folded into `indexingSafe()` — nested `IndexingConfig` record can't take a top-level `xxxSafe()`). Read fresh per operation by **every** consumer (`DocumentIndexer`, `MarkdownCorrectionService.correct()`, `TextToMarkdownService.convert()`, `LazyVisionService`) — none may cache in a field. `max-concurrent-llm-calls` sizes a **separate `Semaphore` per consumer**, not a shared global budget.
  - **LLM** (apply on next LLM call): all four temperatures are hot. `llm.temperature` (§6.18, clamp [0.0, 0.3], folded into `llmSafe()`) — every interactive gated caller (`ClassifierService`, `AnswerService` answer+eval, `RerankerService`) reads it fresh per call, attached via `Prompt`/`ChatClient` options; still also baked into each provider's `OpenAiChatOptions` at bean creation by `LlmConfig.llmRouter()` as the startup-time fallback for framework-internal callers that build their own `ChatClient` around the injected model and can't take a per-call override (e.g. `RetrievalService`'s `MultiQueryExpander`) — those only pick up a change on restart. `llm.direct-temperature` (clamp [0.0, 1.0]) is hot — `DirectAnswerService` reads it fresh per call, attached via `Prompt`/`ChatCompletionRequest` options. `llm.creative-temperature` (clamp [0.0, 1.0], default 0.7, folded into `llmSafe()`) is hot — read fresh per call by `AnswerService` for the C response mode on **both** the blocking and streaming path (§6.24). `llm.shrink-step` (INT, default **1**, clamp [1,10], folded into `llmSafe()`) is hot too — read per call by `AnswerService.withShrinkRetry()`, so an operator watching `[SHRINK]` lines pile up can widen the step without a restart. `llm.creative-mode-enabled` (BOOL, default **true**, folded into `llmSafe()`) is the on/off switch for that mode as a whole — the temperature says *how* C answers, this says *whether* C is open at all; the two sit together on `/settings`, the knob first and the switch that makes it moot right after it. `llm.indexing-temperature` (clamp [0.0, 0.1], default 0.0, also folded into `llmSafe()`) is hot too — every ungated `executeWithTracking()` background caller (`KeywordExtractor`, `MarkdownCorrectionService`, `TextToMarkdownService`, `VisionDescriptionService`, `ImageTypeClassifier`, `ThreadMetaService.generateTitleAsync()`, `ConversationSummarizerService.summarize()`) attaches it per call via its own `OpenAiChatOptions`, so a higher general/RAG or Direct temperature can never leak into these extraction/classification-style calls. `llm.max-tokens` (INT, clamp [1000, 32000], folded into `llmSafe()`) became hot in §6.26 A6 — it had been the last view-only value on the page, which was awkward because it is **not just an output cap**: the history budget (×0.5), the MD-correction section size, the indexing output reservations and the context input budget all derive from it, so an operator fighting context pressure had to restart to move the one knob that mattered most. Two things had to change for it to be honest: `MarkdownCorrectionService`'s section size stopped being a constructor field, and `MaxTokensCappingChatModel` took an `IntSupplier` instead of an `int` so the per-provider ceiling is recomputed **per call** (that also picks up a window changed by the §6.26 A5 re-probe — `LlmConfig.liveMaxTokens()` reads both). **The one thing a restart still changes** is each provider bean's `defaultOptions`, the fallback for framework-internal callers that attach no options of their own (`RetrievalService`'s `MultiQueryExpander`) — the same exception `temperature` already carries. Streaming answers stay uncapped by design (see PIPELINE.md §4.1 for the local-LLM context-window sizing tradeoff). Default routing mode stays view-only (no runtime consumer).
  - **UI** (apply on next page render): `ui.source-preview-enabled` (`UI_HOT_SPECS`, BOOL, default ON via `SettingsService.sourcePreviewEnabled()`) — the global kill-switch for the chat source-preview popovers. `ui.retrieval-metrics-enabled` (BOOL, default **OFF** via `retrievalMetricsEnabled()`) — renders the per-source retrieval diagnostics (see the `SourceRef` entry below). A new UI-facing toggle goes in this group rather than into the LLM/search groups.
  - Writes go through `/admin/settings/**` (inherits §6.17 ROLE_ADMIN gating) and are audited (`settings.update`/`settings.reset`). ### 6.23 청크 변경 시 답변 재사용 무효화 + 대화 기록 표시 ✅ 완료

**유지해야 할 결정**
- **검증 범위 = 응답 지분(`answer_share > 0`)이 있는 청크만.** 한 글자도 반영 안 된 청크의 수정으로 멀쩡한 답변을 폐기하면 문서를 손볼 때마다 재사용이 통째로 무력화된다. 단 지분을 모르면(구 데이터, 귀속 `Method.NONE`) 전체를 검증한다 — **차단의 폴백은 항상 엄격한 쪽**
- **의도한 비대칭**: 구 데이터는 "배지 없이 재사용만 막히는" 상태가 된다. 차단의 폴백은 안전한 쪽, 표시의 폴백은 조용한 쪽
- **`updateChunk()`가 유일한 해시 사각지대** — 재임베딩 없이 저장 텍스트만 고쳐 `chunk_fts`를 건드리지 않으므로 원문이 바뀌어도 해시가 그대로다. 명시적 통지(`invalidateChunk`)로만 잡힌다. **청크를 바꾸는 새 경로를 추가하면 반드시 통지를 함께 붙일 것**

### 6.24 응답 모드 재설계 — S/N/C (L 제거 · 모드별 전용 시스템 프롬프트) ✅ 완료 2026-08-24 — 설계 확정 2026-08-22 (분량 지침·`/settings` 배선 보강 2026-08-23, 완료 후 보정 2026-08-25)

**유지해야 할 결정**
- **상한(cap)과 목표(target)는 다르게 작동한다.** 짧은 출력에 건 상한은 모델이 스스로 멈추는 지점보다 **앞**이라 구속력이 있고, 긴 출력에 건 목표는 그 **뒤**라 아무 일도 하지 않는다. 그래서 숫자를 말하는 건 S뿐이고 N·C는 "무엇을 더 다룰지"를 지시한다. 긴 답변 수요가 재발해도 레버는 숫자가 아니라 섹션별 분할 생성(호출 3배) 또는 문서 내보내기다
- **S의 숫자는 모드가 아니라 경로별이다** — RAG `prompt.answer.system.s`는 1,000자, Direct `prompt.direct.system.s`는 1,500자(인용할 발췌가 없어 스스로 풀어 써야 한다). 고정해야 할 불변식은 숫자 자체가 아니라 **한/영 번들이 같은 숫자를 말하는 것**이며(언어에 따라 답변 길이가 달라진 사고가 실제로 났다) `ResponseModeSystemPromptTest`가 이를 잡는다
- **`maxTokens()`는 폭주 방지 안전판이지 분량 통제 수단이 아니다.** `min(configured, …)` 클램프로 설정 상한을 넘지 않게 하되(구 L의 잠복 버그), 비율항은 유지한다(제거하면 16,000 환경에서 N이 6,400→5,000으로 회귀). 어느 항이 이겼는지는 `/settings` 응답 예산 행이 보여준다. 프롬프트 상한보다 **넉넉히 위**여야 하므로 S의 프롬프트 상한을 올리면 `minChars`도 함께 올린다. S 가드는 **구조만** 본다 — 글자 수로 자르는 로직을 넣지 말 것
- **C의 오염 방지 3건이 공개의 전제였다**(다크 런치 이유). 특히 큐레이션 제외(당시 `allowsCuration()`)가 **가장 위험한 단일 지점**이었다 — C 답변이 `curated_qa`에 들어가면 가중 RRF 축으로 다시 검색돼 모델이 지어낸 코드가 다음 턴의 "문서"가 되고, 되돌리려면 벡터를 찾아 지워야 한다. §10.11 이 그 제외를 풀었다: 치명적이었던 것은 게이트가 없었기 때문이고, 사람 편집 + 관리자 승인이 그 자리에 들어갔다. 재사용 제외(`allowsReuse()`)와 펜스 절단 복구가 나머지 둘
- **C는 검증을 끄지 않고 바꿔 낀다.** `grounded`는 창의 답변에서 정의상 거짓이라 그대로 두면 재시도로 정상 턴의 3배를 태우고, 통째로 끄면 API 발명이 무방비가 된다. 같은 호출이 이미 답변과 발췌를 들고 있어 **추가 왕복 0회**로 `apiGrounded`/`inventedSymbols`를 묻는다. 배지는 초록 `검증됨`이 아니라 파랑 `생성` — **다른 질문을 통과한 것**이므로 같은 배지를 쓰면 독자가 후자를 전자로 읽는다
- **분기는 값 비교가 아니라 성질 질의로**(`ResponseModeBranchConventionTest`). 이 그물은 **문자열 안을 못 본다** — 3-b의 제외 규칙이 SQL 리터럴 `<> 'S'`로 두 쿼리에 박혀 있었고, 이제 제외 목록을 enum에서 만들어 공유한다. **허용(IN)이 아니라 제외(NOT IN)** 여야 `parse()`의 관대함과 같은 방향으로 떨어진다

**계획이 틀렸던 지점 (같은 실수 방지)**
- **서버 가드 위치**: 가드를 두 진입점 값 객체(`ChatRequest` 컴팩트 생성자 · `ChatForm.responseModeOrDefault()`)에 둔 것은 맞다 — Direct 배타는 **요청 하나에서만 파생되는** 판정이라 레코드가 스스로 답할 수 있고, HTMX 폼과 SSE 가 그 값 객체를 공유한다. 다만 그때 적어 둔 근거("`ChatController.normalizeResponseMode()`는 SSE 경로를 지나가지 않는다")는 **사실이 아니었다** — `streamChat()`도 `postChat()`도 그 메서드를 부른다(2026-08-06 `ee68ba5` 이후). 틀린 전제가 맞는 결론을 떠받치고 있었고, 그 문장이 UI.md·javadoc으로 퍼져 "SSE는 컨트롤러 가드를 안 탄다"는 오독을 남겼다(2026-08-31 정정). **설정에 의존하는** 가드는 반대로 레코드가 답할 수 없어 컨트롤러에 있다 — C 모드 운영자 스위치의 `normalizeResponseMode()`/`withAvailableResponseMode()`. 교훈: 가드 위치의 근거는 "어디를 지나가는가"가 아니라 **"판정에 무엇이 필요한가"**로 적을 것
- **"히스토리"가 히스토리가 아니었다**: `message-assistant.html`은 no-JS 폴백이고 새로고침 후 기록은 `chat.html`의 자체 루프다. 그 루프는 검증 배지를 **아예 렌더하지 않았다**(저장이 없어서) — 즉 "새로고침 전후 동일" 기준은 S/N에 대해서도 이미 거짓이었다. 검증 결과를 저장하고, **렌더러가 셋**(HTMX 폴백·기록 루프·스트리밍 JS)이라 배지 규칙을 `VerificationSnapshot` 한 곳으로 모았다
- **3-c의 절반이 틀렸다**: 절단은 뒤에서 덜어낼 뿐이라 없던 줄 중간 펜스를 만들 수 없다 — 실제 결함은 홀수 펜스 하나뿐이었다. 처음 쓴 테스트 2개가 이미 결함 있는 입력을 먹여 통과해 버렸다 → **새 테스트는 반드시 수정 전 코드에서 실패시켜 볼 것**
- **순서 제약**: 0-c(스타일 지시문 층 제거)는 1-a/1-b와 **한 커밋**이어야 한다 — 그 층이 S/N의 분량 지시를 나르는 유일한 통로라, 대체 프롬프트 없이 걷어내면 두 모드가 공용 5섹션 형식으로 붕괴한다

**완료 후 보정 (2026-08-25)**: ① 검증 응답을 읽지 못하면 `grounded=true`로 위조하던 폴백을 **판정 없음**(`grounded=null`, 배지 없음·재시도 없음)으로 교체 — 검증한 적 없는 답변에 `검증됨`/`생성` 배지가 붙고 `sufficient=false` 재시도까지 사라지던 경로였다(운영 진단은 OPERATOR_MANUAL §8). ② 중지 버튼이 화면만 멈추고 LLM 스트림은 계속 소비하던 것을 실제 취소로 수정(`CancellableTokenStream`). ③ Direct S 상한 1,000→1,500자.

**미착수 — 4-c (검색 부스트 상향)**: `retrievalBoost()`는 `RetrievalService`에 배선돼 있으나 **모든 모드에서 0**이고 `app.search-creative-top-k-boost` 외부화도 하지 않았다. **노브와 `MAX_EVAL_EXCERPT_CHARS`(20,000) 상향은 한 변경에 함께 들어가야 한다** — 지금 `/settings`에 노브만 내면 부스트를 1만 올려도 상한을 넘어 하위 순위 문서가 검증 창에서 빠지고, `AnswerService`가 `.limit(5)`를 없애며 고쳤던 오탐(문서 #10~12에만 있는 값을 정확히 인용한 답변이 `grounded=false`)이 되살아난다. 부스트 근거 자체도 약하다 — 실사용 topK가 이미 10~12라 +4면 ~40,000토큰으로 32K 모델에서 앞부분이 **조용히** 잘린다(창의 모드에서 환각 금지 조항이 잘리는 것이 최악).

### 6.26 컨텍스트 초과 대응 — 창 인지 + 입력 예산 ✅ 완료 2026-09-01

**유지해야 할 결정**

- **`max_tokens` 는 상한이 아니라 예약이다.** 서버가 `프롬프트 + max_tokens ≤ n_ctx` 를 검사하므로 **큰 캡이 초과의 원인**이다. 그래서 방향은 "캡 제거"가 아니라 "창에서 파생"이다. 기동 시 `max-tokens >= context-size` 를 잡아 창의 절반으로 낮추는 검사가 그 첫 조각 — 그 조합은 입력 자리가 0 이하라 **모든 요청이 실패하는데 설정만 보면 멀쩡해 보인다**.
- **"모름"을 값으로 표현한다.** `ProviderContextWindows` 는 창을 못 구하면 항목 자체를 두지 않고, 예산 로직은 그때 **아무것도 자르지 않는다**. 추측한 숫자로 근거를 버리는 것이 초과보다 나쁘다.
- **서버가 주는 "모델 상한"을 절대 쓰지 않는다.** llama.cpp `/v1/models` 의 `meta.n_ctx_train` 과 LM Studio 최상위 `max_context_length` 는 **모델이 지원하는** 최대치라, `-c 8192` 로 띄운 서버도 131072 를 돌려준다. 집어 쓰면 예산이 16배 틀려 초과를 막으려던 코드가 그 초과를 부른다. 로드된 값을 못 찾으면 상한으로 대신하지 않고 빈 값을 준다.
- **버리는 순서는 문서 → 이력.** 검색 결과는 RRF 내림차순이라 뒤가 최저 관련도이고, 이 앱의 응답 참여도 측정이 "검색 1위조차 답변에 한 글자도 기여하지 않는 경우가 흔하다"고 말한다. 반면 이력이 사라지면 사용자는 즉시 체감한다. **첫 문서는 예산을 넘어도 남긴다** — 다 버리면 프롬프트가 "문서를 찾을 수 없습니다"가 되어 검색이 성공했는데도 모른다고 답한다.
- **축소는 반드시 사용자에게 보인다.** 축소는 프롬프트에만 걸리고 출처 목록은 줄지 않으므로, 안내가 없으면 사용자는 화면의 출처를 모델이 다 읽었다고 읽는다. 턴 단위 안내(`budgetNote`)가 **몇 개**인지, 출처별 `미사용` 배지가 **어느 것**인지를 말한다. `answerShare=0`("읽고도 안 썼다")과 **다른 사실**이라 따로 표시한다 — 앞은 검색이 그럭저럭 맞았다는 뜻이고 뒤는 답변이 불완전할 수 있다는 뜻이다.
- **검증 호출은 답변 호출과 따로 예산을 잡는다.** 같은 문서에 답변 전문과 스키마가 얹히고 이력은 빠져 모양이 다르다. 이 앱 최대의 단일 요청은 답변이 아니라 이쪽이다.
- **재시도로 받아 낸 답과 그 답을 믿는 것은 다른 문제다.** 축소 재시도가 검증 발췌를 줄이면 `EvalExcerpts.trimmed()` 가 참이 되고, 그러면 기존 가드(`unreliableNegative()`)가 그 `grounded=false` 를 **판정 없음**으로 떨어뜨린다. 이 연결을 유지하려고 `buildEvalExcerpts()` 가 `totalAvailable`(원본 문서 수)을 따로 받는다 — 줄인 목록의 크기를 전체로 쓰면 `trimmed()` 가 거짓이 되어 **줄어든 근거로 내려진 부정 판정을 그대로 믿게 된다**. `.limit(5)` 사고의 정확한 모양이라 재시도가 그것을 되살리게 둘 수 없다.
- **재시도한 축소도 사용자에게 보인다.** `withShrinkRetry()` 가 성공한 단계를 함께 돌려주고 호출부가 `withBudgetNote(state, level)` 을 그 단계로 **다시** 세운다. 안 하면 화면은 0단계 기준으로 안내하고 모델은 그보다 적은 문서를 봤다는 상태가 남는데, 그건 이 기능이 막으려던 바로 그 상태다(7단계).
- **스트리밍은 토큰이 하나라도 나갔으면 재시도하지 않는다.** 화면에 앞부분이 두 번 찍힌다. 초과는 생성 전에 거절되므로 실제로는 늘 재시도 가능하지만, 그 가정이 깨졌을 때 사용자가 보는 것이 중복 텍스트라 조건으로 못 박아 둔다.
- **검증 발췌를 "답변에 실제로 쓰인 문서"로 좁히지 않는다.** 어느 문서가 쓰였는지는 그 호출이 끝나야 알 수 있고(`usedDocs` 는 출력, `AnswerAttribution` 은 FINALIZE), 설령 미리 안다 해도 **답변을 닮은 문서만 골라 채점**하는 셈이 된다. 무엇보다 근거는 답변이 인용한 문서에만 있지 않다 — `.limit(5)` 사고가 정확히 그 모양이었다(#6~8 문서에만 있는 포트·경로를 정확히 인용한 답변이 근거 없음 판정). 순위 기반 축소는 정직하게 로그·화면에 남지만, 답변 기반 축소는 `grounded=true` 를 쉽게 만들면서 그 사실이 어디에도 남지 않는다.

**계획이 틀렸던 지점 (같은 실수 방지)**

- **`/v1/models` 로 창을 알 수 있을 거라 가정했다.** OpenAI 호환 규격에는 컨텍스트 필드가 없다. 서버별 경로(llama.cpp `/props`, LM Studio `/api/v0/models`)를 따로 두드려야 하고, 각 서버가 함께 노출하는 비슷한 이름의 필드가 **오답**이라는 것이 이 단계의 핵심이었다.
- **"프로바이더별 설정을 빈에 구우면 된다"가 틀렸다.** `defaultOptions` 는 호출자가 옵션을 안 줬을 때만 쓰이는데 블로킹 호출부는 매번 자기 `maxTokens` 를 실어 보낸다 → 채팅 경로에서 무효. 호출부를 고쳐 프로바이더를 알게 하는 방법도 안 된다(누가 받을지는 라우터가 나중에 정한다). 답은 **선택 이후에 도는 데코레이터**(`MaxTokensCappingChatModel`)였다.
- **예산을 한 번만 계산하면 된다고 봤다.** PROGRESSIVE 업그레이드는 **창이 더 큰** PREMIUM 으로 가므로, 원래(로컬) 프로바이더 기준 예산을 재사용하면 "불충분해서 다시 만드는" 답변이 오히려 문서를 덜 받는다. 호출부마다 다시 계산하는 것이 맞고, 그래서 `buildAnswerPrompt()` 가 프로바이더 이름을 명시로 받는다.
- **"경계를 못 찾으면 전부 버린다"가 이력에서 사고를 냈다.** `trimHistory` 는 `"Q: "` 턴 경계를 가정했는데 §6.10 요약 경로는 요약문 + 최근 턴을 준다 → 경계가 없어 **대화 맥락이 통째로** 사라졌다. 폴백은 항상 "가능한 만큼 남기는" 쪽이어야 한다.
- **핫 값 하나가 생성자에 굳어 있었다.** `MemoryService.maxConversationChars` 가 그것이고, 축소 로직이 **같은 `max-tokens`** 에서 파생되면서 둘이 서로 다른 상한을 믿는 상태가 만들어졌다. 새 기능이 기존 값을 근거로 삼을 때는 그 값이 핫인지 먼저 확인할 것.

### 6.26 컨텍스트 초과 대응 — 창 인지 + 입력 예산 ✅ 완료 2026-09-01 — 해소된 이슈

- ~~**입력 예산은 답변·검증 호출에만 걸린다.**~~ **해소 2026-09-01(8단계)** — 인덱싱의 **재작성** 호출(MD 교정 `MarkdownCorrectionService`, txt→md 구조화 `TextToMarkdownService`)이 조각 크기를 창에서 파생시킨다. 남은 것은 분류·MultiQuery 확장·키워드+맥락 추출인데, 이들은 입력이 질문 한 줄이거나 청크 하나여서 성격이 다르다(창 압박의 원인이 아니다). **재작성만 따로 다룬 이유**: 출력이 입력에 비례해 예약을 먼저 빼는 식이 순환이 되고(`S ≤ (창 − 지시 − 여유) / 2.5` 로 풀었다), 무엇보다 답변 경로처럼 **버리는 축소가 아니라 조각을 더 잘게 나누는 축소**라 내용 손실이 0이다 — 그래서 "창을 모르면 아무것도 하지 않는다"의 반대편 위험(근거를 버림)이 여기엔 없다. 그럼에도 **줄이기만 한다**: 창이 넉넉하다고 조각을 키우면 경계가 이동해 멀쩡한 배포의 교정·청킹 결과가 바뀐다.

- ~~**축소 후 재시도(shrink-and-retry)는 만들지 않았다.**~~ **해소 2026-09-02(9단계)** — `AnswerService.withShrinkRetry()`, 초과 1회당 문서 `app.llm.shrink-step` 개(기본 **1**), 재시도 상한 5회 → 기본 조합에서 topK=10 이면 10→9→8→7→6→5. **계획(이진 축소)을 따르지 않았다.** PLAN 이 적어 둔 "절반씩으로 왕복을 log(n) 으로" 는 왕복만 세고 **버려지는 근거를 세지 않는다**. 사전 예산이 이미 창에 맞춰 놓은 뒤라 여기까지 오는 초과는 대개 아슬아슬하고(`TokenEstimator` 오차의 정상 범위가 0.75~1.35), 그런 초과에 문서를 반으로 자르면 한 개만 덜어내면 됐을 자리에서 다섯 개를 버린다 — 답변은 나가지만 근거의 절반이 없는 답변이다. 실패한 시도의 왕복은 생성 전에 거절되므로 빠르고(느린 것은 마지막 성공 호출 하나뿐), 그래서 왕복보다 근거를 아끼는 쪽이 맞다. 대신 상한(`MAX_SHRINK_ATTEMPTS`=5)이 필요하고 `step × 5` 가 도달 가능한 최대 축소폭이다. **교훈**: 계획에 적힌 알고리즘도 그것이 최적화하는 지표가 실제 비용인지 다시 확인할 것.

- ~~**토큰 추정 계수가 가정이다.**~~ **해소 2026-09-01** — `TokenEstimateCalibration` 이 블로킹 호출마다 `TokenEstimator` 추정과 서버가 준 실제 prompt 토큰을 대조해 50건마다 누적 계수를 로그로 낸다(`[TOKEN_CAL]`, 정상 범위 0.75~1.35 밖이면 WARN). **관측만 하고 예산을 자동 보정하지는 않는다** — 표본 수에 따라 같은 질문이 다른 양의 근거를 받으면 재현이 안 된다. 계수가 1에서 크게 벗어나면 사람이 조정한다.

- ~~**스트리밍 출력 예약이 과보수적이다.**~~ **해소 2026-09-01** — 스트리밍은 `max_tokens` 를 보내지 않아 서버가 예약하지 않는데도 블로킹과 같은 값(N 7,000)을 빼고 있었다. 그건 폭주 방지선이지 예상 분량이 아니다(§6.24 실측: 목표 5,000자→3,047자, 10,000자→3,187자). 이제 `ResponseMode.minChars()` 로 낮춰(N 5,000) 입력 예산이 2,000 토큰 늘었고, 여전히 블로킹 예산을 넘지 않는다. **경로마다 다른 값이라 `buildAnswerPrompt()` 가 `streaming` 플래그를 받는다** — `provider.stream()=false` 경로는 `answerOptions()` 를 붙여 보내므로 블로킹 쪽이다.

- ~~**`qualityScore` / `app.llm.progressive-threshold`**~~ **제거 2026-09-01** — 문서에만 있던 개념이었다. 프로퍼티는 `AppProperties.LlmConfig` → `LlmRouter` 필드까지 실려 다녔지만 `getProgressiveThreshold()` 의 호출부가 **하나도 없어** 0.0~1.0 어느 값을 넣어도 동작이 같았고, 점수를 계산하는 코드도 없었다. 실제 승격 조건은 `PROGRESSIVE` + `sufficient=false` + 재시도 소진 셋뿐이다. **교훈**: 확장 여지로 남긴 설정이 소비처 없이 오래 남으면 튜닝 손잡이처럼 보이는 거짓말이 된다 — 스칼라 점수를 도입한다면 **소비처와 같은 커밋에서** 다시 넣을 것.

- ~~**`max-tokens` 는 여전히 핫 편집 대상이 아니다.**~~ **해소 2026-09-02(11단계)** — 이 페이지에 마지막으로 남아 있던 조회 전용 값이었는데, 하필 **가장 열려 있어야 할 값**이었다: 단순한 출력 상한이 아니라 이력 예산(×0.5)·MD 교정 섹션 크기·인덱싱 출력 예약·컨텍스트 입력 예산이 전부 여기서 파생되므로, 컨텍스트 압박과 싸우는 운영자가 정작 가장 크게 듣는 손잡이를 만지려면 재기동해야 했다.
  - **앞 항목이 적어 둔 다섯 소비처 점검이 그대로 작업 목록이 됐다.** 실제로 고칠 것은 둘뿐이었다 — `MarkdownCorrectionService` 의 섹션 크기(생성자 필드 → 메서드)와 프로바이더 캡. 나머지 셋은 이미 매 호출 `props.llmSafe().maxTokens()` 를 다시 읽고 있었다. **남겨 둔 메모가 없었다면 이 둘을 찾는 데 대부분의 시간이 갔을 것이다** — 핫으로 열 수 없는 값을 만들 때는 무엇이 막고 있는지 그 자리에 적어 둘 것.
  - **캡을 `int` 대신 `IntSupplier` 로 받는다.** `MaxTokensCappingChatModel` 이 호출마다 `LlmConfig.liveMaxTokens()` 를 부르므로 전역 `max-tokens` 변경과 **10단계의 창 재탐지**가 같은 경로로 들어온다 — 두 기능이 우연히 만난 것이 아니라, 상한이 그 둘의 함수라서 하나를 런타임 값으로 만들면 다른 하나도 따라와야 했다.
  - **그래서 10단계의 재기동 안내를 좁혔다.** 예전엔 창이 바뀌어 상한이 달라지면 무조건 재기동을 알렸는데, 이제 그 상한은 따라온다. 남은 것은 프로바이더 빈의 `defaultOptions` 하나 — **옵션을 실어 보내지 않는** 프레임워크 내부 호출자(MultiQuery 확장기)의 폴백이고, 캡 데코레이터는 손댈 옵션이 없어 그 경로를 그냥 지나간다. 그래서 창이 **좁아져** 그 기동값이 새 창을 넘게 될 때만 경고한다(넓어진 경우는 작을 뿐 안전하다 — 잦은 경고는 아무도 안 읽는다). `temperature` 가 이미 갖고 있던 예외와 같은 모양이다.
  - **범위의 바닥이 0 이 아니다**(1,000~32,000). 이 값이 순수한 출력 상한이었다면 0 = 무제한이 자연스럽지만, 여기서 이력 예산과 섹션 크기가 파생되므로 0 에 가까운 값은 "짧게 답한다"가 아니라 **이력도 근거도 없는 상태**가 된다.

- ~~**`ContextWindowProbe` 는 기동 시 1회다.**~~ **해소 2026-09-02(10단계)** — `/settings` 의 **컨텍스트 다시 탐지** 버튼(`POST /admin/settings/context-window/reprobe`).
  - **왜 타이머가 아니라 버튼인가**: 주기적으로 다시 물으면 예산이 스스로 움직여 같은 질문이 시각에 따라 다른 양의 근거를 받는다 — `TokenEstimateCalibration` 이 "관측만 하고 예산을 자동 보정하지 않는다"고 정한 것과 같은 이유다. 창을 바꾼 사람은 자기가 바꿨다는 것을 알고 있으므로 갱신 시점을 그 사람이 정하는 편이 정직하고, 감사 로그(`settings.context-window.reprobe`)에도 남는다.
  - **컨텍스트 초과를 신호로 삼는 안(B안)은 뺐다**: 그건 창이 *줄어든* 경우만 잡는다. 정작 위험한 쪽은 창이 *커졌는데* 앱이 옛 값으로 계속 자르는 경우인데, 그쪽은 초과가 나지 않아 영영 안 잡히고 **조용히 품질만 깎인다**(사용자에겐 `budgetNote` 만 뜨고 이유는 아무도 모른다). 게다가 A4 축소 재시도와 자리가 겹쳐 "먼저 다시 물을까, 먼저 줄일까"라는 순서 문제를 만든다.
  - **버튼이 상황을 악화시키지 않도록 세 가지를 안 한다**: `context-size` 선언 프로바이더는 묻지 않고(관측이 의도를 덮어쓰지 않는다), 탐지 실패는 이전 값을 지우지 않으며(알던 값을 "모름"으로 되돌리면 입력 예산이 통째로 꺼진다), LOCAL 이 아닌 프로바이더는 대상이 아니다. 셋 다 결과 표에 이유와 함께 남는다 — 특히 "물어봤고 같았다"(UNCHANGED)와 "안 물어봤다"(SKIPPED_DECLARED)를 구분하지 않으면 버튼이 고장 난 것처럼 보인다.
  - **재탐지가 고치는 것은 입력 예산뿐이다.** 출력 예약은 `cappedMaxTokens()` 로 빈 생성 시점에 굳어 `MaxTokensCappingChatModel` 안에 들어가므로 재기동 말고는 되돌릴 방법이 없다. 그 경우를 `restartNeeded` 로 함께 알린다 — 안 알리면 "재탐지했으니 이제 괜찮겠지"라는 잘못된 안심이 남는다. 기동과 재탐지가 **같은 공식**을 쓰도록 순수 함수를 `ProviderContextWindows` 로 옮겼고(`apiBase()`/`isLocal()`/`declaredContextSize()` 도 `ProviderConfig` 로 올렸다), 복제했다면 한쪽만 고쳐졌을 때 탐지가 조용히 404 를 받거나 재기동 안내가 틀렸을 것이다.
