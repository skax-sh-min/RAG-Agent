# RAG Agent — Project Guide

## Stack

- **Backend**: Spring Boot 3 + Spring AI, Java 21 (virtual threads on), SQLite (WAL, pool=1)
- **Frontend**: Thymeleaf + HTMX, Bootstrap 5, no JS framework
- **Vector DB**: `app.vectorstore.type` selects the backend (Phase 5) — `chroma` (default; per-version collections via `VectorStoreRegistry`) or `sqlite-vec` (vec0 virtual table in the SQLite file). Both behind `VectorStoreProvider`, injected into `VectorStoreFacade`.
- **LLM**: OpenAI-compatible endpoint (Spring AI `ChatClient`); local LLM-Studio or remote

## Architecture

```
AgentGraph (state machine) → nodes: CLASSIFIER → RETRIEVAL → ANSWER → CRITIC → FINALIZE
AgentState: immutable record, each node returns new instance via state.toBuilder().xxx().build()
```

Flow:
- `meta` question → DIRECT_ANSWER (skip retrieval)
- others → RETRIEVAL → ANSWER (sufficiency check) → CRITIC → FINALIZE, retry loop up to `maxRetryCount`
- `directMode=true` → AgentGraph skips CLASSIFIER/RETRIEVAL/CRITIC entirely
- `AgentService.chat()` pre-runs history load + classify in parallel; AgentGraph skips CLASSIFIER when `questionType != null`
- SSE streaming → `StreamingAgentService.run()` drives `AgentGraph.runStreaming()` with `SseGraphListener`

| `ingestion/ChunkSplitter.java` | Pure chunk-splitting/merging algorithm; no Spring bean deps, extracted from `DocumentIndexer`. **Two chunking strategies selected by `app.chunk-split-granular` (hot, applies on the next indexing / ↺ re-index)**: `false` (default) = everything described below — size-driven merging toward `chunkSize`; `true` = **최대 분할** (`splitChapterGranular()`), which splits at every heading and **never consults `minChunkSize`** (neither `mergeSectionsByChapter()` nor `backwardMergeShortChunks()` runs), so a short subsection stays its own chunk. Its one merge rule is `groupLeadInSections()`: a section that is a heading plus ≤2 content units (`isLeadInSection()` — units = `max(sentence-terminator count, non-blank line count)`, and any table row or code fence disqualifies it outright) folds forward into **strictly deeper** headings only, re-evaluated after each step so a heading ladder collapses only while every level so far is still lead-in text, never across a sibling/parent heading, a `PAGE_OR_SLIDE` boundary, or `chunkSize`. For pptx/pdf, granular skips only the **cross-slide** merges (`mergeIdenticalHeadingSlides()` + `mergeShortSections()`) and instead runs `joinSectionsWithinPage()`, which collapses each `PAGE_OR_SLIDE` group into one Document — heading lines are section boundaries in the loader too, so a titled slide arrives as a `"## 제목"` section plus a `"### 소제목"`+body section, and emitting those separately would produce a body-less title-only chunk. Net effect is a true 1 slide = 1 chunk; heading-based splitting never applies to these formats since their headings are slide titles, not chapter structure. Boundary handling is shared but parameterized: `blockToleranceFor(granular, chunkSize, overlap)` feeds `adjustEndForCodeBlock()`/`adjustEndForTableBlock()` — the default path passes `overlap` (unchanged, but note `app.chunk-overlap` now defaults to **0**, which makes both block guards no-ops and lets every straddling table/fence get cut), granular passes `max(overlap, chunkSize/2)` so a chunk may reach ~1.5×`chunkSize` to finish a block or end early to let one start the next chunk. **Two section-aware strategies** routed by filename (**and**, for PDF, `MetaKey.SOURCE_TYPE != "ocr"`): **chapter-structured** (md/docx/txt) → `splitChapterStructured()`/`mergeSectionsByChapter()`; **page-structured** (pptx/non-scanned pdf) → `mergeIdenticalHeadingSlides()` pre-pass then legacy `mergeShortSections()`; scanned PDF and any other extension get plain sliding window. **`mergeSectionsByChapter()`** (md/docx/txt): only a section still below `minChunkSize` (normalized length) forward-merges into the next, and **never into a higher/parent heading** (`next.level < accLevel`, level = leading `#` count) — then the next section's size decides: 규칙1 combined ≤ chunkSize → merge; 규칙2 next alone ≤ chunkSize → stop; 규칙3 next > chunkSize → merge only if prepending keeps the sliding-split's last piece ≥ `minChunkSize*1.5` (`rawSlidingPieces()` look-ahead, extracted from `slidingWindow()` so simulation and real split share boundaries). Each `SectionGroup` keeps the first section's metadata + original index — **except `MetaKey.CHAPTER_NO`**: if the starting section's chapter number is still the `"0"` prologue placeholder (no real H2+ heading seen yet — chapter counting in `DocumentLoaderService` only starts at H2, so a leading H1-title-only or heading-less section stays `"0"`) but the merge absorbed a later section that already carries a real chapter number, the group reports that first real number instead of `"0"` (`firstRealChapterNo()`) — otherwise a document opening with a short H1 title/intro would mislabel its first chunk as chapter `"0"` even though the merged content actually starts inside chapter 1. No-op (keeps `"0"`) when every merged section is still `"0"`, and no-op when the starting section already has a real chapter number (ordinary "first section's metadata wins" applies). `splitChapterStructured()` then sliding-splits oversized groups (+ `reinjectHeadingForSplitPieces()`), `prependParentBreadcrumb()` prepends the immediate parent heading (one level up) to the **first (non-tail) piece** of a child chapter (heading level ≥ 3; `##`/heading-less skipped), and `backwardMergeShortChunks()` folds any still-sub-`minChunkSize` chunk into the previous one (cross-section analog of `mergeTinyChunks()`). **`mergeIdenticalHeadingSlides()`** (pptx/pdf, runs first): groups raw sections into per-slide bundles by `MetaKey.PAGE_OR_SLIDE`, then merges consecutive slides whose assembled `##`+`###` heading pair is **exactly identical** (both levels must be present — never true for non-scanned PDF, which emits no headings) into one chunk, up to `MAX_IDENTICAL_HEADING_MERGE_SLIDES` (default **2**) slides per group, as long as the combined normalized size stays `≤ chunkSize` — once a group hits the cap the next slide starts a fresh group of its own (4 identical-heading slides in a row → two 2-slide chunks, not one 4-slide chunk). Every slide after the first in a group has its duplicate `##`/`###` lines stripped (`stripDualHeadingLines()`) but gets a `[페이지: N]` text marker inserted in their place so the merged chunk still shows where each slide's content began (the merged `Document`'s `PAGE_OR_SLIDE` metadata itself still only reflects the first slide, same "first section's metadata wins" convention as everything else here). **`mergeShortSections()`** (pptx/pdf) then merges by 40%/75%-of-chunkSize thresholds and refuses to merge across a `MetaKey.PAGE_OR_SLIDE` mismatch (no-op for md/docx/txt) so PPTX/PDF keep a "1 chunk = 1 slide/page = exact citation" guarantee. Size-budget checks (`mergeSectionsByChapter`/`mergeShortSections`/`enforceMaxChars`) measure normalized length (`MarkdownNoiseNormalizer`) — `slidingWindow()`/`rawSlidingPieces()` and offset-based helpers stay on raw text. `mergeTinyChunks(chunks, minLength, maxOverlap)`'s **`maxOverlap` must be the real sliding-window `overlap`**, not `minLength` — it is how many characters of a join `mergeAdjacentText()` may treat as duplicated and delete, and only the overlap region can legitimately be duplicated. Passing `minLength` (as it did before) made the join scan up to `min-chunk-size` (default 500) chars for a matching suffix/prefix even at `chunk-overlap=0`, where pieces are disjoint — on repetitive content (repeated table rows, uniformly formatted list items) that match is coincidence and the text was silently lost. `maxOverlap <= 0` now joins verbatim. When `slidingWindow()` cuts a fenced code block across pieces, `reopenTruncatedBlock()`/`reopenCodeFence()` re-wrap each piece with the opening/closing fence plus a `CODE_CONTINUATION_BEFORE`/`CODE_CONTINUATION_AFTER` marker line (plain text **outside** the fence, never inside it) — these markers live in `Document.getText()` itself, so they're searchable (flow into `SearchTextBuilder`) and visible as-is in the `/admin` chunk view |

- **Records everywhere**: `AgentState`, `ThreadMeta`, `ChatResponse`, `SourceRef`, `LlmProvider` — all immutable records
- **No Spring Data JPA**: raw `JdbcTemplate` for all DB access (SQLite incompatibility)
- **HTMX fragments**: endpoints return `"fragments/xxx :: selector"` strings
- **Thymeleaf JS inlining**: any `<script>` using the `/*[[${x}]]*/ default` pattern **must** carry `th:inline="javascript"`. Without it Thymeleaf falls back to text mode, which evaluates the expression but writes it *inside the comment* and leaves the literal default in force — `const X = /*true*/ false;`. That is valid JS, so there is no error anywhere: the page silently runs on defaults forever. `chat.html` shipped without it, which pinned `SOURCE_PREVIEW_ENABLED` to its `true` fallback (the `/settings` source-preview toggle did nothing in chat), froze every `#{...}` message constant on the page at its hardcoded Korean default (EN locale unaffected by the switcher), and made `ui.retrieval-metrics-enabled` unturnable-on. Grep for `/*[[` when adding a script block
- **Spring AI auto-config excluded**: `spring.autoconfigure.exclude` drops `ChromaVectorStoreAutoConfiguration` (`ChromaConfig` manages beans manually) **and all six OpenAI model auto-configs** — `OpenAiChat`/`OpenAiEmbedding`/`OpenAiAudioSpeech`/`OpenAiAudioTranscription`/`OpenAiImage`/`OpenAiModeration`AutoConfiguration. The app builds its own chat (`LlmConfig.llmRouter`/`primaryChatModel`), embedding (`EmbeddingBeanConfig`) and per-provider `OpenAiApi` (`OpenAiApi.builder()`) beans, so it never uses a Spring AI OpenAI autoconfig bean. Left active, each of these eagerly creates an `openAiApi` bean that runs `Assert.hasText(spring.ai.openai.api-key)` and crashes startup with `OpenAI API key must be set` when `LOCAL_LLM_KEY` is blank (the normal local-only setup) — this hits the chat/embedding ones too (their *model* bean is skipped via `@ConditionalOnMissingBean`, but their `openAiApi` bean is not)
- **Null-safe config**: always use `props.llmSafe()` / `props.indexingSafe()` / `props.authSafe()` / `props.imageDescriptionSafe()` / `props.memorySafe()` / `props.summarySafe()` — never access the raw getters directly (`AppPropertiesSafeAccessorTest` enforces this for every `xxxSafe()`)
- **Korean prompts**: all LLM system/user prompts are Korean
- **MetaKey constants**: all vector store metadata access goes through `MetaKey.*` — never inline strings
- **Embedding/FTS input ≠ stored text (§10.1 Contextual Retrieval)**: `Document.getText()` (Chroma document, `vec_document_chunks.content`, source accordion, `/admin` chunk view) is always the untouched original. `SearchTextBuilder.build()` derives the embedding + `chunk_fts.content` text (`MetaKey.CHUNK_CONTEXT` + `MarkdownNoiseNormalizer.normalize()`); `AnswerService.buildAnswerPrompt()` calls `MarkdownNoiseNormalizer.normalize()` directly (no context header) for the `[검색된 문서]` block
- **Upload validation**: call `FileTypeDetector.matches(path, ext)` after writing to temp file; return 422 on mismatch
- **Input validation**: `PromptInjectionGuard.validate()` must be the first call in any public chat entry point
- **AgentState mutation**: use `state.toBuilder().xxx().build()` — the old `state.withXxx()` methods were removed (were deprecated since 0.2.0)
- **Parallel tests**: `src/test/resources/junit-platform.properties` runs test CLASSES concurrently (methods within a class stay serial). Any test that loads a Spring context (`@WebMvcTest`/`@SpringBootTest` — Spring Boot re-inits Logback on context start + `@MockitoBean` reset isn't concurrency-safe), attaches a Logback appender (`ListAppender` log capture), or mutates `AppProperties`' static override source **must** carry `@ResourceLock("global-state")` so it doesn't run concurrently with the others. `ParallelIsolationConventionTest` fails the build if one is missing the lock

- All new LLM providers must go through `LlmRouter`, not direct `ChatClient` injection
- `ProviderRole`: LOCAL / NORMAL / PREMIUM (orthogonal to `TaskType`)
- `classifyOnly()` does not accumulate tokens into `AgentState` → `llmCallCount` under-reported by 1 (accepted trade-off)
- `DocumentIndexer.syncDirectory()` calls `saveRegistry()` once after all parallel work — never call it from parallel threads
- `DocumentIndexer.index()`/`reindexFromMd()` read `props.chunkOverlapSafe()` exactly once per call, into a local `usedOverlap`, reused both for `chunkSplitter.splitDocuments()` and the `DocRegistry.DocRegistryEntry.chunkOverlap` written afterward — `app.chunk-overlap` is hot-editable (§6.13), so re-reading it after chunking could record a value the chunks weren't actually cut with. § 문서 내보내기's `ChunkReassembler` overlap-removal step relies on this being accurate; `ChunkOverlapBackfill` (`ApplicationReadyEvent`) fills in `NULL` for documents indexed before this column existed. `app.chunk-overlap` now defaults to `0`, which makes the whole step a no-op for newly indexed documents
- `DocumentIndexer.index(IndexRequest)` is the single entry point for both bulk sync (`IndexRequest.parallel(...)`) and interactive single-file upload (`IndexRequest.single(...)`) — neither call shape calls `saveRegistry()` itself (caller's responsibility); only `reindexFromMd()` (at its end) and `syncDirectory()` (once after all parallel work) call it
- Document storage is shared (no per-user isolation): `data/documents/`, `data/images/{docId}/`, `data/converted/{docId}.md`; DocRegistry and Chroma collection use `DocRegistry.SHARED` as the owner key
- PPTX / non-scanned PDF → Markdown: the `[페이지: N]` marker (NOT a synthetic heading) is the per-slide/page section boundary — `PptxToMarkdownConverter`/`PdfToMarkdownConverter` no longer emit `## N번 슬라이드`/`## N페이지`, and both `DocumentLoaderService.splitMarkdownBySections()` and `MarkdownCorrectionService.splitBySections()`/`splitByPages()` split on the marker. Only PPTX/PDF emit `[페이지: N]`; DOCX/TXT/MD never do (so the marker-as-boundary logic is a no-op for them). At PPTX conversion time, image-less duplicate + agenda/TOC slides are dropped (`app.pptx-remove-duplicate-slides`, default on), title-only section-divider slides are dropped (`app.pptx-drop-divider-slides`, default on, keeping sentence-like key-message titles), a title-only slide (no image, no group/diagram/chart/table text) whose exact title also appears in the immediately following slide is dropped as a "preview title" slide (`app.pptx-drop-redundant-title-slides`, default on — last slide never affected, no next slide to compare against), and the very last slide is dropped when its image-less normalized content contains an ending marker (끝/END/The End/감사합니다/Thank you) with at most 10 other normalized characters left over (`app.pptx-drop-ending-slide`, default on); dropped slides never shift `page_or_slide` numbering (`slideNum = i+1`). `MetaKey.CHAPTER_NO` stays `"0"` for PPTX/PDF (`skipChapterNumbers=true`) — real hierarchical chapter numbers come only from DOCX/MD/TXT H2–H6 headings
- PPTX multi-line shape text → code fence or block separation, in **both** shape paths: `appendShapeTextBlock()` for a text shape inside a group/diagram, `appendSlideBodyShape()` for a standalone slide-body text box (code lives in standalone boxes more often than in groups). Single-line shapes are unchanged (group: tight `\n` for short node labels; body: `appendBodyLine()`'s `\n\n`). **Multi-line** shapes get fenced with ``` when `looksLikeCodeBlock()` says code — the fence body uses `rawParagraphText()` (`stripTrailing()`, never `trim()`, so indentation survives) with interior blank lines preserved, and no emphasis markers, so code is reproduced verbatim and `MarkdownNoiseNormalizer`/`splitMarkdownBySections()` both leave the interior alone. The converter emits a **bare** ``` fence; `MarkdownCorrectionService.correct()` then finishes the job — `normalizeCodeContent()` strips the interior blank lines except one before a multi-line-comment or function/class signature (which is why preserving them in the converter matters), and `postProcessMarkdown(md, isPptx=true)` guarantees a blank line around the fence. The same pass also infers the fence's language tag from its content (`inferLanguage=true`), which is deliberately **decoupled from the `addHeadingNumbers` checkbox** so PPTX (which always forces it `false`) and any file uploaded with the box unchecked still get tagged fences — the `addHeadingNumbers` branch now only runs `addHierarchicalHeadingNumbers()` (fence-aware, so it never needs a code re-polish). Non-code multi-line text is blank-line separated in the group path only; the body path already separates paragraphs via `appendBodyLine()`. `appendSlideBodyShape()` collects a shape's surviving `BodyLine`s before emitting (a whole-shape fence can't be decided line-by-line) but runs heading promotion + consecutive-dup skipping in the original paragraph order, so those verdicts are unchanged. `looksLikeCodeBlock()` is deliberately conservative: **blank lines count toward neither the numerator nor the denominator** (a snippet's interior blank lines must not dilute the ratio), any `-`/`*`/`1.`-prefixed line (or a native `para.isBullet()`) means **not** code, an existing ``` means not code, and otherwise ≥`CODE_LINE_RATIO_PERCENT` (60%) of non-blank lines must hit `CODE_LINE_SIGNAL`. Arrows (`->`/`=>`) are excluded from the signal set on purpose — "요청 -> 응답" flow labels are far more common in diagrams than code
- PPTX shape-group text: a group-member shape whose entire text is a bare counter/step-badge label (`"1"`, `"1."`, `"(2)"` — `BARE_NUMBER_LABEL` regex in `PptxToMarkdownConverter.appendGroupText()`) is skipped from the extracted `[도형 그룹]` text — the group is already rasterized to an image separately, so a lone digit with no context is noise, not content. A label with trailing text (`"1단계"`) is unaffected — the regex only matches when the **entire** trimmed text is numeric (with optional surrounding `()`/`[]`/`.`/`)`). If filtering leaves a group with no other text, `appendShapeGroup()`'s existing empty-check suppresses the whole `[도형 그룹]`/`[/도형 그룹]` block, same as a purely decorative group with zero text shapes.
- **Code-fence parity is a pipeline invariant** in `MarkdownCorrectionService`: every pass after the LLM assumes fence lines pair up 1-2, 3-4, … and `normalizeCodeBlocks()` *writes* `"```" + resolvedLang` onto whatever it treats as an opener — so one unpaired fence makes it stamp a language tag onto a **closing** fence (the observed ```` ```java … ```java ```` corruption), and mispair prose into code blocks. Three guards keep it: (1) `correctSection()` discards an LLM response whose kept span (post-`cutOverlap`) has an odd fence-line count and keeps the original section — input sections are balanced by construction, and `cutOverlap()` can otherwise take half a pair with it when the model wraps marker-spanning code in one fence; (2) `fixClosingFences()` heals an unclosed fence at an H2–H7 heading, at a `[페이지: N]` marker (PPTX/non-scanned PDF emit **no** `##` headings, so a heading is never reached there), and at end of input; (3) `normalizeCodeBlocks()` refuses the whole document — no tagging, no `normalizeCodeContent()` — when the fence count is odd or when `fenceLineCount() != fenceMarkCount()` (a mid-line ```` ``` ````, e.g. prose ending in "…감쌉니다: ```" or a table cell, is invisible to the line-based passes but counted by the anchorless `FENCED_BLOCK` regex, so the two views disagree on pairing). Any new fence-touching pass must preserve this invariant. The re-index path (`DocumentIndexer.postProcessIfNeeded()`) deliberately runs only `postProcess()`, so a file already saved in a broken state is **not** self-healed by ↺ re-index — instead `POST /admin/documents/{docId}/reindex` runs a read-only pre-flight (`RagService.checkReindexFenceHealth()` → `DocumentIndexer.checkFenceHealth()` → `MarkdownCorrectionService.findFenceProblems()`) and returns **409** with `{status:"fence_problems", problems:[{line,kind,message}]}` **without starting any work**; the admin UI lists the line numbers and offers 무시하고 진행 (re-POST with `?force=true`) or 중지. `findFenceProblems()` is the read-only counterpart of `fixClosingFences()` and must stay in sync with it (same line-based scan, same three defect kinds)
- `MarkdownCorrectionService.postProcessMarkdown()`'s Pass B guarantees a blank line **before and after** three line kinds, all fence-aware (code-block *contents* are never touched): a fenced code block, a GFM table block (`markTableRows()`), and an H2–H7 heading (`looksLikeChapterHeadingNotComment()` — so `### 주석 ###`-style banner comments and any `#` line inside a fence are excluded). The heading rule deliberately matches the **raw** line (no `stripLeading()`, unlike the fence check), so an indented `##` inside a list item or indented code block is left alone; H1 is also out of scope (document-title line). Blank-line *collapsing* runs in the same pass, so the inserted blanks are never doubled and a trailing blank at EOF is trimmed. This pass also runs on re-index and on document export (`DocumentExportService` → `postProcess()`), so hand-edited MD files get the same guarantees
- `MarkdownCorrectionService.correctSection()` never sends GFM table content to the LLM: `extractTables()` (uses the same `markTableRows()` the table-aware blank-line pass in `postProcessMarkdown()` already relied on) replaces each table block with a `[TABLE_PLACEHOLDER_N]` marker before building the prompt, and `restoreTables()` substitutes the original table text back into the response afterward — a prose "표는 변경 금지" instruction alone wasn't reliable (local models were observed replacing `:` with `|` inside cells). If a placeholder is missing from the response (model dropped/mangled it), the whole section falls back to its untouched original text rather than guessing where the table belongs — same discipline as the `<<<SECTION_START/END>>>` overlap-marker check in `cutOverlap()`.
- Response mode (**S/N** in the chat input bar + **C** server-side only, default `N` — PLAN §6.24, PIPELINE §3.1): the per-message **답변의 성격** axis, orthogonal to routing mode. S/N are the *length* axis; **C (응용) is a different axis — 근거 엄격도**: it builds new code/config *using* the retrieved documents as material, so it gives up "nothing outside the documents". All three are selectable in the chat input bar. **C and Direct are mutually exclusive** — the client disables the C button while Direct is on, and **any RAG↔Direct toggle resets the response mode to `N`** (either direction, whatever was selected, stored preference included — the reset lives in the toggle's `change` handler, deliberately *not* in `updateResponseModeAvailability()`, which also runs on page load and would wipe the stored choice every time), and the server enforces it independently in `ChatRequest`'s compact constructor (REST) and `ChatForm.responseModeOrDefault()` — the one point the HTMX form path and the SSE path share, since `ChatController.normalizeResponseMode()` is not on the SSE path. `AgentGraph`'s guard (Step 2-c) is separate: it stops a null Direct prompt key from throwing, while these two also keep the stored `response_mode` honest. `L` was removed and `M` renamed to `N`; `ResponseMode.parse()` is lenient so legacy `"M"`/`"L"` in `conversation_turns.response_mode` and in the browser's `localStorage['chatResponseMode']` both degrade to `N` — **no migration**. **Each mode owns a whole system prompt** (`prompt.answer.system.{s,n,c}`, and `prompt.direct.system.{s,n}` for the Direct path; meta keeps `prompt.direct.meta.system` regardless of mode). **C has no Direct prompt on purpose** (`directSystemPromptKey=null` → `allowsDirect()=false`): retrieval is its premise, so `AgentGraph` sends neither a `directMode=true` request nor a `"meta"` classification to DIRECT_ANSWER for it — the first would NPE on the null key, the second would skip retrieval entirely and silently neuter the mode ("문서에 있는 날짜 함수로 예제 만들어줘" classifies as meta). The old approach — one shared prompt plus a `prompt.answer.style.*` instruction appended to the *user* message to override it — is gone, because it failed for S: the system prompt's list of five section headers beat the one-line negative instruction, the model emitted all of them, and the server truncated afterwards so the screen and the stored answer disagreed. **S's prompt therefore never names the section headers at all** — listing them to forbid them is enough for a weak local model to follow the list (`ResponseModeSystemPromptTest` pins this, plus S's character cap and N's absence of any number). **S's cap is per path, not per mode**: the RAG prompt says 1,000자, the Direct one 1,500자 — Direct has no document excerpts to cite, so the answer has to spell itself out. The number itself is not the invariant the guard holds; what it holds is that the ko and en bundles name the *same* number, since a mode that answers at two different lengths depending on UI language is the failure that actually shipped. **Length policy is asymmetric on purpose**: a cap on short output sits *before* where the model stops on its own and binds; a target on long output sits *after* it and does nothing (old M asked ~5,000 chars → 3,047 actual; L asked ~10,000 → 3,187 — that measurement is why L died). So N names no number and instead says what to cover. **Branch on capabilities, never on the enum value** — `skipsVerification()` (S: no eval call, no CRITIC), `summaryOnly()` (deliberately separate from the former: same value on S today, different questions), `allowsDirect()`, `allowsCuration()`, `retrievalBoost()`, `usesCreativeTemperature()` (which temperature knob), `usesCreativeEval()` (which record the returned JSON is read into); `ResponseModeBranchConventionTest` fails the build on a `== ResponseMode.X` in main. The last two always move together today but answer different questions, so they stay apart — and picking the parser by comparing the *prompt key string* is deliberately avoided: renaming the key would silently select the wrong parser. **`maxTokens(configured)` = `min(configured, max(256, max(round(configured*ratio), minChars)))`** — S 0.15/2,000, N and C both 0.70/5,000 (C's length policy is N's, so its budget is too). The `min` is what stops a mode floor from punching through the operator's ceiling (default 6,000 used to hand L 10,000). It applies to **blocking calls only**; streaming has no cap, and this budget is a runaway guard, not a length target — it must stay comfortably *above* the prompt's own cap (S: prompt 1,000자 — 1,500 on the Direct path — vs budget 2,000+), so raising S's prompt cap means raising `minChars` too. `/settings` renders a read-only 응답 예산 row per mode showing which term won (`2,000 (최소 보장)` / `8,400 (상한의 70%)` / `3,000 (설정 상한)`) since the crossover differs per mode (S 13,334, N/C 7,143). **S is excluded from curation** (`allowsCuration()=false`): its answer is entirely one `## 요약` section, so `CuratedTextUtils.stripStructuralSections()` leaves nothing and the vector would carry only the question — `CuratedQaService.onLike()` returns immediately, creating no `curated_qa` row, which makes 좋아요 a no-op on S turns (LIKE's only consumer is curation). 싫어요 is unaffected. **`SummaryOnlyGuard` is a conditional safety net, not a rewriter**: it returns a compliant answer by identity and only salvages the first section when the model emitted 2+ headings (fence-aware); it never cuts by character or line count, and it logs at INFO when it fires — that frequency is the only measurement of whether the S prompt is working. **When the server changes the answer after streaming** (that guard, `truncate()`'s 20,000-char cut, a PROGRESSIVE re-generation), the SSE `done` payload carries `finalAnswer` and `chat-stream.js` replaces the bubble — omitted when unchanged so a 20,000-char answer isn't sent twice. Without it the screen kept the streamed text while the DB held the corrected one, surfacing only on refresh (and 좋아요 saved a different text than the user saw). **C specifics**: (a) it uses `app.llm.creative-temperature` (default 0.7, clamp [0,1.0], hot) instead of `app.llm.temperature` — that one is clamped to [0,0.3], which makes creative generation impossible on it; `AnswerService.answerTemperature()` picks between them and must be honored on **both** the blocking and the `streamDirect()` streaming path, since the chat UI only ever streams. (b) Verification is **replaced, not disabled** — `prompt.answer.eval.creative` returns `sufficient`/`apiGrounded`/`inventedSymbols`/`envNote` into a separate `CreativeEvalOutput` record (a second `BeanOutputConverter`; folding `inventedSymbols` into the shared `EvalOutput` would put it in N's generated JSON schema too). `apiGrounded` rides in `AgentState.grounded`, so `CriticService` still reads one boolean (its `null` handling did change once — see the '판정 없음' bullet below). The ordinary `grounded` gate is false *by definition* for a creative answer, which would burn ANSWER×3 + EVAL×3 + RETRIEVAL×3 and still end in a 미검증 badge. `inventedSymbols` never triggers a retry — inventing a name is not the failure, presenting it as document-sourced is — and lands in `AgentState.inventedSymbols` for the Phase 4-b badge. (c) **Its passing badge is blue `생성`, not green `검증됨`** (`generative()`) — the two modes passed different questions (is this grounded in the documents? vs do the names it presented as document-sourced exist?), and one green badge for both invites the reader to take the second for the first. Any flagged `inventedSymbols` get their own amber badge plus an expanded line, shown **even on a passing answer**. All of this is decided in `model/VerificationSnapshot`, which is both the stored shape (`conversation_turns.verification`, JSON, defensive ALTER) and the display rule — there are three renderers (the no-JS HTMX fragment, `chat.html`'s history loop, and `chat-stream.js`), the two server-side ones read that record, and the JS implements the rule a second time because SSE never touches a template. `generative` is **stored, not derived** from `response_mode`: it records what was actually verified on that turn, so redefining the flag later must not relabel old answers. Parsing is lenient (`FAIL_ON_UNKNOWN_PROPERTIES` off, one bad blob skips only its own turn) because these rows outlive the code that wrote them. A NULL column means "no verification record" — every pre-existing turn plus meta/Direct/S — and renders no badge, exactly as before. (d) **Never reused** (`allowsReuse()=false`): C's request is "build me one", so returning a stored answer to 다시 만들어줘 declines the only thing that was asked. The rule lives in `QuestionReuseRepository`'s WHERE predicate, shared by the suggestion and the reuse query and **generated from the enum** — it used to be a `<> 'S'` literal in both, where a mode value comparison is invisible to `ResponseModeBranchConventionTest`. It is `NOT IN` over the excluded modes, never `IN` over the allowed ones, so NULL/blank/legacy `'M'`/`'L'`/unknown all stay eligible exactly as `ResponseMode.parse()` would read them. (e) **Never curated** (`allowsCuration()=false`): a C answer in `curated_qa` is searched back at the curated axis's RRF weight, so model-invented code becomes the next turn's "document" — the single most dangerous point in this design, and unwinding it means hunting down vectors. (f) `retrievalBoost()` is wired into `RetrievalService` (added to the retry escalation, not replacing it) but is **0 for every mode**; raising it requires lifting `AnswerService.MAX_EVAL_EXCERPT_CHARS` first (PLAN §6.24 Step 4-c), otherwise lower-ranked documents drop out of the verification window and the `grounded=false` false-positive the `.limit(5)` removal fixed comes back.

Owner failure propagates to joiners and clears the in-flight entry so the next call retries fresh. Only exact-text collisions merge — near-duplicate questions still miss (§10.5 semantic cache, deferred)
- §6.12 overload-aware circuit breaking: `LlmRouter` catches `HttpStatusCodeException` (covers both 4xx `HttpClientErrorException` and 5xx `HttpServerErrorException`) for 429/402/503 and routes through `blockForOverload()` before calling `CircuitBreaker.block()` — if `findFirst(taskType, roleOrder, tried)` still finds a fallback provider, block normally (Retry-After header or `circuit-breaker-minutes` default); if there's no fallback (the common lone-LOCAL-provider deployment) AND no explicit Retry-After header, block for a short fixed duration (`SHORT_BLOCK_SECONDS`, "30") instead — a full multi-minute block on the only viable provider just turns a transient capacity blip into a total outage until the block expires. An explicit Retry-After header is always honored regardless of fallback availability (authoritative provider/operator guidance, never second-guessed). Other status codes (500/502/504/etc.) keep the pre-existing flat 30s block, now expressed via the same `SHORT_BLOCK_SECONDS` constant
- §6.12 same-priority load balancing: `LlmRouter.findFirst()` groups eligible candidates within a role by the lowest priority present (unchanged tie-break/failover semantics — a different priority always wins over load); when multiple providers tie at that priority (e.g. two LOCAL providers registered for horizontal throughput), `selectWithinTopPriority()` picks the one with the most free permits on its concurrency-gate `Semaphore` (`availablePermits()`) — a "least-connections" balancer that reuses item 1's semaphores with zero new bookkeeping. Ties (both fully idle) deterministically keep the first-registered provider. Pure deployment-config feature: register two `providers[]` entries with the same `role`+`priority` and a different `base-url` — no schema/code changes needed. Not yet applied to embedding providers (different routing point, `EmbeddingModel` decorator chain)
- §6.13 settings override layer: `/settings` shows the effective LLM/RAG config; three families of values are **hot-editable** without a restart via a process-wide **static** `OverrideSource` on `AppProperties` (it's an immutable `@ConfigurationProperties` record, so the store can't be a ctor arg or injected field) — `SettingsService` binds itself via `AppProperties.bindOverrides(this)` at `@PostConstruct`, unbinds at `@PreDestroy`. Hot accessors read **override → else property default** then apply existing clamping; unbound (unit tests) = old behavior, regression 0. Full key list: `SettingsKeys`/`SettingsService.SEARCH_HOT_SPECS`/`INDEXING_HOT_SPECS`/`LLM_HOT_SPECS`.
  - **search** (apply on next search): similarity-threshold, RRF weight/k, candidate/tag multipliers, multiquery min-length/enabled, retry-escalate, topK, hybrid-enabled, `search-curated-qa-weight`(좋아요 축)/`search-submission-weight`(지식 제안 축). `RetrievalService` reads all of these fresh via `props.xxxSafe()` per `execute()`/`shouldExpand()` (topK/multiquery/hybrid used to be ctor-cached, which defeated hot-reload); only `rerank-enabled` stays cached (structural `@ConditionalOnProperty` bean, can't hot-swap).
  - **indexing/chunking** (apply on next indexing/↺ re-index, not next search): chunk size/overlap/min, `chunk-split-granular` (§ 청크 분할 전략 — flipping it changes nothing until a document is re-indexed, so the two strategies coexist in one collection and ↺ re-index is the supported way to move one document across), `indexing.max-concurrent-files`/`max-concurrent-llm-calls` (folded into `indexingSafe()` — nested `IndexingConfig` record can't take a top-level `xxxSafe()`). Read fresh per operation by **every** consumer (`DocumentIndexer`, `MarkdownCorrectionService.correct()`, `TextToMarkdownService.convert()`, `LazyVisionService`) — none may cache in a field. `max-concurrent-llm-calls` sizes a **separate `Semaphore` per consumer**, not a shared global budget.

Default routing mode stays view-only (no runtime consumer).
