# RAG Agent — Project Guide

## Stack

- **Backend**: Spring Boot 3 + Spring AI, Java 21 (virtual threads on), SQLite (WAL, pool=1)
- **Frontend**: Thymeleaf + HTMX, Bootstrap 5, no JS framework
- **Vector DB**: `app.vectorstore.type` selects the backend (Phase 5) — `chroma` (default; per-version collections via `VectorStoreRegistry`) or `sqlite-vec` (vec0 virtual table in the SQLite file). Both behind `VectorStoreProvider`, injected into `VectorStoreFacade`.
- **LLM**: OpenAI-compatible endpoint (Spring AI `ChatClient`); local LLM-Studio or remote

## Architecture

```
AgentGraph (state machine) → nodes: CLASSIFIER → RETRIEVAL → ANSWER → CRITIC → FINALIZE
AgentState: immutable record, each node returns new instance via state.toBuilder().xxx().build()
```

Flow:
- `meta` question → DIRECT_ANSWER (skip retrieval)
- others → RETRIEVAL → ANSWER (sufficiency check) → CRITIC → FINALIZE, retry loop up to `maxRetryCount`
- `directMode=true` → AgentGraph skips CLASSIFIER/RETRIEVAL/CRITIC entirely
- `AgentService.chat()` pre-runs history load + classify in parallel; AgentGraph skips CLASSIFIER when `questionType != null`
- SSE streaming → `StreamingAgentService.run()` drives `AgentGraph.runStreaming()` with `SseGraphListener`

| `ingestion/ChunkSplitter.java` | Pure chunk-splitting/merging algorithm; no Spring bean deps, extracted from `DocumentIndexer`. **Two section-aware strategies** routed by filename (**and**, for PDF, `MetaKey.SOURCE_TYPE != "ocr"`): **chapter-structured** (md/docx/txt) → `splitChapterStructured()`/`mergeSectionsByChapter()`; **page-structured** (pptx/non-scanned pdf) → `mergeIdenticalHeadingSlides()` pre-pass then legacy `mergeShortSections()`; scanned PDF and any other extension get plain sliding window. **`mergeSectionsByChapter()`** (md/docx/txt): only a section still below `minChunkSize` (normalized length) forward-merges into the next, and **never into a higher/parent heading** (`next.level < accLevel`, level = leading `#` count) — then the next section's size decides: 규칙1 combined ≤ chunkSize → merge; 규칙2 next alone ≤ chunkSize → stop; 규칙3 next > chunkSize → merge only if prepending keeps the sliding-split's last piece ≥ `minChunkSize*1.5` (`rawSlidingPieces()` look-ahead, extracted from `slidingWindow()` so simulation and real split share boundaries). Each `SectionGroup` keeps the first section's metadata + original index. `splitChapterStructured()` then sliding-splits oversized groups (+ `reinjectHeadingForSplitPieces()`), `prependParentBreadcrumb()` prepends the immediate parent heading (one level up) to the **first (non-tail) piece** of a child chapter (heading level ≥ 3; `##`/heading-less skipped), and `backwardMergeShortChunks()` folds any still-sub-`minChunkSize` chunk into the previous one (cross-section analog of `mergeTinyChunks()`). **`mergeIdenticalHeadingSlides()`** (pptx/pdf, runs first): groups raw sections into per-slide bundles by `MetaKey.PAGE_OR_SLIDE`, then merges consecutive slides whose assembled `##`+`###` heading pair is **exactly identical** (both levels must be present — never true for non-scanned PDF, which emits no headings) into one chunk, up to `MAX_IDENTICAL_HEADING_MERGE_SLIDES` (default **2**) slides per group, as long as the combined normalized size stays `≤ chunkSize` — once a group hits the cap the next slide starts a fresh group of its own (4 identical-heading slides in a row → two 2-slide chunks, not one 4-slide chunk). Every slide after the first in a group has its duplicate `##`/`###` lines stripped (`stripDualHeadingLines()`) but gets a `[페이지: N]` text marker inserted in their place so the merged chunk still shows where each slide's content began (the merged `Document`'s `PAGE_OR_SLIDE` metadata itself still only reflects the first slide, same "first section's metadata wins" convention as everything else here). **`mergeShortSections()`** (pptx/pdf) then merges by 40%/75%-of-chunkSize thresholds and refuses to merge across a `MetaKey.PAGE_OR_SLIDE` mismatch (no-op for md/docx/txt) so PPTX/PDF keep a "1 chunk = 1 slide/page = exact citation" guarantee. Size-budget checks (`mergeSectionsByChapter`/`mergeShortSections`/`enforceMaxChars`) measure normalized length (`MarkdownNoiseNormalizer`) — `slidingWindow()`/`rawSlidingPieces()` and offset-based helpers stay on raw text. When `slidingWindow()` cuts a fenced code block across pieces, `reopenTruncatedBlock()`/`reopenCodeFence()` re-wrap each piece with the opening/closing fence plus a `CODE_CONTINUATION_BEFORE`/`CODE_CONTINUATION_AFTER` marker line (plain text **outside** the fence, never inside it) — these markers live in `Document.getText()` itself, so they're searchable (flow into `SearchTextBuilder`) and visible as-is in the `/admin` chunk view |

## Conventions

- **Records everywhere**: `AgentState`, `ThreadMeta`, `ChatResponse`, `SourceRef`, `LlmProvider` — all immutable records
- **No Spring Data JPA**: raw `JdbcTemplate` for all DB access (SQLite incompatibility)
- **HTMX fragments**: endpoints return `"fragments/xxx :: selector"` strings
- **Spring AI auto-config excluded**: `spring.autoconfigure.exclude` drops `ChromaVectorStoreAutoConfiguration` (`ChromaConfig` manages beans manually) **and all six OpenAI model auto-configs** — `OpenAiChat`/`OpenAiEmbedding`/`OpenAiAudioSpeech`/`OpenAiAudioTranscription`/`OpenAiImage`/`OpenAiModeration`AutoConfiguration. The app builds its own chat (`LlmConfig.llmRouter`/`primaryChatModel`), embedding (`EmbeddingBeanConfig`) and per-provider `OpenAiApi` (`OpenAiApi.builder()`) beans, so it never uses a Spring AI OpenAI autoconfig bean. Left active, each of these eagerly creates an `openAiApi` bean that runs `Assert.hasText(spring.ai.openai.api-key)` and crashes startup with `OpenAI API key must be set` when `LOCAL_LLM_KEY` is blank (the normal local-only setup) — this hits the chat/embedding ones too (their *model* bean is skipped via `@ConditionalOnMissingBean`, but their `openAiApi` bean is not)
- **Null-safe config**: always use `props.llmSafe()` / `props.indexingSafe()` / `props.authSafe()` / `props.imageDescriptionSafe()` / `props.memorySafe()` / `props.summarySafe()` — never access the raw getters directly (`AppPropertiesSafeAccessorTest` enforces this for every `xxxSafe()`)
- **Korean prompts**: all LLM system/user prompts are Korean
- **MetaKey constants**: all vector store metadata access goes through `MetaKey.*` — never inline strings
- **Embedding/FTS input ≠ stored text (§10.1 Contextual Retrieval)**: `Document.getText()` (Chroma document, `vec_document_chunks.content`, source accordion, `/admin` chunk view) is always the untouched original. `SearchTextBuilder.build()` derives the embedding + `chunk_fts.content` text (`MetaKey.CHUNK_CONTEXT` + `MarkdownNoiseNormalizer.normalize()`); `AnswerService.buildAnswerPrompt()` calls `MarkdownNoiseNormalizer.normalize()` directly (no context header) for the `[검색된 문서]` block
- **Upload validation**: call `FileTypeDetector.matches(path, ext)` after writing to temp file; return 422 on mismatch
- **Input validation**: `PromptInjectionGuard.validate()` must be the first call in any public chat entry point
- **AgentState mutation**: use `state.toBuilder().xxx().build()` — the old `state.withXxx()` methods were removed (were deprecated since 0.2.0)
- **Parallel tests**: `src/test/resources/junit-platform.properties` runs test CLASSES concurrently (methods within a class stay serial). Any test that loads a Spring context (`@WebMvcTest`/`@SpringBootTest` — Spring Boot re-inits Logback on context start + `@MockitoBean` reset isn't concurrency-safe), attaches a Logback appender (`ListAppender` log capture), or mutates `AppProperties`' static override source **must** carry `@ResourceLock("global-state")` so it doesn't run concurrently with the others. `ParallelIsolationConventionTest` fails the build if one is missing the lock

## Key Constraints

- `spring.autoconfigure.exclude` must keep the Chroma exclusion and all six OpenAI model exclusions (chat/embedding/audio-speech/audio-transcription/image/moderation) — do not remove (see the "Spring AI auto-config excluded" convention above; dropping any OpenAI one lets its `openAiApi` bean crash local-only startup on a blank `LOCAL_LLM_KEY`)
- SQLite pool size must stay at 1
- All new LLM providers must go through `LlmRouter`, not direct `ChatClient` injection
- `ProviderRole`: LOCAL / NORMAL / PREMIUM (orthogonal to `TaskType`)
- `classifyOnly()` does not accumulate tokens into `AgentState` → `llmCallCount` under-reported by 1 (accepted trade-off)
- `DocumentIndexer.syncDirectory()` calls `saveRegistry()` once after all parallel work — never call it from parallel threads
- `DocumentIndexer.index(IndexRequest)` is the single entry point for both bulk sync (`IndexRequest.parallel(...)`) and interactive single-file upload (`IndexRequest.single(...)`) — neither call shape calls `saveRegistry()` itself (caller's responsibility); only `reindexFromMd()` (at its end) and `syncDirectory()` (once after all parallel work) call it
- Document storage is shared (no per-user isolation): `data/documents/`, `data/images/{docId}/`, `data/converted/{docId}.md`; DocRegistry and Chroma collection use `DocRegistry.SHARED` as the owner key
- PPTX / non-scanned PDF → Markdown: the `[페이지: N]` marker (NOT a synthetic heading) is the per-slide/page section boundary — `PptxToMarkdownConverter`/`PdfToMarkdownConverter` no longer emit `## N번 슬라이드`/`## N페이지`, and both `DocumentLoaderService.splitMarkdownBySections()` and `MarkdownCorrectionService.splitBySections()`/`splitByPages()` split on the marker. Only PPTX/PDF emit `[페이지: N]`; DOCX/TXT/MD never do (so the marker-as-boundary logic is a no-op for them). At PPTX conversion time, image-less duplicate + agenda/TOC slides are dropped (`app.pptx-remove-duplicate-slides`, default on), title-only section-divider slides are dropped (`app.pptx-drop-divider-slides`, default on, keeping sentence-like key-message titles), a title-only slide (no image, no group/diagram/chart/table text) whose exact title also appears in the immediately following slide is dropped as a "preview title" slide (`app.pptx-drop-redundant-title-slides`, default on — last slide never affected, no next slide to compare against), and the very last slide is dropped when its image-less normalized content contains an ending marker (끝/END/The End/감사합니다/Thank you) with at most 10 other normalized characters left over (`app.pptx-drop-ending-slide`, default on); dropped slides never shift `page_or_slide` numbering (`slideNum = i+1`). `MetaKey.CHAPTER_NO` stays `"0"` for PPTX/PDF (`skipChapterNumbers=true`) — real hierarchical chapter numbers come only from DOCX/MD/TXT H2–H6 headings
- PPTX multi-line shape text → code fence or block separation, in **both** shape paths: `appendShapeTextBlock()` for a text shape inside a group/diagram, `appendSlideBodyShape()` for a standalone slide-body text box (code lives in standalone boxes more often than in groups). Single-line shapes are unchanged (group: tight `\n` for short node labels; body: `appendBodyLine()`'s `\n\n`). **Multi-line** shapes get fenced with ``` when `looksLikeCodeBlock()` says code — the fence body uses `rawParagraphText()` (`stripTrailing()`, never `trim()`, so indentation survives) with interior blank lines preserved, and no emphasis markers, so code is reproduced verbatim and `MarkdownNoiseNormalizer`/`splitMarkdownBySections()` both leave the interior alone. The converter emits a **bare** ``` fence; `MarkdownCorrectionService.correct()` then finishes the job — `normalizeCodeContent()` strips the interior blank lines except one before a multi-line-comment or function/class signature (which is why preserving them in the converter matters), and `postProcessMarkdown(md, isPptx=true)` guarantees a blank line around the fence. The same pass also infers the fence's language tag from its content (`inferLanguage=true`), which is deliberately **decoupled from the `addHeadingNumbers` checkbox** so PPTX (which always forces it `false`) and any file uploaded with the box unchecked still get tagged fences — the `addHeadingNumbers` branch now only runs `addHierarchicalHeadingNumbers()` (fence-aware, so it never needs a code re-polish). Non-code multi-line text is blank-line separated in the group path only; the body path already separates paragraphs via `appendBodyLine()`. `appendSlideBodyShape()` collects a shape's surviving `BodyLine`s before emitting (a whole-shape fence can't be decided line-by-line) but runs heading promotion + consecutive-dup skipping in the original paragraph order, so those verdicts are unchanged. `looksLikeCodeBlock()` is deliberately conservative: **blank lines count toward neither the numerator nor the denominator** (a snippet's interior blank lines must not dilute the ratio), any `-`/`*`/`1.`-prefixed line (or a native `para.isBullet()`) means **not** code, an existing ``` means not code, and otherwise ≥`CODE_LINE_RATIO_PERCENT` (60%) of non-blank lines must hit `CODE_LINE_SIGNAL`. Arrows (`->`/`=>`) are excluded from the signal set on purpose — "요청 -> 응답" flow labels are far more common in diagrams than code
- PPTX shape-group text: a group-member shape whose entire text is a bare counter/step-badge label (`"1"`, `"1."`, `"(2)"` — `BARE_NUMBER_LABEL` regex in `PptxToMarkdownConverter.appendGroupText()`) is skipped from the extracted `[도형 그룹]` text — the group is already rasterized to an image separately, so a lone digit with no context is noise, not content. A label with trailing text (`"1단계"`) is unaffected — the regex only matches when the **entire** trimmed text is numeric (with optional surrounding `()`/`[]`/`.`/`)`). If filtering leaves a group with no other text, `appendShapeGroup()`'s existing empty-check suppresses the whole `[도형 그룹]`/`[/도형 그룹]` block, same as a purely decorative group with zero text shapes.
- `MarkdownCorrectionService.correctSection()` never sends GFM table content to the LLM: `extractTables()` (uses the same `markTableRows()` the table-aware blank-line pass in `postProcessMarkdown()` already relied on) replaces each table block with a `[TABLE_PLACEHOLDER_N]` marker before building the prompt, and `restoreTables()` substitutes the original table text back into the response afterward — a prose "표는 변경 금지" instruction alone wasn't reliable (local models were observed replacing `:` with `|` inside cells). If a placeholder is missing from the response (model dropped/mangled it), the whole section falls back to its untouched original text rather than guessing where the table belongs — same discipline as the `<<<SECTION_START/END>>>` overlap-marker check in `cutOverlap()`.
- Response mode (chat input bar, S/M/L, default `M`): `model/ResponseMode` carries a `tokenRatio` (S=15% / M=40% / L=70% of `app.llm.max-tokens`) **and** a `minChars` floor (S=2,000 / M=5,000 / L=10,000) — `maxTokens(configuredMaxTokens)` returns `max(256, max(round(configuredMaxTokens*ratio), minChars))`, i.e. the larger of the two, so a small configured ceiling can't collapse every mode down to the same tiny budget (previously S and M were hard to tell apart). Korean tokenizes at roughly 1 token/char (unlike English's ~4 chars/token), so this same number is reused with **no chars↔tokens conversion** both as the blocking call's `ChatOptions.maxTokens` AND as the "약 N자" character target named in the `prompt.answer.style.{s,m,l}` instruction (`{0}` MessageFormat placeholder) — for streaming this prompt target is the *only* length control, since streaming has no per-call token cap. `AnswerService.truncate()`'s absolute `MAX_ANSWER_LEN` (20,000) is unchanged by the mode either way. Flows `ChatForm.responseMode` / `ChatRequest.responseMode` → `AgentState.responseMode` → `AnswerService` (+ `DirectAnswerService` for the blocking direct path), where it appends the style instruction just before `[질문]` so the question stays last. Parsing is lenient everywhere (`ResponseMode.parse` → `DEFAULT` on null/blank/unknown), so an old client that sends no `responseMode` behaves exactly as before. The chat page persists the pick in `localStorage['chatResponseMode']`. UI: a `.btn-check` S/M/L toggle group (not a `<select>`), right-aligned on the same row as the version selector and tag chips (`flex-grow-1` spacer between); each button's `title` carries the native-tooltip description. `L` is client-side `disabled` whenever the RAG/Direct switch is on Direct — it only makes sense with retrieved context — and the pick falls back to `M` if `L` was active when the switch flips; the server has no matching guard (a hand-crafted `responseMode=L&directMode=true` request is accepted as-is, since the backend has no notion of "L requires RAG"). - §6.12 concurrency gate: `LlmRouter.executeGated()`/`acquirePermit()` (per-provider `Semaphore`, sized `app.llm.providers[].concurrency` else `app.llm.default-provider-concurrency` default 3) is used ONLY on the interactive chat/query path (`ClassifierService`, `AnswerService`, `DirectAnswerService`, `RerankerService`, `RetrievalService`'s MultiQuery model via `ConcurrencyLimitingChatModel`). Indexing/background callers (`KeywordExtractor`, `MarkdownCorrectionService`, `TextToMarkdownService`, Vision/title/summary services, etc.) deliberately keep the ungated `executeWithTracking()` — they already have their own semaphore (`app.indexing.max-concurrent-llm-calls`) and no synchronous HTTP caller waiting on a deadline. A timed-out gate wait throws `LlmBackpressureException` (`RAG-LLM-002`, HTTP 429 + `Retry-After`) — never caught by `LlmRouter`'s generic retry/circuit-breaker logic, since capacity pressure isn't a provider failure
- §6.12 in-flight single-flight: `CachingEmbeddingModel` holds a `ConcurrentHashMap<String, CompletableFuture<float[]>>` alongside its existing Caffeine `Cache` — a text miss either becomes the "owner" (batched into one delegate call with other new-this-call misses, same as before) or a "joiner" that `join()`s another concurrent call's in-flight future for the same (post-normalization) text instead of recomputing. Owner failure propagates to joiners and clears the in-flight entry so the next call retries fresh. Only exact-text collisions merge — near-duplicate questions still miss (§10.5 semantic cache, deferred)
- §6.12 overload-aware circuit breaking: `LlmRouter` catches `HttpStatusCodeException` (covers both 4xx `HttpClientErrorException` and 5xx `HttpServerErrorException`) for 429/402/503 and routes through `blockForOverload()` before calling `CircuitBreaker.block()` — if `findFirst(taskType, roleOrder, tried)` still finds a fallback provider, block normally (Retry-After header or `circuit-breaker-minutes` default); if there's no fallback (the common lone-LOCAL-provider deployment) AND no explicit Retry-After header, block for a short fixed duration (`SHORT_BLOCK_SECONDS`, "30") instead — a full multi-minute block on the only viable provider just turns a transient capacity blip into a total outage until the block expires. An explicit Retry-After header is always honored regardless of fallback availability (authoritative provider/operator guidance, never second-guessed). Other status codes (500/502/504/etc.) keep the pre-existing flat 30s block, now expressed via the same `SHORT_BLOCK_SECONDS` constant
- §6.12 same-priority load balancing: `LlmRouter.findFirst()` groups eligible candidates within a role by the lowest priority present (unchanged tie-break/failover semantics — a different priority always wins over load); when multiple providers tie at that priority (e.g. two LOCAL providers registered for horizontal throughput), `selectWithinTopPriority()` picks the one with the most free permits on its concurrency-gate `Semaphore` (`availablePermits()`) — a "least-connections" balancer that reuses item 1's semaphores with zero new bookkeeping. Ties (both fully idle) deterministically keep the first-registered provider. Pure deployment-config feature: register two `providers[]` entries with the same `role`+`priority` and a different `base-url` — no schema/code changes needed. Not yet applied to embedding providers (different routing point, `EmbeddingModel` decorator chain)
- §6.13 settings override layer: `/settings` shows the effective LLM/RAG config; three families of values are **hot-editable** without a restart via a process-wide **static** `OverrideSource` on `AppProperties` (it's an immutable `@ConfigurationProperties` record, so the store can't be a ctor arg or injected field) — `SettingsService` binds itself via `AppProperties.bindOverrides(this)` at `@PostConstruct`, unbinds at `@PreDestroy`. Default routing mode stays view-only (no runtime consumer).
